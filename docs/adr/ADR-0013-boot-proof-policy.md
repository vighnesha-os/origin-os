## Context

Every boot proof prints a result. `kernel_main` stopped for five of them: relocations not applied, an invalid boot info, a CPU below x86-64-v3, no room for the frame bitmap, and SMEP/SMAP. It ignored the result of every other proof. A failed proof printed a line such as `: clock failed`, which `cargo xtask` turned into a failed boot, and on a real machine nothing acted on it: the kernel went on and ended with `M1 entry complete; halting`.

Two things made this worth deciding rather than patching.

**Ignoring results is not always harmless.** A kernel whose page-table proof failed carried on with no heap. Control C0 in Evidence shows what that looked like: twelve more lines that all read as healthy, then `panic: memory allocation of 40 bytes failed` on the first heap allocation, with nothing connecting the panic to its cause.

**Stopping on every failure would be worse.** Proofs have already failed on real processors with nothing wrong, and one of the five existing stops was among them. A 2.1 to 2.5 times imbalance between two workers failed the scheduler proof on a Xeon 8370C. A TSC step of 16 ticks in 261,083 handoffs failed the clock proof on an EPYC 9V45. A ring that never filled failed the NIC proof there too. On three Intel Xeons the SMEP proof failed in 9 of 10 boots because of a stale translation in the proof's own setup (since fixed by an INVLPG on the CI branch), and that proof already halts. The evidence is the CI boots through KVM on real processors, listed in the research ledger. Under every one of those a halting policy would have stopped a working machine.

So the policy has to say which proofs can stop a boot, and on what grounds.

## Decisions

### R1. A proof stops the boot in two cases

(a) **Nothing can run without what it covers.** The APIC timer is the example: with no tick there is no preemption, clock or timeout. Whether a correct kernel could fail the proof does not matter here, because stopping loses nothing the machine could have gone on to do. It can still be a machine the kernel should support (F3); the fix then is a better proof or a better calibration, not a looser rule.

(b) **It covers a P0 property (memory safety, data integrity, isolation, concurrency correctness, authorization) and it is structural:** a correct kernel on a correct machine cannot fail it through timing, load or being a different machine. It may wait on something with a budget of seconds (running out of budget means something that must make progress did not), but it may not compare two measured quantities, assume which devices a machine has, or demand a tight time bound.

Either case makes it **Refuse**: the kernel stops (R4, R5). P0 outranks availability, so a false positive costs a boot, and that cost is accepted. Rule (b)'s second half is what keeps false positives rare, and it is why a proof of a P0 property that can fail on a correct kernel is Report until the proof is fixed, not Refuse.

Where one result mixed the two kinds, it is split. Scheduler fairness (a factor-of-two bound on loop counts) is separate from preemption (both workers ran on their processor and were switched at least 15 times). Wait-queue timing is separate from wait-queue correctness.

### R2. A proof that covers one capability withdraws that capability

**Withdraw** means the boot goes on without that one thing, and the thing is withheld where it would be used, so the check cannot be forgotten. The gates all existed before this ADR: `DeviceDma::attach` refuses every driver when the quiesce or the IOMMU failed (ADR-0007), a processor that did not start is not used, and the loader's memory is not reclaimed unless every processor came up. Only the record of it is new.

There is no system-wide degraded mode. A kernel-level "safe mode" has nothing to run without user space. §69's safe mode belongs to the services layer, which does not exist yet.

### R3. Everything else is reported and the boot goes on

**Report** means nothing relies on the result yet, or the proof can fail on a correct kernel. The proof prints its line as before, and the verdict (R6) names it.

A proof moves from Report to Withdraw or Refuse when something comes to depend on what it proves. Entropy is the plain example: nothing consumes it yet, and whatever first does must withhold keys when the proof failed (§59).

### R4. When the kernel stops

Immediately, for the proofs everything else stands on: page tables, frame allocator, heap, the APIC timer, and each processor's control state. There is nothing useful to run on top of them.

At the end of the thread proofs, for the proofs inside `sched::prove`. They run to the end and are judged together. Everything that runs after a failure is the kernel's own fixed proof programs, not outside code, and the operator gets every result instead of the first. The device proofs that follow do not run.

### R5. What stopping means

The kernel prints `origin-kernel: boot refused: <proofs> failed; the kernel stops rather than run without it (ADR-0013)` on every console ("them" for more than one proof) and halts the boot processor. The application processors keep running what they were, which is their idle loop unless a proof timed out; nothing new starts on them.

It does not reset. Nothing yet records a boot attempt (§20), so a reset would only erase the one diagnostic on the screen. When the boot manager exists, a refusal becomes how the kernel tells it this deployment failed, and it can fall back to the previous one (§64, §65).

### R6. Every boot ends with a verdict

Before the halt line the kernel prints what its proofs found, on every console, because a real machine's operator has no `xtask` and the individual lines scroll away:

- `origin-kernel: boot verdict: 57 of 57 proofs passed`
- `origin-kernel: boot verdict: degraded: 54 of 57 proofs passed; failed: IOMMU bring-up (no device drivers), NVMe (no storage), i8042`
- `origin-kernel: boot verdict: degraded: 33 of 33 proofs passed; 24 did not run`

It claims only what was recorded. "Passed" means the proof found nothing wrong: a proof that finds the hardware it needs absent says so on its own line and counts as passed, the proofs' existing convention (no HPET, no NVMe controller, no 8042). "Did not run" counts proofs a failure prevented, and is what "degraded" means there. The virtio-net proof is the one proof it does not cover (see Migration).

### R7. The table is the policy

`framekernel::bootproof` holds one table of every proof, its name and its consequence, generated so a new proof cannot be added without saying what its failure means. A host test pins the Refuse and Withdraw sets, so changing one fails until this ADR changes with it.

### R8. What did not change

`cargo xtask` still fails a boot on every `: X failed` line, Report-class ones included: the test is stricter than the policy on purpose. The proofs' own lines are unchanged. The new failure marker is `origin-kernel: boot refused`.

## Follow-ups this inventory found

Each was a proof that could not tell a fault from an absent device or a machine difference. **F1 to F6 are fixed** (Evidence); F7 is left.

- **F1, fixed.** `prove_nmi_ist` sent itself an NMI through the Self shorthand (ICR bits 19:18 = 01b with delivery mode NMI), which Intel's table of valid combinations marks invalid. It now sends to the processor's own APIC ID with no shorthand and the assert bit set, and waits up to a second. The result is split: where the NMI ran (Refuse, under R1(b)) and whether one arrived at all (Report). A second's wait covers what R1(b) calls a budget of seconds.
- **F2, fixed.** `i8042::init` failed on a machine with no controller. The FADT's IAPC_BOOT_ARCH bit 1 is now read (revision 2 and later); a machine that says it has none reports that and passes. Firmware that says it has one and a controller that does not answer is still a failure.
- **F3, fixed for calibration.** The timers calibrated only against the 8254 channel 2 and, with none (or one that did not count), failed or read garbage. A window whose OUT2 never went low says nothing and is not used, so a dead 8254 no longer returns a nonsense rate; the calibration then falls back to the ACPI PM timer (a known-rate counter the FADT names, usable before any MMIO mapping), then CPUID 15h's TSC rate. The window budget went from 50 million port reads (tens of seconds on real hardware, gated) to about two seconds of TSC. The boot-time proofs that need PIT interrupts (`irq::prove`, `irq::prove_remapped`) check whether the 8254 counts when nothing arrives, and report that they cannot run rather than failing. The HPET is not used as a reference: `framekernel/frame` claims MMIO mappings once, and the HPET is the clock proofs' to map.
- **F4, fixed.** `storage::prove_iommu` no longer fails when the IOMMU translates and no NVMe controller is present: nothing was disproved.
- **F5, fixed.** `pcie::prove_bus_mastering` skips on a platform with no IOMMU (no domains exist to compare against), and with an IOMMU that failed it fails only for a real wrong state.
- **F6, fixed.** Fairness now adds up each worker's own running time, as the weights proof already did, so a processor sharing a physical core cannot skew it.
- **F7, left.** `smp::start`'s interrupt-stack guards and trampoline pages are printed but not visible to `kernel_main`, so they are not in the table. The framework crate has landed, so nothing blocks this any more.

A settle that fails fails the proof, its line saying "not settled", where, and what: ending threads not yet exited (TASKS item 79), exited threads unreaped, stacks retired, or stacks lost to a stalled shootdown while it ran. **A stalled reclaim is safe by design**, since the slot and its 4 frames are withheld while a stale translation may remain, **but it costs 4 frames each**; a processor left unscheduled by a busy host under QEMU does it, and on a real machine a processor held in SMM for over a second would too, so it is named. `cargo xtask settle-gate` refuses a kernel function that reads `memory::stats` without settling at both ends, unless it lists the function with its reason. Reporting every stall where it happens, and what the checker's `lost: 0` means on the oversubscribed machines, belong to TASKS item 66.

**A settle also waits for every thread whose end was seen (TASKS item 79, 2026-11-19; the coordinating session's rulings R1 to R7).** A thread's end is seen before it gives anything back. A user thread raises its `TERMINATED`, closes its process's handles and sets the process's `ending` with interrupts on, and only then reaches the scheduler's exit, which keeps its stack, FPU area and address-space reference as a zombie; a kernel thread raised its done-flag and then exited. `settle` waited for zombies alone, so it found none for a thread in that stretch and the proof counted with that thread's memory held. Two ways: an earlier proof's thread at a proof's first count (H1: the directory proof after the entry-flags proof, the kernel stacks proof after the user-clock proof, the IPC proof after the wait-queue proof's workers), and a proof's own last thread at its compare (H2), whose stack the compare's re-check then reaps after the trim, into the cache of kept stacks: four frames short, the heap exact, a second path to the four frames TASKS item 70's T70-7 was taken to explain.

- **What a thread does now.** It counts itself as ending on its processor before anything about its end can be seen (`sched::end_with`: `Process::thread_ended` for a user thread, `sched::finish` for every kernel thread, which now has no other way to end). The scheduler's exit stops counting it once it has counted its zombie, and the reap lowers the zombie only after giving back what it held. A settle reads every processor's ending count before any zombie count, and waits until both are zero (`origin_sync::exits`, whose module states the ordering argument; Loom models E1 to E4 check it, controls X1 to X6 break each step). Since the review of TASKS item 79 (T79-1), a thread's count as ending is a token, a `Mark` that only `Exits::end` makes and only its exit consumes, so no other thread's exit can lower it; and `cargo xtask names-gate` refuses the framework's `cpu::thread_exit` outside `sched.rs` (T79-2), so no kernel thread can end without being counted.
- **What a thread that never exits does to the verdict: a deliberate change.** A thread whose end was seen and that never leaves its processor, a kernel bug (a hang in `close_out` or in the exit path), now makes every later settle wait `OTHERS_PATIENCE`, 10 s, and fail with "not settled …: N ending threads not yet exited", so every Refuse proof that settles after it fails, naming it, and the boot is refused. Before TASKS item 79 those settles passed and read counts that moved whenever the thread moved on. The reason: a kernel bug is named instead of miscounted. The cost falls only on such a boot. Under `cargo xtask` it is one settle, or two: a boot stops at the first failing line that carries one of its markers, every proof that settles has one but the kernel stacks proof, and the next settle after that proof is the scheduler's own, whose line has one. Since TASKS item 81 a settle that is not settled makes up to three passes, each waiting its 10 s for the thread (see below), so each such settle costs 30 s: 30 s or 60 s in all. Its boots take about 13 s of their 120 s on 1 to 4 processors and about 76 s of 242 s on 65, so the refusal is said before the timeout. On a machine with no `xtask`, the proofs inside `sched::prove` run to the end (R4), and each of the boot's later settles, up to about 20, waits its 30 s before the verdict. A thread whose exit kept no zombie, and leaked what it held, is unchanged: it has left the processor, so no settle waits for it, and the owning proof's compare finds the leak. A zombie its processor never reaps is unchanged too: the settles fail "exited threads unreaped", as before.
- **Amendment 3 (b) does not run such a boot again.** "Ending threads" is not a stalled shootdown: `lost_stacks_only` forgives only a lost-stacks clause standing alone, and an xtask host test pins that a line naming ending threads, before or after the lost stacks, is not forgiven. Amendment 3's text and scope are unchanged. Since TASKS item 73 ended Amendment 3 (item 316, `c548658d`), `cargo xtask` runs no boot again, and that test went with the allowance.
- **Performance cost:** Unmeasured, owed (CL42): a thread's end takes the run queue's and the threads' locks once more, with interrupts off, and two more atomic read-modify-writes; a settle reads one more count for each processor at each poll of its first wait.

**A settle also waits for every closed channel's reaping (TASKS item 81, 2026-11-20; the review of TASKS item 79, T79-6; the coordinating session's rulings Q8 to Q10 and additions (e) and (f)).** A closed channel's undelivered messages wait on a list for whoever reaps them: any thread's system call, a process's exit, a proof, and now `settle`. `ipc::reap_closed` lowered its count when it took a channel off the list, before it freed the channel's messages and what they held (ends, processes and their address spaces, memory objects). So a proof's own `reap_closed` on another processor, or a settle, could find nothing pending while those were still allocated, and a "before" read could count them, as TASKS item 79's H1 did for ending threads.

- **What the count means now.** "Listed, or being reaped": `origin_sync::backlog::Backlog`, lowered only after a channel's messages and the list's reference to it are dropped, with AcqRel, and read with Acquire. Its module states the ordering argument; Loom model B1 checks it, and controls BX1 (the order before, T79-6 itself), BX2 and BX3 break each part.
- **A channel is counted before anyone can take it** (the review of TASKS items 75, 77 and 81, R81-1). `Backlog::add` raises the count while the list's lock is still held, and a reap takes under the same lock, so no reap can take a channel uncounted and have its lowering cancel the raise of another channel still listed, which would let a settle read 0 with that channel's messages allocated: T79-6 again, through another interleaving. Loom model B2, the reviewer's own, checks it, and control BX4 (the raise after the lock, as first built) breaks it.
- **What a settle does now** (the coordinating session's rulings on R81-2). Each pass first drains the list itself and waits, up to `OTHERS_PATIENCE`, until no closed channel is listed or being reaped anywhere; then it waits for ending threads and zombies, trims, reclaims and waits for retired stacks. The drain comes first because it can wake a thread that then ends: as first built, with the drain after the retired wait, such an end came after the exits wait and before the verdict, and the settle failed on what it had itself done (R81-2). After a pass that left a closed channel, an ending thread or a zombie pending, or whose own drain freed a channel (`ipc::reap_closed` returns how many), the boot flow yields once with an interrupt window, so that a thread the drain woke gets the processor, and makes another pass, at most three in all (`settled::again`, host-tested); then it judges. A wait past 2 s is said on its own line ("closed channels' reaping"), and a settle still not settled after its last pass names "N closed channels not yet reaped", after the retired stacks and before the stacks lost. The proofs' own `reap_closed` calls stay.
- **The reverse case needs no control of its own.** A thread that ends during the exits wait lists and reaps its own channels in its `end_with`; if another processor's reap had taken one of them first, that processor may still be freeing its messages after the closed wait. The next pass waits for it.
- **Two limits.** A thread a drain woke on another processor that has not ended by the next pass's look is an end no one has seen, which a settle does not wait for: the same promise as TASKS item 79, which covers ends that were seen. And a drain in the third pass is followed by the verdict, with no pass after it.
- **Where those drops run** (addition (e)). On the boot flow, which waits with interrupts off and holds no lock: the list's lock and each channel's message slots are taken only to take from them, each with interrupts off, and the messages are dropped with neither held. What they free takes its own lock only around its own change, and waits for no other processor: an address space's drop leaks one a processor still has loaded instead of shooting it down, and frees one no processor has loaded without a shootdown. A TLB shootdown started there would not deadlock either: the boot flow would hold no lock while it waited for answers, and a processor waiting for its turn serves the request in progress. Only the boot flow settles. Control C81e frees an address space through this path.
- **Amendment 3 (b) does not run such a boot again.** "Closed channels not yet reaped" is not a stalled shootdown: an xtask host test pins that a line naming them, before or after the lost stacks, is not forgiven. Amendment 3's text and scope are unchanged. Since TASKS item 73 ended Amendment 3 (item 316, `c548658d`), `cargo xtask` runs no boot again, and that test went with the allowance.
- **Performance cost:** the count's two read-modify-writes are the ones it had, the raise now under the list's lock. A processor whose system call finds a count while another processor's drain is under way takes the list's lock once and leaves, which can last a whole drain (CL44, the review's R81-3). A settle's new wait is one load a poll, and an undisturbed boot makes one pass and pays nothing more (CL20).

**A stalled reclaim is retried, not lost (TASKS item 73, 2026-11-20; ADR-0004 Amendment 1, the note on A2; item 316).** A reclaim's shootdown waits its patience, 1 s, for every processor. Until TASKS item 73, a reclaim whose shootdown stalled withheld the slot and its frames for good, which the settles named as "kernel stacks lost to a stalled shootdown" and Amendment 3 excused on the named machines. Now the stack waits, with its frames, outside the tables. A later reclaim first asks whether the processor that did not answer has served a request since (`Shootdown::answered`, a filter only: it is never taken as proof that the pages were dropped). If it has, the reclaim sends a fresh shootdown and gives the stack back only if that completes.
- **One reclaim at a time.** Reclaims are served one at a time (`Slots::reclaim`'s role, given up on every way out by a guard). At most one stack waits, nothing is unmapped while one waits, and while one waits a reclaim costs a load, a lock and a read, and sends no interrupt. A reclaim that finds the role held returns `Busy` and leaves its stacks to the holder, whose loop takes them. It reads the role first and tries the compare-and-swap only if the role reads free (`f3f485df`): the diagnostic round counted 30,000 to 80,000 such refusals a boot on the 65- and 67-processor machines, from idle processors in their reap during bursts of exits.

Before TASKS item 73 it cost one stack's frames for each reclaim that stalled, each after a 1 s wait.

**Timing proofs that judge the kernel, not the host's load (TASKS item 66, 2026-11-19).** Under QEMU's software processor the boots' timing failures since 2026-11-14 came from time the guest did not get, not from the kernel. Three causes:
- **Spoiled calibration windows.** On the 65- and 67-processor machines about 98 % of the calibration's 10 ms windows are spoiled. With all 32 spoiled, the least disturbed window was kept, up to 2.9 % off, and the RTC second then refuted it: every refuted second in the records, and on 2026-11-19 two `boot-matrix` runs without this task's change at the gates' own load (the AMD-IOMMU 65-processor machine, "32 disturbed windows discarded", a TSC of 983,917 kHz, an RTC second of 1,016,848 µs).
- **Merged ticks.** QEMU merges a periodic timer's expiries while the virtual processor is away. The timed waits, the preemption rounds and the tick proof count those ticks.
- **Late threads on other processors.** A 2 s wait can end before a starved processor runs its thread.

Each proof can see its own disturbance, from its own processor's ticks or its own brackets. So each now follows the rule the ping-pong, the timer queue and the weights already followed: evidence of a disturbance buys a repeat against the same bound, never a looser verdict; a run over the bound without that evidence fails at once; the budget is bounded, and the line says which run decided. The changes:
- **Calibration:** up to 1,024 windows instead of 32 (APIC timer, Refuse).
- **The APIC timer's rate** (Refuse; the addendum review's T66-R13; TASKS item 78). The rate comes from the timer's count against the TSC (`apic::sample_period`, `apic::PeriodSample`).
  - **Reads.** In each run the running timer's count is read back to back. Each read is bracketed by the TSC, fenced so that the bracket encloses the read: RDTSCP then LFENCE before, RDTSCP after (`cpu::TscFence`; TASKS item 78, Q7).
  - **Pairs.** A pair runs from one read for 2 ms, or to the read before the reload, at least 0.5 ms. Undecided at 2 ms, it goes on toward the reload, up to 9 ms. A gap of more than a hundredth of the period between two reads breaks it.
  - **The verdict.** A pair decides by its period's bounds: between the shortest and the longest time its reads can be apart, and a fall of one count more and one less. Bounds wholly within 97 % to 103 % of nominal pass. Bounds wholly beyond fail the run at once (`apic::judge_period`). A pair whose bounds straddle 97 % or 103 % decides nothing.
  - **Stretches.** The pair's reads are cut into stretches wherever a step from one read's bracket's start to the next one's end exceeds a twentieth of the period. A pair whose slope misses its stretches' is set aside. A pair is judged only when its stretches' upper slope is within twice its own lower one.
  - **The budget.** A run reads for at most 64 fifths of the period, about 128 ms, with broken steps not counted. With no pair decided, the run is undecided: measured again, and never passed. The interrupts, stamped at the polls that saw them, judge delivery only (`apic::judge_ticks`): all 50 within 2 s and not under 95 % of their nominal time in total, or the run fails at once; a median gap over 150 % of the period fails at once; slow, with a gap of two periods or more, is measured again. Up to 4 runs. A wrong rate is named before a fault in delivery (`apic::tick_verdict`).
- **The RTC second:** decided within 5.2 s instead of 3.2 s (Clock sources, Report).
- **The timed waits** (Wait timing, Report): a late run is run again, up to 8 runs, only if the late waiter's processor lost 3 ticks or more, or, for the signalled wait, the boot flow was away a tenth of the run; otherwise it fails at once.
- **The preemption window** (Preemption, Refuse). It ends when every processor has taken 50 of its own ticks, within 10 s.
  - Every run is first judged on correctness: every worker exited within 10 s, and on every processor both workers ran, and ran there. A failure fails at once and is never repeated (the addendum review's T66-R11).
  - Each processor's timer, read back at its first watched tick, must equal the boot processor's initial count, divide configuration and LVT entry as its timed run held them, or the run fails at once (the coordinating session's ruling A on the review's T66-R1; the addendum review's T66-R14).
  - Each processor's 15th context switch since the watch was armed must come within 500 ms of TSC time, the bound from before TASKS item 66 (the addendum review's T66-R15).
  - A late run with a gap of two periods between a processor's ticks is measured again with fresh workers after a 2 s pause with every processor idle, while the next run can start within 120 s of wall time from the first run's start, the pauses counted, and at most 32 runs (`runqueue::window_again`); it never passes. A count was not enough: on the oversubscribed software-processor machines stalls come in episodes of seconds, and one outlasted 8 runs in the gates' own `boot-matrix` (the coordinating session's rulings of 2026-11-19 and 2026-11-20; the ledger, §3.1). The cost is up to about 120 s more boot time on a stalled large software-processor machine, and nothing on an unstalled one. Each run's line gives its number and the seconds spent. A repeat starts only once every worker of the run before has exited, and each worker carries its run, so a worker of one run counts nothing for another.
  - Late with no such gap, fewer than 15 switches in the window, or a processor short of its ticks at the budget, fails.
- **The clock proofs' handoffs:** 5 s instead of 500 ms (TSC consistency and the monotonic clock, Report).
- **Waits on other processors:** each is 10 s (`sched::OTHERS_PATIENCE`), ending as soon as its condition holds: the TLB proof's two, `sched::settle`'s three in each of up to three passes (since TASKS item 81 the first waits for every closed channel's reaping; the second, since TASKS item 79, also for every thread whose end may have been seen to leave its processor), the preemption workers' exit, the kernel-wide bound's three and the Rust program's one (Refuse), and the clock proofs' four (Report: the turn-takers' start and finish, the cost readers' start and finish). The timed waits' own wait for their waiters went from 4 s to 10 s. Since the seventh batch the kernel stacks proof's four switch-window waits, which were 5 s, are `OTHERS_PATIENCE` too.
- **Stalled shootdowns:** each is recorded (`origin_frame::stalls`), and every reclaim the scheduler makes prints a line where a stack is lost. The stacks proof's own reclaims and a user space's stalls print no line of their own; they are counted in the next line's `stall N of this boot`.

**Every extension is said.** A wait that went past its former bound prints `waited N ms for …, past the former M ms`; a run of the clock's turns past 500 ms says so on a line of its own; every run of the timed waits whose wait went past 4 s says so, with its number (the addendum review's T66-R16); a calibration that discarded windows says how many; each run of the tick proof measured again prints a line of its own with what made it say nothing; the timed waits' and the preemption window's lines say which run decided. The tick proof's lines give the period its count showed, in parts per million of nominal, with the pairs of reads it took. *(Since TASKS item 78, every run of the tick proof also prints, before its verdict's line, what its count reads showed (`origin-kernel: APIC timer: run N: brackets from … ns, steps to … us; spoiled: … gap, … short, … wide, … flat, … aside; best +/-… ppm`):*
- *the narrowest bracket in nanoseconds;*
- *the longest step from one read's bracket's start to the next one's end;*
- *the steps broken by a gap;*
- *the pairs given up for ending short at a rise of the count, for bounds that straddled 97 % or 103 %, for a count that did not fall, and for a slope not their stretches';*
- *the least uncertainty of a pair that spanned enough.*

*Every count is capped at 99, so the line stays under 160 bytes. It judges nothing; it lets a refusal in CI be diagnosed from the log alone)*

**What a passing run meets.** Every timing bound a passing run met before, it meets now: the tick proof's 50 interrupts within 95 % to 150 % of 500 ms, and now also its count's period within 3 % of nominal; the preemption proof's 15 switches within 500 ms of TSC time, as before TASKS item 66. Only the budgets grew, the time a proof may spend on runs, windows, edges or waits. **Stated limits, not allowances:**
- A rate within 3 % of nominal passes the tick proof.
- A timer 20 times fast or more, whose reload a stall inside a stretch's read hides, can pass the count check. Its delivery then fails it as too fast in total: 50 interrupts in under 25 ms, unless the same run's interrupts are held off for over 475 ms. Every processor's divide, count and mode are read back (ruling A), and on a machine without a hypervisor any repeat is a finding.
  - *(History: before TASKS item 78 the limit was a timer from about 3.4 times fast, corrected on 2026-11-21 from "over 5 times fast": 3.42 times with the gap allowed after the held read, 3.5 times without (the second addendum review's T66-R17; the coordinating session's ruling (a)).)*
  - *(Round 3 of TASKS item 78's diagnostic showed it on a boot: a timer 3.6 times fast passed the tick proof at 972,763 ppm.)*
  - *(Since TASKS item 78, a pair's stretches must agree with its slope. No stretch can hide a reload under 20 times fast. A pair with one hidden reload reads near nominal only about twice as fast or more, where its stretches' slope is over twice its own, and under about 2.06 times it cannot fit in 0.9 of a period.)*
  - *(Host tests: from 2.2 to 19 times fast at 351 hold placements; a randomized model of 1,500 cases from 20 times fast to 2.5 times slow.)*
- The boot processor's rate is measured, and every other processor's timer must read back as the boot processor's registers. A processor whose timer reads back as timed but ticks slower, its own timer clock being wrong, is caught only below about 30 Hz: 15 switches in 500 ms. A processor whose own timer clock runs fast is not caught at all: the preemption proof bounds its tick from below only, and the count's period is measured on the boot processor alone. That is acceptable because every processor's divide configuration, initial count and mode are read back against the boot processor's timed registers, and on the platforms in scope one clock drives every core's APIC timer; on a real machine a different rate from the same registers would be a finding for qualification review (the second addendum review's T66-R19).

**Why the preemption proof does not judge a median.** The review's first answer judged each processor's median tick gap within 95 % to 150 % of the period. Under TCG a tick delivered late is followed by a short one, QEMU keeping the period's phase, so a third of a correct timer's gaps fall under 95 % on a quiet two-processor machine. On the large machines a processor's median wandered across both bounds: it failed a right rate in 2 of 4 large boots (the ledger, §2). Ruling A replaced it with the read-back.

**Why the tick proof's rate comes from the count.** The first two answers to the review's T66-R5 judged the rate from the interrupts. A median gap under 95 % counted as too fast failed correct timers with a stall. A run with any gap of two periods never passing failed correct timers under any load. A ten-gap span (`66f47442`) could not catch a fast rate whose total recurring stalls brought into bounds: twice the rate with a stall of five periods in every tenth gap passed (the addendum review's T66-R13). The count falls at the timer's own rate, so neither delivery nor a host's stall moves it. Before relying on it, a diagnostic measured it in 26 runs: 208 clean pairs, all within −0.45 % to +0.55 % of nominal (the ledger, §3.3).

## Alternatives

| Alternative | For | Against |
|---|---|---|
| Keep ignoring results | Simplest | Runs on with broken isolation the moment anything real runs. The kernel's last line says nothing failed |
| Halt on every failure | One rule | Stops working machines. The proofs have already done this on real Xeons and EPYCs |
| A kernel-wide "degraded" flag instead of per-capability withdrawal | One bit to check | Nothing would know what it may still do. The gates exist already and are per capability |
| A global safe mode | Standard name, §69 | Needs a service layer to be safe in. Belongs there, later |
| Refuse only on memory safety, leaving isolation proofs as Report | Fewer stops | P0 includes isolation and authorization. A kernel that cannot show them must not run outside code |
| Report the proofs but run a boot-manager reset on a refusal | Self-healing | No boot manager records attempts yet; a reset loop would erase the screen, the only diagnostic |
| A kernel command line or firmware switch to continue past a refusal, for first physical boots | Sees further on a bad machine | A switch that can be left on in a product. The verdict already shows everything up to the refusal; a one-line local edit does the rest for a bring-up session (question 4) |

## Trade-offs

A refused boot is a machine that does not start, and the same code may be working perfectly (a Xeon with a stale translation in a proof's own setup is the proof of that). R1(b)'s structural test is the defence. It can leave a P0 property covered by a proof that cannot refuse until the proof is fixed, as the NMI stack was before F1. The alternative is worse: a boot that halts because of how a proof asked the question.

The Refuse list costs a stricter boot on real machines than the proofs had before, but no stricter than they had already been in QEMU, where every one of these has always been a failed boot.

## Threat model (§58)

| Who | What they can do | What happens |
|---|---|---|
| Firmware or a device forcing a Refuse-class proof to fail | Stop the boot | Availability only, and they could already stop a boot by hanging it. Nothing is read or written out of bounds |
| Firmware or a device forcing a Withdraw or Report proof to fail | Lose a capability or a line | Fails closed: the capability is withheld |
| Anything making a proof pass wrongly | Not addressed: this ADR decides what results mean, not whether they are right | The proofs' own soundness is each proof's concern |
| The verdict and refusal lines | Fixed text and proof names only; no addresses, keys or user data (§61) | Safe to show |

## What this does not prove

- **Physical hardware (§74, rule 30).** Everything is QEMU. CI through KVM runs real processors with QEMU's devices and firmware, and that is the strongest evidence here; it is not qualification.
- **Hangs.** A proof that never returns is still a hang. There is no watchdog (§69).
- **Persistent records.** A refusal is not recorded anywhere that survives the halt (§20, §69).
- **That the Refuse proofs detect what they name** beyond each proof's own controls.

## Amendment 1 (Accepted, 2026-11-10): the entropy proof becomes Withdraw with the kernel's generator

**Status: Accepted by the owner on 2026-11-10, as recommended ("Accept all", decision sheet item 113; CLAUDE.md §18). Built on 2026-11-11 (task 18b), under QEMU only.** The inventory's row, `framekernel::bootproof`, the host test that pins them and the boot test's markers changed in one commit, with the generator's proof: the row is now "random-number generator", a Withdraw row, and "hardware entropy" and `prove_entropy` are gone. The evidence is finding 8 of `docs/engineering/DESIGN_REVIEW_2026-11-10.md`.

**Why.** R3 moves a proof "when something comes to depend on what it proves", and gives entropy as its example of a result nothing consumes. That stopped being true with task S3-3:

- a start record's address is drawn from RDSEED or RDRAND (`framekernel/src/launch.rs`);
- so are the DHCP and TFTP identifiers (`framekernel/src/virtionet.rs`);
- task S3-5b draws one value for each mapping.

Each consumer refuses when a draw fails. None of them sees what the proof checks: a source that is stuck but still reports success.

**The decision.** When the kernel's random-number generator lands (CLAUDE.md §59), "hardware entropy" becomes a Withdraw row. What is withheld is randomness. With no healthy seed, nothing is launched and nothing is placed at a random address. The generator's ADR decides the health tests that replace today's proof. *(2026-11-10: it is ADR-0016, accepted by the owner the same day. Its R4 gives the tests and its R8 what this row withholds. Still not built: task 18b.)* *(2026-11-11: built by task 18b, which is in the second step-3 batch since `c2245ef`. In that batch the memory-object proof is a third that does not run when randomness is withheld, beside process start and the service directory, because its maps at a place the kernel chooses need a draw. That such a map then fails with `not_supported` is shown by a host test of `mapping::place_at_random` and by no boot.)*

**Alternatives.**

| Alternative | For | Against |
|---|---|---|
| Leave it Report | No change | A stuck source gives predictable addresses and identifiers, and nothing acts on the proof that saw it |
| Refuse: stop the boot | Simplest gate | It fails R1(b): a correct kernel can meet a slow source, or fail a statistical health test by chance. Withdraw withholds exactly what depends on the result, and the boot still reaches its verdict |
| Withdraw now, before the generator | Sooner | Each consumer would need the tally passed to it, only to be rewritten when the generator becomes the one consumer |

**Trade-offs.** A machine whose source fails its health tests starts no program until it has a seed. That is the point (P0).

**Migration consequences.** `framekernel::bootproof`'s table, its host test and this inventory change together. No ABI or format changes.

On every other machine, those of 1 to 4 processors included, R8 stands on any host: the 2× bound holds and the line fails the boot. Preemption stays a Refuse proof everywhere, so a worker that never ran still ends the boot.

**Alternatives that were put.** Dropping the fairness proof on those machines; or taking them out of the gate, which leaves ADR-0008 D7's large machine untested.

**Performance cost (ADR-0018 V3).** None, by construction: it changes what the build host's test tool accepts, and nothing that ships.

**Trade-offs.** A fairness regression that shows only on a large machine is reported there and not failed; the small machines still fail on it.

**Migration consequences.** None: no ABI or format changes, and the kernel's verdict is unchanged.

## Amendment 3 (Accepted, 2026-11-15): a kernel stack lost to a stalled shootdown on the oversubscribed software-processor machines is reported, not failed, or its boot is run once more

**Status: Accepted by the owner on 2026-11-15 ("Accept 313", decision sheet item 313). Its second part was replaced the same day, before the amendment reached `main` ("Accept 314 (re-run)", item 314). Built by TASKS item 69 under QEMU, on `main` since 2026-11-19 (pull request 41). It holds until TASKS item 73 lands, and ends then (item 316, accepted by the owner on 2026-11-19; "How long it holds", below). Ended by the change that lands TASKS item 73, 2026-11-20 (`c548658d`); the text below is kept as the record of what held.** Until then this line said it held "until TASKS item 66 decides a lasting rule from measured figures". TASKS item 66 proposed that rule, and item 316 is the owner's answer.

**Why.** When a retired kernel stack is reclaimed, the reclaim's shootdown waits at most its patience, 1 s, for every processor to answer. If one does not, the slot and its 4 frames are withheld for good, because a stale translation may remain: safe by design, and a cost in memory, not in correctness. On the 65- and 67-processor machines of ADR-0008 D7, which run 65 or 67 guest processors on the development Mac's 10 threads under QEMU's software processor, a guest processor left unscheduled for over a second produces exactly that. On 2026-11-14 TASKS item 59's `boot-matrix` failed three times that way, before any of its own code ran (one to three slots lost, on the 67-processor machine and on both 65-processor machines), and passed on other runs of the same build. Under R8 `cargo xtask` fails a boot on the stacks proof's `lost: 0` and on every `: X failed` line, so those machines could not be a gate that passes reliably. TASKS item 67 (the settle before whole-machine count compares) names such a loss in the kernel's own proofs as "N kernel stacks lost to a stalled shootdown".

**Decision.** On the 65-, 67- and 288-processor software-processor machines of ADR-0008 D7, named, `cargo xtask` does two things and no more:

- **(a) Reported, not failed (item 313).** A boot that ran whole, and whose stacks proof's final count shows kernel stacks `lost` above zero, is not failed on that count. `cargo xtask` reports the count and the machine.
- **(b) Run once more (item 314).** A boot can stop because a Refuse proof failed only with "not settled …: N kernel stacks lost to a stalled shootdown", with nothing failed before it. If so, it is run once more on the same machine. The gate passes only if that second run passes whole under (a) and R8. Both runs are reported, the first with its loss. A second run that stops the same way fails the gate.

Nothing else is forgiven or run again: a stall or timeout, a stack lost any other way, or a frame or heap mismatch without that cause. On every other machine, R8 stands: a lost stack fails the boot. That covers the machines of 1 to 4 processors and any physical machine. The allowance is keyed to the machine, never to the host's thread count. The kernel's verdict is unchanged on every machine.

*Note (TASKS item 79, 2026-11-19; not an amendment).* A settle that names "ending threads not yet exited", alone or beside lost stacks, is not a stalled shootdown, and (b) does not run that boot again: `lost_stacks_only` forgives only a lost-stacks clause standing alone, which an xtask host test pins. Nothing in this amendment's text or scope changes.

*Note (TASKS item 81, 2026-11-20; not an amendment).* The same for "closed channels not yet reaped": not a stalled shootdown, not forgiven, pinned by an xtask host test. Nothing in this amendment's text or scope changes.

**Why (b) was replaced (item 314).** Item 313, as first accepted, said `cargo xtask` would not fail a boot on a proof that failed only with the "not settled" line. That cannot be built without changing the kernel.
- **Every proof that settles is a Refuse row of this ADR's inventory:** IPC and handles, process and thread objects, live address spaces, a message's writer, process start, the call pin, the service directory, events and ports, kernel stacks and the kernel-wide bound among them. When one fails, the kernel stops, and the rest of the boot never runs.
- **The stacks proof's own leak check fails the same way** if the loss lands inside it.
- **Such losses are now more likely.** Since TASKS item 67, a boot settles about 22 times, and each settle reclaims stacks, so a stall is now likely to land inside one of those proofs.

TASKS item 69's session found this before any code was written. The coordinating session wrote the text the owner accepted without checking the proofs' classes.

**Alternatives that were put.**
- **Against item 313:** keeping it a failure and rerunning until a run passes, at about an hour of the shared machine for each failed run.
- **Against item 314, first:** leaving (b) out until TASKS item 66 has figures. Those machines could then still fail when a stall lands in a settle, and such runs would be repeated by hand.
- **Against item 314, second:** changing the kernel, so that a stack lost to a stalled shootdown no longer fails those proofs on any machine, and `cargo xtask` fails on the kernel's note everywhere except on the named machines. That would weaken the kernel's own verdict on physical machines, where no checker reads it.

**Performance cost (ADR-0018 V3).** None, by construction: it changes what the build host's test tool accepts and when it runs a boot again, and nothing that ships. A second run costs the shared machine that one machine's boot, and only when it happens.

**Trade-offs.**
- A defect that loses stacks only on a large machine would be reported there, not failed.
- A defect that loses them inside a proof only now and then could pass on its second run.

The small machines still fail on either, both runs are reported, and TASKS item 66 decides with figures.

**Migration consequences.** None: no ABI or format changes, and the kernel's verdict is unchanged.

**How long it holds (item 316, accepted by the owner on 2026-11-19, "Accept 316").**

- **Decision.** Amendment 3 stays as it is until TASKS item 73 lands, and ends then.
  - TASKS item 73 changes the reclaim. A stack whose reclaim's shootdown stalls stays retired, is asked again at a later reclaim, and is given back once every processor has answered. `lost` then counts only a processor that never answers again.
  - The change that lands TASKS item 73 also removes both parts of `cargo xtask`'s allowance, item 313's report and item 314's second run, with their host tests. It records here and in the matrix's row A13-Am3 that the amendment has ended.
  - From then on, R8 holds on every machine: a lost stack fails the boot.
- **Why.** TASKS item 66, which this amendment waited for, measured the large machines' timing failures and traced them to the host leaving guest processors unscheduled (its finding F1). Its rule, ruled by the coordinating session the same day, is that a proof which sees its own disturbance repeats against the same bound, and `cargo xtask` gains no allowance. A stack lost to a stall is not that kind of failure. The kernel withholds the stack for good, safely, and no repeat of the proof brings it back. TASKS item 73 removes the cause, a stall that loses a stack for good, rather than excusing its symptom.
- **Evidence.** As the coordinating session read them on 2026-11-19, no stack had been lost this way since 2026-11-14, in TASKS item 66's diagnostic boots or in the sixth batch's runs. Unused, the allowance changes no verdict.
- **The alternative put:** ending the amendment at once. Those machines would then fail again on any stall of over a second that loses a stack, before anything can retry the reclaim.
- **Performance cost (ADR-0018 V3).** None, by construction.
- **Trade-offs.** Until TASKS item 73 lands, the trade-offs above stand.
- **Migration consequences.** None: no ABI or format changes.
- **Ended (2026-11-20).** TASKS item 73 is built: a reclaim whose shootdown stalls keeps the stack retired, with its frames, and a later reclaim asks again; the stack is given back only once a shootdown sent after its unmap completes on every processor (ADR-0004 Amendment 1, the note on A2). A stall no longer loses a stack.
  - **The figures the ruling rests on.** The coordinating session ruled the removal on 2026-11-20 from that task's diagnostic round, with the allowance still in place. The round ran on the 65-processor Intel and AMD machines and the 67-processor sparse machine, 10 boots each idle and 5 each beside three spinning shells. All 45 passed. Between them they made 29,777 reclaim shootdowns, and none stalled. A planted stall on the 65-processor machine (control K1-65) was given back after one fresh shootdown, 1,501 ms after its unmap, well inside `sched::OTHERS_PATIENCE`. Of the round's two `boot-matrix` runs, the first failed on a defect of TASKS item 73's own (the kernel stacks proof's cost clause, control K5) and the second, with its fix, passed. The figures are in TASKS item 73's entry and the controls under "Evidence".
  - **What the change removes:** item 313's report (`allow_lost_stacks`, `stacks_lost`, `forgave_lost_stacks`) and item 314's second run (`lost_stacks_only`, `stopped_by_lost_stacks`, `REFUSE_COUNT_LINES`, `run_scenario`'s second boot), with their ten host tests. A host test pins that every machine's kernel boot requires `lost: 0`, the named machines and KVM included (`every_machine_requires_no_stack_lost`), and control K4, a stack leaked on the 65-processor machine, fails the boot.
  - **From now on**, a lost stack fails the boot on every machine (R8). `lost` now counts only a stack whose drop found a processor's records still holding it (`Slots::leak`), never one that a stall withheld.
  - **How item 316's words are built.** The owner accepted three things: a stalled reclaim is retried, not lost; this amendment ends when TASKS item 73 lands; a lost stack fails the boot on every machine. As built:
    - `lost` counts only stacks dropped while a processor's record held them, a leak;
    - a stack whose shootdown stalls is withheld and asked again, and if it never comes back, every later settle names it, "N kernel stacks retired (one withheld since CPU c did not answer its shootdown)", and fails its proof on every machine;
    - so nothing the allowance forgave is forgiven any more.
