| Result | Thirteen loader runs in six boots. In every run the FCH's checks passed (an AMD processor; the DSDT's 256-byte region at `0xfed80300`; the firmware's page tables mapping it to itself). The run found no stand-in table and read the board: the FADT's reset register `0xbe` to I/O port `0xb2`; `SMIxC0 0x04000000`, bits 27:26 = 01, so a write of bit 2 to `0xCF9` raises an SMI; `PMx00 0xe3070bf7, PMx08 0x021c0514, PMx60 0x0800, PMx74 0x1e060117, PMxD2 0x40`: `0xCF9` decoded, the FCH's own reset at `0xCF9` off, the shutdown message and a shutdown as a PCI reset both set. Only `PMxC0` changed, always one cause beside bit 20. **The control,** one in each boot (six runs): `PMxC0` named bit 19 (after the provider's own restart, boot 1) or bit 21 (after each of the tool's restarts), so the run triple-faulted and made no call; each time the firmware started again, its first byte 48.3 to 48.9 s after the control's line, and the next run read bit 23, a shutdown. **The call,** seven runs, each after a run that read bit 23: `X`, then nothing but the firmware starting again. In five (boots 1, 3, 4, 5 and 6) its first byte came 48.8 to 48.9 s after `X`, 29 to 47 s before the tool's next restart or the rental's end: the same delay as after each triple fault and after the provider's restart (48.8 s). The one run that followed such a reset before a restart (boot 1's, at 09:06:53) read bit 23 and made the call again. In the other two (boot 2), the tool's restart was issued 5.6 s before `X` and 3.8 s after it, and the next run read bit 21. No `Y` and no Amendment 2 line in any run. No verdict: after `EFI_SUCCESS` the mode writes nothing before its triple fault (decision item 349) |
