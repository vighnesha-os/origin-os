## 2. How QEMU 11.1 can present an APIC ID above 255 to a TCG guest

QEMU builds an APIC ID from fields (Q1). The thread ID takes the low bits, then the core, module and die IDs. Each field is ⌈log₂ count⌉ bits wide, and the package (socket) ID starts above them. So package 1 starts at APIC ID 256 once the fields below the package total 8 bits. The processors present at boot are the first `cpus` in index order, all in package 0. A processor in package 1 therefore needs either more than one package's worth of present processors, or a cold-plugged `-device` CPU.

| Option | Possible processors | Verdict |
|---|---|---|
| `-smp N` with N large enough to reach package 1 | ≥ 76 present, each a TCG vCPU thread | Rejected: slow, and it tests nothing more |
| `-smp 1,maxcpus=257,sockets=257` and `-device …,socket-id=256` | 257 | Works, but has more MADT and SRAT entries for no gain |
| **`-smp 1,maxcpus=150,sockets=2,dies=3,modules=5,cores=5,threads=1` and `-device max-x86_64-cpu,socket-id=1,die-id=0,module-id=0,core-id=0,thread-id=0`** | **150** | **Chosen.** Dies take 2 bits, modules 3 and cores 3, so package 1 starts at 256. Of the ways to make 8 bits from counts per field, 3 × 5 × 5 = 75 per package is the smallest. |

Measured through QMP (`qom-get … apic-id`, `query-cpus-fast`): the cold-plugged processor has **APIC ID 256** and CPU index 81. The boot processor has APIC ID 0.

What QEMU enforces under TCG:
- the processor needs the x2APIC CPUID feature: `-cpu qemu64,-x2apic` is refused with "APIC ID 256 requires x2APIC feature in CPU";
- nothing else. `intel-iommu,intremap=off`, `intremap=on,eim=off` and no IOMMU at all are all accepted (Q1: the check is KVM-only). **QEMU will run machines in which no MSI can reach APIC ID 256 on real hardware**, so the kernel must refuse that case itself. It does: `iommu::msi_message` without remapping uses compatibility format, which refuses IDs above 255 (ADR-0007 I8).

`threads=1` avoids a QEMU warning. Under TCG, `-cpu max` reports an AMD vendor, and QEMU warns "This family of AMD CPU doesn't support hyperthreading(3)" for `threads=3`. The Homebrew EDK2 build shipped with QEMU 11.1.3 boots this machine and leaves both processors to the kernel.

## 3. What the MADT and SRAT then list

From Q2 and Q3, and as the kernel reads them on this machine:
- **MADT:** 150 processor structures, one per possible processor. Package 0's 75 IDs (0–164, sparse) use type 0 structures. Package 1's 75 IDs (256–420) use type 9. Two are enabled (IDs 0 and 256). The other 148 have flags 0: disabled, not online-capable. One Local x2APIC NMI structure follows. Kernel: `ACPI MADT: 150 processors, 2 enabled (largest APIC ID listed 420)`.
- **SRAT:** 150 CPU affinity structures (75 type 0, 75 type 2), all flagged enabled. Package 0 is in node 0 and package 1 in node 1 (QEMU's default mapping with two `-numa` nodes). Kernel: `numa: 2 nodes, 150 cpus, 3 memory ranges, 511 MiB; consistent true`.
- **CPUID leaf 0Bh:** the core level's shift is 8. The kernel reads 256 logical processors per package and splits APIC ID 256 into package 1, core 0, thread 0: `topology: 2 logical, 2 cores, 2 packages`.

## 4. What failed before this work (the kernel at `1c790fe`)

Booted on the machine of §2:
- `ACPI processor discovery failed: invalid MADT`: 150 processor structures for a 64-entry buffer. So the processor at APIC ID 256 was never started.
- `numa: invalid SRAT; consistent false: numa failed`: 150 affinity structures for a 64-entry buffer.
- Underneath, every per-CPU array was indexed by APIC ID with 64 slots. Even with bigger buffers, APIC ID 256 would have had no CPU-local area (its ID read as `u64::MAX`), no run queue and no NVMe queue: it could never schedule.

## 5. Design (detail in ADR-0008, Proposed)

- **C1** A dense CPU index at discovery: the boot processor 0, then the MADT's enabled processors in table order (`framekernel::cpumap`).
- **C2** Per-CPU arrays are indexed by the `CpuIndex` newtype, never by APIC ID.
- **C3** The APIC ID is only an address: IPIs and MSI/IRTE destinations use the ID recorded for the index.
- **C4** An AP gets its CPU-local area only if the ID recorded for its index is its own.
- **C5** The MADT and SRAT lists are sized from the table's length, on the heap.
- **C6** 64 indexes for now; extra enabled processors are reported and left in firmware.

## 6. Tests defined before completion (CLAUDE.md §16.12)

- **Host:** `cpumap`. The boot processor is 0 wherever, and whether, it is listed. Enabled processors follow in table order; disabled ones are skipped. QEMU's 150-processor table gives index 1 to APIC ID 256, and 75 of its IDs need type 9. Capacity beyond 64 is counted, a duplicate is indexed once, and the broadcast ID is refused. A randomized test over 2000 tables checks every invariant.
- **Boot, `cargo xtask boot-matrix` (1, 2, 4):** unchanged behaviour. APIC IDs equal indexes there, and the reports now name `CPU n (APIC ID n)`.
- **Boot, `cargo xtask boot-x2apic`:** the MADT line above. `CPU 1 (APIC ID 256) online`. Scheduler workers, weights, TSC, console, TLB-shootdown and wait-queue IPI proofs pass on CPU 1. The NVMe interrupt-driven thread is on `CPU 1 (APIC ID 256)` and the last interrupt arrives there. Its per-CPU queue's interrupts arrive there too. The x2APIC line requires: the compatibility format refuses 256; the MSI-X entry holds only a remappable handle; its IRTE holds destination 256, the vector and the source-ID check; and every block of a thread there was ended by an interrupt taken there. The virtio-net receive thread on CPU 1 is woken by its NIC interrupts. The IOMMU's own interrupt-remapping proof passes.
- **Negative controls (each must fail the scenario):** the IRTE destination truncated to 8 bits, so the interrupts land on APIC ID 0 and the thread on APIC ID 256 is never woken; interrupt remapping off (`ORIGIN_QEMU_IOMMU=intel-iommu,intremap=off`), so the kernel refuses to program APIC ID 256; and an AP whose recorded APIC ID is wrong, which must refuse its index.
