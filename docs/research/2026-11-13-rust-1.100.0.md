## 2. What a new compiler changes for Origin, whatever the notes say

These follow from how the tree is built, not from any line of the notes.

1. **Every image's bytes.** A new code generator (LLVM 23.1.5; 1.99.1 has 23.1.1) and newly built `core`, `alloc` and `compiler_builtins`. The eleven files of the reproducible-build gate get new digests, and must again be the same from two builds and on two kinds of host.
2. **The kernel's image names its compiler.** `onbf-pack` writes the compiler's release, commit and LLVM version into the KRN manifest (`developer-tools/onbf-pack/src/toolchain.rs`), from `rustc -vV`. One test holds the release to the pin (`tests/rustc_kernel.rs`).
3. **The remap.** `xtask` remaps the toolchain's source directory to `/rustc/<commit>` (TASKS item 32). The commit comes from `rustc -vV`, so the remap follows the compiler; the gate that searches every image for the machine's paths says whether it is still enough.
4. **The linker.** rust-lld is the toolchain's. Its own line in `.comment` is replaced through `LLD_VERSION` (TASKS item 44); the gate reads `.comment` of every ELF and says whether lld still honours it.
5. **The prebuilt libraries' figures.** ADR-0017 Amendment 1 states, for the kernel of 2026-11-10, 113 returns in the prebuilt libraries, 33 without an INT3, and 2 jump tables. The image gate prints the figures on every run; they will differ.
6. **The one expected warning.** `expected_warning.rs` matches the five lines of the compiler's warning about `-C target-feature=+harden-sls-ret` exactly. Other words, and it is no longer collapsed; a refusal, and ADR-0017 Z10 has lost its means. What the build showed is in §4.5: other words, and an announcement.
7. **Options §14 records as unavailable.** `verify.sh` looks in `rustc -C help` for `cf-protection` and `stack-protector`.
8. **Four places hold the pin together**, and `verify.sh` fails unless they agree: `rust-toolchain.toml`, `Cargo.toml`, `verify.sh`, `developer-tools/toolchain/rustc-commit-hash`.

## 4. The four changes that need more than a build

### 4.1 The "Rust" ABI and SSE registers (#161583)

Read: the pull request's description. It restores passing vectors in SSE registers for functions with Rust's own calling convention on x86 targets that require SSE, which an LLVM bug had forced off, and it makes the check on ABI-relevant target features a hard error, because the convention now depends on SSE being present.

What that means here, by this reading:

- **The kernel** (`x86_64-unknown-none`) is a soft-float target: SSE is not "always available" there, so its convention does not change. It passes no feature that the hard error is about.
- **Ring 3** (`x86_64-unknown-linux-gnu` used as a code generator, with `x86-64-v3`) and **the loader** (`x86_64-unknown-uefi`) require SSE2. Functions with Rust's convention may pass vector values differently. That convention was never an interface: CLAUDE.md §42 forbids exposing compiler layouts as stable, the system-call path is `extern "C"` stubs and a `syscall`, and nothing here links Rust code built by two compilers together.
- **`extern "C"`** is not what the change is about.

To be checked on the installed toolchain: §10's FFI-bool test; the OIDL suite; the ring-3 boot proofs unchanged; that no build passes a feature the new hard error refuses.

### 4.2 SSE or AVX on a soft-float target (#160302)

Read: the pull request's description. LLVM does not support vector features together with the soft-float ABI and can crash; the compiler now refuses `sse`, and with it every x86 vector feature, on such a target. It began as a warning reported even from dependencies; the notes for 1.100.0 call it an error.

- The kernel's target is the one soft-float target here. Its flags are `-C jump-tables=no` and `-C target-feature=+harden-sls-ret`: no vector feature. No source file has a `target_feature` attribute.
- **A rule for decision item 123.** When the kernel gets x86-64-v3's integer instructions, they must be named one by one (`+popcnt`, `+lzcnt`, `+bmi1`, `+bmi2`, `+movbe`). `-C target-cpu=x86-64-v3` would turn on AVX2 and the rest, which this compiler refuses on the kernel's target. Proposed to the coordinating session as wording for wherever item 123 is built.

To be checked: the kernel builds; the warning about `harden-sls-ret` is the only one.

### 4.3 Volatile accesses may trap (#160564)

Read: the pull request's description. The language now says a volatile access to memory outside the abstract machine may trap, and that undefined behaviour is fully sequenced with respect to observable events, of which a volatile access is one. For writes LLVM already behaved so; for reads it does from LLVM 23, which both compilers have.

- This is the semantics MMIO needs: a read of a device register is an event the compiler may not move a fault across, and may not assume returns.
- `read_volatile` and `write_volatile` are used in the framework's MMIO, IOMMU, DMA, early-console and CPU code. No code change is expected. The driver contract's record of MMIO ordering can now cite the language's own statement instead of the code generator's behaviour.

To be checked: nothing by a test; recorded.

### 4.4 Cargo's layout for intermediate files (cargo #17354)

### 4.5 The kernel's hardening option is to become a hard error (not in the notes)

**No line of the release notes says this. Only the build showed it.** The kernel is built with `-C target-feature=+harden-sls-ret` (ADR-0017 Z10; decision item 129), which makes the code generator put an INT3 after every return. Rust 1.99.1 accepted it with a warning of five lines: the feature is "unknown and unstable" and is passed through to the code generator. Rust 1.100.0 accepts it too, and the image gate passes on the kernel it builds. Its warning has two more lines: the option was previously accepted, is being phased out, and will become a hard error in a future release; and a pointer to `rust-lang/rust` issue 162235.

**The issue, as read on 2026-11-13** through GitHub's public API (the issue and its twelve comments):

- A tracking issue, open, created on 2026-09-03 and last updated on 2026-09-28.
- What is to become an error: `-C target-feature` with a feature the compiler does not know, knows as unstable, knows as internal, or knows as one that would change the target's ABI. `harden-sls-ret` is of the first kind.
- **No release is named.** The issue's text says the error will likely wait until two things are stable.
- **The two replacements it names:** an unstable option that passes a feature straight to the code generator (`-Zllvm-target-feature`), which needs the standard library built with the same flags (`-Zbuild-std`, also unstable); or having the feature itself stabilized, for which it asks users to say which features bring the warning up.
- None of the twelve comments names this feature.
- **Its third comment, of 2026-09-04, is a moderator suspending a commenter** whose comments looked like automated submissions, under the project's policies on spam. So nothing is posted there by any session of this project: whether and how Origin tells the Rust project which feature it relies on is the owner's, in the owner's own words (decision item 281).

**What ADR-0017 said when item 129 was accepted** (Z10's table, 2026-11-10): an INT3 after every return is on, and "the only way is a target feature the stable compiler accepts with a warning that it is unsupported". The same table turned retpolines off, because their only way was "a target feature the compiler warns will become an error". With Rust 1.100.0 the warning for the INT3 feature is of that second kind too.

**What was decided** (decision items 280 and 281, accepted by the owner on 2026-11-13; ADR-0017 Amendment 2, on the coordinating session's records branch): Z10 keeps the option for as long as the pinned compiler accepts it; the image gate stays what holds the protection; the line the build prints in place of the warning repeats the compiler's announcement on every build; and every compiler upgrade checks by name that the option is still accepted and still does its work.

**What this task does about it:** `expected_warning.rs` matches 1.100.0's seven lines and no longer collapses 1.99.1's five; its one line says the option is to become a hard error, with the issue's number. `verify.sh` gets a check of its own for the option (§7).

### 6.2 After the pin moved

All on the development Mac (Apple M1 Max; boots under QEMU's software CPU), each full build under the machine's turn.

**The first full run with the pin** (2026-11-13, 02:19 to 02:27 UTC; `f0cd1f8` with the pin's four places changed and not yet committed). `cargo xtask check` passed, and `verify.sh` passed 20 of 20. No error, and no lint beyond the two of §6.1. One thing differed: the compiler's warning about the hardening option, which the collapsing filter no longer matched, so 28 copies of it stood in the log (§4.5). The boots that followed passed: `boot-test`, 11 of 11 scenarios, and `boot-matrix`.

**A commit of §6.1 was wrong, and the run that was owed found it.** `817cd16` made the relink step run `cargo clean --release --target <target> --target-dir <directory>`. On a target directory made stale on purpose, that removed the host's own `release` directory of the worktree and left the stale file. Measured in a scratch package, Cargo 1.99.1 and 1.100.0 do the same: without `--package`, `cargo clean` does not look at `--target`, and without `--release` it would remove the whole target directory.
