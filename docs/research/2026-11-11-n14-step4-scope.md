## 2. What step 4 starts from

- **Step 3 is complete** in draft pull request 16 (`land/s3-part2`, pushed at `8c42f15`), which, when this was written, waited for a CI run that boots and then for the owner. On `15baed9`, under QEMU on the development Mac, `cargo xtask check`, `boot-test` and the 122 scenarios of `boot-matrix` passed (`8c42f15`'s records). `origin.kernel` and `user-abi` are at 0.6: calls 0–19, and one named capability, `kernel.debug`. `origin.directory` is at 0.1, with `connect`.
- **There is no `origin.core`.** The generator writes `core_stubs.rs`, one `extern "C"` function per call with an inline `asm!` block holding its `syscall`, and `abi.rs`, the imports a client calls. Nothing compiles them into a library. OIDL's test checks that each stub in the generated crate has one `syscall` with its own number, with the crate compiled alone.
- **The pin is a range** (A6). `syscall.rs` asks `Process::may_call_from(rip)` before dispatch and answers `access_denied`. The creator names the range when it makes the process.
- **Only the kernel launches** (`launch.rs`, S3-3): `Process::child_of`, a start record at a random page of `[0x1000_0000_0000, 0x7000_0000_0000)`, BOOTSTRAP and DIRECTORY.
- **Ring 3 runs only the kernel's proof programs:** hand-written assembly carried in the kernel's read-only image (`proof_programs.rs`), copied to a code page mapped read-execute at a fixed address (`user.rs`), most of them driven by a script interpreter. **No Rust runs in ring 3,** and there is no userspace build: only §11's lint over `cfg`, and the toolchain probes in `tests/toolchain/`.
- **`onbf-pack` writes one profile, KRN.** EXE and LIB do not exist, and their manifest keys are not assigned.
- **The directory's lookup** (`services/directory`) is tested on the host. The boot proof's directory and service are scripts, and how a launcher fills a directory and how a provider receives connections are arrangements of that proof (row D11).
- **Quotas** (`process.rs`, `quota.rs`): handles, channels, queued message bytes, committed bytes, mappings, a change rate, events, ports and bindings, each set by the creator; a kind not given is zero. No count of threads or processes, and no kernel-wide bound (F7).
- **Threads** are started by kernel code on a processor it names (`sched::spawn_user`), and never move. Each processor's run queue holds 16 contexts, its boot context included (`runqueue::CAPACITY`). Each thread has a 16 KiB kernel stack with a guard page, and an FPU area.
- **The clock:** `clock_read` gives the monotonic clock at full resolution (F10). CR4.TSD is clear, so RDTSC runs in ring 3.
- **The log:** `klog.rs` is a ring of records that nothing writes (TASKS item 23). The kernel prints to its consoles, addresses included (design review, finding 14).
- **What each processor set** (ADR-0017 Z1) is kept in one atomic word per processor and printed at boot. No interface serves it.
- **Not built:** 64-bit handles (E1, TASKS item 24); the CPU identification table (ADR-0009 A2, TASKS item 16); `PERFORMANCE_BUDGETS.md` (TASKS item 26).
- **The x86-64 psABI revision is not pinned.** CLAUDE.md §17 says "pin the revision after verification"; it has been open since `docs/research/2026-11-07-onbf.md`. `origin.core`'s C ABI will rest on it.
- **The probe.** A stub in today's generated form was inlined into a function of the same crate that called it twice: the object held three `syscall` instructions loading number 19. A stub written as a naked function (`#[unsafe(naked)]` with `naked_asm!`, which the stable compiler accepted) was called, not inlined, and its number had one `syscall`. One compile and one case: it shows that the inlining happens, not that a naked function can never be duplicated.

### Exit tests, written before any code

**S4-0.** Host: `received_handle` is 16 bytes and `start_entry` 24, field by field against the generated layout. The decoder no longer checks the upper half of a handle's register (OIDL §10, revised). One slot driven past 2^16 generations is not retired, which is today's limit, and a stale handle still never names a reused slot (H2). The fingerprints are re-recorded, citing Amendment 6. Boot: every existing proof passes, with the interpreter loading 64-bit handles. Negative controls: a live handle's low 32 bits alone, and a handle with its generation changed, are each `bad_handle`.

**S4-1.** Host: the conversion refuses each of ONBF §6.1.2's hard errors (a writable and executable segment, a text relocation, `PT_INTERP`, a non-empty `.init_array`, an undefined symbol, a relocation other than RELATIVE, GLOB_DAT and JUMP_SLOT), and gives the same bytes twice from the same input. §11's lint passes over the new crates. Boot (a new Refuse result): the Rust program runs in ring 3 at a random base, and two launches differ; it reads its start record's header and entries as the assembly proofs do; its code is read-execute and its data writable and never executable (a write to code and a jump into data each fault); it ends with its exit code. Negative controls: a program with a writable code segment is refused at build; a launch path that skips one relocation fails the boot line; a fixed base fails "two launches differ".

**S4-2.** Host: the gate refuses an `origin.core` image with a second `syscall` for one number, a `syscall` at an offset the kernel's table does not hold, or a stub whose number load is not its own. It refuses a carried program image that holds any `syscall`, proof programs excepted (candidate 9). The kernel's pin comparisons and the linked image agree (OIDL §13's release fingerprint). Boot (a new Refuse result, "origin.core and the call pin"):
- a Rust program makes every call through `origin.core`, and the existing hostile calls, made through the stubs, give the statuses they give today;
- a `syscall` in the program's own code stops the thread, and the record names the number and the address;
- a jump to call A's `syscall` with call B's number in RAX stops the thread (the E8 attack), and so does a number no stub has;
- `origin.core`'s pages fault on a write; `memory_unmap` and `memory_protect` of its range answer `invalid_args` and leave it mapped; a fixed `memory_map` over it is `invalid_args`;
- two processes see it at different addresses on one set of frames: the count of frames in use rises by its size once.

Costs: one call before the pin and after it. Negative controls: the pin check left out (the E8 lines fail); the base recorded one page off (every call stops, and the boot fails); a stub inlined (the gate fails); A6 kept for a pinned process (the jump line fails).

**S4-3.** Host: a set of limits' figure, kind by kind, from each kind's largest kernel object as the build measures it; paying and repaying to the unit; a launch the root cannot pay for leaves everything as it was. Boot (Refuse): the root figure and the reserve are printed; a launch over what is left is refused, with nothing made; after the proofs end the root is back at its boot value. Negative controls: the payment left out (the refusal line fails); the repayment left out (the leak line fails). O2: the threat model's row cites `origin.kernel` at its version, which has no call that returns a new thread or process.

**S4-4.** Host: the `setup` and `provider` stubs refuse what OIDL §7.5 refuses; a second provider for one key, and a full table, are refused; the hostile corpus for 0.2. Boot (Refuse; S3-4's lines again, with the Rust directory):
- a client's request reaches the provider through `accept`, stamped with the client's identity, and the reply comes back stamped with the provider's;
- `not_found` and `peer_closed` as today;
- a provider whose queue is full gives the client `limit` and a closed end, and the directory goes on serving;
- two clients' connects are answered in the order they arrived;
- a client that sends the `setup` interface's hello on its DIRECTORY channel is refused with `not_supported`.

Negative controls: the wrong end passed on; `accept` made two-way, so that a provider that never reads stalls the directory (the full-queue line fails); the identity lost.

**S4-5.** Host: the report's encoder against the generated layout; the corpus for `origin.diagnostics`. Boot (Refuse, "Diagnostics end to end"): a client that holds the method's capability gets the verdict and every processor's record, equal to what the kernel printed on that boot; a client without it is refused with `access_denied`, and the service's code never runs; the report call from a process without the kernel capability is `access_denied`; no field of any record can hold an address, because the record's type has none. Negative controls: either capability check left out; one field encoded wrongly (the comparison fails).

**S4-6.** Host: the percentiles against known distributions. Boot (a Report result, "service round trip", ADR-0013 R3): for each case p50, p95, p99 and p99.9 with the count of samples, every reply decoded and checked; on the same boot, the channel ping-pong, a null call through `origin.core`, and `clock_read`. Negative control: a reply left unchecked must turn the line false.

## 5. Candidate decisions

Each was checked against CLAUDE.md 7.6, the accepted ADRs and `docs/spec/OIDL.md`. **Six need the owner's eye, because they change or strain an accepted text: 1, 4, 8, 10, 17 and 23.** A method's error set is frozen for a major version (OIDL §8), so the errors in a draft shape are part of it. Candidates 11 and 12 are drafts for later steps; the recommendation is to decide them when those steps begin.

### Getting programs into ring 3

**1. Step 4's programs reach ring 3 inside the kernel's image, laid out at build time, and nothing is parsed at run time.** (**Look**: ONBF §8.3 gives mapping to the Loader Service, and CLAUDE.md §11 says `onbf-pack` "converts the linker output to `.ose`", which under (a) waits for M6.)
- *Options.*
  - (a) As the proof programs do (`proof_programs.rs`; `user.rs` maps their code page read-execute). At build time xtask links each program, and `origin.core`, with `rust-lld` for §11's triple; checks the output against ONBF §6.1.2's hard errors with `onbf-pack`'s ELF reader; and compiles into the kernel a private description: each segment's bytes and permissions, the entry, the relative relocations, and which import slot takes which export of `origin.core`. At run time the launch path places the program at a random base, applies the relocations, binds the imports (candidate 3), makes them read-only, and starts it.
  - (b) ONBF EXE and LIB images now, read by the kernel. ONBF §8.2 says the kernel never parses ONBF for userspace, and the profiles' manifest keys are a format decision of their own (§84).
  - (c) The Loader Service now. It maps from sealed objects whose roots are in the Code Integrity Table, and neither exists (C7, ONBF §8.2).
  - (d) Images the UEFI loader passes beside the kernel: a change to boot info (ADR-0002 B4) and a second verification path, for a stopgap.
  - (e) As (a), and `onbf-pack` also writes `.ose` and `.osl` images that only the host reads, so §11 is met to the letter. The EXE and LIB profiles' manifest keys would have to be decided first (§84), for images nothing on Origin reads yet.
- *Evidence.* The proof programs are the precedent. The KRN image's signature covers the carried bytes, which is how ONBF-R4's "execute only verified code" holds before the CIT exists. N12's closed list already names "the first process and the Loader Service, up to the point where `origin.core` is mapped".
- *Recommended:* (a). The EXE and LIB profiles, and the Loader Service, stay M6's. These programs are first-party and come from the same build as the kernel, so they cannot be out of step with it.
- *Refines:* ONBF §8.3 and ADR-0005 C7, for first-party programs the kernel carries, until the Loader Service exists; CLAUDE.md §11's sentence on `onbf-pack`, which is the owner's text, for the same time.

### `origin.core`

**2. `origin.core` is one image per release, with no writable data and nothing to relocate, mapped read-execute into every process at a random place before its first thread, once, and never unmapped or changed.**
- *Options.*
  - (a) As stated. One set of frames serves every process. It is not a mapping `memory_unmap` or `memory_protect` can name, since both act only on a whole mapping that `memory_map` made (D3), and a fixed `memory_map` over it is `invalid_args`, as over any mapped page (M2).
  - (b) Linked into each program. Every program would then hold the release's call numbers, which are private to the release (§42, ONBF §6.1, P12), and a program built for one release would fail on the next.
  - (c) As (a), with a writable segment for state: frames of its own in every process, for state nothing in step 4 needs. E2 rules out the obvious use, an environment.
- *Evidence.* §42; ONBF §6.1 ("Syscalls are not ABI"); P12. Zircon's vDSO, as its page describes it: built with the kernel and embedded in it; mapped by the process's creator at a random place before the first thread; one executable mapping per process, which must match the code segment exactly and cannot be removed.
- *Recommended:* (a).
- *Refines:* ADR-0011 N5; ADR-0005 P6 (a process starts with `origin.core` mapped, beside its start record); ONBF §6.1 (LIB).

**3. In step 4 the launch path binds each program's imports from `origin.core`, from a table made at build time, and makes them read-only before the first thread.**
- *Options.*
  - (a) As stated: ONBF §6.1's eager binding and full RELRO, done by the kernel for the programs it carries. A program holds no call number and no offset of `origin.core`.
  - (b) The start record names `origin.core`'s base, and each program finds the exports itself. It would carry the release's offsets (2(b)'s objection, one level down), or parse a symbol table.
  - (c) Zircon's way: the base in a register at entry, and the program reads the library's symbol table. That puts a parser in every program before the Loader Service exists.
- *Evidence.* ONBF §6.1 (imports `{dep_index, symbol, min_abi_minor, slot_rva}`, bound eagerly, no lazy PLT) and §8.3 step 5; the vDSO page (the base in `arg2` of `zx_process_start`, then the program reads the ELF headers).
- *Recommended:* (a). The start record gains nothing in step 4. A later minor may give `origin.core`'s base to debuggers and crash records (P10).
- *Refines:* ADR-0005 P6; ONBF §8.3, for step 4.

**4. In step 4 `origin.core` holds the generated stubs and nothing else. P8's synchronous call is composed by the generated channel client from the three stubs, until a kernel fast path is designed with N8's figures.** (**Look**: P8 calls the helper `origin.core`'s.)
- *Options.*
  - (a) As stated. The helper and the fast path enter `origin.core` together, declared in OIDL once OIDL can declare a library call.
  - (b) A hand-written helper in `origin.core` now, with a C signature of its own: a stable export outside the one definition (N7), since revision 1 of OIDL cannot declare a library call (OIDL §18).
  - (c) A revision of OIDL for library calls first, then the helper: a format decision (§84) for a function whose fast path is not designed.
- *Evidence.* P8 ("an `origin.core` helper, with a kernel fast path to come once measured"); OIDL §11 (channel C entry points "would sit on `origin.core`'s call helper (ADR-0005 P8), which does not exist") and §18; N8.
- *Recommended:* (a). A program that composes the call from the three stubs keeps working when the helper arrives, since the stubs stay.
- *Refines:* ADR-0005 P8 (when, not where); OIDL §11 and §18.

**5. `origin.core` exports exactly the entry points OIDL generates for `origin.kernel`, and its version is `user-abi`.**
- *Options.*
  - (a) OIDL §10 and Q10 as accepted: `origin_kernel_<method>`; a status as `int64_t`; `_Noreturn void` for a method that does not return; a boolean as `uint8_t`; structures as the generated header lays them out; handles of 64 bits (S4-0). Each export carries the minor its method arrived in, as ONBF §6.1's exports carry `since_abi_minor`. At major 0 nothing is promised (P12); from major 1 each export is frozen with its method (OIDL §8, §9). Nothing else is exported: no helper (4), no allocator, nothing that reads an environment (M5, E2).
  - (b) Shorter names for the kernel's calls (`origin_channel_write`), Q10's alternative: a special case in the generator.
- *Evidence.* OIDL §10 and Q10; ONBF §6.1. The C ABI rests on the System V x86-64 calling convention, whose revision CLAUDE.md §17 asks to pin after verification. It is not pinned: the repository's tags end at `abi_0_96` (2005), its commit list did not render on 2026-11-11, and the document was not read.
- *Recommended:* (a), with the psABI revision pinned before S4-2 publishes the first export.
- *Refines:* ADR-0011 N4; OIDL §10.

### The pin (E8)

**6. Each stub is a naked function, emitted once, and a gate holds one `syscall` per number.**
- *Options.*
  - (a) Naked stubs (`#[unsafe(naked)]` with `naked_asm!`). A gate reads `origin.core`'s linked image: exactly one `syscall` for each method, at the offset the kernel's table holds, preceded by the load of its own number. It also reads every program image the kernel carries: no `syscall` at all, proof programs excepted (candidate 9).
  - (b) Today's form with `#[inline(never)]`. The probe saw today's form inlined, and the reference's text on when an `asm!` block may be duplicated was not read, so a hint is not a guarantee.
  - (c) `global_asm!` stubs: the same effect, with text assembly in the generator and each symbol declared by hand.
- *Evidence.* The probe (section 2). OIDL's existing test compiles the generated crate alone, where nothing calls a stub, so it cannot see inlining.
- *Recommended:* (a), with the gate, which holds the rule whatever the compiler guarantees.
- *Refines:* OIDL §10's last paragraph and §11's named shim (generated code; no wire format changes); ADR-0005 B2.

**7. The kernel knows each call's offset in `origin.core` from the build, and records `origin.core`'s base when it maps it.**
- *Options.*
  - (a) Zircon's method. The kernel's pin is generated from `origin.kernel.oidl` in the same build as `origin.core`, and OIDL §13's release fingerprint ties the two. The base is recorded for a process when `origin.core`'s code is mapped into it, by the launch path in step 4. The check is `rip − 2 == base + offset(number)`, written as comparisons, as the generated dispatcher is, with no table indexed by the number (Z9, Z10).
  - (b) OpenBSD's method: a call that registers a table once per process, before a second thread exists, made by the loader. One more call, and the pin then rests on the loader and on the order of events.
  - (c) The creator names each process's table when it makes it, extending A6: the pin rests on the creator.
- *Evidence.* The vDSO page: the kernel records the base when the one valid executable mapping is made, and checks each call's offset against fixed offsets generated when the kernel is built. `pinsyscalls(2)`: a table of offsets, indexed by call number, within one text region; registered once by the dynamic linker before any other thread exists, and done by the kernel itself for the dynamic linker and for static programs; a second registration is refused.
- *Recommended:* (a). The pin then rests on nothing a program or a loader says. When the Loader Service maps `origin.core` from a sealed object (M6), the kernel has to recognise that object and record the base at its one executable mapping; that is decided with the Loader Service.
- *Refines:* ADR-0005 B2; ADR-0011 N5; OIDL §18 (the table is generated, and the gate checks it against the linked image).

**8. A call from anywhere but its own stub stops the thread, as a fault does.** (**Look**: A6 answers `access_denied`.)
- *Options.*
  - (a) No status comes back. The thread stops as a fault stops it (P10): the process's exception channel receives the event once such channels exist; until then the thread ends as a faulting thread ends today, with a record of the number and the address. A number that has no stub is the same violation.
  - (b) `access_denied`, as A6 answers a call from outside the range (accepted 2026-11-08).
- *Evidence.* No correct program can make such a call: only code outside `origin.core`, or a jump into a stub past its number's load, can. A status lets a thread whose control flow was taken over try again with other code. Zircon raises a synthetic exception and OpenBSD sends SIGABRT (both pages, 2026-11-11).
- *Recommended:* (a).
- *Refines:* ADR-0005 B2 ("refused"); A6, which it replaces for every process pinned per call.

**9. The kernel's own proof processes keep A6's range; every other process is pinned per call.**
- *Options.*
  - (a) A process is made either with `origin.core` and the per-call pin, or as one of the kernel's proof processes with A6's range over its code. Which one is fixed when it is made.
  - (b) Every proof program moved onto `origin.core`'s stubs. The script interpreter would call each number through a table of stubs the kernel writes, and the hostile proofs that make raw calls would change.
- *Evidence.* The proof programs are the kernel's own fixed code, carried and judged by it, and row E7's proof depends on the range.
- *Recommended:* (a). E8 then closes for every process that is not a proof process, which is what section 3 asks.
- *Refines:* ADR-0005 A6 and B2; ADR-0011 N13's gate on "any crate but `origin.core`" that uses `syscall`, not built yet, which then excepts the kernel's proof programs by name.

### O2 and quotas

**10. O2 closes for step 4 by absence: no call creates a thread or a process, and each step-4 program runs the threads its launcher starts.** (**Look**: the system-call model's list says O2 closes "with the calls that create them".)
- *Options.*
  - (a) As stated. The kernel is the only creator, and starts one thread for each step-4 program. O2's row reads "closed for step 4 by absence; it reopens when a call creates a thread or a process, and that call comes with its quota".
  - (b) A thread-creation call now (candidate 11), with process creation closed by absence.
  - (c) Both calls now (candidates 11 and 12).
- *Evidence.* Nothing step 4 must show needs a second thread, or a creator in ring 3: each program serves its channels from one port (P9). A process made from ring 3 could not be given executable code until the CIT exists (C7), so a creation call could only make empty processes. Threads go where kernel code puts them, never move, and fill a queue of 16 contexts per processor. Placement and load balancing are not built (TASKS item 4), and a creation call would fix a placement rule in an interface. Step 5's Processes domain needs both calls.
- *Recommended:* (a), with candidates 11 and 12 decided when step 5 begins.
- *Refines:* `THREAT_MODEL_SYSCALLS.md`, "What must be closed", item 2; ADR-0005 P11.

**11. When thread creation is built: one call that creates and starts a thread, a `threads` count quota, and a reserve of each processor's run queue for the kernel.** (A draft, for decision with step 5.)
- *Shape.* `thread_create(process: handle<process, manage>, request: thread_request) -> (thread: handle<thread>)`, with `sized struct thread_request { entry: u64; stack: u64; argument: u64; thread_pointer: u64 }` (D1). `manage` is C6's right for thread control, and a process's own handle has it. The thread starts at once, with RIP at `entry`, RSP at `stack`, RDI holding `argument`, and FS at `thread_pointer` (P6, ONBF §6.1.1). Errors `bad_handle, wrong_type, access_denied, invalid_args, fault, limit, no_memory`, the first failure winning in D5's order:
  - the pointers and the request: `fault`, and `invalid_args` for a wrong `size`, an address outside the user half or not canonical, or a stack not aligned to 16 bytes;
  - the handle;
  - what is asked: a process that has ended is `invalid_args`, as D5 has it;
  - the quota: `limit` for the `threads` count, the handle table, or no slot left for a program's thread on any processor;
  - memory: `no_memory` for the kernel stack, the FPU area or the object.

  The `threads` count is charged at creation and refunded when the thread is reaped, a launcher's first thread included. The kernel chooses the processor. On each processor it keeps a reserve of run-queue slots that no program's thread takes, so a program cannot fill the queues the kernel's own threads need.
- *Rejected:* separate create and start calls (nothing can be set between them in v1); a processor named by the program (affinity is a later interface of §25 and §27).
- *Refines:* ADR-0005 P6, P11 and C6.

**12. When process creation is built: a creation call and a start call, each behind a named capability that only the Loader Service and the session launcher hold.** (A draft, for decision with the Loader Service.)
- *Shape.* The creation call takes the child's limits in a sized request, and refuses with `limit` what the creator cannot pay for (candidate 13). The start call has the kernel write the start record from the handles and roles the creator passes (C4), map `origin.core` and record its base (candidate 7), and start the first thread. Both `requires` a capability (OIDL §6), named with the Loader Service's interface (item 108's M1). Row M8's open point: a change rate above 10^9 a second is refused with `invalid_args`, not taken as 10^9.
- *Refines:* ADR-0005 P6 and P11; ADR-0011 Amendment 1, M1–M3.

**13. The kernel-wide bound: what a process's limits could make the kernel hold is paid out of its creator's own, and the kernel holds the root, sized at boot.**
- *Options.*
  - (a) A set of limits is worth a figure in bytes: the most kernel memory and frames they let a process make the kernel hold. That is each count times the largest kernel object of its kind, plus the byte quotas, the page tables up to the framework's bound of 32, and a kernel stack and an FPU area for each thread. A creator pays the figure out of its own when it makes a process, and gets it back when the process is destroyed. The kernel holds the root figure, which is what its frames allow at boot less a reserve for its own use; both are printed at boot. A creation the creator cannot pay for is `limit`. No charge made by a running process changes.
  - (b) A ceiling for each kind across the kernel, checked on every charge beside the process's own quota, answering `no_memory`: a shared counter on every creation path, and a process within its quota can be refused because of another.
  - (c) No kernel-wide bound, relying on fallible allocation (O3). The kernel stays up, but one program can use up the memory every other program needs.
- *Evidence.* P11 ("quotas set by its creator"); D4; F7 ("No kernel-wide bound yet; that is step 4's"); row K5. Every allocation a program can cause is already bounded by one of its quotas (a port's index, K7, by `bindings`), so each kind's largest object can be measured.
- *Recommended:* (a). F7's bound and P11's creator-set quotas become one mechanism, no hot path changes, and no creator can hand out more than it holds. In step 4 the kernel is the only creator, so (a) is built as the root and a payment at each launch. K7's index, which nobody's quota counts, is measured per binding first; otherwise the figure is not honest.
- *Refines:* ADR-0005 P11, D4 and F7.

**14. No implicit default quotas.**
- *Options.*
  - (a) A launcher gives each kind deliberately, and a kind not given is zero, as D4 and F7 say kind by kind. In step 4 each program's limits are written beside its image, and are the least it needs, found from its own high-water marks in its boot result. What the Loader Service gives a program that asks for nothing is decided with its manifest keys (§84, M6).
  - (b) A table of defaults in the kernel for a process made without limits. The kernel would then choose what programs get, against P11.
- *Recommended:* (a).
- *Refines:* ADR-0005 D4 and F7.

### The directory's back side (D11)

**15. A launcher fills a directory through a typed `setup` interface on the directory's BOOTSTRAP channel.**
- *Options.*
  - (a) `origin.directory` 0.2 gains an interface `setup`, with `add(interface_id: u64, major: u16, provider: handle<channel, read | write | wait>)`. Its errors: `limit` for a full table, and a new status appended to `origin.kernel`'s (P5) for a key the table already holds: D2's rule, now on the wire. Only the launcher holds the BOOTSTRAP channel. On a provider's channel the directory is the client: it sends the hello first (OIDL §7.7), and reads only that reply, without waiting for it before it serves its own clients. Entries are added and never removed in v1. A provider that has gone answers `limit` at the next connect, as D7 already does. In step 4 each program that has a directory has its own.
  - (b) As (a), with `invalid_args` declared as `add`'s own error for a key already held, so that no status is added. A client could not then tell it from a refusal of the message (OIDL §7.8, §8).
  - (c) The table in the start record's arguments. M5 and E2 forbid configuring a first-party service through arguments.
  - (d) The table in a memory object handed over at start: a layout to parse, and nothing can be added later.
- *Evidence.* The service-directory ledger (its point 4 and its unknowns); C12; rows D2, D7 and D11; `services/directory`'s `AddError`, which already tells `Full` from `Taken`.
- *Recommended:* (a). The new status makes S4-4 change `origin.kernel.oidl` between S4-0 and S4-5. Whether one directory process serves the tables of many programs is decided with the session launcher (step 5).
- *Refines:* ADR-0005 C12 and P5; ADR-0011 N9.

**16. A provider receives connections as a one-way `accept` on a `provider` interface.**
- *Options.*
  - (a) `origin.directory` 0.2 gains an interface `provider`, with `oneway method accept(interface_id: u64, major: u16, server: handle<channel, read | write | wait>)`, which a provider serves on the channel its launcher gave the directory. One-way, because the directory never waits on a provider (D7): a full queue makes the directory's write answer `should_wait`, and the client gets `limit` and a closed end. The key travels with the end, so one provider channel can serve several keys; the client's hello on the end then names the interface.
  - (b) The boot proof's arrangement: a `connect` call on the provider. A provider would serve the client's interface and answer its errors, and a two-way call makes the directory either wait or ignore a reply.
  - (c) A kernel object that delivers connections: a kernel change for a service protocol.
- *Recommended:* (a).
- *Refines:* ADR-0005 C12; row D7.

### Speculation (I2)

**17. Step 4 goes ahead with I2 "Partly", and I2's closure moves to "before any claim about real hardware, and before any program that is not first-party runs in ring 3".** (**Look**.)
- *Options.*
  - (a) Hold step 4's first program until a boot on a processor in the declared scope reads every control back. No such machine exists or can be rented, and CI's guests offer none of the controls, so step 4 would wait indefinitely.
  - (b) As stated. Step 4's programs are first-party, and run under QEMU and as KVM guests only. Where a processor offers none of the controls, programs are not protected from each other's speculation, which AC6 (item 138) accepts for bench machines. Boots under QEMU keep ending "degraded" (item 154). The system model's "must exist" row and the system-call model's list are reworded to say the same thing.
  - (c) As (b), and also rent a whole machine with Zen 5 or recent Intel cores, once, to read the controls back on silicon. It would be bench equipment outside the scope (ADR-0009 A1), so it claims nothing for the declared machines, and it is external spending, the owner's (§1).
- *Recommended:* (b), with (c) whenever the owner chooses to spend.
- *Refines:* `THREAT_MODEL_SYSCALLS.md`, "What must be closed", item 3; `THREAT_MODEL_SYSTEM.md`, "What must exist", its first row; acceptance AC6.

### The clock and the timer

**18. Ring 3's clock stays at full resolution, and row K15 closes as accepted under AC5.**
- *Options.*
  - (a) As stated. RDTSC and RDTSCP already run in ring 3 (CR4.TSD is clear; Intel SDM Vol. 3 §20.17 and AMD APM Vol. 3, read for S3-6 on 2026-11-11) and are finer than `clock_read`, so coarsening the call alone would deny a program nothing. AC5 (item 137) accepts timing channels between programs in general. N8's figures are taken in ring 3.
  - (b) Set CR4.TSD and coarsen `clock_read`. Every reading of time becomes a call; the SDM asks a system that sets TSD to emulate the instruction; and a coarse clock is beaten by repetition. TSD is an open point of ADR-0017's, not step 4's.
  - (c) Coarsen `clock_read` only: no effect while RDTSC is open.
- *Recommended:* (a).
- *Refines:* row K15; ADR-0005 F10.

**19. The `Timer` object is not needed in step 4.**
- *Options.*
  - (a) Not in step 4. The directory, the service and the client each wait on one port with a deadline (F3), which covers every timeout they have. TASKS item 36 stays owed under P3.
  - (b) Build it now: its own ledger and shapes, for no need of step 4's.
- *Recommended:* (a).
- *Refines:* ADR-0005 P3 and F19.

### Diagnostics and N8

**20. `origin.diagnostics` 0.1 serves the boot report; the kernel log comes in a later minor.**
- *Options.*
  - (a) The boot's verdict (ADR-0013 R6): how many proofs passed, failed and did not run, and the names of those that failed, which are fixed strings of the kernel's table and never a formatted message. And, for each processor, what CPUID reports it is (vendor, family, model, stepping), and which of ADR-0017's controls it set and which it lacks; Z1 says these facts are to be "served through a typed interface". Fixed-size records, and no field that can hold an address. The scope verdict of ADR-0009 A2 joins when the CPU identification table exists (TASKS item 16). The methods require a named capability that the launcher grants (OIDL §6), since the record tells a reader which defences are missing. The kernel log follows once the kernel writes one (`klog` is unused, TASKS item 23), and once addresses are out of it, which ADR-0004 H3's note requires "before the Diagnostics interface serves the kernel log" (item 119).
  - (b) The kernel log first, as N11 names it: a log the kernel writes, address removal, text across the boundary and a cursor protocol, all before the first round trip. More than "the smallest".
  - (c) Counters only: nothing but N8 would read them.
- *Recommended:* (a). The exact records are for S4-5's ledger, put to the owner as shapes.
- *Refines:* ADR-0011 N11 and N14 step 4; ADR-0017 Z1.

**21. The Diagnostics service gets the report through one kernel call that only it may make.**
- *Options.*
  - (a) A call in a new minor of `origin.kernel` that copies the report into the caller's buffer, gated by a named kernel capability held as process state, as `kernel.debug` is. The launch path gives it to the Diagnostics service only.
  - (b) A read-only memory object the kernel fills at boot and hands to the service at launch, under a new start-record role: no new call, but a layout read in place, and a role for one program.
  - (c) The kernel serves `origin.diagnostics` itself (N8's second row). It is then not a service domain, and step 4 would not show the path N8 asks to measure.
- *Recommended:* (a).
- *Refines:* ADR-0005 P4; OIDL §6.

**22. What N8 measures in step 4.**
- *Options.*
  - (a) The typed round trip, client to service and back, for a small reply and for the vector of processor records; with the client and the service on one processor and on two (the launch path places them); at least 10,000 calls a case, so that p99.9 rests on ten samples above it; p50, p95, p99 and p99.9, with the count (§1). On the same boot: the channel ping-pong, a null call through `origin.core`, and `clock_read`, so that N8's three costs sit side by side. Printed at every boot as a Report result. A provisional figure goes into `PERFORMANCE_BUDGETS.md` before the first measurement, as §1 requires ("Establish performance budgets before measurement"), marked a hypothesis (item 115) and derived from a stated model: the calls, switches and barriers in one round trip, each costed from what the boot prints.
  - (b) A mean only: against §1's rule on distributions.
- *Recommended:* (a).
- *Refines:* ADR-0011 N8.

**23. N8's figure "on the declared hardware" is owed before any performance claim and before release qualification; step 5 does not wait for it.** (**Look**: N8 says "before a second one is built".)
- *Options.*
  - (a) N8 as written: no second domain until the round trip is measured on a declared machine. None exists, so step 5 would wait indefinitely.
  - (b) As stated. In step 4 the figures from QEMU and from CI's KVM guests go into `PERFORMANCE_BUDGETS.md` as trends beside the hypothesis, which is what §53 already says "until that hardware exists" (item 115).
  - (c) Step 5 builds its domains, and ships none of them until the figure on declared hardware exists.
- *Evidence.* §53; item 115. Neither QEMU's processor nor CI's guests offer IBPB, so their figures leave out the barrier Z3 adds at every switch between processes on a processor that has one: two in each round trip made on one processor.
- *Recommended:* (b).
- *Refines:* ADR-0011 N8.

**24. No call to drop a message without room for it; a service closes a connection whose next message it cannot take.**
- *Options.*
  - (a) A service reads with a buffer of `max_message_bytes`, and keeps room in its table for `max_message_handles` more. A read that still answers `limit` (A4: its table cannot take the message's handles) makes it close that connection, and the message's handles are closed with the end. A client that sends what the service cannot take loses only its own connection.
  - (b) A discard call or option. S3-2's note says Zircon has one. It would be a new call, since D1 rules out an options word.
- *Recommended:* (a) for step 4; (b) if a service ever shows it needs one.
- *Refines:* ADR-0005 A4; S3-2's finding, "reading without room" (TASKS, "In progress").

## 6. What stays unknown

- **Nothing here has run.** This stage is documents, and every claim of behaviour above is a design until its task builds it.
- **Whether a naked function can ever be duplicated by the compiler.** One probe, one case; the Rust reference was not read. Candidate 6's gate holds the rule either way.
- **Whether `origin.core` links with nothing to relocate.** In the probe, a call from one function of the crate to a naked stub went through the global offset table (`call qword ptr [rip]`, a relocation). With stubs only, and no calls between them, none is expected; S4-2's gate shows it.
- **The form of the kernel-private description** of a carried program: generated Rust source, or bytes and a table. S4-1's.
- **Each kind's largest kernel object,** which candidate 13's figure needs. K7's index is not measured.
- **What a client checks a service's identity against** (row D5; ADR-0011 S9). Not needed in step 4, whose client trusts the directory its launcher built (N9). It comes with principals (§57).
- **One directory process per program, or one per launcher.** Step 5's, with the session launcher.
- **How the Loader Service records `origin.core`'s base** (M6). Zircon's rule of one executable mapping is recommended then (candidate 7).
- **The round trip's cost.** Nothing is measured. QEMU's and CI's figures will lack IBPB (candidate 23).
- **A service that faults is not restarted.** Service supervision is ADR-0014 S7's service management, later, and P10's exception channel is not built.
- **The scope verdict** in Diagnostics' record waits for TASKS item 16.
- **The x86-64 psABI revision** (candidate 5).
- **Not in step 4:** random bytes for programs (ADR-0016 R11); SSBD for a thread (ADR-0017 Z4); Rust `std` (§44); channel C entry points (OIDL §11); thread-local storage beyond the FS value (ONBF §6.1.1); CET (E11); the nested NMI (E12); V2.
- **No hardware.** When built, step 4 runs under QEMU (TCG) with OVMF on the development Mac and as KVM guests in CI. Nothing will have run on a declared machine.
