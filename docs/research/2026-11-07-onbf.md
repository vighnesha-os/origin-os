## 2. Local experiments

All experiments ran on rustc **1.97.0** (`2d8144b78 2026-07-07`, LLVM 22.1.6) in a Linux x86-64 sandbox. CLAUDE.md §9 requires repeating them on **1.99.1 on the M1 Max**; they are not a substitute for that.

- **E1. Target specs** (`rustc -Z unstable-options --print target-spec-json`, inspection only)
  - `x86_64-unknown-none`: `code-model: kernel`, `features: -mmx,-sse,…,-avx2,+soft-float`, `rustc-abi: softfloat`, `disable-redzone`, PIE, `panic: abort`, linker `rust-lld` (gnu-lld).
  - `x86_64-unknown-uefi`: `-mmx,-sse,+soft-float`, `rustc-abi: softfloat`, `msvc-lld`.
  - `x86_64-unknown-linux-gnu`: hard-float System V, PIE, dynamic linking, thread-local support.
- **E2. Float ABI.** Source: `extern "C" fn scale(x: f64) -> f64 { x * 2.5 }`.
  - On `x86_64-unknown-none` it compiles to `callq __muldf3` with both operands in **integer registers**. That is software floating point and a soft-float calling convention.
  - On `x86_64-unknown-linux-gnu -C target-cpu=x86-64-v3` it compiles to `vmulsd …, %xmm0, %xmm0; retq`, which is hardware floating point under the standard System V ABI.
- **E3. Stable hardening flags.**
  - Stable `-C` has `force-frame-pointers`, `relro-level` and `control-flow-guard` (Windows only).
  - `cf-protection` (IBT/SHSTK markup) and `stack-protector` exist only as `-Z` flags.
- **E4. `no_std` on the Linux target.** `no_std` on `x86_64-unknown-linux-gnu`, linked with `rust-lld` and no libc, fails with **undefined `memcpy` and `memset`**. An Origin runtime on that triple must provide the `mem*` functions; `x86_64-unknown-none` gets them from compiler-builtins.

### 2.1 Re-run on rustc 1.99.1, M1 Max (2026-11-07)

Toolchain: rustc **1.99.1** (`58cf8f9c3 2026-10-13`, LLVM 23.1.1), host `aarch64-apple-darwin`, macOS 27.0.1. E2 and the IBT/stack-protector part of E3 are automated in `developer-tools/toolchain/verify.sh` (see `docs/toolchain/VERIFICATION.md`). E1, the rest of E3, and E4 were run by hand.

- **E1: unchanged.** `x86_64-unknown-none`: `code-model: kernel`, `-mmx,-sse,…,-avx2,+soft-float`, `rustc-abi: softfloat`, `disable-redzone`, PIE, `panic: abort`, `rust-lld`/`gnu-lld`. `x86_64-unknown-uefi`: `-mmx,-sse,+soft-float`, `softfloat`, `msvc-lld`. `x86_64-unknown-linux-gnu`: `gnu-cc`, PIE, dynamic linking, thread-local support. The specs were printed with `RUSTC_BOOTSTRAP=1 rustc -Z unstable-options --print target-spec-json`; that is inspection only, and no artifact was built that way (CLAUDE.md §12).
- **E2: unchanged.** On `none` the multiply is `callq *__muldf3@GOTPCREL(%rip)` with the operand in `%rsi`. On `linux-gnu -C target-cpu=x86-64-v3` it is `vmulsd …, %xmm0, %xmm0`.
- **E3: unchanged.** `cf-protection` and `stack-protector` appear only in `rustc -Z help`, not in `-C help`. Stable `-C` still has `force-frame-pointers`, `relro-level` and `control-flow-guard`.
- **E4: confirmed, with two additions.**
  - With a runtime-length `ptr::copy_nonoverlapping` + `ptr::write_bytes`, linked with `-C linker=<sysroot rust-lld> -C linker-flavor=ld.lld`, rust-lld reports **undefined `memcpy` and `memset`**. `libcompiler_builtins` for `x86_64-unknown-linux-gnu` defines no `mem*` symbols; the `x86_64-unknown-none` one defines `memcpy`, `memset`, `memmove`, `memcmp` as weak symbols. A fixed-size copy (the 256-byte copy in `tests/toolchain/none_smoke.rs`) is inlined at `opt-level=3` and links without any `mem*`, so it does not exercise E4.
  - **New: `rust_eh_personality` is undefined** once any `core` panic path is linked in (a slice bounds check is enough), **even with `-C panic=abort`**. The reference is `DW.ref.rust_eh_personality` inside the prebuilt `libcore-*.rlib` for `x86_64-unknown-linux-gnu`, which is built for unwinding. Defining `#[unsafe(no_mangle)] pub extern "C" fn rust_eh_personality() {}` in the program fixes the link on stable 1.99.1 (output: x86-64 static-pie ELF). The function is never called under `panic=abort`.
  - **New: `suspicious_runtime_symbol_definitions` lint** (warn by default on 1.99.1). It fires when a `#[unsafe(no_mangle)]` `memset` uses `*mut u8` instead of the C signature `unsafe extern "C" fn(*mut c_void, i32, usize) -> *mut c_void`. The Origin runtime's `mem*` definitions must use the exact C signatures.
  - The stable linker-flavor spelling is `ld.lld`. `gnu-lld` is rejected without `-Z unstable-options`, and `-C link-self-contained` is not supported on this target.
- **QEMU/OVMF (handoff T7).** Homebrew `qemu` 11.1.3 was installed with the owner's approval on 2026-11-07. The x86-64 firmware is `edk2-x86_64-code.fd` (plus `-secure-code.fd` for Secure Boot + SMM, q35 only). Its NVRAM template is `edk2-i386-vars.fd`, per `share/qemu/firmware/60-edk2-x86_64.json`. The boot banner reports **edk2-stable202408**. File hashes are recorded in `docs/toolchain/VERIFICATION.md`.
  - Smoke boot: `qemu-system-x86_64 -machine q35 -cpu max -m 512M -smp 2`, with code pflash read-only, a copy of the vars template, and a `fat:rw:` ESP holding the 1.99.1-built `tests/toolchain/uefi_smoke.rs` as `\EFI\BOOT\BOOTX64.EFI`.
  - The serial log shows `BdsDxe: loading Boot0001 "UEFI QEMU HARDDISK…"` and then `starting Boot0001`. When the app returned, BDS fell through to `Boot0000 "UiApp"`. So OVMF accepts and starts our PE32+ image.
  - The app's return status is not visible: the smoke app prints nothing. The T8 loader must print to ConOut and the test must assert on that output.
  - Harness note: QEMU ignores a `SIGALRM`-based timeout (`perl -e 'alarm N; exec …'`). Boot tests need an explicit exit path, such as `-device isa-debug-exit` written by the guest, or the harness killing the process.

## 4. Toolchain constraints that shape ONBF

- **T1. Userspace cannot be built for `x86_64-unknown-none`.** It is soft-float and uses the kernel code model (E1, E2). That target is right for the Framekernel and wrong for applications: no SSE/AVX floating point, and a calling convention incompatible with the Origin C ABI (CLAUDE.md §49).
- **T2. Stable options for userspace on 1.99.1:**
  - **U2 (now):** compile `no_std` for the `x86_64-unknown-linux-gnu` triple, purely as a code generator. Origin provides `_start`, the `mem*` functions (with their exact C signatures) and a `rust_eh_personality` symbol (E4; §2.1). `onbf-pack` converts the PIE output. Origin code must never use `cfg(target_os = "linux")`, and a lint enforces that.
  - **U1:** a custom `x86_64-unknown-origin` target needs `-Zbuild-std`, which is nightly and so needs a CLAUDE.md §12 exception.
  - **U3 (long-term):** upstream an Origin target into Rust. This is the only stable route to `std` (CLAUDE.md §44).
- **T3. Hardening on stable.**
  - No `-Zcf-protection` and no `-Zstack-protector` (E3, R14, R15), so IBT and stack canaries are unavailable.
  - CET shadow stack needs no code generation and can be enforced by the kernel.
  - Frame pointers and RELRO are stable.
- **T4. Panics.** `no_std` + `panic=unwind` needs the unstable `eh_personality` lang item. Userspace is therefore `panic=abort` until a real `std` port exists. Even under `panic=abort`, the prebuilt unwind-built `libcore` for the Linux triple references `rust_eh_personality`, so the runtime must define that symbol as a never-called stub (§2.1).
- **T5. The `wcslen` regression (R2)** is triggered when LLVM turns a NUL-terminated 16-bit length loop into a `wcslen` call. UEFI `CHAR16` strings are exactly that loop. The CLAUDE.md §10 regression test should therefore be such a loop inside the `no_std` loader, linked for `x86_64-unknown-uefi`.
- **T6. The FFI-bool regression (R2)** is why ONBF-R7 types ABI booleans as validated `u8`.

## 5. Findings on CLAUDE.md v7.0 (applied in v7.1 with the owner's approval, 2026-11-07)

1. **§10 is accurate.** All three regressions match R2. Add T5's concrete test.
2. **§11 should change.** Userspace must not use `x86_64-unknown-none` (T1). Adopt U2 now and start U3.
3. **§8 `rust-toolchain.toml`.** Add the userspace code-generation target (`x86_64-unknown-linux-gnu`; it is not preinstalled on an Apple Silicon host) and the `llvm-tools` component.
4. **§14.** Record T3. IBT and stack protector wait for stable flags; shadow stack is on by default.
5. **§17.** Re-pin PCIe (6.4 / 7.0). Pin TPM V185, TUF 1.0.37, USB PD R3.3 V1.0 and the USB4 v2.0 edition. Add FIPS 180-4, FIPS 202, FIPS 204 (+ errata), FIPS 205, SP 800-208, RFC 8032, RFC 8949, RFC 8878 and the x86-64 psABI.
6. **§42–§47.** Add the shared-library format, kernel-image format and release-manifest format, covered by the ONBF LIB, KRN and SYS profiles. Decide D1 against §43's "ELF64 payload initially".
7. **§84 and final rule 37** ("do not stop after plans") conflict with the owner reserving format decisions. Add: *ABI and format ADRs require owner approval before "Accepted". Agents may build host-testable parsers against a Proposed spec but must not ship them.*
8. **Windows compatibility** is not mentioned in v7.0 → D5. The owner decided: no `.exe` or `.msi`, no 32-bit, 64-bit only.
9. **§59.** The OS needs signature **verification** only. Signing lives in release infrastructure and host tools, which narrows the original-crypto scope.
10. **§19.** The Microsoft 2011 Secure Boot CAs have expired (R5). The boot ADR must choose between signing under Microsoft UEFI CA 2023 (annual audit) and Origin keys enrolled by the user or OEM.
