# Research ledger: what UEFI 2.8 to 2.11 changed, against Origin OS's loader

| | |
|---|---|
| Date | 2026-11-09 |
| Question | The loader is written to UEFI 2.11 (CLAUDE.md §17), but under QEMU the boot log says "UEFI 2.7". What did UEFI add after 2.7 that 2026+ hardware may use, and does the loader handle it? |
| Method | The specification's own revision history could not be read: uefi.org refuses automated access to the 2.11 HTML and PDF, and archive copies were unreachable. The changes below come from the UEFI Forum's 2.11 announcement and from EDK II, the reference firmware, whose commits implementing 2.11 cite it. A section-by-section check against the 2.11 text itself still needs the PDF (the owner can place it in `specifications/`, as for the IOMMU specifications). |

## 1. Why the boot log says 2.7

The loader prints the revision the firmware reports in its system table header. OVMF is built from EDK II, and EDK II's `MdePkg/Include/Uefi/UefiSpec.h` still sets `EFI_SYSTEM_TABLE_REVISION` to `EFI_2_70_SYSTEM_TABLE_REVISION`, although it defines the macros up to `EFI_2_110_SYSTEM_TABLE_REVISION` (added by commit `4ec3539e3`, 2024-12-10) and implements later features. Vendor firmware built on EDK II may report 2.7 too, whatever it implements. The loader accepts any revision from 2.0 and finds what it uses by GUID, so a reported revision never decides what it does.

## 2. What changed after 2.7, for an x86-64 loader and kernel

| Added in | Change | Origin OS |
|---|---|---|
| 2.8 | Memory attribute `EFI_MEMORY_SP` (0x40000): specific-purpose memory, such as high-bandwidth or CXL-attached memory, not for general use | **Was ignored**, so such memory became general RAM. Now its own region kind (boot info 0.5) |
| 2.8 | Memory attribute `EFI_MEMORY_CPU_CRYPTO` (0x80000): memory the processor can encrypt (Intel TME, AMD SME) | Ignored; matters only when memory encryption is used |
| 2.8 | The runtime properties table: which runtime services still work after `ExitBootServices` | Not used; needed when the kernel first calls runtime services, for example the boot manager writing boot entries (§20) |
| 2.9 | Memory type `EfiUnacceptedMemoryType` (15): memory a confidential virtual machine (TDX, SEV-SNP) must accept before use | Treated as reserved: safe, but such a guest would see little memory. Not used on bare metal |
| 2.10 | Firmware that loads images no-execute where they allow it, with a memory attribute protocol to change permissions | Satisfied: `origin-boot.efi` sets `IMAGE_DLL_CHARACTERISTICS_NX_COMPAT`, its code is read-execute and its data read-write, and no section is both writable and executable (read with `llvm-readobj` on 2026-11-09) |
| 2.10 | The memory attributes table, version 2: a flag says whether runtime code carries indirect-branch tracking | Not used until runtime services are |
| 2.10 | The conformance profiles table | Informational |
| 2.11 | Memory attribute `EFI_MEMORY_HOT_PLUGGABLE` (0x100000; EDK II `12ceee664`): memory that can be removed at run time | **Was ignored.** Now its own region kind (boot info 0.5) |
| 2.11 | The Coherent Device Attribute Table (CDAT) through the adapter information protocol, §11.12 (EDK II `0bc238d06`) | Later, with CXL |
| 2.11 | SM3 in image authentication (EDK II `7742247d1`) | Not used |
| 2.11 | `LoadImage` returns `EFI_NOT_FOUND` when given neither a buffer nor a device path (EDK II `a581eb85f`) | Not called |
| 2.11 | RISC-V, Arm and LoongArch items | Not applicable: x86-64 only |

The Forum's announcement for 2.11 also names "enhancements to protocols, algorithms and boot management" without listing them; those are the part of 2.11 this ledger has not seen.

## 3. What was done

The loader now reads each descriptor's attribute as well as its type. Conventional memory marked `EFI_MEMORY_SP` becomes `SpecificPurpose`, and conventional memory marked `EFI_MEMORY_HOT_PLUGGABLE` becomes `HotPluggable` (specific-purpose wins when both are set). The kernel neither allocates from nor direct-maps either kind. This is boot info 0.5, accepted by the owner on 2026-11-09 (ADR-0002 B4, decision sheet item 69).

## 4. Still open

- Reading the 2.11 text itself, for the unnamed protocol, algorithm and boot-management changes.
- Unaccepted memory, if Origin OS is ever to run as a confidential guest.
- The runtime properties table and memory attributes table, when the kernel first calls runtime services.
- Using hot-pluggable and specific-purpose memory deliberately, which needs memory hot-plug (§28) and CXL support.
