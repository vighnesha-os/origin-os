## 2. What each signal tells a scheduler on the target hardware

The target is ADR-0009 Amendment 1's: Intel generations launched in 2026 or later, often hybrid (Panther Lake has three core types), and AMD Zen 5 or newer launched in 2026 or later (Gorgon Point, a Zen 5 refresh; EPYC Venice, Zen 6).

### 2.1 Topology levels

Already recorded in `docs/research/2026-11-08-cpu-topology-leaf-1fh.md` §2 and built in `origin_frame::topology`: leaves 1Fh and 0Bh (Intel) and 80000026h (AMD) give each processor's thread, core, module, tile, die, die group and package fields, read on each processor itself, because on a hybrid part they can differ between processors. Nothing new was needed for M3. The kernel already prints each processor's fields and checks them against the MADT; nothing schedules by them (matrix row S24-11).

### 2.2 Which processors share a cache

- **Intel, leaf 04H** (I1 §21.3, Table 21-14, pp. 21-21 and 21-22). Each sub-leaf describes one cache. EAX\[25:14\] plus one is the most addressable logical-processor IDs that share it; rounded up to a power of two, it is the number of initial APIC IDs set aside for the sharers, so two processors share the cache when their APIC IDs agree above that many low bits. I3 §11.8 (p. 11-34) says software must use this leaf to learn the sharing, and §11.9.4 (p. 11-42) gives only the general extraction method.
- **Caveats Intel states.** The count is a maximum of addressable IDs, not the processors present. EAX\[31:26\] can be saturated and wrong where leaf 0BH or 1FH exists. Every field of leaf 04H except the line size is in the *Logical Processor* domain (I1 §21.1.4, pp. 21-2 and 21-3): it can differ between logical processors, and Intel names cache and hybrid scope as examples. So each processor must read its own. I3 §11.9.4 says Intel supports systems where every package reports the same values: the symmetry it assumes is between packages, not between core types.
- **AMD, Fn8000_001D**: see §2.7.
- **ACPI PPTT** (ACPI66 §5.2.31, pp. 337 to 343, table revision 3, optional). A processor hierarchy node (type 0) per MADT processor, per group that shares a resource the table describes, and per physical package. Flags say: physical package, processor ID valid, *processor is a thread* (shares functional units with its siblings), leaf, and *identical implementation* (all children the same implementation revision). A cache (type 1) is a private resource of the node that stands for every processor sharing it, so the sharers are the leaves under that node. One cache structure may be listed by many nodes for compactness: two leaves naming the same structure share a cache only if its Cache ID is valid. Values flagged valid in the table take precedence over the processor's own reports. Nothing in 6.6 restricts PPTT to an architecture, or says x86 firmware provides it. QEMU's x86 machines do not build it (`2026-11-08-cpu-topology-leaf-1fh.md`, §1).

**For the design:** cache groups come from each processor's own leaf 04H or Fn8000_001D, and from PPTT where a platform provides one (PPTT then wins, as ACPI says). Where two processors' reports disagree about sharing, the conservative answer, no sharing, is used and the boot says so.

### 2.3 Hybrid parts: what identifies a core, and what does not

- CPUID.07H:EDX\[15\] marks a hybrid part; leaf 1AH then exists on every logical processor (I1 Table 21-21, p. 21-29; Table 21-63, p. 21-66). EAX\[31:24\] is a core type (20H Intel Atom, 40H Intel Core), EAX\[23:0\] a native model ID.
- **The core type is a name, not a measure.** Intel says the value identifies a microarchitecture only, that its size means nothing, and that software must not infer any other attribute from it. It gives no performance order. The kernel already records it as a raw code and derives nothing (`origin_frame::topology`); ADR-0020 keeps it so (S27-10).
- **Same instructions and the same saved state on every core type?** No hybrid-specific rule is stated. The nearest is the domain each CPUID field is in (I1 §21.1.4): the instruction feature flags of leaves 07H and 24H, and in leaf 0DH the supported-XCR0 bitmap, ECX, and each state component's size and offset, are *Platform* domain, which on a properly configured platform every logical processor reports alike (Tables 21-34 to 21-36, pp. 21-42 to 21-44). Only the sizes that follow the current XCR0 or XSS (0DH.00H:EBX, 0DH.01H:EBX) are Logical Processor domain. Leaf 1FH acknowledges cores with one and with two logical processors on one platform (p. 21-71).
- **AMD**: see §2.7.

### 2.4 Intel's Hardware Feedback Interface and Thread Director

- **Discovery** (I1 Table 21-16, pp. 21-24 and 21-25). CPUID.06H:EAX\[19\] is the Hardware Feedback Interface (HFI); EAX\[23\] Thread Director; ECX\[15:8\] the number of Thread Director classes. EDX\[7:0\] says which capabilities the table reports (bit 0 performance, bit 1 efficiency, set together), EDX\[11:8\] its size in 4 KiB pages less one (both Package domain), and EDX\[31:16\] this logical processor's row in the table (Logical Processor domain; rows may be shared and may have gaps).
- **The table** (I3 §17.6.1 and §17.6.2, Tables 17-4 to 17-9, pp. 17-25 to 17-30). One per package, allocated and zeroed by the operating system. A 16-byte header holds a timestamp and, per capability, a change flag (bit 0) and a force-idle flag (bit 1). Each row holds, per class and capability, one byte from 0 to 255, higher being better.
- **Configuration** (I3 §17.6.4 and §17.6.5, p. 17-31). IA32_HW_FEEDBACK_PTR (17D0H) holds the table's page address and a valid bit; IA32_HW_FEEDBACK_CONFIG (17D1H) bit 0 enables HFI, bits 0 and 1 Thread Director. Both are package scope. INIT, SIPI and GETSEC clear them, and the operating system must enable them again afterwards (§17.6.9, p. 17-34).
- **Notification** (I3 §17.6.6, p. 17-32). IA32_PACKAGE_THERM_STATUS bit 26 is set when the table changes, and hardware updates the table no more until the operating system clears it, which is the acknowledgement. IA32_PACKAGE_THERM_INTERRUPT bit 25 enables an interrupt through the thermal LVT, and one is sent when the enable first goes from 0 to 1. Which processor's LVT takes a package's interrupt is not stated.
- **What the values ask of the operating system** (I3 §17.6.7, PDF p. 561, printed p. 17-33; checked). After a change, re-read the capability for every logical processor. A zero performance or efficiency cell says it is better not to schedule threads of that class there; zero in every cell of a processor says avoid it altogether (with SMT, hardware may zero only one sibling). Zero everywhere with force-idle set says to idle the processor and, where work is tied to it, to inject idle time. An efficiency value of 255 asks the operating system to consolidate work, interrupts included, onto those processors, and to spread out again when the work needs more than they give.
- **Thread Director.** The class of the running thread is read from IA32_THREAD_FEEDBACK_CHAR (17D2H: class in bits 7:0, valid in bit 63; when not valid, use the thread's last known class); IA32_HW_FEEDBACK_THREAD_CONFIG (17D4H) enables it per logical processor; HRESET, under IA32_HRESET_ENABLE (17DAH), resets the history (I3 §17.6.8 to §17.6.11, pp. 17-33 to 17-35; I2 p. 3-440; support in CPUID.20H.00H:EBX\[0\], I1 p. 21-73). The suggested use (§17.6.3, p. 17-30): put a thread on the free processor with the highest value in its class's column, and when two threads compete compare their classes' performance ratios. **The SDM gives no meaning to any class number and states no duty at a context switch** (neither reading the class nor HRESET).
- Volume 1 names the class register IA32_HW_FEEDBACK_CHAR where Volumes 3 and 4 say IA32_THREAD_FEEDBACK_CHAR, and Volume 4 lists only bit 0 of IA32_HW_FEEDBACK_CONFIG: inconsistencies to recheck when the driver is written.

**For the design:** the HFI performance column (class 0, or the only one) is the first source of a processor's capacity; a processor with every cell 0 is not a destination for movable threads; efficiency 255 is a consolidation request the placement's "pack" mode follows. Thread Director classes are deferred: their meaning is undocumented, and choosing a column per thread needs measurements on the hybrid machine (ADR-0009 H4's #2).

### 2.5 HWP's per-processor capabilities (Intel)

IA32_HWP_CAPABILITIES (771H) gives Highest (bits 7:0, the top level, not guaranteed), Guaranteed (15:8, can change), Most Efficient (23:16, can change) and Lowest (31:24) on an abstract scale mapped to frequency in a family-specific way (I3 §17.4, pp. 17-6 to 17-19). Volume 4's model tables give its scope as Thread, so the values can differ between logical processors (I4 Table 2-39, p. 2-378). A change of Highest is signalled through IA32_HWP_STATUS bit 3 and IA32_HWP_INTERRUPT bit 2, at most about once a second (pp. 17-13 and 17-16). CPUID.06H:EAX\[14\] names Turbo Boost Max 3.0 and EAX\[15\] the change notification. **The SDM does not say to rank cores by Highest**, and "favored core" appears nowhere in it.

**For the design:** Highest is the second Intel source of capacity, used where HFI is absent, as a ratio between processors; that use is Origin's inference, recorded as such.

### 2.6 CPPC, `_CPC` and `_OSC` (ACPI)

- **The scale** (ACPI66 §8.4.6, p. 639): abstract and unitless; all processors share one scale; on heterogeneous processors the platform builds it so the same work at the same level takes about the same time, and should give different classes of processor different capabilities.
- **The `_CPC` package** (Table 8.23, pp. 640 to 643): revision 4, 25 entries. Highest (the absolute maximum, perhaps not sustainable, perhaps reachable only while others idle, p. 644), Nominal (the maximum all processors can hold together, p. 645), Lowest Nonlinear (the most efficient, p. 645), Lowest, Guaranteed (the present sustained level, at most one change a second, p. 646), and the request and feedback registers; 6.6 adds OSPM Nominal Performance and Resource Priority Registers. If one processor has `_CPC`, all do (p. 643).
- **Different highest performance between processors.** `_OSC` bit 12 of the platform-wide capabilities, "Diverse CPPC Highest Optimization Support", is how the operating system says it handles a change of Highest and can place work by the processors' different Highest values (p. 475; checked). Processor Notify 0x85 says Highest changed, and the operating system re-reads the register (p. 644; checked). 0x83 says Guaranteed changed and 0x84 a minimum excursion (Table 5.236, p. 410). The words "preferred core" and "ranking" are not in 6.6.
- `_CPC` needs the AML interpreter (`origin-aml`, TASKS item 63, ADR-0019) to evaluate.

**For the design:** Highest from `_CPC` is a capacity source on any platform that publishes it, and bit 12 is set only once the kernel acts on Notify 0x85.

At each level, EAX\[31\] says components report different logical-processor counts, EAX\[30\] that they do not all have the same core type, EAX\[29\] (core level) that an efficiency ranking is present and varies; all three zero means the level is symmetric and alike. HighestPerf is what one processor can reach under ideal conditions, not guaranteed, perhaps only with others slower (p. 705); NominalPerf what all can sustain together. The PPRs mark the capability fields volatile. CPPC_ENABLE (C001_02B1h) is write-once and package-wide. **No AMD document defines a notification when HighestPerf changes**; the only feedback is CPPC_STATUS's sticky MinEx bit (C001_02B4h), with no interrupt named. "Preferred core" and "ranking" do not appear. Fn8000_0007_EDX\[15\] "FastCPPC" is named in the PPRs and not explained.
- **Hardware feedback like Intel's.** Fn8000_0021_EAX\[22\] `WL_CLASS_SUPPORT`, "workload based heuristic feedback", is named in PPR70, PPR00, PPR11 and PPRC0, **and reads 0 in every one**; APM Volume 3 marks the bit reserved (p. 677); no register, table or notification for it is documented. The older processor feedback interface (Fn8000_0007_EDX\[11\]) is deprecated (A2 §17.4, p. 701).
- **Zen 5 and Zen 5c.** AMD says Zen 5c is the same register-transfer logic as Zen 5, laid out more densely (WP1 pp. 5 and 9). The server PPRs report the same settable XCR0 mask (2E7h), the same largest XSAVE size (988h) and the same FP datapath report for Zen 5 and Zen 5c. No AMD document says outright that a thread's saved state moves between the two in one package. The APM does expect mixed FP datapath widths in one system: HWCR\[40\] ReportSameFpWidth makes Fn8000_001A report the narrowest width across cores (A2 §3.2.10, p. 72; A3 §E.4.12, p. 665); the width is microarchitectural, and the documents do not say the instruction set changes with it.
- **Per-core power and heat.** CPPC_CAPABILITY_2's present maximum, CPPC_STATUS.MinEx, the P-state current limit (C001_0061h), APERF and MPERF, and a per-core energy counter (C001_029Ah). The thermal LVT may not exist on every part (A2 §16.4.4, p. 671). **No per-core thermal-status register like Intel's was found.**
- **SMT** (A2 §3.2.9, pp. 69 to 72): STIBP stops one thread's indirect predictions steering its sibling's; return predictions are not shared between siblings; Fn8000_0008_EBX\[17\] recommends setting STIBP once at boot (ADR-0017 Z5 does). Automatic IBRS covers ring 0 only (p. 59).

**For the design:** on AMD, a processor's capacity comes from `_CPC`'s Highest where firmware publishes it, else from CPPC_CAPABILITY_1.HighestPerf read on each processor once CPPC is enabled; the static ranking orders processors of one type only. Because no change notification is documented, the kernel re-reads HighestPerf on a slow period (and on any ACPI Notify 0x85) rather than waiting for an interrupt. Gorgon Point's core types and rankings can only be confirmed on the machine (ADR-0009 H4's #5).

### 2.8 NUMA: SRAT, SLIT, HMAT

- **SRAT** (ACPI66 §5.2.16, pp. 236 to 244, revision 3). Processor (local APIC and x2APIC), memory, generic-initiator and generic-port affinity structures, each with a proximity domain and an Enabled flag (cleared entries are ignored, so firmware can list more than it enables). A proximity domain is what is presented as one tightly coupled unit, usually a NUMA node, possibly finer; its number is a label, not a distance (§17.2, p. 912; §6.2.15, p. 480). The table is read at initialisation; every processor started at boot is in it; a processor added later is placed by `_PXM`. Notify 0x0D asks for `_PXM` to be evaluated again (p. 407). A clock domain field says which processors share a clock; with none, one clock is assumed (§6.2.1, p. 447) — the counters of processors in different clock domains can drift apart.
- **SLIT** (§5.2.17, pp. 244 and 245). An N×N matrix of relative memory latency, 10 on the diagonal, 255 unreachable, possibly asymmetric. `_SLI` and Notify 0x0B update it at run time.
- **HMAT** (§5.2.29, pp. 323 to 331, revision 2). Latency and bandwidth between initiator and target domains, in picoseconds and MB/s, for memory and up to three levels of memory-side cache, rated by specification rather than measured; where both are present, HMAT's latency is preferred to SLIT's (p. 329). A hint for heterogeneous memory.
- Already built: `framekernel::numa` parses SRAT and SLIT and answers "which node", "nearest nodes"; the boot-matrix machines have two NUMA nodes, and the ACPI machine an HMAT and a generic initiator.

**For the design:** the node level of the scheduling domains is SRAT's proximity domain, ordered by SLIT's distance; HMAT is for memory placement (§28), not needed by M3's scheduler.

### 2.9 Heat, power and idling

- **Intel per-core thermal status** (I3 §17.8.5.2, pp. 17-42 and 17-43; I4 pp. 2-21 and 2-22): IA32_THERM_STATUS (19CH, core scope) says whether the core is throttling now (bit 0, with a sticky log in bit 1), whether it runs below the requested level (bits 10 and 11) and its distance below the throttling temperature (bits 22:16, valid with bit 31). IA32_THERM_INTERRUPT (19BH) can interrupt at two thresholds and on a power limit; the package registers (1B1H, 1B2H) add the HFI bits. Everything arrives through the thermal LVT. Where HFI exists it already folds heat into the capabilities.
- **ACPI passive cooling** (ACPI66 chapter 11, pp. 792 to 820): the operating system throttles the processors `_PSL` names when `_PSV` is passed, by a loop on `_TC1`, `_TC2` and `_TSP`; with CPPC it lowers Desired and sets Maximum to match (p. 656). **ACPI says nothing about what the scheduler should do with a throttled processor.** The signals it has are Guaranteed falling (0x83), Performance Limited for short events (p. 655) and 0x84.
- **Processor Aggregator Device** (ACPI000C, §8.5, pp. 659 to 661): the platform asks the operating system, through `_PUR`, to idle a number of logical processors, removing them from the set that runs work not tied to a processor, without ejecting them; the operating system should idle every SMT thread of one core before starting on another, and reports through `_OST` how many it idled. `_OSC` bit 0 says the operating system supports it.
- **`_VDM`** (new in 6.6, §6.2.10, p. 459): a voltage domain, an explicit placement hint: group work with similar frequency needs on one plane, or leave a plane idle so its voltage can drop.
- **`_PSD`, `_TSD`, `_CSD`** (§8.3, pp. 593 and 594; pp. 597 to 599, 628, 636 and 637): processors whose performance, throttling or idle states are coupled. ACPI never presents them as placement input; that mixing light and heavy work in one domain costs power is an inference.

**For the design:** M3 builds the mechanisms these signals feed (avoid, consolidate, de-prefer a throttled processor, idle a processor on request) with a fixed default; the policy belongs to power management (CLAUDE.md §67, M10).

### 2.10 Can a thread's saved FPU state move to another processor?

- The standard XSAVE format places each component at the offset CPUID.0DH gives (I1 §13.4.3, p. 13-9), and that offset is Platform domain (p. 21-44). XRSTOR of the standard form checks the image only against XCR0, XSTATE_BV and XCOMP_BV (I1 §13.8.1, p. 13-20): nothing in it depends on which logical processor saved it.
- The "modified" save optimizations (XSAVEOPT, XSAVEC, XSAVES) track the last restore per logical processor (I1 §13.6, p. 13-18; §13.8.3, p. 13-21). The kernel uses plain XSAVE and XRSTOR (`origin_frame::cpu`), which have no such tracking.
- **The SDM never says outright that an image is portable between logical processors.** That it is, given the same XCR0, is an inference from the two points above. ADR-0020 therefore checks it at boot instead of assuming it: each processor's XCR0 and enabled-state size must equal the boot processor's before it may take part in a move.

### 2.11 The time-stamp counter across processors

Recorded in `docs/research/2026-11-09-tsc-consistency.md` §3: an invariant TSC promises a rate on one processor, not agreement between two. ACPI's clock domains (§2.8) say the same from the platform's side. **For the design:** CPU accounting measures time between two readings on one processor only, and a move never compares readings taken on two.

## 3. What the papers establish

### 3.1 EEVDF (P1, P1b)

- **Model** (P1 §2 and §3, pp. 3 to 6). A resource handed out in quanta of at most q; a client's share is its weight over the active weights; its lag is the service it should have had minus what it had. Virtual time V advances at the rate of one over the sum of active weights, so ideal service between two instants is the weight times the change of V.
- **Requests** (pp. 5 to 8). A client asks for service of length r. Its request becomes eligible at the virtual time its ideal service catches up with what it has had, and its virtual deadline is the eligible time plus r over its weight. A request cut short moves the next eligible time by what was used.
- **Selection** (p. 7). The next quantum goes to the eligible request with the earliest virtual deadline.
- **Joining, leaving, changing weight** (§4, pp. 9 to 11). A leave moves V by the leaver's lag over the remaining weight, a join the other way, a weight change is a leave and a join at once; this keeps the sum of lags zero (Lemma 2). The authors note that stride scheduling changes only V's slope. Whether a client keeps its lag across a sleep has "no simple answer" (p. 11): §5 gives three strategies (keep it, drop it, or only let clients join and leave at zero lag).
- **Bounds** (§6). In a steady system (every event involves only zero-lag clients), any active client's lag stays strictly between minus its largest request and the larger of its largest request and q (Theorem 1, p. 18; checked); with requests no longer than a quantum, strictly within ±q (Corollary 2, p. 20; checked); and no proportional-share algorithm can do better than ±q (Lemma 5, pp. 20 and 21). Requests are fulfilled by their deadline plus q (Lemma 3).
- **Latency against overhead** (pp. 5 and 20). Short requests give better accuracy; long ones fewer scheduling events. A latency-sensitive client asks for short requests without asking for more share: this is what decouples latency from weight.
- **Cost** (Appendix B, pp. 30 to 35; Table 1, p. 25). An augmented balanced tree keyed by eligible time, each node holding the least deadline beneath it: selection, join, leave and weight change in O(log n).
- **What it does not cover.** One resource only: no per-processor queues, no migration, no shared V across processors (the multiprocessor case is related work, p. 26). The bounds hold only in steady conditions; the lag kept across a sleep is a policy choice; fixed-point precision and V's overflow are not analysed; no classes, no inheritance (priority inversion is left to higher layers, p. 3).

### 3.2 Stride scheduling (P4), today's run queue

- The relative error between any two clients is never more than one quantum; the absolute error of one client can still grow with the number of clients, O(n_c), with skewed weights (101 clients at 100:1:…:1 give an absolute error of 50, p. 8). A hierarchical version bounds it by the tree's height, O(log n_c) (§4, pp. 8 and 9).
- On leaving, a client keeps its remaining pass relative to the global pass, and rejoins at the global pass plus that remainder (§2.2 to §2.4, pp. 4 to 6). Origin's run queue does something stricter: a context that becomes ready starts at no less than the lowest pass among the ready ones, so sleeping earns no credit (`framekernel/src/runqueue.rs`).

**For the design:** stride stays the baseline (S26-14 asks that simpler policies pass their baselines first). Its weakness, error that grows with the number of contexts and no per-request latency, is what EEVDF would fix; with at most 16 contexts on a processor (`runqueue::CAPACITY`) the weakness is bounded.

### 3.3 Priority inheritance and the priority ceiling (P2)

- **Assumptions** (§I and §II, pp. 1175 and 1176): one processor; fixed priorities; binary semaphores; properly nested critical sections; jobs that do not suspend themselves. **Every result in the paper rests on one processor** (p. 1175, restated p. 1184).
- **Basic inheritance** (§III, p. 1177): a job that blocks higher-priority jobs runs at the highest of their priorities until it leaves the critical section; inheritance is transitive, and inheriting and restoring must be indivisible. A job is blocked at most for min(n, m) critical sections, n lower-priority jobs and m semaphores (Theorems 3 and 6, p. 1181). It neither prevents deadlock nor chained blocking (p. 1178).
- **The ceiling protocol** (§IV, pp. 1178 to 1181): each semaphore's ceiling is the highest priority of any job that may lock it; a job locks only above every ceiling held by others. No deadlock (Theorem 10), at most one critical section of blocking (Theorem 12). It needs every lock's users known in advance.
- **What it does not cover:** holders and waiters on different processors; inheritance under a proportional-share scheduler, where there is no fixed priority to inherit and a weight or a deadline would have to be passed instead; locks whose users are unknown.

**For the design:** Origin inherits *weight and class*, not priority (ADR-0020 S16), transitively with a bounded depth, which is the basic protocol's idea carried to a fair-share scheduler. No ceilings: user locks have no known users. The kernel's spin locks are held with interrupts off on one processor, which is the extreme form of a ceiling: no thread can preempt their holder.

### 3.4 Work stealing (P3)

- **Model** (§2, pp. 722 to 726): fully strict multithreaded computations, work T1, critical path T∞; any schedule on P processors takes at least T1/P and at least T∞.
- **Algorithm** (§4, pp. 729 and 730): each processor keeps a deque; its owner works at the bottom; an idle processor picks a victim uniformly at random and takes the top.
- **Bounds** (§6): expected time T1/P + O(T∞) (Theorem 13, pp. 743 and 744), space at most S1·P (Theorem 5), expected communication O(P·T∞·(1 + n_d)·S_max) (Theorem 14), each optimal within a constant factor. The analysis assumes all P processors work on the one computation, and a contention model in which simultaneous requests to one deque are served one at a time (§5).
- **What it does not cover:** processors shared with other programs; fairness between processes; threads that block on I/O or locks; cache, NUMA and SMT locality (victims are chosen at random); the power cost of idle processors that keep stealing.

**For the design:** the part Origin takes is the *thief-initiated* principle: balancing work falls on processors that have nothing better to do, so a busy processor pays nothing to balance. Random victims, the deque discipline and the bounds do not carry over to an operating system's mix of blocking, fair-share threads; ADR-0020 S7 chooses victims by topology and load instead.

## 5. What QEMU and CI can show, and what they cannot

- **Can:** every move's correctness under QEMU's software processor and as KVM guests in CI: threads moved among 2 to 288 processors, wake-ups carried, stacks covered, FPU state kept, settles compared. Topology domains on QEMU's layouts (packages, dies, modules, cores; two NUMA nodes on every boot-matrix machine; HMAT and a generic initiator on the ACPI machine).
- **Cannot, today:** **SMT.** No boot-matrix machine has more than one thread per core: every `-smp` the boot uses has `threads=1` (`developer-tools/xtask/src/main.rs`, `machine`). The build plan adds one. **Hybrid parts, HFI, Thread Director, CPPC's different Highest values and thermal signals:** QEMU 11.1 models no hybrid processor (`2026-11-08-cpu-topology-leaf-1fh.md` §3), and whether its processors offer HFI, HWP or a thermal LVT was not checked (reading QEMU's processor models is reading another project's source, which needs a named reason under §3; the topology task prints CPUID.06H instead). These are host-tested against table images and qualified only on ADR-0009 H4's hybrid machine.
- **Timing:** the large software-processor machines (65, 67, 288) disturb timing (ADR-0013 Amendment 2), so every balancing-quality proof is Report-class there, as the fair share already is.

## 7. Open questions

1. **AMD's hardware feedback and Gorgon Point** (§2.7): `WL_CLASS_SUPPORT` is named and reads 0 on every public PPR, no HighestPerf change notification is documented, and no PPR exists for a client part mixing Zen 5 and Zen 5c. Which core type and ranking Gorgon Point's cores report, and whether firmware publishes `_CPC` with different Highest values, only the machine shows.
2. **Which processor takes a package's HFI interrupt** (§2.4): not stated by Intel. The driver must find out on the hybrid machine, or route the thermal LVT of one processor per package and read the status from it.
3. **Thread Director classes** (§2.4): no documented meaning. A later amendment, with measurements on hardware, decides whether the scheduler reads a thread's class at switch-out and which column it then uses.
4. **PPTT on 2026 x86 platforms** (§2.2): whether firmware ships it, only real hardware shows.
5. **Cache-hot window and balancing periods:** the figures in ADR-0020 S10 and S7 are hypotheses for hardware to settle.
6. **SMT capacity:** how much one sibling's work slows the other on the declared machines; M3 places on idle cores first and does not model it further.
7. **Wake-time placement: later, by amendment.** ADR-0020 S7 decides version 1: a woken thread is queued on the processor it is on, and only the idle pull, the kick and the periodic pull balance. Placing it elsewhere at its wake-up needs its deadline in monotonic time instead of its processor's ticks (§6, N10), and S10's figures on cache-hot threads to say whether it pays.

## 8. Tests defined before completion (CLAUDE.md §16.12)

The build plan lists, for each task, its host tests, Loom models with their negative controls, boot proofs with their ADR-0013 class and their controls, and acceptance criteria. In short: Loom models for the moves between tables (a scanner that reads the destination first, a move racing the source's own switch, a move racing a retirement, a destination full, the deferred publication), for the wake-up that follows a moving thread, and for the weight lent to an owner; a Refuse-class boot proof that moves threads at random among processors while they block, wake and check their own registers, stack and SIMD state; Report-class proofs of balancing, affinity, classes, accounting, quotas and inheritance; and host tests of every capacity source against table images.
