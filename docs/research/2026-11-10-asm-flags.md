## 1. Why this was needed

The design review found twelve `asm!` blocks that declare `options(…, preserves_flags)` and should not. Five execute `or` or `and`. Seven only move to or from a control register, and the reviewer recalled, without checking, that Intel leaves the status flags undefined after that move. The owner accepted: remove the option from the five, and from the seven unless both vendors say the flags are unchanged (decision item 110). The gate that follows needs a list of instructions known to leave the flags alone, so every instruction a block uses under the option was looked up, not only those seven.

## 3. What the option promises

R1's rule `asm.options.supported-options.preserves_flags` says the assembly code does not modify the flags register, so that the compiler need not recompute the condition flags after it. Rule `asm.rules.preserved-registers` says what "the flags register" means on x86. With the option set, the block must restore, by the time it ends:

- the status flags in EFLAGS: CF, PF, AF, ZF, SF and OF;
- the x87 floating-point status word, all of it;
- the floating-point exception flags in MXCSR: PE, UE, OE, ZE, DE and IE.

`asm.rules.intro` puts this among the rules that "must be followed" to avoid undefined behaviour. The interrupt flag is not on the list, so an instruction that changes only IF keeps the promise. The direction flag has a rule of its own, with or without the option (`asm.rules.x86-df`).

## 4. Moves to and from control and debug registers

| Instruction | Intel (I1) | AMD (A1) |
|---|---|---|
| `MOV` to or from CR0, CR2, CR3, CR4, CR8 | Vol. 2B p. 4-33, Flags Affected: "The OF, SF, ZF, AF, PF, and CF flags are undefined." | p. 427, rFLAGS Affected: None |
| `MOV` to or from DR0 to DR7 | Vol. 2B p. 4-35: the same sentence | p. 428, rFLAGS Affected: None |

I1 defines its own word. §3.1.1.11 (Vol. 2A p. 3-14) says a flag listed as undefined may be changed by the instruction in an indeterminate manner, and a flag not listed is unchanged.

**The vendors differ.** AMD says these moves change no flag. Intel says they may change all six status flags. Origin runs on both, so a block that makes one of these moves does not keep the option's promise on an Intel processor.

**Decision, by the owner's rule:** the option goes from every block that moves to or from a control register. That is the seven the review named.

**Two more the review did not name:** `cpu.rs` also declared the option on `mov dr7, {}` and `mov {}, dr7`. Intel's entry for the debug registers has the same sentence, so the option goes from those two as well.

## 5. `or` and `and`

| Instruction | Intel (I1) | AMD (A1) |
|---|---|---|
| `OR` | Vol. 2B p. 4-164: OF and CF cleared; SF, ZF and PF set from the result; AF undefined | p. 275: OF and CF are 0; SF, ZF and PF modified; AF undefined |
| `AND` | Vol. 2A p. 3-61: the same | p. 94: the same |

Both vendors agree, as the review said. The option goes from the five blocks.

## 6. The gate's list

An instruction is on the list only if **both** vendors' entries say in words that it changes no status flag, and it is not an x87, MMX or SSE instruction. With no such instruction on the list, the x87 status word and MXCSR cannot be written by a listed instruction, so §3's second and third clauses hold without a further argument.

|---|---|---|

| `pushfq` | Vol. 2B p. 4-529: None | A1 p. 301: None |
| `pop` | Vol. 2B p. 4-401: None | A1 p. 286: None |
| `xchg` | Vol. 2D p. 6-33: None | A1 p. 371: None |
| `cpuid` | Vol. 2A p. 3-203: None | A1 p. 172: None |
| `rdmsr` | Vol. 2B p. 4-545: None | A1 p. 438: None |
| `wrmsr` | Vol. 2D p. 6-8: None | A1 p. 515: None |
| `rdtsc` | Vol. 2B p. 4-559: None | A1 p. 443: None |
| `rdtscp` | Vol. 2B p. 4-561: None | A1 p. 445: None |
| `invlpg` | Vol. 2A p. 3-485: None | A1 p. 395: None |

`cli` writes a flag, but not one the option covers (§3).

The list is by mnemonic, so each entry has to hold for every form the mnemonic can assemble to. `mov` is the one with a form that fails, and the gate reads its operands for that. `popfq` is a different mnemonic from `pop` and is not listed.

## 7. Used under the option before this task, and left off the list

| Instruction | Why it is off the list | Blocks that lose the option |
|---|---|---|
| `lfence` | Intel's entry (Vol. 2A p. 3-552) has no Flags Affected section. AMD says None (A1 p. 221) | `cpu.rs`, `ordered_tsc`'s `lfence; rdtsc` |
| `clflush` | Intel's entry (Vol. 2A p. 3-144) has no Flags Affected section. AMD says None (A1 p. 151) | `iommu.rs`, the cache-line flush |
| `xrstor`, `fxrstor` | They load the x87 state and MXCSR from memory (I1 Vol. 2D p. 6-49, Vol. 2A p. 3-409), which is what §3's second and third clauses forbid. Both vendors still print None under flags for `xrstor` (I1 Vol. 2D p. 6-52; A2 p. 1771), so for this family that word says nothing about the state the option also covers | `cpu.rs`, `fpu_restore`, both branches |
| `xsave`, `fxsave` | The same family, kept off as a class. Intel's `fxsave` entry (Vol. 2A p. 3-412) has no Flags Affected section. AMD documents `fxsave` in Volume 5, which was not used | `cpu.rs`, `fpu_save`, both branches |
| `movq` | The forms the kernel uses are documented as flag-free by both (I1 Vol. 2B p. 4-56; A1 p. 247, as `MOVD`). The mnemonic's MMX forms are in AMD's Volume 5, which was not used, and it is an SSE instruction | `cpu.rs`, the two helpers of the FPU proof |

For `lfence` and `clflush`, I1's §3.1.1.11 could be read as covering an entry with no section at all: no flag is listed, so none is changed. That is an inference from a general sentence, and the option is only a hint to the compiler, so the inference was not relied on. A later session with better evidence can put them back.

## 8. Result

Of the 40 blocks that declared the option, 22 lose it and 18 keep it.

| Group | Blocks | Reason |
|---|---|---|
| The review's five | 5 | `or`, `and` (§5) |
| The review's seven | 7 | control-register moves (§4) |
| Debug-register moves | 2 | §4 |
| State restore and save | 4 | §7 |
| `lfence`, `clflush` | 2 | §7 |
| `movq` | 2 | §7 |

## 9. Gaps

- **Nothing was measured on a processor.** What an Intel processor of a given model really does to the flags on a control-register move is not known here and is not relied on. The manual's word decides.
- **Intel's "Documentation Changes" document** (the corrections between SDM versions) was not read. The SDM read is the current version.
- **AMD's Volume 5 is unusable** as AMD serves it today (§2). The combined manual, publication 40332 Rev 4.11 of 2026-10-29, was not fetched, so whether its Volume 5 part carries the same marking is not known. Work on x87 or MMX state will need that settled first.
- **The list is by mnemonic.** It was checked against the forms this tree uses and the forms each entry documents. An assembler alias that maps a listed mnemonic to another instruction was not looked for.
