## The similarity check (§3, §6)

**Verdict: no copied code, identifiers, structure or arrangement found. Only plain facts carry over.**

Compared: the fixture's `lib.rs` and `main.rs`, and the range's other code that builds or parses ACPI structures (`reserved.rs`, the `ivrs.rs` additions and tests, the fixture's tests, xtask's markers), with QEMU `hw/i386/acpi-build.c` at `v11.1.3` (read as in the header).

- **What QEMU's file does.** It builds every table from nothing, field by field, with append helpers and one comment per field. Its DMAR builder writes one DRHD, the I/O APIC's scope and a scope per PCI device, and an ATSR when device-TLBs are on. Its IVRS builder writes IVinfo, then the same device entries under a type-10h and a type-11h IVHD. Its main builder appends user tables after its own and ends with an RSDT. It builds no RMRR and no IVMD **[code, QEMU]**.
- **What the fixture does.** It builds no table. It copies the firmware's table, appends 32-byte structures written by byte index into fixed arrays, fixes the length and checksum, and points an XSDT entry at the copy. Its RMRR and IVMD writers have no counterpart in QEMU's file. Its checksum, growth and XSDT functions have none there either (QEMU leaves checksums to its linker, elsewhere) **[code]**.
- **Names.** The fixture's names (`rmrr`, `ivmd`, `structure`, `grow`, `fix_checksum`, `xsdt_entries`, `xsdt_set`, `plant`, `allocate`, `Placement`, `Region`) share nothing with QEMU's (`build_dmar_q35`, `insert_scope`, `dmar_host_bridges`, `build_amd_iommu`, `insert_ivhd`, `ivrs_host_bridges`, `acpi_add_table`) beyond the table names themselves **[code]**.
- **What matches, as fact.** A device scope's byte order (type, length, reserved, enumeration ID, bus, device, function) is VT-d §8.3.1's layout, and both follow it. The test DMAR in `lib.rs` (one DRHD, endpoints 00:02.0 and 00:03.0, width 48) and the test IVRS (one type-10h IVHD with select entries) describe what QEMU gives; they leave out QEMU's I/O APIC scope and type-11h block, so they are not transcriptions. xtask's `IVinfo 0x2801` marker is QEMU's output (EFRSup and a 40-bit PASize), observed. The ledger's §4 statements (no RMRR or IVMD; user tables after QEMU's own) agree with the file **[code, QEMU]**.
- **The process.** The session that read QEMU's file wrote the fixture, so §3's split was not kept. The fixture is test-only, GPL-free by inspection, and recorded in the provenance entry (per the hand-over; the entry itself was not read). §3's person sign-off is written for drivers; whether it applies here is for the owner.

## Checked and found sound

- **R1, order.** VT-d: identity leaves go into a fresh top table before the context entry is written; the entry's high half is written first and the present bit last; with caching mode a context and domain invalidation follow, else a write-buffer flush **[code]**. AMD: identity leaves before `set_dte`, which writes word 0 (V, TV, root) last, then InvalidateDevice and InvalidatePages for the whole domain **[code]**. No maps at bring-up; a device no driver attaches gets none **[code]**.
- **Only named devices.** VT-d gathers an RMRR only when its segment and `covers(r)` match; a bridge scope covers the bridge and the buses under it **[code]**. AMD gathers by `memory_for` with the translating IOMMU's base, the device's own DeviceID and its alias **[code]**. The alias case asks that the shared domain already hold the new device's identity spans with enough access, and the same never-map spans **[code]**.
- **R4's decoding** matches Table 113: exclusion gives read and write whatever IR, IW and Unity say; IR = IW = 0 gives never-map; otherwise exactly IR and IW, with or without Unity **[code; doc]**. The start is a system physical address, the length may be rounded up **[doc]**; the code rounds the start down and the end up and refuses a wrap **[code]**. `map` refuses a never-map frame before allocating an IOVA **[code]**.
- **Exclusion registers.** Bring-up writes 0 to 0020h and 0028h, so ExEn and Allow are clear **[code]**; nothing else writes them **[code]**. `Dte::encode`'s word 1 is the domain and SysMgt only, so EX (bit 103) is never set **[code]**. Clear ExEn and Allow are also what the specification asks around SEV-SNP **[doc]**.
- **R2.** Every `map` in both drivers allocates through `alloc_skipping` with the domain's identity spans as holes **[code]**. `alloc_skipping` moves strictly forward, refuses `pages == 0`, and checks every addition **[code]**; its host tests include a randomized one **[code]**. Identity maps are made on a fresh domain before any IOVA, and `vtd::map` and `amdvi::map` refuse an already present leaf, so an identity page cannot be mapped over **[code]**. Both `unmap`s refuse an identity page (untested: L7) **[code]**.
- **R3's checks** are each present and ordered: length, width, interrupt range, AMD's special range (`FD_0000_0000h`–`FF_FFFF_FFFFh`, Table 3 **[doc]**), register ranges, then the memory map page by page **[code]**. `first_unreserved` always moves forward and saturates **[code]**. No register list means every identity range is refused (`NoRegisterList`), and a never-map range is accepted without checks **[code]**. VT-d's width is the smallest of every unit's table reach and the DMAR's host address width (stored as the field plus one) **[code]**. AMD's is PASize, at most 48 **[code]**. Each range is reported by name with its verdict, and the boot goes on **[code]**. VT-d §8.4's rule (RMRRs reported as reserved or EFI runtime memory) is what the memory-map check asks **[doc]**.
- **What the kernel allocates.** The frame allocator starts from `Usable` regions and `reclaim` is called only for `LoaderReclaimable` **[code]**, so no frame in an accepted identity span is ever handed to a driver or the heap.
- **A refused device stays stopped.** `attach` refuses it before any side effect (before `next_domain`, before the interrupt table on AMD) **[code]**; `enable_bus_master` refuses a device with no domain of its own when the IOMMU translates (I12) **[code]**.
- **Parsing.** RMRR base, limit and alignment are checked by `dmar::parse`; IVMD length 32, start plus length below 2^64, range order, and the placement after an IVHD are checked by `ivrs::parse` **[code]**. Offsets match Tables 111 and 112, the segment at 8 **[doc]**.
- **Test-only isolation** (I5) and **`vm::read_firmware`**: a volatile copy, refused unless the memory map calls the whole range the firmware's **[code]**.
- **The hand-over's claims on merges.** `git diff --stat 9a9c62f f8bc72e` over `iommu.rs`, `iommu/amd.rs`, `reserved.rs`, `storage.rs` and the fixture is empty, and `c0cd136..f8bc72e` changes nothing outside `docs/` **[code, git]**.

- **M1, `fc5a2ae` and `970bb94`, with its boot test in `741b442`.** `reserved::Lending` holds the ranges `vm::firmware_bytes` has lent as references and the ranges devices may write, under one lock in `vm`, in fixed arrays of 128 each that fail closed when full. The kernel lends tables before its heap exists, and the first boot of `fc5a2ae` panicked in the allocator for that reason; `970bb94` removed the allocation. a lend over device-writable memory is refused, and so is a grant of writes over lent memory, whichever comes first. `reserved::check` refuses a writable identity range over a lent table (`Refusal::Lent`, reported with the table's address), and `note_writable` refuses one over a table lent after it was judged. Read-only and never-map ranges over a table are accepted: no device can change it. Host tests: the refusal at both edges, read-only and never-map accepted, both orders of lending and granting. At boot the fixture now keeps its table copy in `EfiReservedMemoryType` pages, so a range over it passes the memory-map rule, and plants a writable range over that copy for a device no driver attaches. The kernel refuses it by name, with the copy's own address, under both IOMMUs; xtask holds the address to the one the fixture put in the XSDT. Control RM-7: `firmware_bytes` recording nothing it lends.
- **M2, `741b442`, as ruled: the proof changed, nothing restored.** The write leg runs only on a page that holds the TEST ONLY step's fill (`framekernel::testfill`: 16 bytes of magic, the page's own physical address, then 4,072 bytes derived from it, so another page's fill does not match). Any page without the fill is reported "was not run" and must be unchanged when the proof ends, a clause of the proof itself. The read leg, a DMA read of the page to the test disk, still runs everywhere. The fixture plants a writable reserved page for the NVMe controller that holds another page's fill, under both IOMMUs. Control RM-6: the write leg forced onto every page. The proof's own clause "the page is unchanged: false" fails the boot, as does xtask's line count. The two copies of the fill are held equal by an xtask test.
- **L1, `fc5a2ae`.** `reserved::rmrr_range` refuses an RMRR `from_rmrr` cannot use as beyond 64-bit addresses (`Refusal::Width(64)`), so its devices stay refused. Host test with base `0xFFFF_FFFF_FFFF_F000` and limit `u64::MAX`.
- **L2, `fb0c0fd`, decision item 293 (boot info 0.7).** The loader gives `Reserved` to UEFI type 0 alone, `Unaccepted` to type 15 and `FirmwareOther` to type 13, the OEM and OS types and every unknown type; `reserved_kind` accepts neither new kind. Host tests: the loader's kind for every type UEFI 2.11 defines and for OEM, OS and unknown types; an RMRR over each new kind refused; `overlaps_ram` for each.
- **L3, `fc5a2ae`.** `kernel.rs` adds every accepted identity range (`reserved::identity_ranges`) to the ranges `pcie::init` holds BARs against, so a BAR inside one is refused as reserved and reported. Host test in `pci`: a BAR inside such a range refused, one beside it and one under a never-map range kept.
- **L4, `fc5a2ae`.** A device's identity spans together are bounded at `reserved::MAX_DEVICE_PAGES` (4 GiB, as one range is), and a device past it is refused by name. An attach that fails before its context entry or device table entry is written gives back every table page it made and its top page (`Page::give_back`), and uses up no domain ID. The ID is now consumed just before the entry names it. Host test of the bound; the give-back is not exercised, since no attach fails part-way at boot.
- **L5, `fc5a2ae` and `741b442`.** `vtd::find_physical` and `amdvi::find_physical` walk every present entry for a leaf that names a physical page (host-tested at both depths, after unmaps, and past an entry `map` does not make). The proof asks `iommu::maps_physical`: an unnamed domain must reach the page at no address at all; a named one must map it to itself.
- **L6, `c634f40`, decision item 291 (ADR-0007 Amendment 2, R6).** `Ivrs::memory_for` gives a never-map type-20h IVMD to every device of every IOMMU in every segment; an identity type-20h keeps R5. Host test over two IOMMUs and a third segment; the AMD-Vi machine plants one, and its boot line names "every device in the system, on every IOMMU".
- **L7, `fc5a2ae`.** Both drivers' refusals are `reserved::may_unmap` and `reserved::may_map`, host-tested at each edge.
