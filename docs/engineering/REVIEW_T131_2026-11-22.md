## Findings

### R131-1 (Medium): `bench_reset` never produces `Tried::NotCalledSwitch`, so the "stale key twice" bisect scenario fails

- **Where:** `boot/uefi/src/main.rs:1877-1881`, the `tried` match in `bench_reset`. The variant is
  defined at `boot/uefi/src/bench.rs:975` and only ever built by the test at `bench.rs:1720`.
- **What is wrong:** the match has arms for `After::Fadt` (giving `NotCalled`) and
  `After::StandInNoReset` (giving `NotCalledStandIn`), but none for `After::SwitchNoReset`. A
  bisect run with `BENCH-FCH … noreset` therefore falls to `None => Tried::Unavailable`, and its
  Fallback line reads "there was no ResetSystem to call, …". That is false: `ResetSystem` was
  there, and it was skipped on purpose.
- **Failure scenario:** the scenario "bench: bisect, a stale key twice …"
  (`developer-tools/xtask/src/bench.rs:1215` and `:2261`) expects `BIS_CF9_SKIPPED`, which is
  "ResetSystem was not called (BENCH-FCH's noreset), …". The UART carries the `Unavailable` text,
  so `check_bisect_both_failed` fails. `boot-bench` is part of `boot-matrix`, so that run fails.
  A rented board is not affected, because the rental tool refuses `BENCH-FCH`.
  The host test builds `Fallback { tried: NotCalledSwitch }` by hand, so it misses the gap.
  Related: `After::said(Some(Some(SwitchNoReset)))` (`bench.rs:262`) is never printed, so the
  bisect console never says that `noreset` was taken.
- **Fix:**
  - Add `None if plan.after == bench::After::SwitchNoReset => bench::Tried::NotCalledSwitch,`.
  - Better, move the choice from `After` to `Tried` into a host-tested `const fn` in `bench.rs`, so
    a missing arm shows up in a test.
  - Print the `noreset` choice in the bisect `BENCH-FCH` block.

### R131-2 (Medium): `through_live_table` checks only a local pattern, so a live-table read hoisted or spilled before the call passes

- **Where:** `developer-tools/xtask/src/bench.rs:460-520` (`LOAD_WINDOW`, `last_load`,
  `through_live_table`), as used in `check_bisect_code` (`:410`).
- **What is wrong:** the check flags a call only in two cases:
  - its target register was loaded, within 64 instructions, from `[b + 0xe8]`, with `b` itself
    loaded from `[s + 0x60]`;
  - its memory operand is `[b + 0xe8]` directly.

  It does not check that the target comes from the copy. A target read from the live table
  earlier and kept in a stack slot gives `call qword ptr [rsp + N]` or `call qword ptr [rax]`,
  and the check reads that as not live. This happens in two cases:
  - the read is outside the window, for example `let exit = …live…` where `exit` is defined
    (`main.rs:463`, captured by the closure);
  - the compiler spills the pointer.
- **Failure scenario:** a regression makes `exit` come from the live table (say, a reuse of
  `minimal::live_exit`) at its definition. The closure's call stays `call qword ptr [rax]`, so
  `check_bisect_code` passes and a rented run calls through the live table. That is the one
  question this mode keeps fixed (Amendment 6, step 4). The planted test in the scratch copy shows
  the real function returning `false` for exactly this shape: a load from `0x60`, then from
  `0xe8`, a spill, 70 instructions, and `call [rsp + 0x50]`.
- **Fix:** run the same two-load test over every instruction, not only the call's operand: fail
  if any `mov <r>, qword ptr [<b> + 0xe8]` in the bisection image has `<b>` last loaded from
  `[… + 0x60]`.
  - On the existing images, a port of the matcher finds zero such loads in the full bench loader
    and exactly one (the call's) in the minimal loader. The same controls therefore still hold.
  - `bench_table_line` reads the live `ExitBootServices` pointer byte by byte (`movzx`), so it
    raises no false alarm.
  - Say in the doc comment and the error text what the check still misses: a spill between the
    two loads.

### R131-3 (Medium): neither the static check nor the scenarios identify the `ExitBootServices` call, so a firmware call inserted before the triple fault passes both

- **Where:** `developer-tools/xtask/src/bench.rs:592` (`triple_fault_calls`), as used in
  `check_bisect_code` (`:440-452`). The same gap is in `check_minimal_code` from TASKS item 128.
  The scenarios affected are `check_bisect_call` and its callers.
- **What is wrong:** the check needs only that some indirect call reaches the triple fault through
  `mov`, `cmp`, `test` and branches. Suppose another indirect call is placed between the status
  compare and the triple fault. The `ExitBootServices` call then no longer reaches it, the
  inserted call does, and the check passes; `through_live_table(inserted)` is false. Under QEMU, a
  firmware reset such as `ResetSystem` ends QEMU at once with nothing more on the UART (Amendment
  3's scenarios rely on this). So `after_bisect_last == [X]`, and `quiet_before_exit < 2.5 s` also
  holds.
- **Failure scenario:** the change `if status == SUCCESS { if let Some(r) = plan.reset_system { r(…) } triple_fault() }`
  (or any helper call there) breaks Amendment 6 step 5 and B5 ("after a successful call, the
  mode calls nothing in the firmware"). It passes `bench-build --bisect` and every boot-bench
  bisect scenario. The planted test confirms the static half: for "call [rax]; test; jne; mov;
  mov ecx, 0; call [rax]; push 0; push 0; lidt", `triple_fault_calls` returns only the second call.
- **Fix:** identify the `ExitBootServices` call positively. One way: require that the found call
  loads its target the way the full image's call does. `reset_calls(&full)` already locates that
  call; compare its target load sequence (for example `mov rax, qword ptr [rsi + 0x28]` …
  `call qword ptr [rax]`) with the bisection image's, and fail if they differ. Two smaller
  additions:
  - require exactly one such call;
  - add a synthetic negative-control listing (an extra indirect call before the triple fault) to
    the unit tests.

  In the scenarios, it would help to tell a triple fault from other resets. QEMU's logging may be
  able to name it; check this in QEMU's documentation before relying on it.

### R131-4 (Low): the OS-types needle accepts "in 0 descriptors"

- **Where:** `developer-tools/xtask/src/bench.rs:1015` (`BIS_NO_OS_TYPE` ends at "in "), and
  `boot/uefi/src/bench.rs:558-576` (`OsTypesLine`).
- **What is wrong:** a count over an empty or truncated buffer prints "holds no region of an
  OS-defined type … in 0 descriptors". The line claims what step 2 asks, and the scenario accepts
  it.
- **Failure scenario:** a wiring slip, such as counting `map.get(..0)` or the wrong stride, prints
  a vacuous "no OS-defined type" line on a rental. The record then reads it as the second
  question's precondition.
- **Fix:**
  - In `OsTypesLine`, treat `descriptors == 0` as "not counted, so this run does not show …".
  - In the scenario, parse the count and require at least one descriptor.

### R131-5 (Low): two branches of the bisection mode are pinned by no scenario

- **Where:** `developer-tools/xtask/src/bench.rs:1471-1541`, the seven bisect scenarios.
- **What is wrong:** every bisect scenario plants `BENCH-FCH`. Two cases are never booted:
  - the rental's own path: no switch, so the registers are read (under QEMU, not read), the
    decision is `NotRead`, and the call is made with no control;
  - `first noshutdown`: a non-shutdown record with a shutdown bit clear, where the control must
    be withheld (refinement 3, step 3).

  `MinimalDecision::of` is host-tested, but the bisect wiring (`bisect::decide`, the
  `values_minimal` override at `main.rs:521-525`) is checked by reading only.
- **Fix:** add two scenarios:
  - "bisect, no BENCH-FCH": expect the not-read decision line, then `X`, then the triple fault;
  - "bisect, first noshutdown": expect the bits-clear line, no control, then the call.

### R131-6 (Low): step 1's UART register reads come after step 3's branch

- **Where:** `boot/uefi/src/main.rs:1640-1665` (`bench_before_call`).
- **What is wrong:** Amendment 6 lists "the entry state's reads, the `Stall` and the UART register
  reads" in step 1, before step 2's line and step 3's branch. The code keeps the full loader's
  order, which reads the UART registers and writes `BEFORE_CALL` after the FCH decision. A
  control run therefore never reads them.
- **Failure scenario:** none for the answer. The record of a control run lacks the UART-under-the-
  firmware line, which a reader of "in order" would expect.
- **Fix:** keep the order, since it is the full loader's, and record that step 1 is the full
  loader's work in its own order. Alternatively, ask the coordinator.

### R131-7 (Low): Amendment 6's threat-model list of writes is narrower than the work it keeps

- **Where:** ADR-0002 Amendment 6, "Threat model", against `boot/uefi/src/bench.rs:313-325`
  (`UartState::read` writes LCR twice) and `main.rs:1660-1665` (`BEFORE_CALL` written straight to
  the UART).
- **What is wrong:** the ADR says the writes are "the full bench mode's own pages, the loader's own
  IDT …, and the `X` and `Y` bytes". The mode also writes:
  - before the call, the UART's LCR and the `BEFORE_CALL` line, as step 1 requires;
  - after an error, Amendment 2's and 3's lines, the `ResetSystem` call and the FADT register
    write, as step 5 requires.

  The code follows the steps; the threat-model text is the inconsistent part (Amendment 5's has
  the same looseness).
- **Fix:** none in code. Flag it to the coordinator so the owner's text can be reconciled, or so
  the records say the steps govern.

### R131-8 (Low): `BisectSwitch::from_contents` refuses a valid 32-byte switch

- **Where:** `boot/uefi/src/fch.rs:1447-1463`.
- **What is wrong:** each kept word is copied with a separator after it, so `rest` needs up to 33
  bytes. A 32-byte file that ends without whitespace is refused (for example
  `norecord noshutdown smi=04000000`), though `Pretend::from_contents` accepts it.
- **Failure scenario:** QEMU only. A scenario author gets "BENCH-FCH not understood", and the real
  registers are read.
- **Fix:** size `rest` at 33 bytes, or put a separator only between words.

### R131-9 (Low): the rental window was calibrated on the minimal program's short runs

- **Where:** `developer-tools/bench/latitude.py:1145` (`minimal_image`, now true for bisect),
  `:1153` (`window_s`), and `:1447` (`boot_over`).
- **What is wrong:** `figures()` measures only the firmware's delays. A bisect run does the full
  loader's work before its decision and last line: the kernel read and about 40 console lines.
  Each boot has two such runs, plus the next run's time to its PMxC0 line. All of this must fit
  in `SLACK_S` (15 s), and none of it has been measured. Several docstrings still say
  "minimal-mode", and so does `reread`'s text.
- **Failure scenario:** on a slow console, `boot_over` ends a boot before the run after a reset
  prints its PMxC0. The evidence that "the next run reads bit 23" is then missing from that boot.
- **Fix:** add the loader's own time (banner to last byte, which the control runs show) to
  `figures()` and `window_s`. Failing that, note the assumption in the plan's line, and update
  the docstrings.

### R131-10 (Low): a crate-wide `allow(dead_code)` in bisection builds

- **Where:** `boot/uefi/src/main.rs:20`.
- **What is wrong:** it silences dead code anywhere in `main.rs` in this mode, not only the
  after-call functions of the full mode it is meant for.
- **Fix:** put `#[cfg_attr(origin_bench_bisect, allow(dead_code))]` on `bench_after_call`,
  `bench_disturb` and `bench_exited` only.

### R131-11 (Low): small gaps in documents and tests

- `developer-tools/xtask/src/bench.rs:2437`: `no_signing_path_takes_a_bench_file` does not check
  a `bisect_target()` path. The code (`is_bench`, `:256`) is right.
- `Cargo.toml:101-111`: the cfg comment block describes every flag except `origin_bench_bisect`,
  although `BISECT_FILES` cites Cargo.toml for that flag's declaration.
- `latitude.py:1127-1131` (`CALL_LINES`) and `:1470-1474` (`resets_after_call`): the comments
  name only the minimal and full modes.
- Nothing prevents a build with both `origin_bench_minimal` and `origin_bench_bisect`, which would
  silently run the minimal mode. A `compile_error!` would stop it.
- `fch::BisectSwitch`'s doc does not say that `noshutdown` now clears PMx74 bit 17, which decides
  the control as in the minimal mode. In the full mode it meant "no triple fault after the call".

## Checked and found sound

1. **Steps 1 to 5:**
   - `BISECT_LINE` is printed first, after the boot services check.
   - Step 1, the full loader's work, is unchanged in code, apart from R131-6's ordering.
   - Step 2: `STACK_TYPE` and `BOOT_INFO_TYPE` are `LOADER_DATA` only under
     `origin_bench_bisect` (`main.rs:70-79`, used at `:400` and `:414`). No other allocation uses
     an OS-defined type: the kernel read, the kernel, the generator, the map and the pool are
     all `LOADER_CODE` or `LOADER_DATA`.
   - Step 3: `bisect::decide` uses `MinimalDecision::of`. The control needs both shutdown bits,
     the call's record is bit 23, and no record, a contradiction or no read all mean a call with
     no control. The control drains the SPCR UART, masks interrupts and triple-faults.
   - Step 4: the marks keep the full mode's `plan.marks` condition (Q10).
   - Step 5 is covered under item 2 below.
2. **After `EFI_SUCCESS`:**
   - The source has only `if status == Status::SUCCESS { triple_fault(); }`.
   - The full mode's `reset_without_firmware` block, `write_cf9` and `bench_fch_decide` are
     compiled out.
   - `ExitOutcome::Exited` is reached only by a warning status, and gives a line and a halt with
     no firmware call.
   - The error path matches the minimal mode's word for word: mask, Amendment 2's line, then
     `bench_reset`, with no UART register read and no write-back (Q5).
3. **The call goes through the copy:** both `exit` and `get_map` come from `bs`, which
   `boot_services()` copies by value at `main.rs:990-1006`.
4. **No `0xCF9` write in the loader's own code:**
   - `bisect_register` turns a FADT `RESET_REG` at I/O `0xCF9` into `Cf9InBisect` before
     `ResetLine` and the plan.
   - Every remaining `out` is to a port from the SPCR or the FADT.
   - `is_cf9_load` keeps its control: the full image has two `mov dx, 0xcf9`.
5. **The OS-types line:**
   - It counts the raw buffer of the page-table map, which is the last map translated before the
     last line (Q6).
   - It adds no firmware call: `read_memory_map_counting` equals `read_memory_map` with
     `os_defined` added.
   - It is printed after the table line and before the branch.
   - A count above zero voids the second question for that run, and the line says so (Q7).
6. **The rulings:**
   - Q2: the switch is read with the same calls, `mine` becomes bit 23 through `values_minimal`,
     and the rental refuses `BENCH-FCH` (`refuse_bench_switches`).
   - Q3: `BENCH-AFTER` is read and its value discarded with a line. The file calls keep the full
     loader's order: STALE-KEY, then AFTER, then FCH.
   - Q8: every line starts with "bench build: bisect:".
   - Q1: `git grep` finds the flag in exactly the five files `BISECT_FILES` lists, and each of them
     is on `FILES`.
7. **Other flavours:**
   - Every changed attribute is either `not(origin_bench_bisect)` or `origin_bench_bisect`. The
     normal, full bench, minimal and stack-measure (± bench) flavours compile exactly what they
     compiled before. All five flavours pass Clippy with `-D warnings`.
   - `MinimalDecisionLine`'s text is unchanged after the `write_decision` refactor; `the_minimal_lines`
     passes.
   - For the normal loader:
     - the constants hold B3's values;
     - `bench` and `fch` are gated in `lib.rs`;
     - `memmap::os_defined` is unused.

     Its bytes should therefore be unchanged. This was not verified in bytes, and is left to the
     reproducible gate as the task says. That includes the check-cfg list change in `Cargo.toml`.
8. **Controls of `check_bisect_code`:** on the existing `32b6e043` images, the ported matcher
   finds:
   - in the full image, one reset call, `call qword ptr [rax]` at `0x140003f0e`, which is not
     live, and no call followed by a triple fault;
   - in the minimal image, one triple-fault call, `call r8` at `0x1400017cc`, which is live
     (`[rcx+0x60]`, then `[rcx+0xe8]`).

   The control clause therefore passes with these shapes. The bisection call should compile to
   the full mode's shape. R131-2 and R131-3 are about what the check misses, not about its
   controls.
9. **The rental tool:**
   - `loader_kind` tests for the bisect before the minimal mode.
   - `minimal_image` makes the boot plan and `boot_over` treat the bisect as the minimal mode.
   - In `read_runs`, `CALL_LINES` holds the bisect's last line. "the control:" appears only in the
     bisect's control line. The PMxC0 regex finds the shared registers line. `boot_result` counts
     the bisect's calls. Breadcrumbs are not read.
10. **`unsafe`:**
    - The one new block, `GetMemoryMap` in `read_memory_map_counting`, is called only under boot
      services, with valid pointers, so its SAFETY comment is true.
    - `triple_fault`'s updated SAFETY comment is true for the bisect's two sites: interrupts
      masked at the control, and as the firmware left them after a successful call.
    - No other new `unsafe`.
