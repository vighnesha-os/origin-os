## What holds

**Item 134, the central claim.** Once the peer is seen blocked, I found no schedule on a machine of two or more processors in which the wake-up does not cross and get counted.

- **The observer's state is the one that sends the IPI.** `RunQueue::wake` makes only a `Blocked` slot ready and answers `true` (`runqueue.rs:904-928`); `sched::wake` sends the IPI only on that answer and only to another processor (`sched.rs:1122-1123`, `1136-1148`); `WaitQueue::wake_all` counts exactly those (`wait.rs:112-119`). `is_blocked` is `Blocked(_)` (`runqueue.rs:992-994`).
- **It must be `Blocked(_)`, not `Blocked(None)`.** `wait_one` always blocks with a deadline: `DEADLINE_INFINITE` is `u64::MAX`, so `block_until` asks for about 1.8 × 10^12 ticks (`sched.rs:789-793`, `runqueue.rs:893-895`). The host test's timed block covers this.
- **Nothing else makes the blocked peer ready before the waker.**
  - A tick readies only a due timed block or sleeper (`runqueue.rs:780-791`), and this one is due in about 580 years.
  - The peer's name is on one wait queue, registered under that queue's lock before the block (`frame/sync/src/wait.rs:155-182`).
  - Only the far end's close, a write or the peer's own handle closing calls `wake_all` there, and the ender holds the only reference to the far end (`ipc_proof.rs:1588-1598`, `ipc.rs:334-350`).
  - A stale name has another generation and wakes no one (`frame/sync/src/threads.rs:690-702`).
  - A user thread is never movable (`sched.rs:1731-1744`, `1787`).
- **The close runs on the boot processor.** `thread_ended` runs on the ending thread (`process.rs:942-957`), which was started on `bsp`; `close_out` drops its table there, and the last `ChannelEnd` dropped closes the side and wakes (`ipc.rs:213-224`, `334-350`, `430-453`). The same for a fault.
- **`TERMINATED` is raised on the boot processor.** `on_exit` lists the zombie in the exiting processor's table (`sched.rs:1618-1629`), `reap_zombies` reads only its own processor's table (`sched.rs:627-641`), and `thread_reaped` raises there (`sched.rs:667`, `process.rs:999-1009`). The boot flow's wait loop reaps on `bsp` (`sched.rs:2122`).
- **The counter.** It only rises. In each case's window I found no other source of a counted wake-up: the thread objects and the waiter's own close have no waiters. So `wakes` is the one wake-up, and nothing can make `wakes > 0` fail.
- **One processor.** `far == bsp`; the boot flow's yield lets the waiter run and block on its own queue, so `peer_blocked` is true and the crossing is not asked for (`ipc_proof.rs:1579`, `1653-1658`).
- **The budget.** At most 10 s (`sched::OTHERS_PATIENCE`), more than the 5 s before, whose result was ignored. When it runs out, the ender still starts, and the case fails on its own line with `false`, provided the peer's reports are right. That is a progress wait in R1(b)'s sense.
- **Blocked elsewhere.** While `waiting > 0`, the only block a thread of these one-thread processes can be in is `wait_one`'s (`ipc.rs:871-875`); see R134-1 for the general case.

**Item 134, the observer.**

- **Lock order.** Queue, then one record's state, each state lock released before the next slot. That is the documented order (`frame/sync/src/threads.rs:46-52`) and the one `spawn_with_parts` (`sched.rs:1840-1863`) and `with_queue` with `follow_thread` (`sched.rs:683-716`, `255`) take. No path takes a queue lock while holding a record's state. `end_with`, `current_user` and `reap_zombies` take the state without the queue lock.
- **No torn record.** It looks only at `Blocked` slots. A zombie's slot is free and names no record before its state is emptied (`runqueue.rs:932-943`, `684-689`; `sched.rs:643`), and a spawn writes the state under the queue lock before the slot can be seen.
- **Identity.** `ObjectRef::same` compares the object's address (`frame/src/objref.rs:57-59`), the proof holds its reference for the whole case, and `start_thread` returns the very object the context holds (`process.rs:882`).
- **Interrupts.** One `without_interrupts` section on the caller's processor; it holds another processor's queue lock as `has_room` and `unaccounted` already do.
- **Callers.** Only `blocked_in_wait`.

**Hot paths.** The diff has no line in `resume`, `on_yield`, `dispatch`, `sched::wake`, `with_queue`, `follow_thread`, `RunQueue::wake`, `block_for`, `switch` or `floor`, and none in anything they call. `sched.rs` gains one function, `runqueue.rs` one method with one caller and a test, and no field. See R134-2 for what the author's count does and does not show.

## Findings

### R134-1 (Low). The observer shows less than "blocked in `wait_one`"

- **Where:** `framekernel/src/ipc_proof.rs:508-531`; `framekernel/src/sched.rs:1396-1428`.
- **What is wrong:** `blocked_in_wait` answers true when the process counts some thread in a wait and this thread is blocked anywhere. `Process::waiting` is per process, and `port::wait` raises it too (`port.rs:270`, `syscall.rs:740`).
- **Scenario:** A later proof reuses the helper for a process with two threads. Thread A is in `wait_one` and has not blocked; thread B, the one passed in, is blocked in `port_wait`. The answer is true, and the waker starts in the very window the helper exists to close.
- **Today:** Both callers have one thread whose first call is the wait, so it is right for them.
- **Fix:** Say in the doc that it holds for a process with one thread, or drop the `waiting` conjunct and name the helper for what it reads.

### R134-2 (Info). The static count covers seven symbols and no placement

- **Where:** `tools/counts134.py` and `turn-counts.sh`, the author's.
- **What I could not establish:** The count compares `resume`, `on_yield`, `dispatch`, `wake`, `wake_inconsistent`, `floor` and `switch`, with addresses, targets and RIP displacements removed. It does not compare `on_tick`, `on_block`, `on_reschedule`, `on_exit` or `follow_thread`, and by design it cannot see where the code sits.
- **Why it matters:** The diff adds code to the kernel image, so functions move. TASKS item 96's form C was withdrawn on a measured cost that the static count did not predict.
- **Decision for you:** Either measure B1 and the ping-pong at the tip against the base, or record that this change was judged on static counts alone.

### R134-3 (Info). No gate holds the order

- **Where:** `framekernel/src/sched.rs:1415`; `framekernel/src/ipc_proof.rs:1635`, `2431`.
- **What is wrong:** `user_thread_blocked` and `blocked_in_wait` have no host test, and no boot fails if the fix is undone.
- **Broken implementation that passes every gate:** `user_thread_blocked` without `queue.is_blocked(slot) &&`. Every boot passes at the old rate; only C134-B and C134-C, run by hand, show it.
- **Fix:** I see no cheap permanent test. Record the controls in ADR-0013 as the evidence, and say there that they must be run again when this code changes.

### R135-1 (Low). No host test fails if the judge stops calling `counts_hold`

- **Where:** `developer-tools/xtask/src/main.rs:8064`, `8321`.
- **What is wrong:** The tests call `pit_routed` and `counts_hold` directly. The closure in `run_scenario` is not reachable from a test.
- **Broken implementation that passes every host test:** the closure back at `.then_some(Ok(()))`. Only the planted boot C135-10 shows the difference.
- **Fix:** Lift the verdict into a function of the text, the markers and the failures, and test it: every marker with 19 gives `Some(Err)`, with 21 gives `Some(Ok)`, and a missing marker gives `None`.

### R135-2 (Low). Two comments say what is not so

- **`main.rs:3907`:** "the 65-processor machine under host load printed 21 on a boot that passed". The kernel's proof passed; xtask failed the boot (`TASKS.md:5344`). The test's comment at `main.rs:9114` has it right.
- **`main.rs:9225-9226`:** "`PROOF_TICKS` in `framekernel/src/irq.rs`, which is the kernel binary's and not the library's". `irq` is a module of the library (`framekernel/src/lib.rs:207`), private and compiled only for `target_os = "none"`. That is why a host test cannot name the constant.
- **Fix:** Reword both.

### R135-3 (Info). The screen's `counts_hold` cannot run today

- **Where:** `developer-tools/xtask/src/main.rs:8321`.
- **What is wrong:** No `Capture::Screen` scenario holds `PIT_ROUTED`; both use `console_markers` (`main.rs:5484`, `5512`). So the call is dead.
- **If it became live:** It reads screen rows. The line is 80 characters at "20" and "207 ms", so on a console of 80 columns or fewer a longer count or time wraps, and `pit_routed` would refuse a correct boot as "not as the kernel prints it".
- **Fix:** Drop the call there with a comment, or refuse the marker in a screen scenario where the scenario is built.

### RC-1 (Medium). C134-A and C134-TA do not pass Clippy, so order A's control never boots

- **Where:** `review-controls134.py:40-53` (`FLAG`), `117-118`, `140-141`.
- **What is wrong:** `FLAG` always plants `ipc::plant_delay`. Only `BEFORE_REGISTERING` and `BEFORE_BLOCKING` call it, and A and TA use neither. `ipc` is a private module of the library, so under `-D warnings` the function is dead code.
- **Result:** The author's run shows it: `error: function plant_delay is never used`, rc 101, for both.
- **Why it matters:** A is the only control that shows the crossing is still required once the peer blocks first, which is the one thing the case keeps of the IPI path.
- **Fix:** Plant the delay function only with a hold, or put `#[allow(dead_code)]` on it.

### RC-2 (Medium). Every failing boot control is "NOT AS EXPECTED" by construction

- **Where:** `review-controls134.py:102-103`, `269-276`.
- **What is wrong:** The script wants exactly one line for "exits" and one for "faults". `boot-test` stops QEMU at the first failure word (`main.rs:8060-8062`), which is on the "exits" line, so the "faults" line is never printed.
- **Result:** C134-B, C and TC printed exactly the line their comments describe and were still reported wrong: "0 lines start '…when a process faults…'". A and TA will meet the same once they compile.
- **A second consequence:** No failing plant reaches the "faults" iteration, which is where the original stop was.
- **Fix:** For a control expected to fail, judge the first case line and require that no later case line is there. To show "faults", have the window set the flag only in the second iteration.

### RC-3 (Medium). C134-N cannot reach its line, and nothing else shows the `false` path

- **Where:** `review-controls134.py:132-138`.
- **What is wrong:** The plant adds `WRITABLE` to the peer's mask, so the wait returns at once and the peer's reports are wrong. `check_groups` prints its own line with ": ipc failed" before the case's line (`ipc_proof.rs:576-581`, `1644`), and the boot stops there.
- **Result:** The author's run: the first failing line is "the peer of a process that: woken -> OK, observed -> 0x2, …".
- **What is left unshown:** That a peer not seen blocked fails the case on its own line, and that xtask's marker needs `true`.
- **Broken implementation that passes everything run so far:** `right` without `&& peer_blocked`.
- **Fix, two controls:**
  1. Plant the observation, not the peer: pass `bsp` for `far` in the `blocked_in_wait` call, or make `user_thread_blocked` answer false inside the window. Expect, after about 10 s, "seen blocked in wait_one before the process started: false, blocked 1 times, …; 1 wake-ups crossed processors: ipc failed", the first failing line being the case's own.
  2. The same plant with `&& peer_blocked` removed from `right`. The kernel then prints `false` and no failure word, and xtask must fail with "first missing marker … started: true, blocked ". It needs a short timeout in the control's environment.

### RC-4 (Medium). The wrapper prints "rc=0" whatever the controls returned

- **Where:** `turn4-controls.sh`, the two lines `…; echo "$(date -u +%FT%TZ) counts rc=$?"` and `…; echo "$(date -u +%FT%TZ) controls rc=$?"`. This is the wrapper, not the script you asked about.

- **Fix:** `rc=$?; echo "$(date -u +%FT%TZ) controls rc=$rc"` for both, and end the script with the worse of the two.

### RC-5 (Low). The holds are near-certain, and the pass controls do not show a hold was reached

## Follow-ups

Outside the change.

- **`ping_pong`, `framekernel/src/ipc_proof.rs:736-737`.** It requires `blocked.0 + blocked.1 > 0` and one crossing over 1,000 rounds. That is certain in practice and not structural. `blocked` also counts a block that returned at once.
- **`byte_quota`, `ipc_proof.rs:1872`.** The wait for the writer to reach its wait is not required and not said. If it runs out, the peer may read before the third write, and "the third is over the quota" fails with nothing wrong.
- **`memory_goes_with_the_last_thread`, `ipc_proof.rs:2573-2582`.** The thread's `TERMINATED` is raised before its exit, so the `sched::reap()` that follows may find no zombie, and "0 spaces freed while a thread ran" is then true without having tested anything.
- **Waits of 5 s where the rule is 10.** `ipc_proof.rs:1717`, `2688`; `events_ports.rs:688`; `kernel_bound.rs:467`; `core_pin.rs:840`. They wait on the boot processor's own thread, so the risk is small.
- **`virtionet.rs:1574-1580` with `1622-1625` and `1690-1693`.** `blocked > 0 && wakes > 0` rests on a 10 ms settle before the ARP is sent, not on seeing the thread blocked. I did not check that row's class in ADR-0013.
- **A refused ender start leaves the waiter blocked for good.** `ipc_proof.rs:1636-1638`, `2432-2434`: the case returns `false` with no line and the waiter's process is never reaped. It was so before this change.
- **Stranded doc comments in `runqueue.rs`.** `has_room`'s is above `describe` (955-961), so `has_room` (996) has none; `Departed`'s is above `SlotState` (450-456).
- **`process.rs:520`.** The doc says `waiting` counts threads in `wait_one`; it counts `port_wait` too.
