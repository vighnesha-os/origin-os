## Findings

### T68-1 (Medium): no proof checks that the A1 record is removed, or that a stack's drop reads it. Either break passes every boot proof

**Where:**
- `framekernel/frame/src/stack.rs:557-563`: `Left::drop`.
- `stack.rs:401-411`: `GuardedStack::drop`, which calls `in_use`.
- `stack.rs:517-520`: `slot_in_use`.
- `framekernel/src/measured_stack.rs:245-298`: R2.
- `framekernel/src/sched.rs:1302-1311`: the "thread reaping" check, which compares only the heap and `counts().live`.

**Break A: the record is never removed.** Suppose `Left::drop` stops clearing its entry, or a refactor loses `drop(left)`.
- R1 leaves three stale entries. They point into the loader's stack, so they have no effect.
- R2 passes, because the record is present while the thread is switched out, which is all R2 checks.
- When R2's thread exits, `reap` drops its own stack. `in_use` finds the stale entry, and `REGION.leak` moves the slot from `live` to `lost` (`slots.rs:323-331`).
- "Thread reaping" compares `live` and the heap, so it passes.
- No proof reads `counts().lost` across R2. `settle` judges only the losses during its own run, and the stacks proof compares only within its own window.

So every boot would pass while every thread that ever made a measured call loses its stack at exit. After 64 such calls, `with_measured_stack` returns `None` for the rest of the boot.

**Break B: a stack's drop stops reading the table.** Suppose `GuardedStack::drop` goes back to calling `cpu::stack_in_use` directly, which is the one line this diff changed at `stack.rs:405`. R2 still passes, because it asks through `slot_in_use`, which calls `in_use` on its own. The drop that ruling A1 is about would then free a switched-out caller's stack. R2 proves the predicate, not its use where stacks are freed.

**Suggested fix:**
1. In R2, after the reap, check that the thread's own stack was not lost: `counts().lost` unchanged since before the spawn, or a small framework query of `LEFT`'s occupied entries that must return to its earlier value.
2. Add a control MS-7 that empties `Left::drop`.
3. For B, either add a check that `GuardedStack::drop` goes through `in_use` (a text gate or a host-built test of the predicate's callers), or state in ADR-0013's R2 row that R2 covers `slot_in_use` and that the drop's use of it rests on reading the code.

### T68-2 (Medium; it predates this range, but the range repeats the claim): while a thread is being switched out, no record holds its own stack

**Where:**
- In the range: `stack.rs:29-37`. The module documentation, which this diff edited, still says the framework knows a stack is in use because "every kernel stack a processor runs on has its top in some processor's TSS and every suspended thread has a saved frame".
- The mechanism, not changed by this diff:
  - `cpu.rs:1092-1095`: `dispatch` runs the scheduler's hook, then `resume`.
  - `sched.rs:260-278`: `with_queue` calls `follow_thread` at line 275.
  - `sched.rs:98-114`: `follow_thread` moves `kernel_stack` to the next thread or clears it.
  - `cpu.rs:792-802`: `resume` records the outgoing frame last, at line 799.
  - `cpu.rs:808-826`: `stack_in_use` reads `kernel_stack` before `SAVED_FRAMES`.

**Failing scenario.** Thread T, on its own stack S, yields on processor A. `dispatch` runs on S. `on_yield`, through `with_queue`, calls `follow_thread(next)`, which sets A's `kernel_stack` to the next thread's top (or 0) and releases A's thread table. Only then does `resume` record T's frame. Between the two, processor A is still running on S, yet S's top is in no `kernel_stack` and no saved frame is on it.

A safe caller on processor B that holds S's `GuardedStack` and drops it in that window gets `in_use == false`. That is exactly the "safe caller that drops one too early" the module documentation names. S is then given back and kept mapped. The next `GuardedStack::new` of that size zeroes it, or, with this diff, `with_measured_stack` paints it, while A is still returning through `resume`, `dispatch` and `exception_saved` on it.

There is also a memory-ordering variant at switch-in. The writer sets `kernel_stack` and then clears the saved frame, while the reader reads `kernel_stack` first. On x86 a reader can see the old `kernel_stack` and the cleared frame.

**Reach:** no caller does this today. Thread stacks are freed only by `reap`, which frees zombies on its own processor. This diff does not cause the gap and does not widen it:
- for a thread inside `with_measured_stack`, `LEFT` covers its own stack for the whole call;
- the measured stack is held by the call itself.

I am confident the window exists in the code as written. Whether ADR-0011 N6 must survive this caller is for the coordinating session to judge, but it is the standard the module documentation itself states.

**Suggested fix** (a separate task):
- Record the outgoing frame before `follow_thread` moves `kernel_stack`. For example, `dispatch` records `here` before it calls the hook, and `resume` takes it back if the scheduler resumes `here`.
- Make every transition add the new record before it removes the old one, and read in the matching order, or use a per-processor sequence count.
- Restate the module documentation's claim with the window and its rule.

### T68-3 (Low): a measured stack in use is in none of the records, and `slot_in_use` reports it free

**Where:** `stack.rs:29-37` and `stack.rs:514-520`.

**Scenario.** Processor A runs `f` on the measured stack M and is not switched out. Processor B calls `slot_in_use` on M's slot, which any safe caller can name through `slot_holding(addr)`. `in_use` checks:
- B's own stack pointer;
- every `kernel_stack`, where A's holds the top of the thread's own stack, not M's;
- `SAVED_FRAMES`, which has none on M;
- `LEFT`, which holds the stack pointer of the thread's own stack.

So it answers `false` while A runs on M. This is not unsound: only the call holds M, so nothing else can drop it. The same is already true of the interrupt stacks and the generator's stack. But the module documentation's "every kernel stack a processor runs on has its top in some processor's TSS" is not true of M, and `slot_in_use`'s "Whether the stack in slot `slot` is in use" invites a liveness reading it cannot give.

**Suggested fix:** say in the module documentation that a measured stack, like the interrupt and generator stacks, is protected by being held by its user, not by the records. Narrow `slot_in_use`'s documentation (or its name) to "what a drop would decide from the records".

### T68-4 (Low): R1's exactness depends on which of two slots LLVM gives `mark`'s local; the records say `mark` writes one word

**Where:** `measured_stack.rs:5-7` and `measured_stack.rs:60-66`; `TASKS.md:2012` ("`mark` writes its one local at `rbp-0x10` ... and nothing else below its saved frame pointer"); the hand-over says the same.

**Evidence from my build of `b200dbbd`:**

```
mark: push rbp; mov rbp,rsp; sub rsp,0x10
      mov qword ptr [rbp-0x10], 0x0      ; `here`
      lea rax,[rbp-0x10]
      mov qword ptr [rbp-0x8], rax       ; black_box's temporary
      lea rax,[rbp-0x8]; mov rax,[rbp-0x8]; add rsp,0x10; pop rbp; ret
```

`mark` writes two words below its saved RBP. R1 is exact to the byte only because `here` got the lower slot. A compiler upgrade, or a small edit to `mark`, that swaps the slots would fail R1 by 8 bytes at both depths with nothing wrong in the function. The module documentation's "the one word that leaf writes below its saved frame pointer" and TASKS's Result do not match the image.

**Suggested fix:**
- Correct the records.
- Name this dependence in ADR-0013's R1 row, under "would a machine fail it": a toolchain upgrade under §15 re-reads `mark`.
- Optionally, restructure the leaf so that the sampled word is its only stack write by construction, and confirm that in the disassembly.

### T68-5 (Low): the module documentation says neither proof runs inside another proof's count window; R2 does

**Where:** `measured_stack.rs:24-27`, against `sched.rs:1072-1075` and `sched.rs:1302-1311`. `sched::prove` takes `heap_before` and `stacks_before` (held stacks) at its start and compares them at its end. R2 runs between those two points.

The Result in `TASKS.md` (line 2014) says this correctly, but the module documentation contradicts it. When R2's thread ends and is reaped, the effect on the window is zero. If it does not end, "thread reaping" fails as well: two failures from one cause.

**Suggested fix:** correct the module documentation to say what TASKS says.

### T68-6 (Low): if the compiler grows `level`'s frame, R1, a Report proof, halts the boot

**Where:** `measured_stack.rs:42-48` and `measured_stack.rs:135-155`.

At 64 levels R1 uses 11,504 of 16,384 bytes, at 176 bytes a level. If the frame grows by about 40% (to about 250 bytes), the 64-level run overflows. That is a double fault and a halt (MS-5's path), not a reported failure: a Report proof would then stop the boot. With the toolchain pinned, this is a risk at an upgrade, not today.

**Suggested fix:** choose the deep level count from the shallow run's measured cost. For example, run 64 levels only if `per_level × 64 + margin < size`, and otherwise report a failure. Or run the deep case on a 64 KiB stack.

### T68-7 (Low): control MS-4 can pass by chance

**Where:** ADR-0013, line 573. The worker thread runs with interrupts on: new threads start with RFLAGS 0x202 (`stack.rs:722`). With the yield removed, a timer tick during the 1,000-iteration spin switches to the boot flow. The boot flow then asks about the stack (and gets `true`) and moves `TURNS`. The timer's trap frame also clears the 128-byte margin, so R2 would pass. The author notes this.

**Suggested fix:** in the control's edit, put the spin inside `cpu::without_interrupts`, so nothing can switch away, and record that in the control's row.

### T68-8 (Low): what the documentation says about the depth

**Where:** `stack.rs:588-595`.

- **(a) A sentence that does not follow.** "Safe Rust reads no stack word it has not written, and the kernel's target uses no red zone, so nothing is written below the stack pointer." The first clause does not support the conclusion. It supports a different one: the "reserved and only read" case does not arise in safe code.
- **(b) The bound can be given as a figure.** In my build every probe is `sub rsp,0x1000; mov qword ptr [rsp],0x0` (65 sites), and the remainder below the last probe is reserved without one. Since there is no dynamic stack allocation, the unwritten part of the deepest frame is under one page. Saying so turns "an upper bound by at most the unwritten part of the deepest frame" into a figure the AML wiring can print.

**Suggested fix:** reword (a), and state (b) with the probe form the build uses.

### T68-9 (Low): `MEASURED_CALLS` and records that are never given back

**Where:** `stack.rs:522-524`, `stack.rs:612-614` and `stack.rs:621-633`.

- The documentation of `MEASURED_CALLS` does not say that a thread that ends inside `f` never gives its record back. Each such record counts against the 64 for the rest of the boot, and nested calls leak one each. The function's documentation mentions the leak but not this cap.
- The table is checked only after the stack has been taken and painted. A refused call therefore costs a stack's allocation and up to 8,192 volatile writes.

**Suggested fix:** document the cap. Optionally, take the record before the allocation, which makes no difference to safety.

## Checked and found sound

- **The switch's `asm!` block** (`stack.rs:698-709`), against my disassembly of `run_on`:
  - The code is `push r12 ... mov r12, rsp; mov rsp, rax; call enter; mov rsp, r12 ... pop r12`.
  - `top` cannot be given R12, because `out("r12")` is not a late output. It cannot be given RDI either, which is explicit.
  - RSP is 16-byte aligned at the `call`, because the top is a page-aligned slot top (`SLOT` is 0x20000).
  - The direction flag is clear on entry under Rust's inline-assembly contract, and the Rust callee keeps it clear.
  - The block does not declare `preserves_flags`, and `clobber_abi("sysv64")` covers the caller-saved registers.
  - The stack pointer is the block's own again at its end.
  - `enter` tail-calls the closure (`pop rbp; jmp [rcx+0x20]`), which is consistent with the empty closure's 16-byte depth.
- **R12 across preemption and migration:** `exception_saved` pushes R12 into the trap frame before clearing it, and restores it on resume, on whichever processor that is.
- **Interrupts in the switch's edges:** an interrupt between `mov rsp, top` and `call`, or after the return and before `mov rsp, r12`, is pushed inside M. The A1 record is already in place.
- **A closure that panics:** the target is `panic="abort"` (`rustc --print cfg`), the panic handler halts the processor, and the image has no unwinder symbols. Nothing unwinds through `enter` or the block. The processor halts on M, and the thread's own stack stays recorded.
- **Nested calls:** each call records its own stack pointer. An outer measured stack is held by the outer call.
- **A thread that ends inside `f`:** its own stack is leaked at reap (`reap_zombies` → drop → `in_use` → `LEFT`). M stays live, because its `GuardedStack` sits in a dead frame. The exit's frame is not recorded (`resume` with `exiting`). All of this is safe.
- **A full table:** the call returns `None` before `f` runs, and the stack is dropped.
- **A1's ordering:**
  - The record is an AcqRel compare-and-swap made before the switch, and is cleared with a Release store after the switch back. `left_on` reads with Acquire.
  - Neither moves across the opaque block or the out-of-line call (in `worker`: `mov rdi, rsp; call Left::record` before `run_on`, and `Left::drop` after it).
  - For the caller's stack, the record covers the whole time its top is out of `kernel_stack`.
- **Every path that frees a stack:** only `GuardedStack::drop` decides, through `in_use`. `reclaim`, `trim` and idle reuse act only on slots that were given back after that check. `map_fresh` and `GuardablePage` never hold a thread's stack.
- **The paint and the scan:**
  - Both stay inside `[top - size, top)`, through exposed provenance, as `bytes_mut` already does.
  - The image shows the unrolled volatile stores and the scan's comparison with `0xB4D57AC69E1F83E7`.
  - The `SAFETY:` comments at `stack.rs:626-628`, `641-643`, `647-649`, `660`, `672-673` and `688-697` are true as written.
- **`stackpaint::depth`** is right, and its seven host tests pass. `PAINT` is non-canonical under both 4-level and 5-level paging (its top byte is 0xB4).
- **The backtrace claim:** `capture_backtrace` bounds its window at M's slot top. The saved RBP in `enter`'s frame points into the caller's stack, outside that window, so the walk stops.
- **R1:**
  - Interrupts are off in the boot flow, and `f` opens no console window.
  - In this build nothing below `mark`'s `here` is written (see T68-4 for why that holds).
  - `level`'s frames match the 176 bytes a level.
- **R2:**
  - The thread runs on the boot processor. The boot flow runs with interrupts off, so its loop body is atomic with respect to the thread, and the `AT_DEPTH`/`ASKED` logic cannot miss.
  - A `true` from `slot_in_use` can come only from `LEFT`: the boot flow's `kernel_stack` is 0, and the thread's only saved frame is on M. This agrees with MS-6.
  - In this build `at_deepest` is inlined into `level` (`int 0x81` in level 0's frame). The trap frame therefore starts at that frame's stack pointer, with the sample 32 bytes below it: at least 144 bytes, so the 128-byte margin holds.
  - Its bounds count yields, not time.
- **Stack probes write zero,** so the paint counts them (Q2).
- **ADR-0004 A6:** the new code prints only depths, sizes and durations.
- **The `unsafe` rules:** `unsafe` appears only in `stack.rs`, which is on the gate's list with an updated reason. `stackpaint.rs` and `measured_stack.rs` forbid it. `stack_pointer`'s single `mov` rightly declares `preserves_flags`.
- **xtask:** the markers are in the kernel's order (matched in order), and the failure word is added. `bootproof.rs` has its two rows and the pinned counts (71).
- **Records:**
  - ADR-0013's two rows and the MS-1 to MS-6 results agree with the code and with the hand-over's figures.
  - The `SOURCE_PROVENANCE.md` entry and rows are complete. It reads no open-source code and makes no claim about KVM, CI or hardware.
  - TASKS item 68's Result matches the code, except as noted in T68-4.

## Resolution

Answered by the TASKS 68 session on 2026-11-19, on the coordinating session's rulings of the same day, on `claude/t68-measured-stack`. The commits, in order: `882a108a` (T68-1, T68-5), `6e4fdee4` (T68-9), `6a29f273` (T68-4, T68-6), `dd6b2649` (T68-2, T68-3, T68-8; the last that changes code), `0e1816a0` (ADR-0013's rows), `150af01d` (this report, as received), and the records after them. Nothing in `cpu.rs` changed.

**T68-1 (Medium): fixed, `882a108a`, with the coordinating session's change to the suggested fix.**
- After its thread is reaped, R2 reads that thread's own slot through `stack::slot_state`, which names no address, and requires it given back (`Idle`, `Retired`, `Reclaiming` or `Free`), not `Lost`. It does not read `counts().lost`, which a stalled shootdown on the 65- and 67-processor machines can move (decision items 313 and 314).
- Why a lost slot here is a leak: R2 now runs just after "thread reaping" has closed with a settle (T68-5). That settle leaves no stack kept for reuse, so the reaped stack is kept (`Idle`), not retired, and no shootdown touches it during R2. On every boot of the gates below it was "kept for reuse".
- Control MS-7 empties `Left::drop`: R2 fails with `its own stack given back after the reap false (lost)`. A stale record can leak the stack only if `GuardedStack::drop` reads `LEFT`, so MS-7 also shows that the drop reads the table (the second half, B).
- A comment in `GuardedStack::drop` says that it and `slot_in_use` must decide through the same `in_use`.

**T68-2 (Medium): recorded as TASKS item 70, on the coordinating session's ruling.** The window in `dispatch`, between the hook's `follow_thread` moving the processor's kernel-stack record and `resume` recording the outgoing frame, is TASKS item 70's, with `resume`'s panic that prints a frame address (the report's "seen in passing"). In this range only the module documentation changed (`dd6b2649`): it no longer claims every stack a processor runs on is in a record, and it names the switch-out window as an open gap, TASKS item 70.

**T68-3 (Low): fixed, `dd6b2649`.** The module documentation says that the interrupt stacks, the generator's stacks and a measured stack while its closure runs are in no record, which is safe because only their holder can drop them. `slot_in_use`'s documentation says it answers what a drop would decide from the records, not whether a processor runs on the slot.

**T68-4 (Low): fixed, `6a29f273` and `0e1816a0`.** The documentation and TASKS item 68's records say `mark` writes two words below its saved frame pointer, its local and `black_box`'s copy of the local's address, and that R1 is exact because the local takes the lower slot in this build (`rbp-0x10`, read again in the build of `dd6b2649`). The 0-byte bound stays. R1's failure line adds, when a depth is 8 bytes more than its sample, that this may be `mark`'s two words in swapped slots, a change in the build rather than the function. ADR-0013's R1 row names the dependence and that a toolchain upgrade (CLAUDE.md §15) reads `mark` again. The leaf was not restructured.

**T68-5 (Low): fixed, `882a108a`.** R2 moved after the window's compare: it now runs just after "thread reaping" and before the kernel-wide bound, which settles before it reads. Its row in the proof table and its markers moved with it. The module documentation says where it runs and why the counts are unaffected.

**T68-6 (Low): fixed, `6a29f273`.** R1 and its empty closure measure on 32 KiB (`BOOT_STACK`), about three times what the deep run needs at 176 bytes a level. MS-5 was run again on it: 200 levels on 32 KiB still overflow, with a double fault reported.

**T68-7 (Low): fixed in the control.** MS-4's edit removes the yield and runs the thread's wait inside `cpu::without_interrupts`, so no tick can switch it away. Run again: `switched away and back false after 1000 yields`, `0 below the sample`, R2 failed.

**T68-8 (Low): fixed, `dd6b2649`, with one departure from the ruling's wording.** (a) The sentence is reworded: safe Rust reads no stack word it has not written, so a word reserved and only read does not arise in safe code; the red zone is a separate reason, that nothing is written below the stack pointer. (b) The documentation states the unwritten part of the deepest frame as **at most** one page, not under one. In the build of `dd6b2649`:
- 60 sites are `subq $0x1000, %rsp; movq $0x0, (%rsp)`, and `cpu::init` probes in a loop with the same zero write;
- LLVM leaves a frame's last page unprobed, since a move of one page or less cannot pass the unmapped space below a stack. `cpu::init`'s third `subq $0x1000, %rsp` is such a page in this image: it is followed by no probe. A frame whose unprobed last page is never written, and from which nothing is called, leaves that whole page below its lowest write.

So a deepest frame's unwritten part can be a whole page. It says the probe form is this build's.

*Corrected for the addendum's T68-11.* The reason first given here was two functions, `UserSpace::shares_kernel_half` and `vm::kernel_half_unchanged`, said to reserve exactly one page with no write after it. Their page is unprobed, but the next instruction, `pushfq`, writes the word just below it, so they leave nothing below their lowest write. They show an unprobed page, not an unwritten one. The conclusion, at most one page, is unchanged.

**T68-9 (Low): fixed, `6e4fdee4`.** The record is taken first, before the stack is taken and painted, so a full table refuses the call at no cost. `MEASURED_CALLS`' documentation says that a thread ending inside a measured closure never gives its records back, and each counts against the 64 for the rest of the boot.

### New findings

#### T68-11 (Low; records): the evidence given for T68-8's departure is not what the image shows

**Where:** the Resolution, T68-8 (b), in `docs/engineering/REVIEW_T68_2026-11-19.md`, and the hand-over's addendum. Both say that `UserSpace::shares_kernel_half` and `vm::kernel_half_unchanged` "reserve exactly one page with no write after it".

**What the image shows** (both builds, at `15a4a0` and `15c480` in the new one): each does `sub rsp, 0x1000` and then, as its next instruction, `pushfq`. That writes the word just below the reserved page. In those frames the lowest write is therefore at the frame's very bottom, and nothing lies below it. They show an unprobed page, not a page left below the lowest write. The conclusion, "at most one page", is still right, for the reason given under T68-8.

The documentation in `stack.rs:624-630` does not cite these functions and is correct. `SOURCE_PROVENANCE.md`'s "two one-page frames unprobed" is also accurate. Only the Resolution and the hand-over carry the wrong reason.

**Suggested fix:** in the Resolution, give the reason as LLVM's rule, that the last page of a frame is not probed, with `cpu::init`'s third `sub rsp, 0x1000` as the example. Or say of the two functions that the page is unprobed but `pushfq` writes just below it.
