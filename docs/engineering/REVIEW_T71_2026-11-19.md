## Findings

### T71-1 — Medium — The census passes when the guard does not cover a changing structure. Its live check tests the locator's list against itself.

**Where:**
- `framekernel/src/acpi_census.rs:533-551`: the live check probes only `fw.changing().ranges()`.
- `acpi_census.rs:145-153`: `consistent()` does not count `unlocated`, `Never::untracked` or `Never::already_lent`.
- `framekernel/frame/src/acpi.rs:257` (`CHANGING_MAX` = 5), `:292-311` (`push`), `:359-376` (silent `continue`s).
- `framekernel/frame/src/firmware.rs:95-104` and `reserved.rs:552-575`: `located` is set whatever was found.

**The defect:** the live check lends into the start and middle of each range the kernel's own locator recorded. It never tries the FACS, FBPT, S3PT or MBPT that the census locates independently (`check_facs`, `performance_tables`). So the check can only show that the registry refuses what the registry was given. If the locator misses a structure, the census says "a lend over each refused: true" and `consistent true`. The miss can come from the locator's limits, from its silent skips, or from a failed first read. Every gap below reaches a pass.

**Scenario 1 (probe P1, run):** the XSDT lists three FPDTs with distinct pointers before the FADT.
- `changing_ranges` fills its five slots with the FPDTs' targets. The FACS is not located (`unlocated = "more structures the firmware changes than expected"`).
- `Lending::lend(FACS+0x10, FACS+0x18)` then returns `true`. Probe output: `PROBE lend into FACS middle allowed by registry: true`.
- In the kernel, `firmware::bytes`' N3 check then guards only the FACS's first four bytes. A pointer into its middle is lent:
  - an XSDT entry with any header there, or
  - the FADT's DSDT pointer: the census reads the header at that address by copy, sees no `FACS` signature, and lends it.
- The census follows only the first FPDT, whose FBPT and S3PT may be valid. It prints "not all located: …" but its verdict passes.

**Other ways to reach the same pass, by reading:**
- an XSDT longer than 1,024 entries with the FADT past entry 1,024;
- an FPDT longer than 1 KiB;
- a structure declaring more than 1 MiB (only its first MiB is guarded; the census's "too large to judge" does not fail the verdict either);
- `untracked > 0` or `already_lent = Some(..)`: printed, never failed. `already_lent` means a reference to changing memory already exists, which is the invariant itself broken.
- `changing_ranges` swallows unreadable XSDT entries, unreadable entry headers and an unreadable FADT body without setting `unlocated` (`acpi.rs:359-376`).
- If the RSDP or XSDT cannot be copied at the first lookup, `record` still runs with no ranges. `never_lend(&[])` sets `located` for good, so all lending starts with nothing guarded. The census then prints "none named; … not all located: the RSDP could not be read; a lend over each refused: true" and passes.
  - Today the first lookup comes after the kernel's page tables (`kernel.rs:182`, and `record_or_stop` halts if paging failed), so this is latent.
  - A future lookup moved earlier (before `KERNEL_SPACE`, where `read_firmware` refuses everything) would silently turn the guard off.

**Why Medium and not High:** every route needs non-conforming firmware or a future code change. On conforming firmware the locator and the census choose the same FACS and FPDT, and host tests catch a regression of the locator itself (`the_changing_structures_are_located_by_copy` and the census test's exact line). Under a strict reading of "a proof that can pass while wrong" this is High. The records do not claim more than the census does ("a lend over each [located] refused").

**Suggested fix:**
- In the census, also probe a lend at the start and middle of each structure the census itself located: the FADT's FACS by `facs_address`, and each FPDT pointer the census followed.
- Count any such structure missing from `fw.changing()` against the verdict.
- Make `unlocated`, `untracked != 0` and `already_lent.is_some()` fail the verdict.
- Do not set `located` when the RSDP or XSDT could not be read. Leave lending refused and say so.
- Set `unlocated` on each silent `continue` in `changing_ranges`.

### T71-2 — Medium — A pointer that does not name its structure is trusted for up to 1 MiB, and can block every table lookup.

**Where:** `framekernel/frame/src/acpi.rs`:
- `:378-382`: the primary FACS, recorded whatever its first bytes are, with the length read at `target+4`;
- `:401-430`: the FPDT's targets, the same;
- `:292`: the clamp to `CHANGING_MAX_LEN` = 1 MiB.

**The defect:** the hand-over's departure 2 rightly refuses to trust the ignored 32-bit `FIRMWARE_CTRL`, so that "a stale 32-bit value could block lending of the XSDT". The same hazard remains for the pointer that *is* chosen, and for every FPDT pointer.

**Probe P2 (run):** `X_FIRMWARE_CTRL` set to the XSDT's address. Result: the range `(Facs, 0x7F000100, 0x7F000140)` is recorded as never lendable. That range is the XSDT, so `lookup`'s `lend_table(rsdp.xsdt, …)` is refused and every `acpi_table` call fails: SPCR, MADT, SRAT, MCFG, HPET, FADT.

**The FPDT case is worse:**
- The FPDT is an optional, informational table.
- One FBPT pointer that names a byte inside the ACPI region, with any value up to 1 MiB at that address + 4, can cover all the static tables.
- Before this change the same firmware booted fully and only the census failed.
- This conflicts with the coordinating session's in-principle ruling: a value the kernel does not act on is reported, never refused.

**Suggested fix:**
- When the target's first four bytes are not its kind's signature (`FACS`, `FBPT`, `S3PT`, `MBPT`), record only the kind's minimum length (64, 8, 8, 24), or do not record an FPDT target at all, and report it.
- In any case, report by name a never-lendable range that overlaps the RSDP or the XSDT, rather than failing every lookup silently.
- Record the decision in TASKS 71's "where it differs" and add a host test.

### T71-3 — Low — F14 is closed only for memory the map types as MMIO. Holes stay readable and are mapped write-back. The headline says more than that.

**Where:**
- `framekernel/frame/src/reserved.rs:416-426` (`names_mmio`, "A hole in the map is not MMIO");
- `vm.rs:612-631` (`is_firmware_data` admits holes and `Reserved`);
- `vm.rs:180-200` (`map_firmware` maps `Attributes::kernel_global(Access::Read)`, write-back);
- `docs/STATUS.md` ("**No table read from MMIO**");
- commit `5b653848`'s subject.

**Scenario:** F14 was about device registers read through a write-back mapping. On PC firmware the local APIC, I/O APICs, HPET and PCIe BARs are usually not described as `EfiMemoryMappedIO`. They lie in holes or in `Reserved`.
- An XSDT entry that names a BAR in a hole is still copied (36 bytes) and, if its "signature" matches, lent.
- Its page stays mapped write-back in the direct map for good.

The TASKS body is precise ("memory the memory map calls MMIO"). The STATUS headline and the commit subject are not.

**Also:** the refusal lives in `firmware.rs`. `vm::firmware_bytes` and `vm::read_firmware` are `pub` and skip it. Only `firmware::bytes` calls the first today, but nothing enforces that.

**Suggested fix:**
- Reword the headline to "no table read from memory the map calls MMIO".
- Either refuse holes for `bytes`, since tables live in described ACPI, NVS, reserved or runtime memory, or map firmware reads that are not in ACPI memory uncached.
- Consider making `vm::firmware_bytes` `pub(crate)`.

### T71-4 — Low — A malformed `X_PM_TMR_BLK` drops a good 32-bit port. This is inconsistent with the fallback for a memory-space `X_` form.

**Where:** `firmware/acpi/tables/src/fadt.rs:523-529` (`port_block` requires `usable(Field::Block(PmTimer))`) and `:655-660` (`block_verdict` runs `check_register` on a non-null `X_` GAS); `framekernel/frame/src/acpi.rs:543-551`.

**Scenario:**
- `X_PM_TMR_BLK` has a reserved address space (0x0C to 0x7E) or a reserved access size (5 or more).
- `PM_TMR_BLK` is a valid port with `PM_TMR_LEN` 4.
- `block()` and `port_block()` both return `None`, so the kernel has no PM timer, and the census fails on a relied-on field.
- Before, the kernel read the 32-bit port.

§5.2.9 says the 32-bit field is used when the 64-bit one "can not be used by the OSPM". That is the rule departure 1 applies to a memory-space `X_` form, which is falling back correctly. It is not recorded as a behaviour change.

**Suggested fix:** in `parse_fadt`, fall back to the 32-bit port when the `X_` form fails only its GAS check, keeping `PM_TMR_LEN == 4` and the hardware-reduced rule. Or record the stricter behaviour as a behaviour change, with a test.

### T71-5 — Low — The PPTT now accepts a nine-cache chain from a node. This is unrecorded, and two docs describe the bound loosely.

**Where:** `firmware/acpi/tables/src/pptt.rs`:
- `:258-260`: a node no longer walks its resource's chain;
- `:164-165`: `parse`'s doc still says "a cache chain longer than [`MAX_CACHE_LEVELS`]" is refused;
- `:31-36`: `MAX_LOOKUPS` doc.

**Probe P3 (run):** a package node whose private resource heads nine chained caches. The base `b983bf6c` refuses it (`Cycle` at offset 0x38, the node's resource). The tip accepts it (10 structures). The `MAX_CACHE_LEVELS` doc mentions "one cache more". TASKS 71's behaviour-change list and `parse`'s doc do not. No real topology has nine levels, so this matters only for the record.

**Bound docs:**
- The `MAX_LOOKUPS` doc says "besides the two whole walks". `parse` walks three times: `Index::build` walks twice, then `parse`'s own walk.
- TASKS and the provenance entry explain 75 as "16 parents, itself, 58 private resources". The `+1` is the seventeenth parent lookup that shows a cycle, not "itself".

The bound of 75 lookups a structure holds by reading:
- a node makes at most 17 parent lookups and 58 resource lookups (a 255-byte node holds at most (255-20)/4 resources);
- a cache makes at most 9 lookups.

**Suggested fix:** record the acceptance change in TASKS 71's behaviour changes and fix `parse`'s doc. Or keep the old limit by having the cache check allow `MAX_CACHE_LEVELS - 1` next levels. Correct the two wordings.

### T71-6 — Low — F13's test cannot fail for an early refusal or for lookup cost, and the crate's documentation claims every parsed table.

**Where:**
- `firmware/acpi/tables/src/hostile.rs:414-438`: `let _ = checked(&t);` at `:423`; the comment "so each was measured large" at `:434`;
- `hostile.rs:400-410`: `step_bound`;
- `firmware/acpi/tables/src/lib.rs:131-133`.

**Measured** (`large_tables_measured`, run):
- NFIT: refused at both 100 and 400 copies. At 100 it stops at 709 steps on a repeated SPA range index; at 400 it stops at 1,025 steps on the structure count. Yet the test asserts each generated signature "was measured large".
- PPTT at 400 copies: 16,400 steps against a bound of 7,029,616.
- VIOT at 400 copies: 6,400 steps against 28,816.

The replicas' references all point into the first copy, so every lookup starts at checkpoint 0. The quadratic part of the PPTT's and VIOT's bounds can never be reached. Their large-table test cannot see a lookup-cost regression; F18's own test does that job for the PPTT.

**Coverage claim:**
- Because the result is discarded, a replica refused at its first structure passes for any signature.
- `lib.rs` says "Every table this crate parses has a test that builds a large one". Only the 12 generated signatures have one. The MPST, NHLT, RAS2, MISC, PDTT, SVKL, SLIT, RSDT and XSDT, among others, do not. By reading, the MPST is linear, so no cost defect follows.
- The contract's and TASKS' "required tests" say "per parsed signature". The departure list (item 5) says "every generated signature" without naming the narrowing.

**Suggested fix:**
- Assert `checked(&t).is_ok()` for every signature but the NFIT, which is named.
- Fix the `:434` comment and `lib.rs`.
- State the narrowing among the departures.
- Optionally, point replica references across copies so the PPTT and VIOT lookups walk.

### T71-7 — Low — Hardening of the census's live check.

**Where:** `framekernel/src/acpi_census.rs:533-551`, and `:137-153` (the doc of `consistent()`).

1. **Probe placement.** It probes only lends that start inside the structure: `(base, 36)` and `(middle, 8)`. A guard broken so that it misses ranges that start before the structure and run into it (an overlap test reduced to `b <= base && base < e`) passes at boot. Only the host test `what_the_firmware_changes_is_never_lent` catches that.
2. **The probe is itself the forbidden act.** When the guard is broken, the probe makes a `&'static [u8]` lend over memory SMM writes, and holds it for the kernel's life. This is acknowledged in the provenance entry, but avoidable: a non-lending query of the same predicate answers the question.
3. **Doc.** `consistent()`'s doc comment does not list the new condition.

**Suggested fix:**
- Probe through a non-lending check, for example `vm::would_lend(base, end)`, the registry's predicate without recording, followed by `firmware::bytes`' own pre-checks.
- Add a probe that starts before the structure and ends inside it.
- Update the doc.

## Checked and found sound

- **The registry (`reserved.rs:470-600`).**
  - `Lending::lend` checks `located`, the writable ranges and the never-lendable ranges before its early "already held" return.
  - The overlap test is half-open and symmetric.
  - `never_lend` deduplicates contained ranges, keeps a range that overlaps an earlier lend and reports it, and counts what does not fit.
  - `NEVER_SLOTS` (8) is at least `CHANGING_MAX` (5), so the locator cannot overflow it.
  - Everything is under the one `LENDING` lock, with interrupts off.
  - `firmware::bytes`' pre-checks (`changing_located`, `never_lent`) use separate lock acquisitions. Both facts only grow, so no time-of-check race can let a lend through. The registry re-checks under the lock.
- **Paths to a lend.** `vm::firmware_bytes` is called only by `firmware::bytes`, which is called only by `acpi_table`, the census and `aml_proof`. Before `located`, every lend is refused, from any processor.
  - Through an XSDT entry: the header is compared by copy, and only the asked-for table is lent through the registry.
  - Through a pointer into the middle of a located structure: refused.
  - Through a second FACS: guarded when it begins with `FACS`.
- **The first lookup's order** (hand-over addition 2).
  - `changing_ranges` is handed only a copy closure. It cannot lend or call `acpi_table`, so there is no recursion.
  - It uses only stack buffers, about 1.8 KiB at most. It allocates no heap; the frame pool for page tables was already used by every copy before.
  - `record` runs before the first lend. `CHANGING` is a `SetOnce`, which allocates nothing.
  - In `kernel.rs`, the first lookup (`adopt_firmware_uart`, line 182) comes after the page tables and before the heap.
  - The host test `the_first_lookup_records_before_it_lends` checks the order.
- **`unsafe`.** None added. No `// SAFETY:` comment was changed. Those in `vm.rs` (`read_firmware`, `firmware_bytes`) and in `once.rs` remain true; `firmware_bytes`' is now better supported. On `timer.rs:413`, see T71-8.
- **The MMIO check** is in both `bytes` and `copy`. It refuses any overlap with an `Mmio` region, including a range straddling an entry's edge. `EfiMemoryMappedIO` and `EfiMemoryMappedIOPortSpace` both map to `Mmio` (`boot/uefi/src/memmap.rs:64`). With no kernel space, `read_firmware` refuses anyway. Holes: see T71-3.
- **The FADT rules against ACPI 6.6.**
  - §5.2.9 says the `X_` form is preferred when it is non-zero *and usable*, else the 32-bit field. The memory-space fallback is right.
  - On a hardware-reduced platform the OS ignores offsets 46 to 108 and 148 to 232, which covers `PM_TMR_BLK` (76), `PM_TMR_LEN` (91), `CENTURY` (108) and `X_PM_TMR_BLK` (208). It also ignores flag bits 1, 2, 3, 7, 8, 13, 14, 16 and 17, which includes `TMR_VAL_EXT`. So no PM timer, no century and no 32-bit flag there is correct.
  - `IAPC_BOOT_ARCH` (109) is outside the ignored range, so the 8042 and CMOS-absent flags are still read. The 8042-from-revision-2 rule is unchanged.
  - `PM_TMR_LEN` must be 4 when a timer exists.
  - §4.8.3.3: the timer may be in I/O or memory space and is read as 32 bits.
  - §5.2.10: a FACS is 64 bytes or larger, so the minimum of 64 is right.
  - §5.2.24.8 and §5.2.24.11: the FBPT's and MBPT's length includes space allocated for records, so the header's length is the right extent.
- **Through the callers.**
  - `timer.rs` `pm_timer`, `time.rs` `init` and `prove_pm_timer`, and `i8042.rs` `init` read the same `acpi::Fadt` fields.
  - The changes reach them only for: a FADT with no DSDT (ruling 1a: also no CMOS-absent flag and no 8042 flag, so both are probed); a hardware-reduced platform (an improvement: a stray `PM_TMR_BLK` there was read before); and a differing `X_` form.
- **Crate robustness.**
  - The new crate code reads only through checked readers. `facs_pointers` handles any prefix. Every `clamp` has `min <= max`.
  - `changing_ranges` slices fixed arrays with constant ranges, or through `get_mut`.
  - The crate's tests pass, the hostile soak included.
- **F18.**
  - The bound of 75 lookups a structure holds (T71-5 covers the doc).
  - Each lookup is at most `ceil(n/64) + 1` steps (`walk.rs:240-262`).
  - AT-H2 reproduces: the old walk takes 1,586,944 steps, which fails the bound of 1,307,648, by about 21 %. The new walk takes 295,168.
  - A cycle of caches reachable from a node is still refused, by the caches' own checks.
- **F13 for the other generated signatures.**
  - At 400 copies: MADT 5,200 steps (bound 20,816); SRAT 2,000; CPEP 800; MSCT 1,600; PMTT 3,200; FPDT 2,400; SDEV 2,000; HMAT 2,400; PHAT 2,000.
  - None is refused. Each bound is 4 steps a structure, so a quadratic regression would fail it.
  - The PMTT's step counter is now counted.
- **The census's printing.**
  - New lines print only physical firmware addresses and ports. Ranges use `0x…-0x…` with an inclusive end, the form `iommu.rs:405` already uses; the PM timer port uses the form `time.rs` already prints.
  - No virtual address and nothing in the stack region is printed (ADR-0004 A6).
- **The other controls, by reading.** I checked that AT-6, AT-9 and AT-10 fail their named host tests, and that AT-H1 fails `mmio_is_named_by_the_memory_map_alone`.
- **Records.**
  - Nothing claims KVM or physical-hardware results.
  - STATUS, TASKS and the provenance entry each say "not shown under KVM or on a physical machine", and say that no review has been made.
  - The commit list matches `git log`.
  - The provenance table's three rows name item 71.
- **The six departures.**
  1. The memory-space `X_` form falls back to the port: right per §5.2.9 (but see T71-4).
  2. The FACS as §5.2.9 chooses it, plus a second only with the `FACS` signature: right for the 32-bit field. The same reasoning applies to the chosen pointer and the FPDT's, and is not applied (T71-2).
  3. F18 without a bitset: correct and bounded, but with an unrecorded change in what is accepted (T71-5).
  4. The live check: worth having, but circular and outside the verdict for coverage (T71-1, T71-7).
  5. F13 at "every generated signature": a narrowing of the contract's "every parsed signature" that is not stated as one, with an overclaim in `lib.rs` (T71-6).
  6. The locator's limits: reasonable values, but going past one fails nothing (T71-1).
