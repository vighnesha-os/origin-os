One independent AI reviewer (a fresh Claude Code agent given the diff, not the author's conclusions), 2026-11-21. Kept as written; the answers are in TASKS item 116's entry and in the commit that names them.

How this review was done: by reading only. I ran no build, test, QEMU or cargo command. I read no other project's source. ## Findings

### R116-1 (Medium): if `ResetSystem` hangs, the result looks exactly like reading A
**Where:** `boot/uefi/src/main.rs:1580-1600` (`bench_reset`).

**What is wrong:** the FADT fallback runs only if `ResetSystem` returns. A firmware `ResetSystem` can also do neither of the two things the design expects: it can neither reset the machine nor return. Examples:
- a reset-notify callback that calls a boot service after `ExitBootServices`;
- a fault taken by the firmware's exception handler, which then loops forever.

The firmware console then stays silent, and no reset follows. That is exactly what reading A looks like. Amendment 3 rejected "FADT register alone" because "a reset that does not happen would read as the call never returning". The same objection applies to a `ResetSystem` that hangs, and the change does not address it.

**Failure scenario:**
1. On rental E, `ExitBootServices` returns (B2: the port is switched off).
2. AMI's runtime `ResetSystem`, called after `ExitBootServices` with interrupts masked, spins.
3. The console shows `X` and then nothing, forever.
4. The rental is recorded as A.

**Suggested fix:** give the rental a positive control that the tool allows. For example, a `BENCH-AFTER` value (say `control`) that calls `ResetSystem` after the same 5 s wait but *before* `ExitBootServices`. Run it as the rental's first boot. This shows that the bench loader's `ResetSystem` call resets this board and that the reset is visible on its console. It is weaker than a call made after `ExitBootServices`, but it is evidence. Also state the reading rule in the records: "no reset" means A, or a `ResetSystem` that hung after the call. If the owner wants this to be decisive, an alternative is to write the FADT register first when it is a plain I/O reset port (`0xCF9`-like). That reverses Amendment 3's order, so it is the owner's call.

### R116-2 (Medium): in reading B1, the one line that survives does not say how `ExitBootServices` ended
**Where:** `main.rs:715-719` and `745-750` (ordering); `bench.rs:408` (`AfterCall`'s `Display`); `bench.rs:698` (`ResetSoon`).

**What is wrong:** after the call, the outcome line is written first, while the UART is still as the firmware's exit left it. That is `bench_exited`'s "exited on the first call" or decision item 342's halting line. Only after that are the firmware's values written back. Under B1 (the divisor or line control changed), the outcome line comes out garbled. The first line that is readable is `AfterCall`, and both it and `ResetSoon` leave out the call statuses.

So the rental would learn "B1, and here are the changed registers" without learning whether the call succeeded. In reset mode the halt path also resets the machine. Under B2 the reset alone therefore cannot tell success from a failure either. The only exception is the `Y` mark, which shows that the first call returned `EFI_INVALID_PARAMETER`.

**Failure scenario:**
1. The first call returns `EFI_DEVICE_ERROR`, and the firmware's exit changed the divisor.
2. The halting line is unreadable, and `AfterCall` is readable.
3. The record says the call returned, with no status.

**Suggested fix:**
- Include `ExitCalls` (each call's status) in `AfterCall`, or write the `Exited`/`Halting` line again after `write_back`.
- For B2, make the outcome visible through the reset itself. For example, wait 5 s after a successful call and 15 s after a failed one. Print that schedule in `ResetPlan`, on the firmware console before the call.

### R116-3 (Medium): the rental tool does not understand the new outcome, and the machine reset-loops
**Where:** `developer-tools/bench/latitude.py:1063` (`breadcrumbs`), `:1083` (`boot_result`), `:1107` (`last_boot`), `:1172-1176` (the install), and `write_record`.

**What is wrong:**
1. **A reset loop.** The install copies the bench loader over the file of the firmware's *first* boot entry. Each reset therefore boots the bench loader again, and the machine resets every POST plus about 10 s, for the whole `--boot-minutes` window and every later `--boots`.
2. **No verdict from the tool.** `boot_result` never ends on a reset. It reports "no verdict; last line: …" for both A and B. `breadcrumbs()` keys on the last `origin-boot:` line, which is now one of the raw lines or a later cycle's line, so its result no longer means anything. The record draft still says "developer-mode loader".
3. **No timing.** A trustworthy B verdict needs the reset to come about 5 s after `X`, not minutes later. Minutes later would mean the UEFI 5-minute watchdog or a BMC watchdog. Rental D saw none in 8-minute windows, but that is not a guarantee for rental E. `sol.log` has no timestamps. `sol-events.log` records only when sessions drop, so the time from `X` to the reset can be recovered only indirectly, from POST length.

**Failure scenario:** rental E ends with `boots.json` and a record draft that say "no verdict" for every boot. The verdict then rests on reading a log of several POST cycles by hand, with no time from `X` to the reset.

**Suggested fix:**
- Teach `boot_result` the item 116 reading:
  - a firmware restart after the loader's last line (the BMC session drop logged in `sol-events.log`, or the BIOS banner reappearing) ends the boot as B, with the time since `X`;
  - no restart within N minutes is A.
- Timestamp console arrival: log an event when `X` or the loader's last line is first seen.
- Default `--boots 1` for a reset build, or make clear that the loop is expected.
- Fix the "developer-mode loader" text in the record draft.

### R116-4 (Low): a slow `Stall` can stretch the 5 s wait without limit
**Where:** `bench.rs:640-646` (`ticks_per_ms`); `main.rs:1487` (`count_ticks`).

**What is wrong:** a counted rate has a lower bound (at least 1 tick a millisecond) and no upper bound. If the firmware's `Stall(20 ms)` overruns badly, every wait grows by the same factor. Causes include a miscalibrated timer library, SMIs, or a stall that rounds up to a coarse tick. For example, if `Stall` takes 2 s, the "5 s" wait becomes about 8 minutes. That outlasts the tool's per-boot window and reads as A.

**Suggested fix:** clamp a counted rate to at most `ASSUMED_TICKS_PER_MS`, since no counter runs faster. Optionally add a floor of about 100 MHz, and say on the console when either clamp was applied.

### R116-5 (Low; I am unsure of AMI's behaviour): interrupts stay as the firmware's exit left them until `bench_reset`
**Where:** `main.rs:713-720` and `744-751`; `cli` at `main.rs:1570`.

**What is wrong:** between the return from `ExitBootServices` and the `cli` in `bench_reset`, the loader does several things: the outcome line, the register read, the TEMT wait, the write-back and the `AfterCall` line. Each can wait up to `POLLS` status reads, so the gap can reach a few hundred milliseconds on a slow or stuck UART.

If a firmware leaves IF set and a timer source armed after exit, a tick enters torn-down DXE code. That code could hang, which reads as A. In kernel mode the entry stub already masks interrupts, so masking earlier changes nothing there. Separately, after `ResetSystem` *returns*, IF may have been set again by the firmware, and the 2 s and 1 s waits run that way.

**Suggested fix:** in bench builds, make `cli` the first statement of both the `Exited` and `Halt` arms, and repeat it after `reset_system(...)` returns.

### R116-6 (Low): the register read before the call opens a DLAB window while firmware interrupts are live
**Where:** `bench.rs:292-312` (`UartState::read`), called from `main.rs:1463`.

**What is wrong:** under boot services interrupts are enabled, and firmware timer callbacks (TPL_CALLBACK or TPL_NOTIFY) can preempt the loader. If a callback in the firmware's serial or terminal driver *writes* offset 0 or 1 while DLAB is set, it writes DLL or DLM instead of THR or IER. That would change the console's divisor, which is the B1 symptom the bench is trying to diagnose, created by the bench itself. A callback that only reads, as an input poll does, gets DLL instead of RBR, which does no harm. The window is a few I/O cycles, so this is unlikely.

**Suggested fix:** wrap the read in `RaiseTPL(TPL_HIGH_LEVEL)` and `RestoreTPL`, or in `pushfq; cli … popfq`. (`raise_tpl` and `restore_tpl` are already in `BootServices`.)

### R116-7 (Low): the marks lengthen the window between `GetMemoryMap` and `ExitBootServices`
**Where:** `main.rs:693-702`.

**What is wrong:** `X` and `Y` each wait for THRE before every byte, which in FIFO mode means the FIFO is empty. Written right after the firmware's last console line, `X` waits for that line's FIFO to drain, up to about 6 ms at 115200 baud with a 64-byte FIFO. On a UART that never shows THRE, it waits up to `POLLS` reads (about 0.1-0.2 s on LPC or eSPI) before giving up.

Any timer event that changes the map in that window makes the call return `EFI_INVALID_PARAMETER`. If that happens twice, the loader halts, and in reset mode it then resets. The bench would then have caused a failure that it reports as the call returning.

**Suggested fix:** before `exit_boot_services` (and so before `GetMemoryMap`), wait for TEMT with the usual bound, so that the mark itself costs only about three character times. Skip the marks if the `BEFORE_CALL` writer stopped, which is when `Uart::stopped()` is true.

### R116-8 (Low): untrusted-input edges in the FADT walk
**Where:** `bench.rs:479-560`.

**What is wrong:**
- **Port 0 is accepted.** A `SystemIo` reset register with address 0 is accepted as port 0, and the loader would write the reset value there. The memory path refuses address 0, and in ACPI a GAS with address 0 names no register.
- **Two refusals stop the walk.** `TooLong` (`:518`) and `Unreadable` (`:523`) end the walk at once. A refused parse instead moves on to a later FADT. That contradicts the doc comment ("the first FADT whose header checks"). It is harmless, because a firmware should list one FADT, but the comment and the code should agree.

**Suggested fix:** refuse `gas.address == 0` for I/O too, for example as `NotSupported`. Either make the comment match the code, or continue the walk on `TooLong` and record the reason, as for `refused`.

### R116-9 (Low): `ResetSoon` promises a reset that may not exist
**Where:** `bench.rs:698-712` and `main.rs:1574-1578`.

**What is wrong:** if there is no `ResetSystem` (`Tried::Unavailable`) and the FADT gave no usable register, the line still says "a reset through the FADT's reset register in 7 s". The `Fallback` line 7 s later then says "halting". The console briefly states something false. The texts "5 s", "2 s" and "7 s" are also written out by hand rather than formatted from `RESET_DELAY_MS` and `FALLBACK_DELAY_MS`.

**Suggested fix:** choose the wording from `plan.register.is_ok()`, and format the numbers from the constants.

### R116-10 (Low): what the xtask checks can and cannot prove
**Where:** `developer-tools/xtask/src/main.rs:7354` and `:7427`; `developer-tools/xtask/src/bench.rs:543` and `:673`.

- **`exited` does not prove a reset.** Under `-no-reboot`, a triple fault exits QEMU just as a reset does. So would a QEMU crash, or the stdout reader thread ending on a read error, which `closed` treats as an exit.
  - Scenario: `ResetSystem` faults with a broken IDT, causing a triple fault, and "the reset through ResetSystem" passes.
  - This is unlikely under OVMF, whose exception handler loops forever instead.
  - Fix: also require QEMU's exit status to be success, and require COM1 to hold no firmware exception dump.
- **The disturb scenario checks only the MCR write-back.** QEMU's chardev ignores the divisor, so a `write_back` that left the divisor out would still pass. The host test `writing_back_undoes_what_a_firmware_might_do` does cover the divisor, so this is a gap in the boot scenario only.
- **The normal-loader scenario does not check that the bare `X`/`Y` marks are absent.** The marks lack the "bench build" text that F2 and `check_normal_loader` search for. A leak is prevented by construction (`cfg`), but no runtime check would catch one.
- **Stale comment:** the doc on `boot` (`bench.rs:718-719`) still says "the four scenarios".

### R116-11 (Low): `read_bench_file`'s NUL termination now depends on the caller
**Where:** `main.rs:1364-1390`.

**What is wrong:** the SAFETY comment on `Open` says the path is NUL-terminated because "the array is longer than the ASCII path". Now that the function takes any `name`, that holds only while every caller passes fewer than 64 bytes. Both current constants are short (25 and 23 bytes). A future name of 64 bytes or more would be zipped to exactly 64 units with no NUL, and `Open` would read past the array.

**Suggested fix:** add `if name.len() >= path.len() { return None; }`, or a `const` assertion on the two constants.

### R116-12 (Low): SAFETY and doc comments that are not quite true
**Where:** `main.rs:1266-1290`.

- **`LoaderPorts::write`** says FCR is "put back to what was read under the firmware". FCR is write-only, and the loader writes `0x07` to it. The comment also does not mention disturb mode's deliberate loopback and divisor writes.
- **`LoaderPorts::read`** implies that reading MSR is the only read with a side effect. Reading LSR clears OE, PE, FE and BI, and the receiver line-status interrupt. That matters only for the firmware's view of line errors, but the comment should not claim otherwise.

## Checked and found correct

- **Runtime services table.** `ResetSystem` is at offset 104: a 24-byte header, then 10 pointers from `GetTime` to `GetNextHighMonotonicCount`, then `ResetSystem`. `RUNTIME_SERVICES_SIGNATURE` (`0x5652_4553_544E_5552`) is "RUNTSERV" in little-endian. The check `HeaderSize ≥ 112` is right, and so are the alignment and null checks.
- **`ResetSystemFn`.** It is `extern "efiapi"` (win64), with `EFI_RESET_TYPE` as `u32` in ECX, `Status` (`repr(transparent) usize`) in RDX, `UINTN` in R8 and `VOID*` in R9. It returns `()`, not `!`, which is correct because a non-conforming firmware may return. `EfiResetCold` is 0. A NULL `ResetData` with `EFI_SUCCESS` is allowed.
- **`StallFn`.** `misc[1]` is `Stall` (the order is `GetNextMonotonicCount`, `Stall`, `SetWatchdogTimer`), and `boot_services()` checks that `HeaderSize` covers `misc`. Transmuting a pointer to `Option<fn>` is size-correct, and null becomes `None`. The argument is `UINTN` microseconds.
- **Inline assembly.**
  - `out dx, al` (reset register and UART) and `in al, dx` correctly claim `preserves_flags`.
  - `cli` correctly does not claim it.
  - The memory reset register is a single volatile byte store, made only to a nonzero address in a region of type 11 or 12 (`Mmio`), which UEFI 2.11 §2.3.4 keeps identity-mapped in the page tables that are still loaded.
- **Between `GetMemoryMap` and `ExitBootServices`.** Only `key_for`, `calls.made()` and `say_on_uart` run there. That is port I/O plus `core::fmt`: no allocation and no firmware call. `Stall`, the runtime-table read, the UART read and every console line come before the final map is read.
- **16550 layout.** DLL/RBR/THR at 0; DLM/IER at 1; FCR at 2, which is write-only (IIR is never read); LCR at 3, with DLAB as bit 7; MCR at 4, with loopback as bit 4; LSR at 5, with THRE `0x20` and TEMT `0x40`; MSR at 6; SCR at 7. The receive buffer is never read with DLAB clear. `read` puts LCR back as it found it. `write_back` writes the divisor under DLAB, then clears DLAB, then IER and MCR, and writes FCR (`0x07`) last, after waiting a bounded time for TEMT. Nothing in flight is cleared.
- **FADT walk.**
  - The RSDP and XSDT are checked by the SPCR walk's shared checks.
  - Every byte is read through `read_described`, which refuses undescribed, MMIO and unaccepted memory and ranges that wrap. Entry addresses therefore lie inside the XSDT that was read and checksummed.
  - The length is bounded to 1024 bytes. A declared length under 36 is refused by the shared `header::check` (declared must equal available), and the walk moves on.
  - The kernel's parser enforces `RESET_REG_SUP`, 8 bits at bit 0, a defined access size and an allowed space. The loader adds: no PCI configuration space, no port above `0xFFFF`, and memory only in MMIO regions.
- **Arithmetic.** `in_mmio` uses `checked_sub` and `saturating_mul`. `wait_ms` uses `wrapping_sub` and `saturating_mul`. `ticks_per_ms` cannot divide by zero, and a count of fewer than 20 ticks falls back to the assumed rate.
- **Normal images.**
  - Every new item in `main.rs` is under `#[cfg(origin_bench)]`, and `bench` is compiled only under `cfg(any(test, origin_bench))`.
  - In `spcr.rs` the change is visibility only (private to `pub(crate)`), which stays crate-internal.
  - The normal release loader in `target/` contains no Origin source path, only one from `core`. The inserted lines therefore move no panic location inside it.
  - I did not rebuild, so the claim that the images are byte-identical rests on the author's evidence.
- **xtask harness.**
  - The ESP is rebuilt for each scenario, so no switch file carries over to the next one.
  - `-no-reboot` is in `qemu_command`.
  - The reset scenarios require exact line lists after the loader's last line. A `ResetSystem` that returns (the `Fallback` line) or a FADT write that fails to reset (`NOT_RESET`) therefore fails the check.
  - The disturb check requires the first-call line to be *absent*, which shows that loopback took effect, and requires `AfterCall` to show loopback and a different divisor.
  - The halt check now requires that QEMU did not exit.
  - The quiet loop now treats a disconnect as the end of the window.
- **`latitude.py`.**
  - Under `set -eu`, each `test ! -e …` stops the install.
  - The new test ties `BENCH_SWITCHES` to every `"\\EFI\\ORIGIN\\BENCH-*"` literal in `bench.rs`, and its regex matches the Rust escaping.
  - The installed message lists both switches.
