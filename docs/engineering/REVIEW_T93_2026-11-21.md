### 4. Findings

#### R93-1 (Low) `tlb::mark_online` uses a section-derived per-processor flag after the section, with no witness

- **Where:** frame/sync/src/shootdown.rs:590-599, frame/src/tlb.rs:153-155.
- **Defect:** `Shootdown::mark_online` reads the index in a section, but the `&AtomicBool` that `self.online(index)`
  returns (lifetime of `self`, not of the witness, since `TlbHardware::this_cpu` returns a bare `usize`) is stored to,
  and the TLB flushed, after the section ends. The public entry `origin_frame::tlb::mark_online()` takes no witness.
- **Failure:** a caller that is not a flow (none today: `run_ap` at src/sched.rs:1117 and `prove` at 2122 are flows)
  reads index A in the section and is preempted on its exit. Once S6 moves threads, it is moved to B, then marks A
  online and flushes B's TLB. A becomes a shootdown target without its full flush. A later request can find A
  online, and an address space can be freed while A still caches translations from before it came online. This is
  stale-TLB use after free. The doc comment ("Its callers are the processors' boot and idle flows") is the only
  guard. This is the one place where N3 is not held by the compiler.
- **Fix suggested:** give `tlb::mark_online` a `Pinned` parameter, or do the store, fence and `invalidate` inside the
  section.

#### R93-2 (Low) `Switch::new` is `pub(crate)`, so any `origin_frame` module can make a `Here` outside a section

- **Where:** frame/src/trap.rs:36-39 (`pub(crate) const fn new`), 44-46 (`Switch::here`).
- **Defect:** the docs (trap.rs:54-65) say only trap.rs's three makers can make a `Here`, and that no other module can.
  But any module in `origin_frame` (tlb, random, smp, timer, stack, …) can write `Switch::new().here()` in thread
  context, with interrupts on. No gate restricts `Switch::new` to `dispatch`; `xtask` has none. `Switch::new` was
  already `pub(crate)` at `0b90dea8`, but `here()` widens what a stray call can do.
- **Failure:** a future helper in `frame/src/tlb.rs`, called from a movable thread, does
  `INTERRUPTS.this(cpu::this_cpu(Switch::new().here()))`. It compiles, and with interrupts on the thread is
  preempted between the read and its use, then moved, and so updates another processor's entry. Only `dispatch` calls
  it today (cpu.rs:1239-1430).
- **Fix suggested:** build the `Switch` in a trap.rs function that only `dispatch` calls (for example a private
  constructor plus a `pub(crate) fn entry<R>(f: impl for<'s> FnOnce(&'s Switch) -> R)`), or add a token gate that lists
  `dispatch` as `Switch::new`'s only caller.

#### R93-3 (Low) The boot flow's witness exists before GS is set, so safe code can make `read_index` read a GS that is not set

- **Where:** src/kernel.rs:67 (witness taken before `early.load_cpu_tables()` at :146); frame/src/trap.rs:284-292
  (`!tables_ready()` ⇒ flow); frame/src/cpu.rs:1035-1040 (`read_index`'s SAFETY: "`load_tables` set GS's base … before
  any code that calls this runs").
- **Defect:** `flow` is valid from the top of `kernel_main`, but `cpu::this_cpu(flow.here())` is only sound after
  `cpu::init`. Safe code holding `flow` breaks `read_index`'s unsafe precondition if it calls `this_cpu` in that window.
  `tables_ready()` is one global flag, so the same holds on an AP between the trampoline and `init_ap`
  (`trap::flow` would read GS there; it is called only after `init_ap` today).
- **Failure:** today both early uses are guarded. `prove_user_isolation(flow, …)` (kernel.rs:126) returns before its
  read because the heap has not started, and `timer::init(flow, …)` (kernel.rs:128) checks `tables_ready()` first
  (timer.rs:495). A reordering, or a new boot step between kernel.rs:67 and :146 that reads the index, runs
  `mov gs:[0]` with the firmware's GS base. That gives a fault under the firmware's IDT (a reset), or a garbage index
  used for `PerCpu` lookups. Before this change the old `this_cpu()` was just as callable, so this is not a
  regression. But the witness now says the read is valid.
- **Fix suggested:** take the boot flow's witness after `load_cpu_tables`, and restructure the out-of-turn checks
  (kernel.rs:125-128) to take it later. Or make `trap::flow` refuse while `!tables_ready()` and give the out-of-turn
  calls a separate path.

#### R93-4 (Low) `X2Apic` handles made under a witness carry no lifetime and are `Send`

- **Where:** frame/src/timer.rs:94 (`pub struct X2Apic(())`, auto `Send + Sync`), 105 `enable(me)`, 125 `here(me)`.
- **Defect:** "this processor's local APIC" is a value derived from the index (N3: "anything derived from it"). The doc
  says "Its uses stay in that witness's life", but the returned handle is owned and `'static`, so the type does not
  enforce that.
- **Failure:** a thread writes `let lapic = { let p = sched::pin(); X2Apic::here(cpu::this_cpu(p.pinned().here())) };`,
  is moved, and later `lapic.stop()` / `timer::start_periodic(&lapic)` writes the timer MSRs of the processor it now
  runs on. That processor may not have x2APIC mode marked ready, and the processor it read under keeps its timer.
  Today every handle is held by a flow (`timer::init`, `smp::start`, `run_ap`, `sched::prove`, `stop_boot_processor`)
  or used within the call (`send_reschedule_ipi`, `send_nmi_to_self`, `interrupt_self`, `programmed`).
- **Fix suggested:** `X2Apic<'a>` holding a `PhantomData<Here<'a>>`.

#### R93-5 (Info) `ThisCpu::index()` is documented as "a value only", but several sites index per-processor tables by it

- **Where:** frame/src/cpu.rs:1802, 1814; frame/src/random.rs:297; frame/src/tlb.rs:85; src/console.rs:1864, 1943;
  src/pcie.rs:235; src/kernel.rs:1802.
- **Defect:** each of these is correct today, under a section, the trap entry or a flow, but the compiler does not
  check it. `PerCpu::get(me.index().get())` compiles and gives a `&'static T` that outlives the witness, and
  `TlbHardware::this_cpu` turns the index into an unbranded `usize` for the shootdown protocol. The Loom control at
  developer-tools/xtask/src/loom.rs:1083 shows that the index can leave its section and still compile.
- **Note:** this limits "a site without a witness does not compile" to the read itself, not to its uses.

#### R93-6 (Low) The preemption/fair-share worker's hot loop gains an interrupts-off section per iteration

- **Where:** src/sched.rs:1190-1195.
- **Defect:** the loop that times its own running steps (`RUNNING_STEP` = 3 ms) and records where it ran now runs
  `pushfq; pop; cli; store; sti` every iteration, where it ran one GS load before. The coordinating session's Q8 ruling
  asked for this. But it changes the timing proofs' hot loop, and the plan's acceptance is "no change of behaviour".
- **Failure:** under QEMU's software processor, `sti` ends a translation block, so each iteration is slower and
  timer ticks that land in the window are held for the interrupt shadow. With a 3 ms step bound, the progress
  accounting should not change. But the project's own record (preemption-proof and timing-window failures on the
  65-, 67- and 288-processor machines) says a change to these loops needs boot-matrix evidence on those machines
  before it is trusted. The same applies, to a lesser degree, to `reap()`'s new section in `yield_until_away_for`

#### R93-7 (Info) `Record::pin`/`unpin` are `pub` on any `&Record`, which other threads' code can reach

- **Where:** frame/sync/src/threads.rs:210-235; other threads' records are reachable through

- **Defect:** "only the running thread writes it" is a convention. `unpin()` is a plain load and store (Relaxed), so

  `record.unpin()` on a thread that is not running could drop the pin `end_with` raised, and the mover would then
  move an ending thread (N5).

#### R93-10 (Info) One `Here` type covers both "interrupts off, never switched" and "may be switched, stays on its processor"

- **Witness makers:** `Here::new` and `Pinned::new` are private to `trap`; struct literals are private by field
  visibility; `ThisCpu`'s fields are private to `cpu`. `Here`, `Pinned` and `ThisCpu` are `Copy`, not `Send`, not

  `host_section` and `host_mint` are `cfg(not(target_os = "none"))`; only the kernel depends on `origin-frame`, so
  they are absent from every shipped image. `PIN_MINT` is private to sched.rs, so only sched.rs can call
  `pinned_for_good`. The exception is R93-2.
- **Pin count:** overflow stops the kernel (`raise_pin`), and so does underflow (`PinGuard::drop`). `PinGuard` is not
  `Send`, so it is dropped by the thread that raised it, on the processor it is pinned to. `mem::forget` leaks a pin:

  over-pins), and repeated leaks end in the overflow stop. The count shares the record's first 16 bytes; the kernel
  asserts 128 bytes (src/threads.rs:58-61). The writes are plain, by the running thread, ordered to a future mover
  by the queue lock of its switch-out; the one other writer is `Block::take`, under the spawn's queue lock.
- **Unsafe:** no new `unsafe` block. The changed `unsafe fn`s (`enable_smep_smap`, `tlb::enable_global_pages`,
  `X2Apic::enable`) keep their contracts. `irq::run`'s transmute still round-trips the same `Handler` type. The
  SAFETY comment in `step_here` was updated. `read_index`'s SAFETY precondition: see R93-3.
- **Loom/core:** frame/sync/src/threads.rs, shootdown.rs and models.rs use `core` and `prim` only (the GAT
  `type Here<'a>: Copy` included); `framekernel/src/runqueue.rs` is unchanged. Every Loom control's `from` text in

- **Trap entry:** every `Here` built in `dispatch` is built while IF=0. The syscall and user-fault hooks, which enable
  interrupts, get no witness and return with IF=0 before the `resume` witness is built.

### Answers to the questions

#### 1. The worker (#14)

**(a) Is a running thread's own `location()` the processor it runs on, at every read in the loop?** Yes, in the
kernel as it is.
- Where the location is written, in `origin_sync::threads` (frame/sync/src/threads.rs):
  - `set_location` stores with Release (:174-176); `clear_location` stores `CLEAR` (:180-182); `location()` loads
    with Acquire (:166-170).
  - The module docs (:10-14) say it is written only under the lock of the queue it names: by a spawn, by the exit,
    and later by a move, which holds both queues' locks.
- Where the kernel writes it. There are exactly two writes:
  - `set_location` in `spawn_with_parts` (sched.rs:1116). It runs under the target queue's lock, after the push, as
    `Location::new(index, slot)`, where `index` is the `cpu` the thread is queued on (sched.rs:1077).
  - `clear_location` in `on_exit` (sched.rs:899). It runs under the queue lock, in the call that frees the slot.
- Why that is the processor it runs on:
  - No mover exists, so between spawn and exit a kernel thread's location is constant: `Some(cpu = its spawn target)`.
  - A thread queued in `QUEUES[cpu]` is resumed only by the processor whose index reads `cpu`, because `with_queue`
    uses `QUEUES.this(this_cpu(…))` (sched.rs:680-681).
  - The worker runs only between its spawn and its exit, and it is not resumed until the spawn's lock is released,
    after `set_location`.
- After S6: ADR-0020 S4 and S6 change the location only while the thread is ready, under both queues' locks. So it
  will name the new processor before the thread runs there.
- One case that is not exact: a move between the worker's `location()` load and its `r.store` would record the
  previous processor until the next iteration. The old per-iteration section existed to rule that out. It cannot
  arise today, because nothing moves and kernel threads are spawned pinned (S2). See D93-3.

**(b) Is `RAN_ON` filled from the location equivalent, for "both workers last ran on id"?** On a correct kernel,
yes.
- `workers_on` (sched.rs:1968-1974) compares `RAN_ON` with `id + 1`.
- `spawn(id, worker, …)` (sched.rs:1960) sets the location to `id`, numbered as the CPU index. `u64::from(at.cpu()) +
  1` gives the same value the old `this_cpu(here).index().get() as u64 + 1` gave.
- So `run_correct` and the per-CPU line give the same verdicts as before on every correct run.

**(c) What does the clause stop catching? Is it caught elsewhere?** This is D93-1. The clause now compares the
worker's spawn target with itself, by way of the scheduler's record. It no longer checks the processor's own view
(its GS index) of where the worker ran.
- What it no longer catches, and what else covers each:
  - **A frame resumed by another processor** (the double-resume or cross-processor-resume family). Covered: the
    table of contexts refuses a frame this processor never saved. `resume` panics on `Refused::NeverSaved`
    (frame/src/cpu.rs:962-990). The integrity proof's "running on" word (ADR-0020 S5, TASKS 96) is to come.
  - **A processor running another processor's queue**, because its CPU-local index is wrong or shared. Covered at
    start-up only: `init_cpu_local` checks the APIC ID, `ap_entry` checks `mine` (frame/src/smp.rs:1157-1166), and
    `Proof::Processors` runs. Two processors sharing an index would share `CONTEXTS[id]` as well, so the
    `NeverSaved` check would not separate them. Nothing after start-up checks it, but GS's base is never rewritten
    after `load_tables`.
  - **A future mover that runs a thread elsewhere without updating its location.** Not covered until TASKS 96's
    integrity proof and S5's word exist.
- The record of this clause, ADR-0013's "and ran there" (docs/adr/ADR-0013-boot-proof-policy.md:804) and TASKS 66's
  invariant (3), still says the processor itself was observed.

**(d) What if `current_thread()` or `threads::record` gives `None`?** It fails closed. D93-4 has the detail.
- `mine` is `None`, so every iteration stores 0 into `RAN_ON`. `workers_on` then sees `right_cpu == false`, so
  `run_correct` is false: the run fails at once and is never repeated, and `Proof::Preemption` records false.
- `current_thread()` is `None` only on a flow, and the worker is a thread.
- `threads::record(number)` is `None` only for a number outside the blocks, and the worker's own number was handed
  out by `threads::take`.
- So neither happens in a correct kernel. If one did, the failure line would not say why.

#### 2. `wake` (#8)

**(a) Is every lock `KernelQueues::locked` takes held with interrupts off? Can `KernelQueues` be made anywhere but
`within`?** Yes to the first, no to the second. D93-5 has the full check.

**(b) Does interrupts-off last longer where it should not? Does any lock order change?**
- Interrupts now stay off across the whole of `origin_sync::threads::wake`, the compare and the reschedule IPI's
  ICR write. Before, `locked` opened its own section per attempt, and the compare and IPI had a second section.
- Today, with no moves, that is one attempt. The only added off time is one Acquire load of `location()` before
  the lock, `WAKES_FOLLOWED`'s add, and the interrupt window that used to sit between the unlock and the IPI. That
  window is gone, so an interrupt that arrives there now waits until after the IPI: a few instructions.
- The IPI was already sent with interrupts off.
- Once moves exist, all of a wake-up's retries, up to `WAKE_TRIES` = 64 attempts each taking a different queue's
  lock, run with interrupts off, with no window between them (D93-2).
- The lock order is unchanged. The same single queue lock is taken per attempt, and nothing else is locked while it
  is held (`wake_slot` is `RunQueue::wake`, data only). `WaitQueue::wake_one` and `wake_all` release the wait
  queue's lock before calling `sched::wake` (frame/sync/src/wait.rs:193-195, 205; framekernel/src/wait.rs:106-119).

**(c) Is the index read under the same witness, and used only inside it?** Yes.
- `cpu::this_cpu(here)` (sched.rs:866) uses the `Here` that `within` hands out (sched.rs:813). That is the same
  section in which the queue lock was taken and released.
- `me` is used only for the compare (:867) and `timer::send_reschedule_ipi(me, apic_id)` (:870), both inside the
  closure.

**(d) Any other behaviour change?**
- None beyond holding interrupts off across the whole wake-up.
- The return values on every path are the same. The `return false` and `return true` now leave the closure, whose
  value `wake` returns.
- `threads::record` still runs before the section and reads no index.
- One side effect: the `Outcome::Exhausted` panic is now raised with interrupts off. It cannot happen while nothing
  moves (D93-6).

#### 3. Is the switch path untouched?

Yes.
- The commit's four hunks are `KernelQueues` and `wake`, the `RAN_ON` doc, and `worker`. Nothing in `dispatch`,
  `resume`, `with_queue`, `follow_thread`, the `on_*` hooks or `entering_process` changed.
- The device-interrupt path reaches `wake` through `WaitQueue::wake_one`, from `storage::on_interrupt` and
  `virtionet::on_interrupt`. It now opens one nested section per wake-up where it opened up to two. The trap entry's
  own code is unchanged.

### Findings

#### D93-1 (Low) The fair-share proof's "ran there" clause now checks the scheduler's record, not the processor

- **Where:** sched.rs:1207-1236 (`worker`), 1968-1974 (`workers_on`), 1979-1985 (`run_correct`); the record:
  ADR-0013:804, TASKS 66 invariant (3) (TASKS.md:2842).
- **Defect:** `RAN_ON` now holds the location `spawn` set, which is the `id` that `workers_on` compares it with. The
  clause therefore holds for any worker that ran one counted iteration with its record. It no longer tests that
  the processor that ran the worker reads its own index as `id`. Verdicts on a correct kernel are unchanged, but
  the clause has lost its own evidence, and the ADR's text still describes the stronger check.
- **Failure:**
  - Suppose processor B's CPU-local index were changed to A's after start-up (only start-up checks it), or a frame
    of A's were resumed by B where both share `CONTEXTS[A]`.
  - Then A's workers run on B, and the old clause would fail the run ("ran there").
  - Now `RAN_ON` still reads A + 1 and the clause passes.
  - The table of contexts catches a frame resumed by a processor whose own table never saved it (cpu.rs:962-990),
    but not two processors sharing one index.
- **Fix suggested:** restore the processor's own observation at no cost to the window. After the loop ends, read
  the index once, in one section, before `finish`: "where it last ran" is where it stopped. Or keep the location
  and change the ADR-0013 and TASKS 66 wording to say the clause checks the scheduler's record.

#### D93-2 (Info) Interrupts-off now spans every retry of a wake-up

- **Where:** sched.rs:856-884, with frame/sync/src/threads.rs:468-507.
- **Defect:** `within`'s single section covers all of `origin_sync::threads::wake`'s attempts. Each attempt takes
  another queue's lock, and before this commit interrupts reopened between attempts.
- **Failure:** none today. Without a mover there is one attempt, and `Exhausted` panics. Once ADR-0020 S6 moves
  threads, a wake-up chasing a thread that moves often keeps interrupts off across up to 64 contended lock
  acquisitions. S1 bounds the retries by S10's move rate. This is a latency item for TASKS 96's or 98's budget,
  not a correctness one.

#### D93-3 (Info) The worker's location read and store are not one atomic observation

- **Where:** sched.rs:1227-1230.
- **Defect:** a preemption and move between `location()` and `r.store` would record the processor the worker just
  left. That is the staleness the per-iteration section used to rule out.
- **Failure:** none today, and none while workers stay pinned: kernel threads are spawned pinned (S2), and no mover
  exists. If a worker is ever spawned movable, its last `RAN_ON` can name its previous processor when `STOP` lands
  just after a move. The comment's "Read live, every iteration, as `RAN_ON` was" should then say so.

#### D93-4 (Info) A worker with no record fails the run without saying why

- **Where:** sched.rs:1215, 1227-1230, 2260-2275.
- **Defect:** if `mine` is `None`, every store is 0, which `workers_on` reads as "never ran". The per-CPU line then
  prints non-zero counts followed by ": scheduler failed", with no cause.
- **Failure:** it cannot happen in a correct kernel (see 1(d)). It fails closed if it does. A diagnosis would have
  to infer the cause.

#### D93-5 (Info) Checked, nothing found: no path takes a run-queue lock with interrupts on through `KernelQueues`

- **Construction:**
  - `KernelQueues<'a>` has one private field, `_section: Here<'a>` (sched.rs:806-808), in the private module
    `waking`.
  - The only struct literal is in `within` (sched.rs:813), inside the closure of `without_interrupts_here`.
  - The module holds nothing else that could make one, and it has no child modules.
  - It derives nothing: no `Clone`, `Copy` or `Default`.
- **Escape:**
  - `within`'s `f` is `for<'a> FnOnce(&KernelQueues<'a>, Here<'a>) -> T`, and the reference's lifetime is also
    higher-ranked. So `T` cannot carry the reference or the `Here`, and no captured cell of an outer lifetime can
    store it.
  - `KernelQueues` is not `Sync`, because `Here` holds `*const ()`, so `&KernelQueues` is not `Send`.
  - `origin_sync::threads::wake` is generic over `queues: &Q`. It returns `Wake`, which has no lifetime, and the
    crate forbids `unsafe` (threads.rs:43). So it cannot keep the reference.
- **Reaching `locked`:** only through `&self` on a `KernelQueues`. The only caller is `origin_sync::threads::wake`'s
  loop (threads.rs:477), called once, from `wake`'s closure (sched.rs:857). The associated `wake_slot` can be
  called without an instance, but it needs a `&mut RunQueue` that is already locked, and takes no lock.
- **Inside the section:**
  - The closure `wake` passes, and the code it reaches, never enables interrupts. That covers `record.location()`,
    `record.generation()`, `RunQueue::wake`, `WAKES_FOLLOWED`, `CpuIndex::new`, `apic_id`, `this_cpu`, and
    `send_reschedule_ipi`, which is `X2Apic::here` plus a `wrmsr`.
  - `origin_sync::threads::wake`'s closure for `locked` captures `record`, `at` and `generation`, and does not call
    `queues` again. So no nested lock is taken.
- **The other run-queue lock sites** (sched.rs:135, 318, 464, 683, 767, 966, 976-985, 1094, 1155, 1442, 1606, 1762,
  1884-1886, 1918-1920; measured_stack.rs:273; threads.rs:223-227): each is in a `without_interrupts` or
  `without_interrupts_here` section, or in the trap entry (`with_queue`). This commit changes none of them.
- The `locked` comment "Interrupts are off: only `within`'s section makes `self`" therefore holds. It rests on the
  section rule that nothing holding a section's `Here` enables interrupts, which is checked here by reading, not by
  the type.

#### D93-6 (Info) `wake`'s `Exhausted` panic is now raised with interrupts off

- **Where:** sched.rs:877-880.
- **Defect:** the panic that stops the kernel after 64 followed moves now starts inside the section. Before, it
  started with interrupts as `wake`'s caller had them.
- **Failure:** none today: the outcome cannot happen without a mover. Once TASKS 96 builds pinned mode (S20) in
  its place, this goes away.

### Addendum: 87673b7e

Reviewed: `git show 87673b7e`, against its parent `f8604f7e`. Read only: no cargo or build, no operating system's
source. HEAD is `87673b7e`, and line numbers are at that commit. The commit changes only `framekernel/src/sched.rs`:
the `RAN_ON` doc (:1179-1180) and `worker` (:1207-1243).

#### (a) Does `RAN_ON` written after the loop give the clause its own evidence back?

**Yes.** `RAN_ON` again holds the processor's own CPU-local index (GS:0), read through `cpu::this_cpu(here)` in a
section (sched.rs:1227-1236). It no longer holds the scheduler's record of the spawn target. So "both workers last
ran on id" (ADR-0013:804, TASKS 66 invariant (3)) once more rests on what the processor says it is. D93-1 is
closed.

**Equivalence with the base's store in every iteration** (base `0b90dea8`: `r.store(this_cpu() as u64 + 1)` in
each iteration with `RUN == run`):

- **A worker that ran and stopped normally.** The base's last value was the index during the last iteration before
  it saw `STOP`. The new value is the index right after the loop. That is the same processor unless the worker
  moved in between, and workers are kernel threads, spawned pinned, with no mover built. Same value.
- **A worker that never counted.**
  - If it looped but every step was at or above `RUNNING_STEP`: the base still stored `RAN_ON` (the store did not
    depend on `step < limit`), and so does the new code. Same.
  - If it never completed an iteration (it saw `STOP` at its first check): the base left `RAN_ON` at 0, and now it
    holds that worker's processor. `right_cpu` alone can therefore now be true where it was false (D93-7). The
    verdict is the same, because every use of `right_cpu` also requires `a.min(b) > 0`, and such a worker counted 0.
    The uses are `run_correct` (:1981-1987), `ok &= right_cpu && lo > 0 && rounds`, and the per-CPU
    `passed = right_cpu && fair && rounds`, where `fair` requires `lo > 0`.
- **A stale run.**
  - `RUN` changes only in `respawn_workers` (:1950).
  - That runs only when `window_again` is true (runqueue.rs:350-362), which requires `correct` and so `run.exited`.
    That means every worker of the previous run has already incremented `EXITED` in `finish`, after its post-loop
    store. So no worker of run N is still running when run N+1's `RUN.store`, reset and `STOP = false` happen.
  - The post-loop `RUN == run` guard (:1228) matters only for a run that failed and is never repeated. Its late
    workers then store into slots no one reads again.
  - The base had the same guard, inside the loop.
- **Ordering against `respawn_workers`' reset and the next run.** Each worker's `RAN_ON` store (Relaxed) comes
  before its `EXITED.try_update(AcqRel)` in `finish`. `run_window`'s `wait_for_others` reads `EXITED` with Acquire
  until it holds every worker of the run (:1932-1937). RMWs continue the release sequence, so every worker's store
  happens-before the boot flow's reads in `workers_on` and before `respawn_workers`' reset to 0 (:1952-1957). The
  next run's workers store only after that run's `STOP`, which the boot flow sets after the window. A value from
  one run can neither survive the reset nor land after it.
- **A run whose workers did not all exit.** The base stored `RAN_ON` during the window, so it held a value when the
  boot flow read it after the timeout. Now `RAN_ON` is set only after `STOP` and may still be 0. The verdict is the
  same: `run.exited` is false, so `run_correct` and `ok` already fail. But the per-CPU lines can now also say
  "scheduler failed" for processors whose workers ran but had not stopped (D93-7).

#### (b) Is anything wrong in the new section or the loop?

Nothing wrong.
- **The section** (:1230-1235): it reads the index under its own witness, uses it only for the store inside, and
  does nothing that yields, blocks or enables interrupts. `r` is `RAN_ON`'s entry for the worker's slot, looked up
  by explicit slot, not by the running processor. That is correct.
- **The loop** (:1210-1222): it counts `step` into `PROGRESS` under the same conditions as the base: `RUN == run`
  and `step < limit`. The one difference is that progress no longer depends on the `RAN_ON` entry being present
  (the base's `if let (Some(p), Some(r))`). Both tables are `PerCpu` tables sized together, so this is not
  observable.
- **The loop is now lighter than the base's** (D93-8): no GS load and no `RAN_ON` store per iteration, where the
  base had both. Correctness and the verdict rules are unaffected. But this is the loop the judge compares against
  the base, so it is a change in what the base comparison measures.

#### (c) Are D93-3 and D93-4 closed?

**D93-3 is closed.** The location is no longer read. The index read and the store share one interrupts-off
section, so they are one observation.

**D93-4 is closed.** `mine` is gone. The only `None` left is `worker_entry(&RAN_ON, slot)`, as in the base. The
per-CPU sizing gate rules it out, and if it happened, `workers_on` would read 0 and fail the run.

#### New findings

**D93-7 (Info) A worker that never iterated now reports where it stopped, and a run with unexited workers reports
more failing CPUs.**
- **Where:** sched.rs:1227-1236, with 1970-1987 and 2260-2276.
- **Defect:** `RAN_ON` is written once, after the loop, whether or not the worker ever iterated, and only once it
  stops. Before, it was written in every iteration of the run.

**D93-8 (Info) The fair-share worker's loop now differs from the base's.**
- **Where:** sched.rs:1210-1222, against `0b90dea8`'s worker.

**The `run_probe` change** is the one change of behaviour the contract did not have: interrupts are now off across the probe's access and its fault, where before they were as the caller had them. The coordinating session accepted it on 2026-11-21 on two conditions. The first was a check that nothing on the page fault's path assumes interrupts are on, which the author made by reading at `ba69370d`:
- the exception entry and return never set or read the flag, and the return restores the interrupted flags, so interrupts stay off inside the section;
- `dispatch` reads only `trap::hooks()`, lock-free, before the probe's recovery on a kernel page fault (the landing and alignment checks are ring 3's);
- `probe_recover` is a bare `ret`;
- the probes are single instructions taking no lock;
- `UserSpace::probe_read` already ran with interrupts off;
- callers that probe in a loop hold the section for one probe at a time.

The second is this paragraph and TASKS item 93's entry, with `boot-test` and `boot-matrix` as its evidence.

- each new section above;
- `mark_online`'s store and fence now with interrupts off as well (R93-1);
- `pin()`'s stop (R93-8);
- the pin count's stops at its largest and below zero, and the mint's stops;
- the flow check at the kernel's entry (a halt, unreachable there) and at each AP's entry, where a failed check refuses the start as `NotMine` (the coordinating session's ruling on `cba7462b`).

**`Switch::new`'s one caller** is `cpu::dispatch` (the ruling on `cba7462b`), as the host test holds.
