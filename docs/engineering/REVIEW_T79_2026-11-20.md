**Reviewed:** `claude/t79-ending-threads`, `6c754c45..aea42421`. That is the brief's `6c754c45..e292f8d1` plus `aea42421`, which changes only a comment in `models.rs` (E2's and E3's bound). It was HEAD when I read the branch.

**Not reviewed:** the author's uncommitted edits to `docs/adr/ADR-0013-boot-proof-policy.md`, `PERFORMANCE_BUDGETS.md`, `SOURCE_PROVENANCE.md` and `TASKS.md`. They were still changing in the worktree while I read it.

**Read against:**

I opened no source outside this repository.

## Summary

I found no High or Medium defect. The fix does what the contract asks.

**The ordering argument holds** in the C++20/Rust model. Two premises need writing down, and the kernel meets both today:
- every lowering of `ending` follows its own thread's mark on the same counter;
- each zombie's raise happens-before its own reap.

**The code matches the argument:**
- Every kernel thread now ends through `finish`, with its done-signal inside the closure.
- Every user thread's end is published inside `end_with`.
- No thread migrates.
- A slot's mark is cleared in the same queue-lock section that frees the slot.
- `reap_zombies` keeps T70-7's order.

**Tests I ran,** each inside `cargo xtask exclusive --`:
- the host tests (`origin-sync` exits 7/7, `framekernel` settled 3/3, xtask `ending_threads_do_not_qualify` 1/1);
- E1 to E3 on a private copy of the Loom workspace: all pass, at the bounds and execution counts the docs state;
- four extra mutations and one extra model of my own.

**The findings are all Low.** Most are about invariants the code relies on but neither encodes nor gates:
- **T79-1 (the most important):** the mark and its lowering are paired only by a `bool` in `sched.rs`. My extra Loom model shows that one unpaired lowering lets a settle pass early.
- **T79-2:** `cpu::thread_exit` is still reachable from every kernel module.
- **T79-3:** nothing states or gates the Release/Acquire half of the handoff at the end signal.
- **T79-4:** the leak branch lowers `ending` before its own drops.
- **T79-5:** documentation nits.
- **T79-6:** a residual of the same class in `ipc::reap_closed`. It predates this change and lies outside the item.

## Findings

### T79-1 (Low): the pairing of a mark with its lowering is the crux of safety, and it lives only in a `bool` that neither `Exits` nor the models check

**Where:**
- `framekernel/frame/sync/src/exits.rs:27-45` (the argument);
- `exits.rs:136-149` (`queued(marked: bool)`, `not_queued(marked: bool)`);
- `framekernel/src/sched.rs:178-180`, `230-250` and `548`;
- `models.rs:3336-3470`.

**What is wrong.** The argument concludes that if `ending` reads 0, T's lowering is at or before the value read. That is true only if every lowering on that counter comes after its own thread's mark on the same counter. Otherwise another thread's lowering can balance T's mark. `exits.rs` states only that "each thread's mark comes before its own lowering". The premise "no lowering without its own earlier mark, on the same processor's counter" is not written down.

`Exits` cannot enforce it, because `queued` takes `marked` on trust. In the kernel it rests on four things:
- `Threads.ending[slot]`;
- slots being freed only by `RunQueue::exit` from `on_exit`, which takes the mark under the same queue lock;
- `spawn_with_fpu` never resetting the flag;
- threads never migrating. Only `spawn_with_fpu` pushes, onto the named processor's queue.

All four hold today. None is asserted.

**Evidence.** I added one model to a private copy of the Loom workspace:
- the first thread ends exactly as in E2;
- a second thread on the same `Exits` calls `queued(true)` and `reap` without ever calling `end`.

It fails at once with "a settle passed while an ended thread still held what it gives back". E1 to E3 and X1 to X5 cannot catch this class: every modelled thread passes `marked = true` correctly.

**Failure scenario.** A later change gives a slot a stale `true`:
- TASKS 75 reworks `spawn_with`'s publication order in the same `Threads` table (the contract calls this a merge point);
- or a second exit path is added that frees a slot without taking the mark;
- or threads ever migrate.

A thread whose flag is wrongly set then lowers `ending` without having raised it. The next settle can pass while a really ending thread still holds its stack, FPU area and space. This is H1 again, silently, and no gate or model says so.

**Suggested fix.**
- **(a)** Make the mark a token:
  - `Exits::end` returns a non-`Copy` `Mark`, carrying the processor index in a debug field;
  - `Threads.ending` becomes `[Option<Mark>; CAPACITY]`;
  - `queued` and `not_queued` take `Option<Mark>` and consume it, with a debug assertion that it came from this `Exits`.

  A lowering without a mark then cannot be written, and a migrated thread is caught.
- **(b)** State the premise in the argument: "every lowering consumes a mark raised earlier on this counter by the same thread".
- **(c)** Add my extra model, or a control "the second thread's `end` removed" on E2, so that the models show why the pairing matters.

### T79-2 (Low): "every kernel thread ends in `finish`" is a convention; `cpu::thread_exit` is still callable from any kernel module

**Where:**
- `framekernel/src/lib.rs:239` (`pub(crate) use origin_frame::{cpu, …}`);
- `framekernel/frame/src/cpu.rs:968` (`pub fn thread_exit() -> !`);
- the doc at `sched.rs:588-593` ("There is no other way for a kernel thread to end").

**What is wrong.** R2's reason for converting all 23 sites, rather than only those before a count, was that a new worker must not be able to reopen H1. `sched::exit` is gone, but `crate::cpu::thread_exit()` reaches the same `int 0x83` from any kernel file without the mark, and no gate looks for it. `git grep thread_exit -- developer-tools` finds only ABI fixtures.

**Failure scenario.** A new proof's worker ends with `DONE.store(true, Release); cpu::thread_exit()`. A later proof's settle passes while that worker still holds its stack and FPU area. That is H1 exactly, with nothing to say so.

**Suggested fix.** Add a text gate in `cargo xtask check`: no file under `framekernel/src/` but `sched.rs` names `thread_exit`. Alternatively, narrow the re-export so that `thread_exit` is reachable only through `sched`. Then correct the doc, or make it true.

### T79-3 (Low): the Release/Acquire half of the handoff is stated nowhere it would bind, and is not gated

**Where:**
- `sched.rs:222-229` (`end_with` doc) and `588-593` (`finish` doc);
- the per-site comments, such as `sched.rs:833-834`.

**What is wrong.** The guarantee needs three things:
- the end signal is written with Release, an AcqRel read-modify-write or a lock release, sequenced after `Exits::end`'s increment;
- the waiter reads it with Acquire or under that lock;
- the waiter calls `settle` afterwards in the same thread.

The models assume a Release store (`models.rs:3361`). The docs of `end_with` and `finish` say only "whatever tells other threads it has ended".

I checked every site and found all 23 correct. Each signal is inside the closure and is a Release store or an AcqRel read-modify-write. Each waiter reads with Acquire:

| File | Waiter lines |
|---|---|
| `wait.rs` | 294, 304, 456–459, 567, 570 |
| `sched.rs` | 872/882, 1004/1014, 1108/1111, 1195/1201, 1240/1268/1277, 1364 |
| `console.rs` | 1283/1288, 1567/1571 |
| `stacks.rs` | 329 |
| `storage.rs` | 1392/1399, 2076/2094/2113 |
| `time.rs` | 749/759, 870/874 |
| `tlb.rs` | 120/130 |
| `virtionet.rs` | 1578/1581 |
| `measured_stack.rs` | 278/292 |

**Failure scenario.** A future `finish(|| FLAG.store(true, Relaxed))`, waited on with a Relaxed load, compiles, passes every gate and the models, and makes the settle's ordering vacuous on paper. On x86-64 the hardware happens to order it, but the compiler may not.

**Suggested fix.**
- Write the requirement into the docs of `end_with` and `finish`.
- Better, take the ordering out of callers' hands with `finish_flag(&AtomicBool)` and `finish_count(&AtomicU64)`, which do the Release write themselves. `stacks.rs`'s `finish(|| ())` stays the one closure use.

### T79-4 (Low): `on_exit`'s leak branch lowers `ending` before its own drops, while the processor is still on the thread's stack

**Where:** `sched.rs:563-570`; the docs at `sched.rs:560-562` and `exits.rs:58-61`.

**What is wrong.** In the `_` arm, `not_queued(marked)` (566) runs before two drops:
- the FPU area, the binding `fpu`, dropped at the end of the `if let Some(threads)` block (570);
- the stack, inside the match scrutinee's tuple, dropped at the end of the `match` (569).

Both run with the processor still on the thread's stack and in its address space, since the switch follows `with_queue`. The comment "It has left the processor all the same" is not yet true at the point where the count drops.

**Failure scenario.** Only case (a), where the zombie table is full:
- a settle on another processor reads `ending == 0` right after line 566;
- it passes, and reads the heap before the FPU area's free on the exiting processor.

The compare fails anyway, because the leaked `user` reference keeps the space, so the verdict does not change. Only the numbers in the failure line vary from run to run, which makes case (a) harder to diagnose. I did not reproduce this.

**Suggested fix.**
- Drop `fpu` explicitly, and move `not_queued` after the `match`, or drop the stack explicitly first.
- Reword: "is leaving the processor; nothing more it holds will be given back".

### T79-5 (Low): documentation accuracy

1. `exits.rs:6` says the user thread's end runs "all with interrupts on". This is wrong for a #DB taken in ring 3: `user_fault` with `stack_fixed` (`syscall.rs:129-147`) runs `thread_ended`, and so `close_out`, with interrupts off on the IST stack. The argument does not depend on it.
2. The argument at `exits.rs:31-45` should also name its zombie premise: each zombie's raise happens-before its own reap. In the kernel, the raise in `on_exit` and the pop in `reap_zombies` happen under the same `Threads` lock. This is the counting step behind "0 there means the reaper's lowering of T's zombie is at or before it".
3. Two comment lines were left short by the edits: `sched.rs:340` ("processor). Each of those moves the counts on its own") and `settled.rs:6` ("and no stack was lost while it ran. A stack is lost when its reclaim's").

**Suggested fix:** as stated in each item.

### T79-6 (Low; predates this change and lies outside TASKS 79): a count lowered before its release in `ipc::reap_closed`, which `settle` cannot see

**Where:** `framekernel/src/ipc.rs:479-484`, and the admission at `process.rs:977-979`.

**What is wrong.** `reap_closed` lowers `CLOSED_COUNT` (480) before it drops the channel's undelivered messages (481-484). The dying thread's own `reap_closed` in `close_out` can therefore see 0 and return. `ending` is then published while another processor is still freeing messages that carried this process's ends: the code calls them "delayed, never lost". `settle` waits on neither `CLOSED_COUNT` nor any in-progress count.

TASKS 79 closes the window on the ending thread's own processor. It does not close this one when the other processor's reaper is an ordinary thread that is not ending. This is T70-7's pattern in another place.

**Failure scenario,** unsure how reachable from today's proofs:
- a proof whose processes pass channel ends in messages, such as the directory or IPC proofs;
- a peer's syscall on another processor reaps the closed list at the moment the last thread ends.

A settle that passes then reads the heap before those messages are freed: high by their size, a false "failed".

**Suggested fix:** a follow-up item. Count an in-progress reap, and lower it only after the drops, then have `settle` call `ipc::reap_closed()` and wait for both counts to be zero. Alternatively, lower `CLOSED_COUNT` after the drops, checking `listed`'s protocol first.

## Checked and found sound

### The memory-model argument (brief item 1)

**The argument for one ending thread T, step by step:**
1. The mark M is sequenced before the Release publish, so M happens-before the settler's Acquire of the end, and so before its load of `ending`. By write-read coherence, that load reads M or a later value in M's modification order.
2. Every write to `ending` and `zombies` is an RMW (`fetch_add` or `fetch_sub`, AcqRel). Under C++20, which Rust follows, a release sequence is the head plus every later RMW, from any thread. So a value read at or after T's lowering L lies in L's release sequence, and the Acquire load synchronizes with L.
3. Z+ is sequenced before L, so it happens-before the later `zombies` loads. A 0 there, by the counting argument (T79-5 item 2), means the reap's Z- is in the prefix. The read then synchronizes with Z-, and everything `release` did happens-before the settler's next step.
4. The per-processor split only adds non-negative terms. `saturating_add` keeps a wrapped counter from summing to 0; wrapping would have hidden one.

**The real end signals,** each written with Release and read with Acquire:
- the process's `ending`: `SpinLock`, with an Acquire CAS and a Release unlock (`sync/src/lib.rs:165`);
- `TERMINATED`: a Release store (`process.rs:287`), read by `raised()` with Acquire;
- the peers' closed ends: inside `close_table`, within `publish`;
- `Process::termination`: raised in `thread_reaped` and `start_failed`, inside the reap's `release`, before Z-;
- `start_failed`'s `close_out`: ordered after every other thread's mark through the lifecycle lock;
- `kernel_bound`'s `ROOT.left()`: Acquire;
- `live()`: under the queue lock, which is held across `on_exit`'s Z+ and L.

No end signal is published before the mark:
- `run`, `refused` and `user_fault` publish nothing before `thread_ended`;
- `pin::judge` is pure;
- `DEBUG_FRAME` is not waited on before a settle.

### Every path by which a thread ends (brief item 2)

**Each path, and where it marks:**

| Path | Where |
|---|---|
| System-call exit | the generated `dispatch` returns `ThreadExit` only after `thread_exit` → `thread_ended`; then `on_exit` (`cpu.rs:1149`) |
| The pin's refusal | `refused`, then `ThreadExit` |
| `user_fault` | `thread_ended` with interrupts in either state, then `hooks.exit` (`cpu.rs:1180`) |
| `start_failed` | no thread of its own; its `close_out` is ordered after the others' marks, as above |
| Kernel threads | the 23 entry functions (every `extern "sysv64" fn(u64) -> !` passed to `spawn`) all end in `finish` |
| Boot and idle flows | slot 0, never marked, never exits |

**Marks happen once per thread:**
- `end_with`'s `!*marked` check makes a second call publish without counting again.
- `RunQueue::exit` fails only for slot 0, so a marked thread always reaches the take.
- Slots are freed only in `on_exit`, under the queue lock that also covers the take, so a reused slot starts unmarked. `prove_lifecycle` exercises reuse at boot.
- No migration (see T79-1).
- `int 0x83` is retried until `on_exit` succeeds, so `finish` never strands a mark.

### Locks and interrupts in `end_with` (brief item 3)

- It takes the queue lock and then the threads lock in sequence, not nested: the guard from `queue.lock().current()` drops at the end of its statement. So it cannot conflict with the nested order queue → threads used in `with_queue`, `spawn_with_fpu` and `on_exit`.
- With interrupts off, `current` cannot change on this processor between the two locks.
- No caller holds a scheduler lock: the three `thread_ended` sites and `finish`, and `user_fault` comes only from ring 3.
- `without_interrupts` restores the caller's interrupt state, so the IST path stays with interrupts off.
- `publish` runs after both locks are released, in the caller's interrupt state, exactly as before. `close_out` and `ipc::close_table` neither block nor lock differently.

### `on_exit` and `reap_zombies` (brief item 4)

- `queued` runs under the `Threads` lock, with interrupts off, so the processor's reaper cannot pop the zombie before Z+.
- T70-7's order is kept. `release` holds the drops of `fpu`, `stack` and `user`, `thread_reaped`, and the `process` clone's drop, which may be the last reference. Z- comes after all of them.

### `settle`'s new wait, and case (c) (brief item 5)

**The wait does not depend on host ticks.** `yield_until` yields and reaps on every iteration, so on 1 processor the boot flow hands the processor to the ending thread and then reaps its zombie.

**No legitimate state holds `ending` up beyond a bounded time:**
- after the mark, a thread does not block in `close_out`, `reap_closed`, `reap` or `reclaim`. A stalled shootdown is capped at 1 s;
- a ring-3 spinner cannot starve the marked thread, because stride scheduling rotates it in;
- that spinner can still starve the zombie's reap, which is case (b), unchanged;
- `stacks::hold_in_window` runs after L, and no proof settles during a hold.

**Case (c)'s verdict is right:** naming a hang beats miscounting.

**One note on Amendment 3 (b),** informational, not a finding. On the large TCG machines, a host stall of over 10 s on a processor holding a marked thread now reads "ending threads not yet exited", which (b) never re-runs. The same stall on a zombie already read "exited threads unreaped", so the class is unchanged in kind. Only the window widens by the [mark, exit) interval, which includes the dying thread's own `reap()`.

### The Loom models (brief item 6)

**The models are the real `Exits` type.** One thread per end, running end, then queued, then reap, is a sound stand-in. The kernel orders those steps by program order and the `Threads` lock, which gives the same happens-before edges the argument uses.

**Clean run** on a private copy: E1 passed in 105 executions (exhaustive), E2 in 325 and E3 in 555 (two preemptions each). These match `models.rs`.

**My mutations, with their results:**

| Mutation | Result | Reading |
|---|---|---|
| `queued`'s lowering made Relaxed | caught by E1, E2, E3 | Causality violation |
| `reap`'s lowering made Relaxed | caught by E1, E2, E3 | Causality violation |
| `queued`'s Z+ made Relaxed | passes | the argument predicts it: Z+ is sequenced before L |
| `end`'s increment made Relaxed | passes | the argument predicts it: M is sequenced before the Release publish |

So the models already reject the two Release halves that no committed control names. Adding them as X6 and X7 is optional. The unmodelled part that matters is the pairing (T79-1).

**Two things I did not check:**
- I did not run the committed controls X1 to X5 through `cargo xtask loom`, nor the deep search.
- I relied on the author's statement that X2 and X3 are caught within two preemptions. By inspection, E1 (exhaustive) catches all five in any case, and every control lists E1.

### The 23 kernel exit sites (brief item 7)

- Each done-signal is inside `finish`'s closure.
- The data written before a signal (`SLEPT`, `SWITCHED`, `RX_FRAMES` and the like) is now ordered by the AcqRel or Release signal. Before, several were Relaxed.
- `storage.rs:1337`'s early partial stores are fine: the waiter needs slot 2, which is written only inside `finish`.
- `WEIGHTED_EXITED.store(0, Relaxed)` before a run is harmless. It is sequenced before the spawns, and a run whose workers did not all exit is never repeated (`sched.rs:1150`).

### Everything else (brief item 8)

- **`settled.rs`:** the judge includes `ending`; the text puts it first; the tests pass.
- **`lost_stacks_only`:** it returns `None` for ending threads alone, before the lost stacks, or after them. The directory line is in `REFUSE_COUNT_LINES`, so the fourth case does test the clause logic.
- **Text consumers:** no xtask gate or checker depends on the old wait text ("exited threads' reaping") or on `ZOMBIES` or `zombies()`. The only hits are historical review records.
- **`percpu` sizing:** it names `EXITS`.
- **`unsafe`:** `exits.rs` forbids it. `models.rs` is on `unsafety.rs`'s list.
- **Cost:**
  - each thread end adds one `pushf/cli/popf`, two uncontended spin-lock round trips and one `lock add`;
  - each exit adds one `lock sub`;
  - each settle poll adds one Acquire load per processor.

  None of these is a hot path.
