## Findings

**R121-1 (Medium): a set bit 19 does not mean the loader made the reset.** `fch.rs` (`Branch::of`, the decision line), `latitude.py` (the install's reboot).
- `PMxC0` bit 19 records a `0x06` written to `0xCF9` by anyone.
- Boot 1 starts from the provider system's own reboot. That reboot plausibly goes through the FADT's reset register, an SMI command whose handler is unknown. If the handler writes `0x06` to `0xCF9`, boot 1's first run takes the "mine" branch, and no control runs.
- The line then says "the last reset was this loader's own", which is untrue.
- If that run hangs, the boot reads two ways again: the call never returned, or both `0xCF9` and the shutdown failed. The hand-over's reading table has no row for it.
- **Fix:** word the line "a `0x06` to `0xCF9`", without claiming the loader made it. Count a "mine" run as evidence only when a control run precedes it in the same boot. Or start boot 1 with the provider's API reboot.

**R121-2 (Medium): with no record in `PMxC0`, the boot never makes the call.** `fch.rs` (`Branch::of`); `main.rs` (the control arm).
- If the firmware clears `PMxC0`, or the register does not record a `0xCF9` reset, every run takes the control branch and resets before the call.
- Amendment 4 says such a run "can only count runs", but none of those runs calls `ExitBootServices`, so the count answers nothing. The hand-over accepts "the reading is lost".
- **Fix** (it needs the coordinating session: D4 says "anything else" is the first run): when `PMxC0` names no documented cause at all, take D6 instead of the control: make the call, then reset. The reset that started the boot normally leaves a cause bit, so boot 1's first run is still the control, and a later run that finds no record makes the call.

**R121-3 (Medium): a second run proves only that the first call returned, not that it succeeded.** `main.rs` (the `ExitBootServices` closure).
- D6 resets after the first `ExitBootServices` whatever its status.
- Suppose the first call returns `EFI_INVALID_PARAMETER` and the retry is what hangs. That was rental C's first-ranked cause, and Amendment 2's motivation. The rental would read it as "the call returns", and the normal loader's retry path would never run.
- **Fix** (it changes D6, so it is the coordinating session's call): branch on the status in RAX first, a compare of a processor register, not a device read. On success, `0x06` to `0xCF9`. On an error, skip `0xCF9` and triple-fault at once, so the next run's `PMxC0` (bit 19 or bit 23) says which happened. At least, add the reading to the hand-over's table.

**R121-4 (Medium): the fall-through after the triple fault cannot happen on real hardware.** `main.rs` (`reset_without_firmware`, `triple_fault`); Amendment 4, step 3.
- A triple fault that does not reset leaves the processor in shutdown: it is not "still running", so Amendment 3's order is never reached.
- Rental E's research says a shutdown reaches the FCH only when `PMx74` bit 17 is set, and that bit's reset value is 0.
- Failure case: a board with bit 17 clear, whose firmware's exit handling also disables the `0xCF9` reset (for example by setting `PMxD2` bit 6). The "mine" run then hangs silently, exactly like reading A, and `ResetSystem`, the FADT's register and the lines never run.
- **Fix:** set `Free.shutdown` only when the printed `PMx74` bit 17 is set; otherwise skip the triple fault and fall through. Add the row to the reading table.

**R121-5 (Low): the walk proves a mapping exists, not that it is the identity.** `fch.rs` (`walk`).
- It never checks that the leaf's frame is `PM_BLOCK`'s. UEFI guarantees the identity map only for memory in its map, and `map_says` may print "not described".
- It also ignores reserved bits, and the U/S bit under CR4.SMAP.
- **Fix:** compute the leaf's physical address, masking per level (bit 12 is PAT in a large leaf), and require it to equal the address read.

**R121-6 (Low): the checks are printed only after the reads.** `main.rs`.
- The registers are read during the table walk, but the line saying where they are and which checks passed comes much later.
- A read that hangs or machine-checks leaves "console: the walk read …" as the last line, and nobody can tell where it stopped. D1 says each check is printed.
- **Fix:** print that line, with `out` in scope, before `read_fch_registers()`.

**R121-7 (Low): the reads' precondition is not enforced by the types.** `main.rs` (`read_fch_registers`, `fch_read32/16/8`).
- They are safe functions whose SAFETY comments rest on checks a caller must have made.
- **Fix:** make them `unsafe fn` with a `# Safety` section, or have them take a private witness value that only `bench_fch_read` can make after the three checks.

**R121-8 (Low): the order after the call rests on one disassembly.** `main.rs` (`write_cf9`).
- `write_cf9` uses `nomem`, so the compiler may move memory operations across the `out`.
- No scenario can detect an `out` moved before the call: under QEMU the call always returns, so `mine slow` passes either way. Nothing gates the instruction sequence.
- **Fix:** drop `nomem` from `write_cf9`, and from `mask_interrupts` on this path. Add an xtask check on the bench loader's disassembly: the first port instruction after the indirect call to `ExitBootServices` is `out` with DX `0xcf9` and AL 6, with no `in` or `out` between.

**R121-9 (Low): the vendor check and the walk are never tested on their own.**
- Under TCG the default processor reports AMD, so the vendor check changes nothing there. Under any QEMU the DSDT check stops the run before the walk.
- Removing only `is_amd()`, or only the walk loop, passes all 13 scenarios. BC-11 removes two checks at once.
- **Fix:** plant each check separately, and add a TCG scenario with an Intel processor model that expects "not AMD's".

**R121-10 (Low): a `PMxC0` with several documented causes is taken as "mine".** `fch.rs` (`Branch::of`).
- The documents say each reset sets one bit and clears the others. Under the debug "sticky" setting, a stale bit 19 would persist.
- **Fix:** treat more than one documented cause as a contradiction (D3), or at least as "first", and say so.

**R121-11 (Low): the research list describes the loader before this change.** `docs/research/2026-11-21-loader-before-the-call.md`, pinned to `c8ecfc9d`.
- It leaves out what item 121 adds before the call in rental F's loader:
  - CPUID leaf 0;
  - a third RSDP, XSDT and FADT walk;
  - the DSDT scan, about 470 KB, with a 4 KiB stack buffer nested inside `with_fadt`'s 1 KiB one (which matters for the document's own candidate 2, the stack's depth);
  - CR3's read and the page-table reads;
  - the six FCH loads;
  - a third switch file opened;
  - in a control run, the `0xCF9` write.
- It still says switch files are read 16 bytes at a time; the tip reads 32.
- Its line references at `c8ecfc9d`, which the reviewer sampled, are correct.

**R121-12 (Low, cosmetic):** `fch.rs`'s module comment links [`describes`], which names no item, and the comment on `read_bench_file` still names two switches.

## Checked and found sound

- **Gating:** every addition in `main.rs` is under `cfg(origin_bench)`, and `fch` under `cfg(any(test, origin_bench))`. The `with_fadt` refactor is in a bench-only module, and `find_reset` behaves as before.
- **The AML scan:**
  - `DefOpRegion`, `NameString` (root, parent prefixes, null, dual and multi names) and the constant forms follow §20.2.2, §20.2.3 and §20.2.5.2.
  - Every index is bounds-checked, and no arithmetic overflows.
  - A `0x5B` at a chunk's end opens a window read again from its absolute offset; nothing is counted twice.
  - The header, the 4 MiB cap and short tables are handled.
  - Every miss is a false negative (more than four segments, many parent prefixes, computed bounds, regions only in SSDTs), never a false positive.
- **The walk:** CR3's PCID, PWT and PCD bits are masked off. 1 GiB and 2 MiB pages are followed, and a PS bit at the PML4 is not taken as one. Nothing overflows. The five-level branch is dead, since the loader refuses LA57 earlier.
- **The reads' gating:** the registers are read only after the vendor, the DSDT and the walk. The switch's path reads nothing. Widths and alignment match the comments.
- **D3, D4 and D7** match the code. All ones is caught before the branch, and the switch's parser is strict.
- **The machine code matches the source:** `Option<Free>`'s none is the value 2 in `shutdown`, with `cf9` at +8 and `wait_ticks` at +0. The status is kept in R9, then the `out`.
- **The triple fault's asm is right:** two zero pushes give a 10-byte IDTR with limit 0, so `int3` escalates through #GP and #DF to shutdown. Leaving out `nostack` is right, and the UEFI target has no red zone.
- **The wait's arithmetic** saturates and wraps where it should. The rate is never 0: a failed count falls back to 6,000,000 ticks a millisecond.
- **A failed `ExitBootServices` status** still gets the reset.
- **The planted controls** each fail a scenario:
  - BC-8: `mine slow` exits only after about 5 s, against 2.5 s;
  - BC-9: lines after the mark;
  - BC-10: the decision lines for `first` and `mine` are wrong;
  - BC-11: the "where" line is not one QEMU should print;
  - BC-12: `bad` takes the "mine" branch.
- **`quiet_before_exit`** is measured on COM2, which carries the mark. The margins are about 0 s against 2.5 s, and 5 s against 4 s. The reader's latency can only shorten what is measured.
- **The rental tool** refuses `BENCH-FCH` before it copies anything. It copies only the loader and the kernel. The test ties every `.rs` file's switch names to the tool's list.
- **`unsafe`:** one operation per block, each block with its SAFETY comment. `fch.rs` has none.

## Could not determine

- Whether the normal images are byte-identical: no build was run.
- Whether this firmware keeps `PMxC0` across a reset, what the provider system's reboot writes, and the board's `PMx74` and `PMx08`.
- How flaky the 2.5 s bound is under host load.
- Whether OVMF returns from `ExitBootServices` with interrupts on, which would leave a short window before the `cli`.
- What reads at `0xFED80300` would return with the checks bypassed while QEMU emulates an AMD IOMMU, whose default MMIO base is `0xFED80000`.
