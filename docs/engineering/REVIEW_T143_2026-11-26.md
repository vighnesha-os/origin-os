## What holds

- **F-1 is right and its test would fail without it.** `reclaim` now returns 0 for a kind already taken over (`frames.rs:231`), and the shift is reached only for `raw < 32` because `||` evaluates left to right. Before the fix a second `reclaim` freed every frame of the kind that was in use (`allocatable && !is_free`, `frames.rs:240`), i.e. frames already handed out. `a_second_reclaim_leaves_handed_out_frames_alone` (`frames.rs:531-556`) would have seen 4, not 0. Before the first call no frame of a non-`Usable` kind can be handed out, freed or claimed (`allocatable` is false for it, `frames.rs:208-215`), so freeing them all at the first call is right.
- **F-2 is right and its test would fail without it.** `reserved_frames` (`frames.rs:77-83`) is exactly "every frame holding a byte of `[base, base + pages·4 KiB)`", and saturation only widens it. Before the fix `new` reserved `base/4096 .. base/4096 + pages`, missing the last touched frame, and `allocatable` tested the frame's first byte, so the first touched frame could be freed back. With the old code the new test (`frames.rs:562-587`) would count 7 free frames, not 6, and `free(0x1000)` would succeed. The new `.min(a.frames)` (`frames.rs:144`) also bounds a walk that used to run `pages` times however large `pages` was.
- **The ownership specification is independent where it matters, and equals the code on every map the kernel can pass.** `owned` (`frames/proofs.rs:174-186`) uses "wholly inside a region" and "shares a byte with a reserved range", not the code's "first byte inside" and frame range. Only the kind test copies the code, which is unavoidable because `reclaimed` is the state. On page-aligned, ordered, disjoint maps (what `summarize` accepts, `boot.rs:142-170`) the two agree; `rv_equiv.py` found no difference in 87,480 cases.
- **Checking ownership at one free frame is sound.** Each harness assumes ownership at `frame` and asserts it at the same `frame`, so it proves the step over more pre-states than the invariant allows (`frames/proofs.rs:15-19`, `233-248`). The extra assumption at the handed-out frame (`:411`) is implied by the invariant.
- **`free` and `claim` assert their exact result** against `expected`/`takeable` computed from the specification (`frames/proofs.rs:450-467`, `506-515`), so the code's `allocatable` is checked against `owned` at every frame a call can name. `new` asserts "clear exactly when owned" (`:327-330`). These, with the post-call ownership check in `free_run`, are the paths that clear bits, so they are the ones that matter.
- **The bound of 2 reserved ranges is the kernel's own**: its only `FrameAllocator::new` passes exactly two (`early.rs:349`), and `new_case` proves slots 2 to 7 stay empty (`frames/proofs.rs:319-324`), which is what lets `owns` read two.

## Findings

### R143-1 (Medium): the frame allocator's "any sequence of calls" claim is not what the harnesses compose to: the base case and three of the steps never share a state, and the composed bound is unstated

**Where.** `framekernel/frame/src/frames/proofs.rs:21-29` (the induction claim), `:31-40` (the table), `:56-62` (the bounds), `:24-25` ("the reserved ranges are all `kani::any()`"); the harness bounds at `:76`, `:95`, `:353`, `:370`, `:401`, `:444`, `:499`, `:539`, `:588`, `:652`.

**What is wrong.**
- The base case, `new`, is proved only with a bitmap of 1 word (`new_case::<1>`, `:353`) or 0 words (`:370`), over maps of at most 5 frames (`MAP`, `:95`).
- The steps for `allocate`, `free` and `claim` are proved only on a bitmap of exactly 2 words (`Model::<WORDS>`, `WORDS = 2`, `:76`, `:401`, `:444`, `:499`). No state `new`'s harnesses produce is a state those three harnesses start from, so the induction step for those methods is never proved on any state the base case reaches.
- The bridge is true of today's code: those methods read only words below `frames.div_ceil(64)` (`frames.rs:180-186`, `250-256`), so a second word past `frames` changes nothing. But it is an argument, not a proof, and the module does not state it.
- Even with the bridge, a sequence stays inside every harness's bound only up to 5 frames, one word, 3 regions, 2 reserved ranges, runs of at most 4 frames, and no `reclaim`. The table's "128 frames" against `allocate` is the bound of one step, not of any sequence the induction covers. `:24-25` also says the reserved ranges are all `kani::any()`; only the first 2 of 8 slots are (`:135-138`).

**Failure scenario.** The requirements matrix records "the frame allocator's invariant holds after any sequence of `allocate`/`free`/`claim` calls (Kani, 128 frames)", reading the module's claim and its table. No harness establishes that: `new` is never proved past 5 frames, and the three steps are never proved on the one-word bitmaps `new` is proved for. CLAUDE.md rule 29 asks for exactly the property proved.

**Fix.**
- Instantiate `allocate`, `free` and `claim` at one word as well (make the three generic over `N` and run `N = 1` over 64 frames beside `N = 2`). They are the cheap harnesses. Alternatively, prove `new` at two words if that becomes affordable.
- Add one sentence to the module documentation: composed, the claim holds for allocators built over at most 5 frames (one word), 3 regions and 2 reserved ranges, with runs of at most 4 frames and no `reclaim`; each row's memory is the bound of that step alone.
- Change `:24-25` to "the first 2 of the 8 reserved slots".

### R143-2 (Low): `kani-gate`'s `cfg(kani)` check is a substring test that misses `cfg(any(kani, …))`, `cfg(all(…))`, `cfg_attr(kani, …)` and `cfg!(kani)`

**Where.** `developer-tools/xtask/src/kani.rs:894-911` (`cfg_problems`); the claims it backs at `kani.rs:24` and `Cargo.toml:108-110` ("Nothing a normal build makes holds any of it").

**What is wrong.** A line is examined only if its code contains `cfg(kani` or `cfg(not(kani` (`:899`). `#[cfg(any(kani, test))]`, `#[cfg(not(any(kani)))]`, `#[cfg(all(kani, …))]`, `#[cfg_attr(kani, …)]`, `cfg!(kani)` and `cfg( kani )` contain neither. Today's tree is clean: outside the proof files and xtask, `kani` appears only on the two declaration lines (`frames.rs:349`, `heap.rs:285`).

**Failure scenario.** To speed a proof, someone adds to `frames.rs`:
`#[cfg(any(kani, test))] pub const MAX_RESERVED: usize = 2;` and
`#[cfg(not(any(kani, test)))] pub const MAX_RESERVED: usize = 8;`.
`kani-gate` and `check` pass, CI's `kani` job passes, and Kani now proves a two-slot allocator while the kernel ships eight.

**Fix.** Outside the proof files and the two declaration lines, flag any non-comment line of a `.rs` file that contains the identifier `kani` (`\bkani\b`), or parse the predicate of every `cfg(`, `cfg_attr(` and `cfg!(` and flag any that names `kani`. Add a test for each form above.

### R143-3 (Low): `free_run_is_all_or_nothing` never requires a valid run to be accepted, and no control shows its namesake property can fail

**Where.** `framekernel/frame/src/frames/proofs.rs:582-628`; the one control, `kani.rs:203-213`.

**What is wrong.**
- `free`'s harness asserts its exact result (`:464-467`). `free_run`'s asserts only what an `Ok` implies (`:601-614`) and that an `Err` changes nothing (`:621-624`). It never asserts `Ok` for a run whose frames are all owned, in use and inside the map, nor which error is returned.
- The one control removes the ownership check. No control frees part of a run before failing, so nothing shows the "all or nothing" assertion (`:621-624`) can fail.

**Failure scenario.** An off-by-one at `frames.rs:313` (`end > self.frames` becomes `end >= self.frames`) refuses every run that ends on the map's last frame. All assertions still hold, the covers at `:600` and `:617` are still satisfied by other runs, and the control is still caught. The kernel's heap then gets `HeapError::Pages` for such a large free (`heap.rs:210-211`), and the frames stay allocated for good.

**Fix.** Compute `expected` as the `free` harness does (`EmptyRun`, `Misaligned`, `OutOfRange`, `NotAllocatable`, `DoubleFree`, `Ok`, in the code's order, from the specification) and assert `result == expected`. Add a control that frees each frame as it checks it (caught by `:621-624`) and one for the off-by-one above.

### R143-4 (Low): FI-3 and `new`'s refusal are checked against the code's own `covered_end` and `words_for`

**Where.** `framekernel/frame/src/frames/proofs.rs:217` (`check_whole`'s cover), `:234` (`any_state`'s `frames`), `:300` (`new_case`'s `needed`); the functions at `frames.rs:57-71`.

**What is wrong.** "`frames` is the map's covered end" is asserted as `a.frames == covered_end(a.regions) / FRAME`, the very function `new` uses (`frames.rs:115`, `127`), and `needed` is `words_for(covered_end(…))`, the very expression `new` compares (`frames.rs:115-119`). A wrong `covered_end` is invisible to the proofs. The independent half of the cover check, `frames <= bitmap.len() × 64` (`:217`), does catch a `words_for` that is too small.

**Failure scenario.** A change to `covered_end` drops the `LoaderReclaimable` term. Every harness stays green, because both sides of every comparison use the same function. Loader memory above the last `Usable` region then lies past the bitmap, and `reclaim` counts it without freeing it (see R143-11). Today the host test `a_second_reclaim_leaves_handed_out_frames_alone` (`frames.rs:532-556`) catches this particular change, so the protection comes from the host tests, not the proofs.

**Fix.** In `frames/proofs.rs`, write the covered end from FI-3's own words (the largest `base + pages × 4096` over regions of kind `Usable` or `LoaderReclaimable`, else 0) and the words needed as two ceiling divisions, and use these in `check_whole`, `any_state` and `new_case`.

### R143-5 (Low): `plan_fits_every_layout`'s documentation says "refuses exactly"; the assertions prove only one direction for an overflowing block

**Where.** `framekernel/frame/src/heap/proofs.rs:420-423` (the claim), `:428-464` (the assertions).

**What is wrong.** `None` implies "alignment not a power of two, or `size.max(align) > 2^63`" (`:432`), and both `Some` arms require a power-of-two alignment (`:439`, `:453`). But no arm requires `size.max(align) <= 2^63`, so "an overflowing block gives `None`" is not proved. For `size = 2^63 + 1` and `align = 1`, a plan of `Run { pages: 2^51 + 1, align: 1 }` satisfies every assertion of the `Run` arm (`:452-461`). The natural mutant (a saturated block) is still caught, at `size = u64::MAX`, where `pages × 4096` overflows. So the gap is in the claim rather than a likely missed bug.

**Fix.** Add `&& size.max(align) <= 1 << 63` to both `Some` arms.

### R143-6 (Low): the heap's block paths do not assert that `large_pages` is unchanged

**Where.** `framekernel/frame/src/heap/proofs.rs:535-559` (`allocate`, block) and `:611-635` (`free`, block); `check_whole` at `:165-169`.

**What is wrong.** The brief's property for `allocate` is "nothing else changes", and the module's (`:502-505`) is "every live block stays live". The block arms constrain the table and the source's counts. `check_whole` ties `bytes_in_use` to `large_pages` only as a sum. Nothing asserts `h.stats.large_pages == stats.large_pages` on a block path.

**Failure scenario.** A change to `allocate_block` or to the block arm of `free` that also moves `large_pages` by k pages and `bytes_in_use` by k × 4096 passes both harnesses: `check_whole` still balances, and the table assertions still hold. (An increase is caught only at the overflow edge of `HELD_MAX`; a guarded decrease is not caught.)

**Fix.** Add `h.stats.large_pages == stats.large_pages` to both block arms.

### R143-7 (Low): the page source's contract, as documented, is weaker than the model the heap's proofs use

**Where.** `framekernel/frame/src/heap/proofs.rs:48-55` (the contract), `:40` (the overlap claim); the model's `overlaps` at `:249-253`, the alias path at `:266-271`, `may_alias` set at `:519`, and `Source::new` without it at `:672`.

**What is wrong.**
- The contract says the source hands out frames "that no large run of the heap holds". The model also refuses every frame the heap holds as a slab at the start (`:251`), for every request, except a slab request in `allocate_keeps_the_heap_whole`.
- So `two_allocations_never_overlap`, which line 40 presents as "no byte is handed out twice", is proved only against a source that never hands out a slab's frame. That is stronger than the documented contract. The paragraph's own next sentence ("could make a run overlap a slab") assumes the stronger form.
- The overlap harness also compares only the two new allocations with each other. "A new allocation never overlaps a block live at the start" follows from `allocate_keeps_the_heap_whole` with HI-1, not from this harness.

**Failure scenario.** A reader takes `:48-53` at its word ("it may hand out a frame the heap already holds as a slab, which the heap must refuse") as covering the overlap proof. That proof never exercises the refusal.

**Fix.** State the contract as the model has it: "frames the heap holds neither as a slab nor in a large run, except that where `allocate_keeps_the_heap_whole` asks for a slab's frame it may hand out a slab's frame". Narrow line 40 to "two allocations from one state never share a byte".

### R143-8 (Info): one cover sits before the assumption it should guard

**Where.** `framekernel/frame/src/frames/proofs.rs:408` (cover), `:411` (assume).

**What is wrong.** CBMC checks a property under the assumptions that come before it. So the cover at `:408` can be met by a trace that `:411` later excludes, and it does not show that the assertions at `:412-419` are reachable under that assumption. The control `allocate-does-not-mark` (`kani.rs:135-148`) expects `:416-419` to fail, which shows the branch is reachable today. So nothing is vacuous now.

**Fix.** Move the cover after the assumption.

### R143-9 (Info): the stub documentation calls core's rotation an assumption when, for the lengths used, the proof makes it a result

**Where.** `framekernel/frame/src/heap/proofs.rs:31-36`, `:393-396`.

**What is wrong.** As "What holds" shows, every rotation the stubbed harnesses make is of length 1 or 2, by 1, and the equality harness covers lengths 1 to 3. The stubbed proofs therefore carry over to core's rotation as Kani's compiler builds it. Nothing about core's documentation needs to be assumed beyond the general compiler caveat (`:62-63`). The documentation also does not say why 3 is enough (`SLABS = 2`).

**Fix.** Reword: "proved equal to core's for every length the heap's harnesses reach (1 and 2, since `SLABS = 2`); the result rests on no claim about core beyond the compiler caveat below".

### R143-10 (Info): frame 0's error follows the code, not `FrameError`'s documentation, and the harness encodes the code

**Where.** `framekernel/frame/src/frames.rs:34-36` (`NotAllocatable` lists frame 0), `:28-29` (`OutOfRange`: beyond the bitmap), `:313-314` and `:334-335` (both return `OutOfRange` for frame 0); the harness's `expected` at `frames/proofs.rs:451-455`.

**What is wrong.** Freeing frame 0 returns `OutOfRange`. The host tests expect it (`frames.rs:467`, `602`), and so does the harness's `in_map`. That is the code's choice, not the documented one.

**Fix.** Either move frame 0 to the `NotAllocatable` check or reword the two variants' documentation.

### R143-11 (Info): the `reclaim` exclusion's reasons are slightly off, and `reclaim` has a counting quirk for TASKS 154

**Where.** `framekernel/frame/src/frames/proofs.rs:44-50`; `frames.rs:229-247`, `:153-155`.

**What is wrong.**
- "Which its host tests check" (`:48`): the host tests check examples, not that `reclaim` keeps the invariant.
- "`allocatable` walks all 8 reserved slots, so Kani must unwind at least 9 times" (`:44-45`) is equally true of `free`, `claim` and `free_run`, which are proved at unwind 10 and 18 (`:442`, `:497`, `:586`). The cost particular to `reclaim` is its walk over every frame of every region of the kind, each calling `allocatable`.
- `reclaim` accepts any kind but `Usable` (`frames.rs:231`). For a region of such a kind lying past `covered_end`, it counts as added (`:240-243`) frames that `set_free` ignores (`:153-155`), so its return overstates. The kernel's only call reclaims `LoaderReclaimable` (`memory.rs:101`), which `covered_end` covers, so this is unreachable today.

**Fix.** Reword `:44-48`. In TASKS 154's harness, assert that `reclaim`'s return equals the number of bits it cleared, or refuse any kind but `LoaderReclaimable`.

### R143-12 (Info): runner and gate parsing that fails safe, or misnames

**Where.** `developer-tools/xtask/src/kani.rs:371-377`, `:342-354`, `:795-799`.

**What is wrong.**
- **Cover lines.** The cover summary is parsed only if the line ends exactly with ` cover properties satisfied` (`:372`). If Kani appends an unreachable count to that line, as it does to the failed-checks line in the module's own sample (`:922`), `covers` stays `None` and the run fails with "no cover property" instead of naming the unreachable cover. This fails safe, but the message is misleading.
- **Harness names.** `harness_names` takes the next trimmed line starting with `fn ` (`:347`). A `pub fn` harness, or `#[kani::proof] fn x()` on one line, is misnamed or missed. `run` catches either case ("reported, but not a harness", `:663-668`), but `kani-gate` in `check` then misses that harness and so cannot report it as uncontrolled.
- **The workflow check** (`:795-799`) is a substring test: a job disabled with `if: false` still passes it.

**Fix.** Parse the cover line by its prefix (`** N of M cover properties satisfied`, then anything). Accept `pub`, `pub(crate)` and one-line attributes in `harness_names`. The workflow check is acceptable as it is.

### R143-13 (Info): supply-chain notes on the install path

**Where.** `.github/ci/install-kani.sh:27`, `:38`; `developer-tools/toolchain/verify.sh:584-593`.

**What is wrong.**
- **The driver.** `kani-verifier` 0.68.0 is trusted by version: crates.io versions are immutable and cargo checks the registry index's checksum. But the repository holds no digest for it, and it is built and run (its build scripts included) before the bundle's digest is checked. The script's header says so (`:3-4`).
- **The nightly.** `setup` installs `nightly-2026-08-21` through rustup, which verifies it only against the channel manifest it downloads. No digest in the repository covers it.
- **`verify.sh`'s guard** (`:592`) checks for the pinned bundle's directory, not the installed `cargo-kani`'s version. If a different `cargo-kani` is installed while the 0.68.0 bundle is present, `cargo kani --version` (`:593`) would set itself up and download, against the comment at `:584-586`.

**Fix.** None required for a verification-only tool. Optionally, check `cargo-kani --version` in `verify.sh` before calling it.
