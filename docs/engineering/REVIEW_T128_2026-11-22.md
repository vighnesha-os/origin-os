## Medium

### R128-1 (Medium): the minimal mode's first line says every successful call ends in a triple fault, which ruling Q3 makes false

- **Where:** `boot/uefi/src/bench.rs:520` (`MINIMAL_LINE`); printed first by `minimal::run` (`boot/uefi/src/main.rs`, `mod minimal`).
- **What is wrong:** the line ends with "after a successful call, a triple fault". Under ruling Q3, the triple fault follows `EFI_SUCCESS` only when the plan read before the call has both shutdown bits set (`MinimalDecision::Call { shutdown }`). Otherwise the run takes Amendment 3's order: `ResetSystem`, then the FADT's register, then the halt. In those runs the console's first line contradicts the decision line the same run prints later ("after EFI_SUCCESS, Amendment 3's order, since no shutdown is known to reset this system").
- **Scenario:** on a board whose `PMx08` bit 20 is clear, the first line promises a triple fault. The decision line then says Amendment 3's order. Someone reading the log, or a records digest that quotes the first line, records the wrong reset method.
- **Fix:** reword it, for example "...; after a successful call, a triple fault where both shutdown bits are set, else Amendment 3's order". Keep "bench build: minimal" in it, because `latitude.py` and the F2 checks key on that text.
- **Records note:** see R128-17. The ADR's "B5 is unchanged: after a successful call, the mode calls nothing in the firmware" has the same conflict with Q3.

### R128-2 (Medium): the rental tool counts no loader runs for a minimal-mode image, and reports "breadcrumbs: none"

- **Where:** `developer-tools/bench/latitude.py:1081`, `:1092` (`breadcrumbs`), `:1121` (`boot_result`) and the `RESET_BUILD_LINE in console.text(start)` branch near `:1272`.
- **What is wrong:** the tool counts loader banners (`loader_runs`) and times the gap after the last line only when the console holds "BENCH-AFTER". The minimal mode reads no switch file, so it never prints that text. `check_minimal_console` even requires that "BENCH-" never appears. For a minimal image:
  - `breadcrumbs()` sees the bench line and no "BENCH-AFTER". It scans the bytes after the last `origin-boot:` line, finds the `X` mark (not one of `RS12345678`), and returns `""`. Each boot's summary then ends "; breadcrumbs: none", but this image has no kernel stage and no breadcrumbs.
  - Neither "loader runs: N" nor the next-byte and next-loader timings are computed.
- **Why it matters:** the experiment's whole answer is whether a second run follows the call (the triple fault after a returning call), and that is exactly the count that is lost. The findings would rest on someone counting banners in the raw console.
- **Scenario:** a rental of the minimal image, with the call returning and a triple fault each run. `boots.json` and the record draft show "no verdict; last line: ...; breadcrumbs: none", with no run count.
- **Fix (needs a ruling: Q-rulings allow no rental-tool change beyond `loader_kind`):**
  - Treat "bench build: minimal" like "BENCH-AFTER" in those three places.
  - Return `None` from `breadcrumbs()` for a minimal image.
  - Add one line to `test_latitude.py`.

  If the coordinator keeps the tool as it is, the findings template must say the counts are manual.

### R128-3 (Medium): ruling Q4's host test passes without testing what it names

- **Where:** `boot/uefi/src/fch.rs:1175` (`StandIn::from_table(body, minimal)`), `:2251` (`the_stand_in_table_is_ignored_by_every_build_that_is_not_the_minimal_mode`).
- **What is wrong:**
  - The `minimal` parameter is not derived from the build. Its only caller (`mod minimal` in `main.rs`) passes the literal `true`, and no build calls `from_table` with `false`.
  - The test only shows that a function given `false` returns `None`. It says nothing about any build.
  - What actually keeps the full bench build from taking the table is structural: `find_stand_in` and `from_table` are called only inside `#[cfg(origin_bench_minimal)] mod minimal`. The behavioural check is the QEMU scenario "no switch, the reset through ResetSystem, the stand-in table ignored", which is sound.
  - The test's name claims a property it cannot show.
- **Scenario:** a later edit makes `boot` call `fch::find_stand_in` and pass its values as `pretend` with `minimal = false` in `bench_fch_read`. The host test still passes. Only the QEMU scenario would catch it, and only if that scenario is selected.
- **Fix:**
  - Drop the parameter.
  - Add an image-level check in `bench::build()`: the full bench loader must not hold the bytes `OXFC`. The signature compare compiles to an `imm32` whose little-endian bytes are "OXFC". Likewise, `build_minimal()` can require that the minimal loader holds them, as the positive control.
  - Alternatively, compile `StandIn` and `find_stand_in` as `#[cfg(any(test, origin_bench_minimal))]`, so the full bench library does not contain them at all.
  - Either way, tell the coordinator that a host test alone cannot show a property of a build.

### R128-4 (Medium): the stand-in table carries test hooks beyond ruling Q4, and they act on any machine

- **Where:** `boot/uefi/src/fch.rs:1175-1205` (`stale1`, `stale2`, `noreset`); used in `mod minimal` (`bench::key_for(calls.made(), stale, key)` and `After::StandInNoReset`).
- **What is wrong:**
  - Ruling Q4 and Amendment 5 step 3 give the table one job: stand-in values for the FCH reads. The ruling lists its body as BENCH-FCH's words, with `mine` meaning bit 23, plus `smi=<hex>`.
  - The implementation adds three more words:
    - `stale1` and `stale2` make the loader pass a deliberately wrong key to `ExitBootServices`;
    - `noreset` removes `ResetSystem` from Amendment 3's order.
  - In the full mode these hooks are switch files, which the rental tool refuses on a rented ESP. In the minimal mode nothing guards them: they act wherever a firmware's XSDT lists an `OXFC` table.
  - `nocf9` and `slow` are also accepted and silently do nothing in this mode (R128-15).
- **Scenario:** the risk on real firmware is negligible, since `OXFC` is not a registered signature. The issue is conformance: a hook that changes the call under test is in the rented image without a ruling.
- **Fix:** ask the coordinator to extend Q4 to cover `stale1`, `stale2` and `noreset`, and record it in TASKS 128's contract. Otherwise remove them and drop the retry and FADT-skip scenarios. Optionally honour the table only when the processor is not AMD's (QEMU's default CPU model is not), so no rented board can take it.

### R128-5 (Medium): the triple fault's SAFETY comment is false at both minimal-mode call sites

- **Where:** `boot/uefi/src/main.rs:2078-2080` (`triple_fault`), called from `mod minimal` at the control (after `wait_ticks(CONTROL_SPIN)` and `mask_interrupts()`) and in the `exit` closure (`if status == Status::SUCCESS && shutdown { triple_fault(); }`, `:2609`).
- **What is wrong:** the comment states "CPL 0, interrupts masked, after `ExitBootServices`, ... (decision item 345)".
  - At the control, `ExitBootServices` has not been called: boot services are live.
  - After the call, interrupts are not masked. Correctly so: Amendment 5 forbids anything between the compare and the triple fault, so there must be no `cli`.
  - The authorising decision for both sites is item 347, not 345.
- **Behaviour:** sound either way. With an IDT limit of 0, an external interrupt or NMI between `lidt` and `int3` also shuts the processor down. Before `lidt`, it goes to the firmware's still-intact IDT.
- **Why it matters:** this project treats SAFETY text as the documented invariant (CLAUDE.md §13, final rule 5). A later reader could rely on "interrupts masked" here.
- **Fix:** state the real contract. CPL 0; either boot services still active (the control) or after `ExitBootServices` with IF possibly set; the result is a shutdown whatever arrives once the zero-limit IDT is loaded; only to end a diagnostic run (items 345 and 347). Do not add a `cli` to the post-call path.

### R128-6 (Low): the line before the call names the FADT's register at port `0xCF9` as if it would be written

- **Where:** `boot/uefi/src/main.rs:2541`, `bench::ResetLine(register)` printed with the unfiltered register, while `plan.register` takes `bench::minimal_register(register)`.
- **Scenario:** under QEMU the console says "the FADT's reset register: write 0x6 to I/O port 0xcf9" in a mode that never writes `0xCF9`. The skip only appears later on the UART.
- **Fix:** print `ResetLine(bench::minimal_register(register))`. Its `Err(Cf9InMinimal)` text already says why the register is not used.

### R128-7 (Low): the minimal mode's waits assume a 4 GHz time-stamp counter

- **Where:** `boot/uefi/src/bench.rs:525` (`MINIMAL_TICKS_PER_MS = 4_000_000`), used for `CONTROL_SPIN` and every wait in `bench_reset`.
- **What is wrong:**
  - On a Zen 5 part whose counter runs at its base clock above 4 GHz (several desktop and workstation parts are 4.3 GHz or more), each wait is shorter than stated, and the "in 5 s" and "in 7 s" lines are wrong.
  - Under QEMU, the time "minimal, Amendment 3's order, the FADT's register at 0xCF9 skipped" takes depends on the host counter's rate (KVM: the host's; TCG: QEMU's emulated counter). I could not check it on this M1 host.
  - The full mode's fallback is `ASSUMED_TICKS_PER_MS` (6 GHz), "above any rate a processor's counter runs at".
- **Fix:** use `ASSUMED_TICKS_PER_MS`, so waits are never shorter than stated, or word the lines as "at least". Confirm the FADT-skip scenario's wall time on the M1 and on CI.

### R128-8 (Low): `triple_fault_after_call` does not identify the `ExitBootServices` call, and accepts a few writes as reads

- **Where:** `developer-tools/xtask/src/bench.rs:347` (`triple_fault_after_call`) and `step`.
- **What is wrong:**
  - **Not anchored.** It passes if any indirect call has a clean path to `push 0x0; push 0x0; lidt [rsp]`. Today only the `ExitBootServices` site can satisfy it: the control path has `rdtsc` and `cli` before its triple fault. If that path is ever simplified (no spin, no `cli`), an inlined `OutputString` call (`call qword ptr [...]`) followed by compares and a jump into a tail-merged triple fault would satisfy it, even with the post-call path broken.
  - **Writes accepted as reads.** `step` admits `mov` into any non-memory destination: `mov cr3, rax`, `mov cr0, rax`, `mov rsp, rbp`, `mov ss, ax`, `mov dr7, rax`. These are writes to processor state, not "reads into registers". Compiled Rust does not emit them outside `asm!`, so the gap is theoretical.
  - **Branch direction.** The check ignores which way the branch goes. The QEMU retry scenario covers this behaviourally.
- **Fix:**
  - Accept only `mov` into general-purpose registers.
  - Require that the call's operand was loaded from offset `0xE8` (`ExitBootServices` in `EFI_BOOT_SERVICES`) within a few instructions before the call.
  - Require exactly one such site.
  - Add a negative control: run the check on the full bench loader's listing and require `false`. That loader's triple fault is preceded by `out`, `cli` and a wait.

### R128-9 (Low): `writes_cf9` has no positive control on the path a rental uses

- **Where:** `developer-tools/xtask/src/bench.rs:338` and `build_minimal`.
- **What is wrong:** it matches only `mov dx, 0xcf9` and `mov edx, 0xcf9`. `boot-bench` implicitly shows that the compiler emits one of those forms, because `check_reset_after_call` on the full loader uses the same patterns. `cargo xtask bench-build --minimal`, the command that makes the rented image, runs no such control.
- **Fix:** `build_minimal()` already builds the full bench loader first. Disassemble it and require `writes_cf9 == true` before trusting `false` on the minimal loader.

### R128-10 (Low): some of the minimal mode's paths are never booted under QEMU

- **Where:** `developer-tools/xtask/src/bench.rs` (the five minimal scenarios).
- **What is missing:**
  - the second-error path (step 6, third bullet: Amendment 2's line, then Amendment 3's order). `stale2` is parsed but no scenario uses it;
  - `BitsClear` (another cause with a shutdown bit clear: the call, no control);
  - `Contradicts` (`bad`);
  - the first-map-does-not-fit path.

### R128-11 (Low): a live table that fails its check at the call is reported as a failed call

- **Where:** `boot/uefi/src/main.rs:2599` (`let Some(exit) = live_exit(system_table) else { return Status::UNSUPPORTED; }`).
- **What is wrong:** no `ExitBootServices` call is made and nothing is recorded, yet `exit_boot_services` returns `Halt`.

### R128-12 (Low): the minimal mode does not apply R116-7's guard to its marks, and `plan.marks` goes unread

- **Where:** `boot/uefi/src/main.rs:2575` (`marks: early_uart.is_present()`) and the `exit` closure, which calls `say_on_uart` unconditionally.
- **What is wrong:** R116-7 gated the full mode's marks so that a mark never waits between `GetMemoryMap` and `ExitBootServices`. The minimal mode cannot drain beforehand, because of "no UART register reads", so `X` and `Y` may poll the line status up to 100,000 times per byte there.
  - That is what the specification asks for ("`X` written straight to the UART").
  - It is harmless to the key, since nothing allocates. A firmware timer event during a long wait could still make the key stale, and the retry handles that.
  - `BenchPlan::marks` is set and never read in this mode.
- **Fix:** add a comment saying the minimal mode writes the marks unconditionally by Amendment 5 step 5, and set `marks` to `false`, or leave it with a comment.

## Checked and found sound

### 1. Amendment 5's list, in order (`mod minimal`, `boot/uefi/src/main.rs`)

**What it does, step by step:**
- **Step 1.** `efi_main` checks the system table, opens `ConOut` and prints the banner, as now. Then `minimal::run` prints its own line, and `boot` is never called. `boot` is a private, non-generic function, so it is not generated into the image.
- **Step 2.** The map goes into a 64 KiB `static mut [u64; 8192]` (8-byte aligned for the descriptors) and is translated into 1,024 static regions (ruling Q5). There is no `AllocatePages` or `AllocatePool`, no file-protocol call, no `LocateHandle`/`HandleProtocol`, no `Stall`, no generator, no page tables and no framebuffer search. I traced every function `run` reaches.
- **Step 3.** `spcr::find`, `bench::find_reset`, `fch::find_stand_in` and `bench_fch_read` (`fch::locate` for the FADT and the DSDT, `gate_smi`, `gate`, then the reads). Every byte goes through `read_described`, which is bounded by the first map. There is no write.
- **Step 4.** `MinimalDecision::of` matches the step:
  - bit 23 makes the call;
  - another cause with both bits set (`PMx74` bit 17, `PMx08` bit 20) is the control: a line, a 50 ms spin by the counter, `cli`, the triple fault;
  - either bit clear makes the call with no control, and says so;
  - no record, a contradicting layout, or nothing read makes the call with no control.
  
  Bit 20 (`0x0E` to `0xCF9`, cleared only by software) cannot hide bit 23, because bit 23 is tested first and bit 20 is outside `RESET_CAUSES`.
- **Step 5.** The map is read again through the live table's `GetMemoryMap`, then `X` (via `say_on_uart`), then `live_exit`. `live_exit` reads `system_table->BootServices` volatile, checks the signature and `HeaderSize`, reads the `ExitBootServices` member volatile, and the call follows. The pointer is read "there and then", after the mark.
- **Step 6.**
  - After `EFI_SUCCESS` with both bits: the status compare, then the inlined triple fault (ruling Q3).
  - After an error: the retry with `Y` and the same check.
  - After a second error, or no retry: Amendment 2's line, then `bench_reset`.
  - After a successful call without both bits: `bench_reset`.

**What it must not do:**
- **Port `0xCF9`.** No path in the minimal image writes it:
  - `write_cf9` and `reset_without_firmware` are reached only from `boot`;
  - the UART port is limited by `origin_spcr::port_block_allowed`, which rejects every block below `0x1000` except the four COM blocks;
  - the FADT's register goes through `minimal_register`, which turns I/O port `0xCF9` into `Err(Cf9InMinimal)`, so Amendment 3's order goes from `ResetSystem` straight to the line and the halt (the addition to ruling Q3);
  - the minimal mode writes nothing to the FCH.
- **Ruling Q5.**
  - A first map that does not fit means no walks, no FCH reads and no UART: the call with no control, and Amendment 3's order with no register.
  - A last map that does not fit means `ExitOutcome::NotAttempted`: the reason on `ConOut`, a line, a halt.
  - A retry map that does not fit means `Halt`: Amendment 2's line, then Amendment 3's order.

### 2. Between the call's return and the triple fault

- In the source, only `status == Status::SUCCESS && shutdown` comes between them. `shutdown` is a `bool` settled before the call, so it is a load or compare of the plan, which the ruling allows.
- `triple_fault` is `#[inline(always)]` and `asm!(..., noreturn)` without `nomem`, so the compiler moves no memory access across it.
- `calls.record` follows the branch in program order. The machine-code check exists to catch a compiler that moves it, and fails closed on any instruction it does not admit (including a spill such as `mov [rsp+..], rax`).
- The check's limits are in R128-8.

### 3. The `unsafe` blocks

- **The statics.** `&raw mut` with no reference to a `static mut` (Rust 2024), one thread, `run` called once; `[u64]` reinterpreted as `[u8]` of the same size.
- **`live`, `live_get_memory_map`, `live_exit`.** The place is formed through a validated pointer, then volatile loads. `HeaderSize >= size_of::<BootServices>()` (264 bytes, no padding) bounds every member read. `Option<fn>` is valid for any bits.
- **`read_smi_control`.** 4-aligned `0xFED802C0`, read only after `gate_smi` passed: AMD, a DSDT system-memory region holding all four bytes, the first and last byte identity-mapped by the firmware's tables. The read happens after the where-line, so a fault there still leaves the line on the console.
- **`bench_table_line`.** It reads the copy's bytes as `u8`; the struct has no padding. Live bytes are read only below `size`, and only once the live header's `HeaderSize` covers it.
- **The exception.** `triple_fault`'s comment text; see R128-5.

### 4. The full bench mode

It changes only by Amendment 4's addition:
- the table-compare line, before the last line: the live pointer, whether it moved, the first differing byte over the copy's 264 bytes, both `ExitBootServices` pointers, both CRC32 fields;
- the `SMIxC0` line, behind its own gate built from the same `gate_for`, with `holds_range` overflow-safe; the 4 KiB region `GSMM` holds it on rental F's layout;
- the `PMxD2` wording;
- a `smi=` word in `BENCH-FCH`, needed for the stand-in line.

Nothing else in it behaves differently:
- `After::StandInNoReset` cannot come from `BENCH-AFTER`;
- `skips_reset_system` gives the old result for every full-mode value;
- the `NotRead` display refactor prints the same text;
- the full mode never calls `find_stand_in` (the QEMU scenario checks this; R128-3 covers the host test).

### 5. Ruling Q2

- `origin_bench_minimal` is given only through `toolchain::bench_minimal_config()`, used by `build_minimal_loader` (in `bench-build --minimal` and `boot-bench`) and by the minimal Clippy run inside `boot-bench`.
- It goes into its own `target/bench-minimal`.
- F1 holds it as a third entry, with each listed file also on the bench list.
- `is_bench` and `refuse` cover the new directory.
- `build()` refuses a full bench image that holds "bench build: minimal".

### 6. The QEMU scenarios

Each would catch its target fault:
- **The control:** no `X`, no last line, QEMU exits.
- **Bit 23 and no record:** after the last line, exactly `[X]`, and QEMU exits within 2.5 s. `ResetSystem` or a line first would fail both conditions.
- **The retry:** exactly `[X, Y]`. A triple fault after the failed first call would leave `[X]`.
- **The FADT skip:** the two lines, and QEMU still running. A write to `0xCF9` would reset QEMU.
- **The full mode's no-switch scenario:** it plants `OXFC` and requires the not-read FCH lines and no stand-in text. It is not vacuous, because the same `stand_in()` planting is shown to work by the minimal scenarios.
- **The absence list:** the full path's line strings in it match what the loader prints, except `"origin-boot: framebuffer:"`, which covers only one framebuffer line. That entry is redundant with the kernel-read line anyway.

### 7. Register facts

These match the facts given for PPR 55901 rev 0.47 volume 5:
- `SMI_CF9_CONTROL = 0xFED80200 + 0xC0`;
- the `SmiLine` routes 00, 01, 10 and 11 map to none, SMI, NMI and IRQ13;
- bit 23 is a shutdown, required together with `PMx08` bit 20 and `PMx74` bit 17;
- `PMxD2` bit 6 is `cf9rstdisable`.

### 8. `latitude.py`

The only change is `loader_kind`, which tests "bench build: minimal" before "bench build", with a unit test. That is as the ruling allows; see R128-2.
