### Findings

#### R96-1 (defect): a failed delivery proof withdraws moves only when tokens went undelivered

- **Where:** `framekernel/src/migration_proof.rs:906`, with `ok` at `:962-968` and the function's documentation at `:811-815`.
- **The code:** `let entered_here = !delivered && pinned::enter(pinned::Trigger::DeliveryFailed);`. The proof fails when any of these is false: `spawned`, `delivered`, `posted == taken`, `ended`, `back`, `reached`, `pinned_mode.is_none()`. Pinned mode is entered only for `!delivered`.
- **What goes wrong:** any of these failures records `Proof::MigrationDelivery` as failed, Withdraw("no thread moves"):
  - a refused spawn;
  - receivers that did not end;
  - a heap, frame or stack leak (`back`);
  - no move that carried a pending wake-up (`reached == false`). This is likely on a fast host where receivers are rarely preempted mid-spin, or on a slow one where the senders' window is short (R96-4).

  The verdict then says moves are withheld, but `pinned::withdrawn()` stays false, and every later caller of `sched::migrate` moves threads. This breaks:
  - ADR-0013 R2: "the thing is withheld where it would be used, so the check cannot be forgotten";
  - ADR-0020 S20 trigger 1: "at boot, when the proof 'thread migration: delivery' fails";
  - the function's own documentation: "On a failure it enters pinned mode".
- **Impact:** today no mover runs after the proofs, so the harm is a false verdict. TASKS item 98's balancing would move threads on a machine whose verdict says it does not. Under `cargo xtask` the scenario still fails, through `: scheduler failed`.
- **Fix:** compute the verdict first, then enter pinned mode whenever it fails, for example `if !ok_without_pinned { entered_here = pinned::enter(DeliveryFailed) }`. Exclude the proof's own entry from `pinned_mode.is_none()`. The receivers have stopped by then and the mover has finished, so entering after the final wake-ups loses nothing.

#### R96-2 (risk): delivery's `reached` can be met by stale pending wake-ups, so it does not show that a token's wake-up crossed a move

- **Where:**
  - `migration_proof.rs:945`: `reached = moves.carried_wake != 0`;
  - `sched.rs:1393`: `carried = departed.wake_pending()`;
  - the sender wakes twice per token, `sched::wake(name)` at `migration_proof.rs:763` and `to.queue.wake_one()` at `:797`;
  - the receiver's two forms are at `:680-699`.
- **What goes wrong:** in the `wait_until` form the receiver is registered and blocked. The sender's direct wake makes it ready. If the receiver has not yet re-checked its condition, the queue's `wake_one` then finds its registration and wakes it again. It is ready, so `RunQueue::wake` sets `wake_pending`. This is certain when sender and receiver share a processor, because the receiver cannot run before the sender yields.
  - That stale bit carries no token. `wait.rs:111-112` says such a bit is harmless, and the next block consumes it.
  - A move of a receiver holding only a stale bit still counts in `carried_wake`.
  - So `reached` can be true when no token-bearing pending wake-up was ever moved. A run of the dropped-pending fault (C96-2) then passes if, by timing, every carried bit was stale.
- **Fix:** count the event the proof is about. In the direct form, the receiver reads its processor under a section before and after the spin. It counts a "carried token wake-up" when `block()` returns with `posted > before` and the processor changed. Require that count to be above 0 in place of, or beside, `carried_wake`. Or drop the second wake for a receiver that is not in its `wait_until` form.

#### R96-3 (risk): `threads::unaccounted` compares per processor, which moves and cross-block takes break

- **Where:** `framekernel/src/threads.rs:315-334`; the module documentation at `:22-31`; `take` via `take_from_any` at `:266`.
- **The code:** for each processor, `held(block) == live(queue) - 1 + zombies(table)`.
- **What goes wrong:** a thread whose record is in block P but which is queued on Q, or is a zombie on Q, adds 1 at P and 1 at Q. That covers a moved thread and a thread spawned through the new fallback to another block. Any settle while such a thread lives then reports "records out of place" (`settled::judge`, `sched.rs:586`), and every settle's verdict fails.
  - Today this is latent. The migration proofs' threads are all reaped before `bracket_after`'s settle judges, and the fallback never runs in a boot.
  - It becomes a false failure as soon as moved threads outlive a proof (TASKS item 98) or a block fills. The module's new paragraph says the bound holds "for the machine", but the check is still per processor.
- **Fix:** compare machine-wide sums, or count each slot's and zombie's record against the block its number names (`Block::split`), not against the processor that queues it.

#### R96-4 (risk): integrity is Refuse, but its `reached` clause depends on timing, and both proofs' windows start before their threads do

- **Where:**
  - `migration_proof.rs:620` and `:634`: `reached` in integrity's `ok`;
  - `bootproof.rs:131`: `MigrationIntegrity => Refuse`;
  - deadlines at `:579` (integrity, SECONDS+1) and `:842` (delivery, SECONDS), both set when `Shared` is made, before the spawns and the start wait of up to 2 s (`:597-601`, `:867-871`).
- **What goes wrong:**
  - ADR-0013 R1(b) admits a Refuse proof only if a correct kernel on a correct machine cannot fail it through timing or load. "Every processor a source and a destination" needs enough successful moves inside a 2 s window, paced at one per thread per boot-processor tick.
  - On a heavily loaded emulated host, the ticks are merged, the mover gets few iterations, the threads' deadline has partly passed during the start wait, and moves meet `NotReady` or `TryLater`. A correct kernel can then fail `reached`, and the boot is refused. ADR-0020 S23's integrity row does not list this clause.
  - For delivery, the same start wait shortens the senders' window. A missed `reached` then fails the proof without withdrawing moves (R96-1).
- **Fix:**
  - Make integrity's coverage clause Report (split it out, as R1 says for mixed results), or a structural guarantee, such as a directed move to each processor, retried on refusal with a budget of seconds.
  - Set each proof's deadline after its threads have started.

#### R96-5 (risk): `followed` classifies a wake-up's follows by a `movable()` read made after the loop, with no lock

- **Where:** `sched.rs:1194-1206`; the read semantics at `framekernel/frame/sync/src/threads.rs:275`.
- **What goes wrong:** the follows go to `Follows` if `record.movable()`, and to `WAKES_FOLLOWED` otherwise. That read happens after `follow` has released every lock. Take a wake-up of a movable thread that followed a move, then ended `Reached`, `Gone` or `Stale`. In the window before `followed`, the thread exits, is reaped, and its record is taken by a spawn that is not movable (`Block::take` clears the flag at `threads.rs:367`). The follows then land in `WAKES_FOLLOWED`, which every settle and the IPC proof require to be 0, and that settle fails falsely.
  - With interrupts off the window is short on hardware. Under the emulator, the host can deschedule the virtual processor for milliseconds inside it.
  - No spawn runs concurrently with moves in today's proofs, so it is latent.
- **Fix:** read `movable()` under the lock, when the generation was found equal, and return it in `Wake`, for example as a `movable: bool` alongside `retries`.

#### R96-6 (risk, low): the search after a misplaced location can miss a thread that an in-flight move carries past it

- **Where:** `framekernel/frame/sync/src/threads.rs:751-770` (`after_misplaced`) and `:773-806` (`search`).
- **What goes wrong:** `pin` sets pinned mode, then the search locks queues 0 to n−1, one at a time. A mover that read `withdrawn() == false` under its source's lock before the entry may still complete one move.
  - If it moves the thread from a queue the search has not reached to one it has passed, the search finds it nowhere. The wake-up then ends `Outcome::Misplaced`, and the kernel returns `false` (`sched.rs:1180-1184`). The wake-up is lost, and that thread may block for ever.
  - This is reachable only after an inconsistency, but S20 says the system then "goes on pinned".
- **Fix:** if the search finds nothing, follow the location once more with moves withdrawn (`follow`, which now ends within one move), or search a second time. Count it as a later trigger.

#### R96-7 (note): a debug build stops on the first exhaustion of a movable thread, not on the second

- **Where:** `sched.rs:1196-1199`, reached from `wake_inconsistent` at `sched.rs:1169-1171`.
- **The behaviour:** after trigger 4, the second loop reaches the thread with `retries ≥ 64`. `followed` then asserts `retries <= 8` and panics in a debug build. S20 says trigger 4 enters pinned mode "and the boot or the system goes on pinned", and the kernel's own rule (Q17) is to stop only on a second exhaustion. Release builds behave as designed.
- **Fix:** skip the assertion when `retries ≥ WAKE_TRIES` (the inconsistency path), or move it to the `wake` common path only.

#### R96-8 (note): the "register canaries" are almost certainly on the stack, not in registers

- **Where:** `migration_proof.rs:502` and `:513`.
- **Why:** `black_box(register_canaries(index))` gives six `u64`s. They stay live across calls to `take_word`, `wait_until`, `yield_now` and others, and the second `black_box` needs them in memory. With frame pointers forced, only five callee-saved registers remain, and other values are live too. The compiler will spill them.
- **Consequence:** the check is a second stack canary. Wrong general-register restoration across a move is caught only indirectly, as a crash or a wrong pointer in `shared` or `me`. The line and the ADR's "register canaries" claim more than the code checks. Precise register canaries need `asm!`, and this file forbids `unsafe`. Either reword the claim, or add a framework helper that loads values into named callee-saved registers and reads them back across a yield.

### Verdicts on properties 1–11

**1. A context runs on at most one processor across a move: holds (by reading).**
- **The window between hook and switch.** `lend` reads `current` (Acquire) first and refuses `NotYet` when the running home is in the frame's stack (`contexts.rs:1188-1203`). It reads the leaving record next (`:1204`), then the slots, taking the frame by compare-and-swap (`:1206-1225`).
  - `switch` writes the leaving record (`:578`) before its Release store of `current` (`:527`).
  - A mover holds the source's queue lock, taken after the hook that named the frame released it. So it reads either the old `current` (T's slot, giving `NotYet`), or the new one, synchronized with the Release, which shows the leaving record or its later publication (`Leaving`, or found in the slot).
  - Publication happens only on another stack, at the next call into the table.
- **The same-stack check is the kernel's own.** `move_context` passes `crate::stack::same_slot` itself (`cpu.rs:954`), and the caller cannot pass another. The mover publishes only its own processor's leaving frame, while it runs on its own stack (`cpu.rs:946-948`). That frame is never the mover's own, because a switch records only the outgoing context's frame.
- **The source cannot resume the frame.** The run-queue checks (`runqueue.rs:897-903`: ready, not current, not slot 0) under the source's lock mean the source's scheduler has not named the frame. `depart` removes the thread before the lock is released.
- **The destination resumes it only after adoption.** `adopt` claims the slot and stores the frame (Release) before `between` runs, and the destination's scheduler can pick the thread only after the mover releases its lock (`sched.rs:1403`). `forget` comes after `between` (`contexts.rs:875-905`).
- **What I did not establish:** LV3 and its controls LX5 and LX6 (`loom.rs`) were not run by me. The S5 race itself (trap exit versus resume) is covered by LV1 and the leaving record, not by the boot proof's word, as ADR-0020 says.

**2. Every move under both queue locks in index order, with every check: holds.**
- `move_once` locks in index order (`sched.rs:1346-1356`).
- Under the locks it checks, in turn:
  - the location read again (`:1357`);
  - the generation (`:1360`);
  - `withdrawn()` (`:1364`);
  - that the slot holds the record (`:1369`);
  - ready, not current, not slot 0, through `frame` (`:1373`, `runqueue.rs:897`);
  - movable, and pins 0 (`:1377`);
  - that both processors take part (`:1381`);
  - room at the destination (`:1385`).

  Then it moves under the gate (`:1388-1402`).
- `cpu::move_context` is the only function that calls `MOVES.relocate` or `begin` (`cpu.rs:937`, the host test at `trap.rs:864`). Its only caller is `move_once`, which I checked with git grep.
- The pin and movable reads are ordered after their writers by the chain of queue locks: the spawner's push, the switch-out hook, and each earlier mover.

**3. Pending wake-up and lag survive a move; nothing else is lost or duplicated: holds.**
- `depart` (`runqueue.rs:919-950`) takes the frame, weight, pending wake-up, record and lag (pass less floor, its own pass included, saturating). It frees the slot and clears its record, woken mark and pending wake-up.
- `arrive` (`:954-980`) pushes, which sets a new slot generation, the weight and record, and the pass at the floor before it joins. It adds the lag, sets the pending wake-up and marks the slot woken.
- The record's location moves in the same critical section (`sched.rs:1400`).
- The randomized model test (`runqueue.rs`, the `against_a_model` module) checks every field after each step, with `held` too.

**4. Wake never loses a moving thread's wake-up, nor wakes the wrong slot: holds on every consistent path.** See R96-6 for the inconsistent path.
- `follow` compares the generation, then `holds` (an address compare through `held`, which reads the record without the state), and only then wakes (`threads.rs:680-692`; `sched.rs:830-845`; `runqueue.rs:671-685`).
- The loop is bounded by `WAKE_TRIES = 64`. Exhaustion enters pinned mode, then a second loop runs, and a second exhaustion panics (`sched.rs:1175-1179`).
- A misplaced location makes one search, one lock at a time (`threads.rs:773-806`), which wakes only a slot found by number with an equal generation.
- The kernel composes `follow` with `wake_inconsistent`, which calls `after_inconsistency` (`sched.rs:1067-1101`, `1143-1185`). That is the generic `wake`'s composition (`threads.rs:603-631`), with the number found by `number_of`.
- What differs: the models' `holds` compares the number through `record()`, while the kernel compares addresses through `held()`. Both are allowed by the trait's documentation, but the kernel's form is untested against a different record (R96-11).

**5. Pinned mode: holds as specified, except trigger 1 (R96-1) and the debug-build stop (R96-7).**
- **Recording.** A compare-and-swap records the first trigger, and later triggers are counted (`sched.rs:948-958`).
- **Movers.** Every mover reads `withdrawn()` under both locks and holds them to the move's end (`:1364`, `:1403`).
- **The line.**
  - It is owed only by the caller that entered pinned mode: `report` runs only if `entered` (`threads.rs:740`, `:761`); `owed` is set only when `enter` returns true (`sched.rs:1326-1331`); delivery uses `entered_here`.
  - For a wake-up it is written inside the section, through `Console::new()`, after `follow` or the search has released every queue lock.
- **No deadlock.** `SINKS` is taken only with interrupts off (`console.rs:734-745`, `873`), and nothing under it takes a run-queue lock or calls `wake`; I checked `console.rs` with grep. The panic handler takes no run-queue lock (`kernel.rs:2126-2147`), and its urgent writer tries the lock a bounded number of times, then writes around it. So neither lock nests in the other, including on a panic.
- **The second exhaustion** panics (`sched.rs:1175`).

**6. The interrupts-off token: holds.**
- `InterruptsOff`'s field is private, and its constructor is private and on the kernel target only (`trap.rs:106-131`).
- Its makers are `section_off`, whose closure takes a lifetime for every `'a` so the token cannot escape (`trap.rs:364`), and `Switch::interrupts_off`, whose token is bounded by the borrow of a `Switch` that only `dispatch` makes (`trap.rs:40`, `:59`).
- `host_section_off` exists only off the kernel target (`trap.rs:415`).
- The token is `!Send` and `!Sync`. Its doctests show it can be neither returned nor sent.
- `Moves::begin` requires the token, and `Moving<'a>` cannot outlive it (`contexts.rs:850`).
- Only `move_context` begins a move: the host test at `trap.rs:864` checks this, and `MOVES` and `CONTEXTS` are `pub(crate)`.

**7. `take` from any block, and `number_of` as the inverse of `record`: holds.**
- `take_from_any` looks in the processor's own block, then in each other block round from `cpu + 1`. It returns `None` when the count is 0, and cannot overflow (`threads.rs:422-433`, and its host test).
- `take` resolves the number from the block it took from (`framekernel/src/threads.rs:266-275`).
- `number_of` searches each block by address and builds `Block::number(block, index)` (`:255-260`). `record` is `split`, then `get`. Records never move, so the two are inverse.
- See R96-3 for the accounting that cross-block takes break.
