## Findings

1. **R94-1. High: six host tests in `framekernel/src/bootproof.rs` were not updated for the new proof row.** Adding `FpuFormat` makes `Proof::ALL.len()` 72, but the tests still expect 71:
   - line 313: `assert_eq!(Proof::ALL.len(), 71)`
   - line 376: "64 of 65 proofs passed; 6 did not run"
   - line 427: "71 of 71"
   - line 439: "68 of 71"
   - line 450: "69 did not run"
   - line 461: "70 of 71"

   `bootproof` is compiled for the host (`lib.rs:119`; xtask uses `Proof::ALL`), so all six fail. The commit message itself says QEMU now prints "71 of 72", so the boot ran but these tests evidently did not. **Fix:** 72; "65 of 66 … 6 did not run"; "72 of 72"; "69 of 72"; "70 did not run"; "71 of 72".

2. **R94-2. Low: the records are missing the new proof row.** ADR-0013's Report table (`docs/adr/ADR-0013-boot-proof-policy.md`, about lines 137–160) has no "FPU format" row. Earlier proofs added theirs ("added by TASKS item 62/68"). No requirements row cites `proof:FPU format` either. **Fix:** add the row (Report until item 96; a correct kernel fails it on a machine whose processors differ) and cite it in the matrix.

3. **R94-3. Low: `takes_part_in_moves` returns true for an offline processor.** Scenario: an AP passes every check and stores `FPU_ALIKE` (`smp.rs:1118`), but answers after the 200 ms wait. `answer` fails (`smp.rs:1121`) and the AP is parked, yet `CPU_STATE[index]` still says alike (`cpu.rs:692`). This is documented ("ask only of online"), but item 96's mover gets a trap. **Fix:** have the mover's query take `&Online` (or check online inside), so it cannot be asked about an offline index.

4. **R94-4. Low: an allocation in the AP start loop that cannot fail gracefully.** `differing.push` (`smp.rs:404, 413`) panics on an empty heap mid-bring-up. That goes against F8's rule that bring-up allocations fail as `NotStarted::Memory`. It is rare: only an AP whose format differs, on an exhausted heap. **Fix:** `try_reserve`, or print the CPU's line inside the loop and keep only a count.

5. **R94-5. Info: `USE_XSAVE` is still a global that every AP writes before it is judged** (`cpu.rs:2358`). This is safe only because the boot processor halts below the baseline (`kernel.rs:155–169`), so XSAVE is always on there. If that ever loosened, an AP that is refused would leave the boot processor running XSAVE with CR4.OSXSAVE clear (#UD). **Suggest:** derive it once from `BOOT_FPU` (`xcr0 != 0`).

6. **R94-6. Info: the AP reads EBX from leaf 0Dh without checking that the leaf exists** (`cpu.rs:2363`, no `max_basic >= 0xD` check). Only a hypervisor that reports XSAVE without leaf 0Dh could feed garbage here. A garbage EBX smaller than the real size would get past the TooLarge refusal and allow an XSAVE past the area. **Suggest:** treat that case as refused.

7. **R94-7. Info: the host tests pin only `fpu_fit`.** They cover equality on both fields, the room check first, `None` before the record, and a randomized pass, so the comparison itself is pinned. Not covered on the host: the AP's order of reasons to refuse (SMEP/SMAP, baseline, room) and the `CPU_STATE` bit encoding. That code is in `cpu.rs`/`smp.rs`, which build only for the kernel target. The boot controls C94-1/C94-2 are cited in comments, but nothing in this diff shows they ran. The plan's acceptance needs them. **Suggest:** a pure `ap_lacks(smep_smap, baseline, fit)` function with a host test.

## The invariants (all hold)

- **I1 holds.**
  - The boot processor's XCR0 is written once (`early.rs:274–276` guard).
  - Each AP writes it once in `ap_entry`, before its answer.
  - The alike bit comes only from `FpuFit::Alike`, which needs equal XCR0 and equal size (`smp.rs:1070, 1118`; `features.rs` `fpu_fit`).
  - The boot processor is alike by construction (`smp.rs:294`, after the STARTED guard).
- **I2 holds.**
  - The area is in `BOOT_FPU`, a SetOnce (`cpu.rs:2259, 2386`).
  - Its only caller is `early.rs:283`, at `kernel.rs:126`, before the heap exists, so no area can be allocated earlier.
  - The size is max(ECX, EBX).
  - `FpuArea::new` (`stack.rs:949`) and `fpu_init_area` (`cpu.rs:2410`) read the same value.
  - The old per-AP overwrite of the area size is gone, which is a real fix.
- **I3 holds.** The AP refuses before its handshake (`smp.rs:1081–1093`). `start_one` parks it before returning `NoFpuRoom` (`smp.rs:920`), and it is never added to the online list.
- **I4 holds** (with finding 3 as the caveat).
  - One Release store, no read-modify-write (`cpu.rs:656–660`).
  - The AP records only after every check, including the check that it is the processor its CPU index names, so its `this_cpu()` slot is its own. The old code recorded before that check, which allowed a second writer; that is fixed.
  - Reads are only over processors online (`smp.rs:412, 505`; `kernel.rs:305`).
  - Ordering: the fpu fields, `lacks` and `CPU_STATE` are written before the AP settles the handshake (an AcqRel compare-exchange). `abandon` acquires on failure (`apstart.rs:121–127`), so the boot processor's later reads see them.
- **I5 holds.** XGETBV reads back the XCR0 and CPUID EBX is read after XSETBV (`cpu.rs:2357–2363`). The area uses ECX, which does not depend on XCR0.
- **I6 holds.** `fpu_save`, `fpu_restore` and `FpuArea::save`/`restore` are untouched. Only `fpu_area_size()` changed, and it runs on spawn, not on a switch.
