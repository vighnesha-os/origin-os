2. **R94-2. Low: the records are missing the new proof row.** ADR-0013's Report table (`docs/adr/ADR-0013-boot-proof-policy.md`, about lines 137–160) has no "FPU format" row. Earlier proofs added theirs ("added by TASKS item 62/68"). 3. **R94-3. Low: `takes_part_in_moves` returns true for an offline processor.** Scenario: an AP passes every check and stores `FPU_ALIKE` (`smp.rs:1118`), but answers after the 200 ms wait. `answer` fails (`smp.rs:1121`) and the AP is parked, yet `CPU_STATE[index]` still says alike (`cpu.rs:692`). 4. **R94-4. Low: an allocation in the AP start loop that cannot fail gracefully.** `differing.push` (`smp.rs:404, 413`) panics on an empty heap mid-bring-up. That goes against F8's rule that bring-up allocations fail as `NotStarted::Memory`. It is rare: only an AP whose format differs, on an exhausted heap. **Fix:** `try_reserve`, or print the CPU's line inside the loop and keep only a count.

5. **R94-5. Info: `USE_XSAVE` is still a global that every AP writes before it is judged** (`cpu.rs:2358`). This is safe only because the boot processor halts below the baseline (`kernel.rs:155–169`), so XSAVE is always on there. If that ever loosened, an AP that is refused would leave the boot processor running XSAVE with CR4.OSXSAVE clear (#UD). **Suggest:** derive it once from `BOOT_FPU` (`xcr0 != 0`).

6. **R94-6. Info: the AP reads EBX from leaf 0Dh without checking that the leaf exists** (`cpu.rs:2363`, no `max_basic >= 0xD` check). Only a hypervisor that reports XSAVE without leaf 0Dh could feed garbage here. A garbage EBX smaller than the real size would get past the TooLarge refusal and allow an XSAVE past the area. **Suggest:** treat that case as refused.

7. **R94-7. Info: the host tests pin only `fpu_fit`.** They cover equality on both fields, the room check first, `None` before the record, and a randomized pass, so the comparison itself is pinned. Not covered on the host: the AP's order of reasons to refuse (SMEP/SMAP, baseline, room) and the `CPU_STATE` bit encoding. That code is in `cpu.rs`/`smp.rs`, which build only for the kernel target. The boot controls C94-1/C94-2 are cited in comments, but nothing in this diff shows they ran. The plan's acceptance needs them. **Suggest:** a pure `ap_lacks(smep_smap, baseline, fit)` function with a host test.

## The delta review of the answers (2026-11-21)

> The four commits are correct. I found one gap that breaks P5. It was there before these commits, but R94-4's fix left it in place. The other findings are hardening or notes.
>
> 1. **R94-8. Medium: `smp.rs:221-224` (`Online::add`, called at `smp.rs:426`) does an infallible `Vec::push` inside the AP start loop.**
>    - Scenario: a machine with many processors and a heap nearly used up by the per-AP stacks, tables and `ApStart` records. `start_one` succeeds, so the AP is online and running its scheduler. Then `online.cpus` has to grow (capacity 1, then 4, 8, …), the allocation fails, the default no_std alloc-error handler panics, and the boot processor halts.
>    - This is the same class of bug as R94-4 and F8: `differing` was made fallible, but `online` was not.
>    - Fix: reserve before INIT is sent. Either `online.cpus.try_reserve(1)` before `start_one`, with a failure counted as `NotStarted::Memory` and `continue`, or `try_reserve_exact(to_start)` once before the loop.
> 2. **R94-9. Low: `early.rs:503-505`. `start_heap` does not require `enable_simd` to have run.** P2 holds only because `kernel.rs:126` calls `enable_simd` before `init_memory` and `start_heap`.
>    - Scenario: if those calls are reordered, `FpuArea::new` (`stack.rs:949`) sizes an area at 512 bytes, because `fpu_area_size()` falls back to that before anything is recorded. `record_boot_fpu` then sets `USE_XSAVE`, and an XSAVE into that area writes past its end.
>    - Fix: have `start_heap` return `false` while `self.xcr0.is_none()`, or have `FpuArea::new` return `None` while `boot_fpu_format()` is `None`.
> 3. **R94-10. Low (existed before; trusts CPUID): `cpu.rs:2388`. Under XSAVE the area has no minimum size.**
>    - Scenario: a hypervisor reports leaf 0DH with ECX below 576, so `xsave_area_size` gives `None`, and EBX also below 576. The area is then 512 bytes while `USE_XSAVE` is true, so every save writes the 64-byte XSAVE header, and the AVX state at offset 576, past the end.
>    - Fix: when `xcr0 != 0`, refuse below the baseline unless `enabled_size >= 576`, plus 256 when AVX is in XCR0. Apply this in both the `kernel.rs:158` check and the AP's baseline check.
> 4. **R94-11. Info: `smp.rs:245-251`. The binary search depends on `add` only ever adding larger indexes.** That is true today: `CpuMap::iter` is `enumerate()` (`cpumap.rs:152-154`), `add` is called only at `smp.rs:426`, and the boot processor is index 0 (`cpu.rs:388`). Suggest `debug_assert!(self.cpus.last().is_none_or(|l| l.get() < index.get()))` in `add`.
> 5. **R94-12. Info: `USE_XSAVE` is stored Relaxed after `BOOT_FPU.set` (`cpu.rs:2395`).** APs see it in time because it is written long before INIT-SIPI and through the handshake chain. That is fine in practice, but nothing in Rust's memory model guarantees it.
>
> - **P1: holds.** XSAVE is used only when `xsave_usable` is true, so `xcr0 != 0` exactly when the boot processor's CR4.OSXSAVE is set, and `USE_XSAVE` is derived from that. Boot processor without leaf 0DH, or without XSAVE: XCR0 is 0, `avx_state` is false, and the kernel halts before the heap starts or any thread runs. AP with XSAVE but no leaf 0DH, or with no XSAVE: XCR0 is 0, the baseline fails, and it refuses and halts without ever saving. Every AP online has XCR0 & 7 == 7, so OSXSAVE is set; no CR4 write clears OSXSAVE.
> - **P2: holds at runtime, but only through call order (finding 2).** `USE_XSAVE` is written once, only after `SetOnce` succeeds, and `record_boot_fpu`'s only caller is `early.rs:283`.
> - **P3: holds.** `cpus()` is `..count` with `count == len`, the list is strictly ascending (finding 4), and the `&&` means the record is read only for a processor online.
> - **P4: holds.** `ap_lacks` gives the same order and the same constants, and the host test covers all 12 input combinations. Every refusal halts before `record_cpu_state`.
> - **P5: partly.** Fails: `online.add` can panic (finding 1). Holds: `differing` uses `try_reserve` and then `push`; when every processor is alike, the line is unchanged; `Console::write_str` writes into a fixed buffer and does not allocate.
> - **P6: holds.** The diff adds no `this_cpu()` call.
>
