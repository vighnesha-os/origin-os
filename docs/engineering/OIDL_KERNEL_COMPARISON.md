## Summary

Every value matches: 13 statuses and `OK`, 9 rights and their mask, the channel-rights constant, 5 signals and their mask, 7 object types, 11 call numbers, 3 limits, the `read_sizes` layout, `INVALID_HANDLE` and the boolean rule. Argument decoding gives the same status in all 2.26 million cases.

One behaviour differs, in one narrow case (item 5). Everything else below is a difference in shape, naming, or what the definition can express.

## Differences in behaviour

| # | Where | Hand-written | Generated | Effect |
|---|---|---|---|---|
| 5 | `handle_duplicate` | Checks the handle, that `rights` fits in 32 bits, the `out_handle` pointer (`FAULT`), then undefined rights bits (`INVALID_ARGS`) | Decodes `rights` as the `rights` bits type, so undefined bits are refused **before** the pointer is looked at | A call with both an undefined rights bit and a bad pointer gets `INVALID_ARGS` instead of `FAULT`. Status precedence between two errors is not an ADR-0005 promise, and only such a doubly invalid call can see it. To reproduce today's order exactly the definition could use `u32`, losing the type |

That is the only behaviour difference in decoding. The other checks and their order are the same, including `channel_write`'s limits (`INVALID_ARGS` before the copy), `channel_read`'s clamped capacities, `wait_one`'s mask rules and the developer-call gate.

## Differences in the declared errors

Each method now has a closed set of errors (spec §8). The kernel's code was read to see what each call can actually return:

| Method | Declared in OIDL | The kernel today | Difference |
|---|---|---|---|
| `channel_write` | … and `wrong_type` | Only channels exist, so `wrong_type` is unreachable (`let Object::Channel(end) = object` is irrefutable) | Declared for the future, not returned today |
| `channel_read` | … and `wrong_type` | The same | The same |
| every other call | exactly the statuses its code can return | — | none |

The hand-written kernel also answers `ACCESS_DENIED` before `dispatch` when a call comes from outside the process's permitted code range (`may_call_from`, ADR-0005 A6). That check sits outside the interface: a program going through `origin.core` cannot reach it, and it is not declared on any method.

| 9 | `syscall::THREAD_EXIT` … | `server::number::THREAD_EXIT` … | Moved out of the types module, as ADR-0011 N9 requires |

| 11 | `limits::DEADLINE_INFINITE` | The same `u64` | — |

## Things the definition does not express

| Item | Why it stays hand-written |
|---|---|
| The `start` module of `origin-abi` (the start record: `HEADER`, `ENTRY`, `MAX_HANDLES`, `role`, `encode`, `decode`) | It is not a system call. Its variable-length tail after a header is not a form the language has: variable-length data exists only as a method's parameters (§3.1). Its header and entries would fit as plain structs |
| `run()` in `syscall.rs` (interrupts on, `reap_closed`, `sched::reap`, `may_call_from`) | The kernel's entry path, outside any interface |
| The user-memory checks (`checked`, `copy_in`, `copy_out`) | They need the calling process's page tables. The decoder produces typed descriptors, and the kernel does the copy, as today |
| The rights a call needs | Declared in OIDL and carried to the kernel in `HandleArg::need_rights()` and `HandleSlice::need_rights`, but the check stays in the kernel's handle table |

## What switching would take

Nothing here was switched: another session may be restructuring the kernel (ADR-0011 N6). The owner accepted the format on 2026-11-09 (`docs/spec/OIDL.md` §19), so what remains is the work itself:

1. Replace `origin_abi`'s hand-written tables with the generated `types.rs`, and adjust the handful of names in the table above.
2. Have `framekernel::syscall` implement the generated `Calls` trait, honouring `need_rights`.
3. Decide item 5: keep the definition's stricter order (accepted here) or use `u32` for the `rights` argument.
4. Wire the generator into `cargo xtask check` (ADR-0011 N13): generated code up to date, and the fingerprint gate.
