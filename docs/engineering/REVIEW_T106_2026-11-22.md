## What holds

- **The notification protocol, as `service` orders it, is Intel's** (Vol. 3 §17.6.6, p. 560; §17.6.5, p. 559). The service reads the status under the package's lock with interrupts off. If bit 26 is clear, it returns `Quiet`. If set, it copies the class-0 flags, then every member's class-0 cells, then runs the rescale, and **only then** writes the acknowledgement. Since the hardware writes nothing while bit 26 is set, every row read belongs to one update. A second processor taking the same interrupt finds the bit clear. An update that lands after the acknowledgement sets the bit again, and some processor takes its own interrupt for it, so no update is lost. The one gap is the stale-bit case in R106-7.
- **The acknowledgement value matches Vol. 3 §17.9** (pp. 573 and 574):
  - R/WC0 logs 1, 3, 5, 7, 9 and 11 are written as 1, which leaves them;
  - the read-only bits 0, 2, 4, 6, 8, 10 and 22:16 are written as read;
  - bit 26 (R/WC0, §17.6.6) is written as 0;
  - every reserved bit is written as 0.

  `hwp_acknowledgement() = 0b11_0101` matches §17.4.6 (pp. 541 and 542). It writes 1 to the R/WC0 bits 0, 2, 4 and 5, and 0 to bit 3 and to reserved bit 1. -093 defines bits 4 and 5 whatever CPUID says; only their interrupts need EAX\[16\].
- **Control C5 is caught.** If `service` acknowledged before reading, the model's `write_status` would run `hardware()`. With an update pending, the copies would then read the new table, and `view != expected` would fail. With none pending, the copies would run while bit 26 is clear, and `reads_while_clear` would fail. The random test reaches both, so `no_update_is_lost_and_no_row_is_read_after_the_acknowledgement` tests what its name says. `the_acknowledgement_clears_bit_26_alone` catches C6.
- **The MSR probe is built correctly.**
  - **Argument registers.** Under sysv64 the arguments arrive in RDI, RSI, RDX and RCX. `read_msr` takes the register in ECX and stores EDX:EAX through RDI. `write_msr` moves the low half from EDI to EAX, takes the high half in EDX and the register in ECX.
  - **`WRMSR_AT = 2`.** `.byte 0x89, 0xf8` is MOV r/m32, r32 with ModRM 11 111 000, which is `mov eax, edi` in two bytes, so WRMSR sits at offset 2.
  - **Recovery.** #GP is a fault, so the saved RIP is the instruction itself. The error code, 0 for RDMSR and WRMSR, can never equal `COMPLETED`. `probe_recover`'s `ret` pops the probe's return address, because neither naked function pushes anything.
  - **Nothing else recovers.** A #GP is recovered only when its RIP is armed on this processor *and* is one of the two MSR-probe addresses. A user-mode #GP leaves `dispatch` earlier. Every other probe's #GP still reaches the report. `run_probe` keeps interrupts off around the access, so no nested interrupt can arm or disarm the probe.
- **Hostile inputs are bounded.**
  - `Words::pages()` is at most 16.
  - `row_offset` is checked arithmetic.
  - `Table::copy` checks `at + len <= pages × 4096` before any volatile read.
  - `cells()` is at most 8, the size of `service`'s stack array.
  - `scale_into` multiplies in u64 and writes nothing until the whole list is validated.
  - Every per-processor lookup goes through `PerCpu::get`.

  I found no indexing by a table byte or a CPUID word that is not checked.
- **`choose_into` makes the same choice as `choose` did.** The reference copy of TASKS 97's `choose` in the test is exact. Sources come in the same order. For `_CPC` and the register, any `None` or a 0 refuses the source; for the HFI, a 0 is a value. A top value of 0 refuses the source, and an empty list gives `Equal`.
- **Locks and interrupts.** Every holder of `JOINING`, a package lock and `RESCALE` holds it with interrupts off. The handler runs from an interrupt gate, and the other paths use `without_interrupts`. The handler never takes `JOINING`. `RESCALE` is only ever taken inside a package lock or alone, never the other way round, so I see no deadlock. The handler allocates nothing: the rescale's `Scratch` is allocated once in `start_capacity`.
- **The witnesses follow TASKS 93's rules.** `round` holds a `Pinned`. It makes a fresh `ThisCpu` in each send iteration and holds no `Here` across `interrupt_window`. Its wait loop runs under plain `without_interrupts`, which makes no witness. The handler uses its trap witness. `Switch::new` is still made only in `dispatch`, so `only_the_trap_entry_makes_a_switch` still passes after its dedup.
- **No HWP or CPPC enable or request register is written** (ruling Q2). IA32_PM_ENABLE and CPPC_ENABLE are read only. Highest is read only where they read 1. IA32_HWP_STATUS is touched only where HWP is on (§17.4.2, p. 535).
- **`_CPC` stays where ADR-0019 A2 and A3 put it.** It is evaluated only inside the QEMU-only AML proof, every register is answered "not read", and nothing feeds source 2. The test's counts (7 processors, 5 with `_CPC`, 2/1/1/1) follow from its DSDT.
- **The table memory meets invariant 1.** It is a run given up for ever. It is zeroed through the direct map before IA32_HW_FEEDBACK_PTR names it, it is never mapped to a program, and the pointer is 4 KiB-aligned with the valid bit set (§17.6.4).
- **xtask's TCG lines match the kernel's format strings.** I traced the five capacity lines and the domains line character by character.
- **The gates' inputs are in place.**
  - `hfi.rs` is on `UNSAFE_FILES`.
  - `hfi/tests.rs` and `capacity.rs` forbid `unsafe`, and `cpc.rs` falls under the kernel crate's `forbid`.
  - `hfi::SLOTS` is sized in `size_per_cpu`, and `PerCpu::new` names it `origin_frame::hfi::SLOTS`.
  - The bootproof bitmask is u128, so 74 rows, or 76 after TASKS 96, fit.
- **The ledger's Intel paraphrases agree with Vol. 3 -093.**
  - §17.4.2: the access rule and IA32_HWP_INTERRUPT's exception.
  - §17.4.6: the HWP_STATUS bits.
  - §17.6.4 and §17.6.5: retained across INIT.
  - §17.6.6: bit 26, and the initial notify on bit 25's 0-to-1 change.
  - §17.6.9: GETSEC resets, and INIT or wait-for-SIPI resets only the thread enable.
  - §17.8.2.5: about 1 ms engaged.
  - §17.9: the bit layout.

## Findings

### R106-1 (High): a new host test fails, so `check` fails: `a_rows_cells_read_as_the_whole_table`'s "no copy means no row" arm is false

**Where.** `framekernel/frame/src/capacity.rs:896`, `(None, whole) => assert_eq!(whole, None, …)`.

**What is wrong.**
- `copied` needs all `cells()` bytes of a row inside the table.
- `hfi_row` (TASKS 97's whole-table reader) needs only the bytes it reads: the performance cell and, where enumerated, the efficiency cell.
- So a table that ends inside a row's cells, after the cells read, has no copy but does have a row.

**Failure scenario.** I ported the test's generator and checks from the Rust (xorshift64*, seed `0x0106_CE11`, the same argument order). 28 of the 5,000 cases hit that arm, and the first is case 67:
- Thread Director, capabilities `0b10111`, 11 classes;
- a 107-byte table, the row at byte 104, `cells() = 4`;
- the copy needs bytes 104 to 107 and gets `None`;
- `hfi_row` reads bytes 104 and 105 and returns `Some`.

The assertion panics, so `cargo test -p origin-frame` fails, and with it `cargo xtask check`.

**The kernel is not affected.** Its two paths agree with each other: `Words::row_fits` and `Table::copy` both require the whole `cells()`.

**Fix.** Either:
- in that arm, assert only that the copy path refuses (`shape.row_offset(row).is_none_or(|at| at + cells > table.len())`); or
- compare against `hfi_row` only where the table holds the whole row's cells.

Then re-run the test. Add a fixed case for the boundary, such as case 67's shape and length, so that the arm is tested on purpose, not by chance.

### R106-2 (Medium): ruling Q5's "no thermal source on that package" is not what the code does; the HFI is enabled before the package is known to be the kernel's

**Where.**
- `hfi.rs:837-842` (`join`): the first processor to arrive enables the HFI.
- `hfi.rs:749-766`: heat is enabled per processor, with no check of the package.
- `hfi.rs:12-16`, the module documentation, and the ADR-0020 note's "Source 1" bullet claim the rule.

**What is wrong.**
- **The enable comes too early.** The first processor of a package that holds its own LVT enables the HFI at once: the pointer, CONFIG bit 0, and IA32_PACKAGE_THERM_INTERRUPT bit 25, which is package scope. The other processors of the package have not yet shown whose their LVTs are.
  - If a later one finds its LVT unmasked or set for SMI (the firmware's), `P_NO_LVT` only stops the kernel *reading* the table.
  - Bit 25 stays set, so the processor's notifications also reach the firmware's SMM handler through that LVT.
- **Heat ignores the package.** IA32_THERM_INTERRUPT bits 0 and 1 are set on every processor whose own LVT is free. That includes processors of a package where another LVT is the firmware's. If, as I expect, that register is shared by a core's logical processors, setting it on one sibling also sends transitions to a firmware-held sibling's SMI. The ledger does not record its scope, and I did not read Vol. 4's scope column.
- **Heat is used on such a package.** It counts in `HEAT` and `throttled`, against Q5's "use no thermal source on that package".
- **The contract's order is not followed.** Its §1 step 1 unmasks the LVT of every processor of the package *before* enabling. The code enables at the first arrival.
- **The records claim more than the code does.** The ADR note says such a package "uses no thermal source".

**Failure scenario.** A machine whose firmware masks the thermal LVT on some logical processors and points it at SMI on others: for example, the firmware handles thermal events in SMM on one processor of each core or package.
- The kernel's first processor enables the HFI and its bit-25 interrupts.
- The SMM handler starts receiving HFI notifications and thermal transitions it never asked for.
- The kernel still reports the package as one it does not use.
- Nothing shows this under QEMU.

**Fix.** Split each processor's start into recording and taking. At start, record the words and whether the LVT is free, and take nothing that adds a source. Enable sources only once every processor has started, at the round, per package:
- If every processor's LVT is free and every signature agrees: take the LVTs, set the heat bits and HWP's bit 2 (each on its own processor, for example from that processor's round handler), and enable the HFI once.
- Otherwise: write nothing to that package.

This also removes R106-8's late joiner, because the initial notification then comes after every member has joined.

### R106-3 (Medium): the round's one-second deadline is a new acceptance bound, set with no figure from the 65- and 67-processor TCG machines

**Where.** `framekernel/src/kernel.rs:758`, `hfi::round(…, 1_000_000_000)`, and `hfi.rs:1229-1236`.

**What is wrong.**
- The proof fails if any processor has not taken the vector within 1 s.
- xtask holds `": hardware capacity failed"` as a boot failure, and expects `taken by {n}` on every machine, under KVM too.
- ADR-0020 S23 asks that a task which changes what a proof accepts first run a diagnostic round on the 65- and 67-processor machines. The TASKS 66 lesson is the same: bounds set without those figures failed correct kernels.
- `prove_random`, which waits for every processor in the same way, allows 10 s (`kernel.rs:1873`).

**Failure scenario.** `boot-matrix` on a loaded Mac. One of the 65 software processors is not scheduled for over a second after the IPI, so `handled = 64`. The line ends `consistent false: hardware capacity failed`, and the boot fails although the kernel is correct.

**Fix.**
- Use `prove_random`'s 10 s. The wait ends as soon as every processor has taken the vector, so a correct boot pays nothing for it.
- Print the round's elapsed time.
- Take the figure on 65 and 67 before the bound is settled.

### R106-4 (Low): IA32_HWP_STATUS is written, which the contract's invariant 6 does not list

**Where.** `hfi.rs:939`.

**What is wrong.**
- Invariant 6 names every MSR the kernel may write. IA32_HWP_STATUS is not among them.
- The write is needed, since §17.4.6 (p. 542) says software must clear Highest_Change before the next notification.
- The author disclosed it in the ledger's §4 and in the module documentation, but no ruling records it.

**Failure scenario.** None at run time. The value is correct. The risk is a security invariant that no longer says what the kernel writes.

**Fix.** Get the coordinating session's ruling. Amend invariant 6 in the hand-over and the TASKS entry to read: "IA32_HWP_STATUS, bit 3 cleared, the other R/WC0 bits written as 1, where HWP is already on." Also list the round's ICR IPI (R106-10).

### R106-5 (Low): taking the LVT turns on whatever thermal interrupts the firmware left enabled behind its mask

**Where.**
- `timer.rs:207`, where the LVT is unmasked.
- `hfi.rs:751` and `:893`, where every other bit is kept "as read".

**What is wrong.** After reset the enables are clear and the LVT is masked (§17.8.2.5, p. 567). But firmware may have set other enables while the LVT was masked:
- IA32_THERM_INTERRUPT bits 2 (PROCHOT#), 15 and 23 (the thresholds) and 24 (power-limit notification);
- the package register's bits 0 to 2, 15, 23 and 24 (§17.9, pp. 572 and 575).

Once the kernel unmasks the LVT, each of those sources interrupts. The contract's "no interrupt storm" argument (§17.8.2.5's roughly 1 ms) covers only bits 0 and 1. A power-limit notification is not bounded by it: Intel says only that the limit "may occasionally" push the processor below the requested state. The census reports none of this.

**Failure scenario.** A firmware that left bit 24 set. Every power-limit excursion costs an interrupt, and two or three MSR reads per processor, with nothing reported and nothing in CL58.

**Fix.**
- When the LVT is taken, record which enables beyond bits 0, 1 and 25 read as set, and report the count on the thermal-LVT line.
- Count interrupts that found nothing changed.
- If they matter, ask for a ruling to clear those enables. That would be a write outside invariant 6.

### R106-6 (Low): the #GP branch reads CPU-local data for every kernel #GP before it compares the RIP

**Where.** `cpu.rs:1457-1462`.

**What is wrong.**
- `local(Switch::new().here())` reads `gs:[0]` for every #GP that reaches this point, before `frame.rip == armed && is_msr_probe(armed)` is tested.
- Consider a kernel-mode #GP taken while GS still holds the program's base. The return path's `iretq` after `swapgs` is the case: the saved CS says ring 0, and the program's GS base is 0.
  - That read is of address 0, which faults.
  - The #PF branch then reads `local()` again, and so on until a double fault.
  - Before the change, such a #GP went straight to the report.

It is fatal either way. Only the report is lost.

**Fix.** Compare first: `if frame.vector == 13 && is_msr_probe(frame.rip) { let armed = local(…).probe_rip…; if armed == frame.rip { … } }`. The test is pure, keeps GS out of every other #GP, and leaves less new code in `dispatch` for the static counts.

### R106-7 (Low): a bit 26 already set when the kernel enables makes the first service read an unwritten, all-zero table, and every member reads "avoid"

**Where.** `hfi.rs:860-903` (`enable`), with `service`.

**What is wrong.**
- §17.6.5 (p. 559): when bit 0 is cleared, the processor *sets* bit 26 to acknowledge the disable.
- §17.6.6 (p. 560): while bit 26 is set, it writes no update.
- So firmware that enabled and then disabled the HFI leaves bit 26 set. When the kernel enables, the processor writes nothing.
- The first service then sees bit 26 and reads the zeroed table. Every member's row is all 0, so each gets `flags::AVOID`, and `P_WRITTEN` is set. Capacity falls back to source 3 or 5, because the top value is 0.
- This breaks the contract's invariant 4 (R97-14): a table not yet written never reads as "avoid". It lasts until the processor writes after the acknowledgement.

**Fix.** Either or both:
- in `enable`, read IA32_PACKAGE_THERM_STATUS first and acknowledge a set bit 26 before writing the pointer (the same write invariant 6 already allows);
- treat a table whose timestamp (offset 0, which Table 17-4 says the OS initializes to 0) is still 0 as not written: no `P_WRITTEN`, no rows. The timestamp check also covers any other way a stale bit could arise.

### R106-8 (Medium): `start_capacity` judges "every processor or none" over the processors that have *finished* starting, and the rest keep 1024, perhaps for good

**Where.**
- `hfi.rs:1121-1138` (`rescale` skips processors without `STARTED`).
- `kernel.rs:1707` (`start_capacity` in `prove_domains`).
- `smp.rs:1180` (`hfi::start_this_processor` runs after the handshake answer).

**What is wrong.**
- An AP counts as online before it runs `random::start_this_processor` and then `hfi::start_this_processor`.
- The kernel itself expects some APs to still be starting their generator later than `prove_domains`: `prove_random` waits up to 10 s "to give the last of them a moment". Each AP starts its generator before its HFI.
- So `start_capacity`'s rescale can run while some processors are not `STARTED`. It chooses a source over the others, and the missing ones keep the store's boot value, `FULL`.
- On a machine where only source 3 exists, such as AMD with CPPC enabled by the firmware, no notification ever comes, so no rescale follows. Those processors read 1024 permanently, beside scaled ones.
- The census's `started == processors` is checked only at `prove_capacity`, by when they have started, so nothing reports it.
- **Late joiners have the same root cause.** A processor that joins after its package's update was acknowledged gets no row until the processor writes again. The round's `check` finds bit 26 clear and reads nothing.

**Fix.**
- In `rescale`, iterate every online CPU index and give an unstarted one `None` for every source, so that "every processor or none" covers it.
- In `start_capacity`, wait, bounded, for `STARTED` on every online processor, as `prove_random` does, and report a processor that never starts.
- Late joiners go away with R106-2's fix, which enables at the round. Otherwise, keep a pre-allocated copy of the table from the last service and read late joiners' rows from it.

### R106-9 (Low): the handler takes two locks, while invariant 8 and the reason for "no Loom model" assume one

**Where.**
- `hfi.rs:1005` → `1044` → `1118`: the package lock, then `RESCALE`.
- `hfi.rs:940`: `RESCALE` alone.

**What is wrong.**
- Invariant 8 says the handler "holds only its package's lock". The contract dropped Loom because "the locking is one spinlock per package".
- The order (package, then `RESCALE`, never the reverse) is correct today, but nothing states it. A later edit could invert it, for example a rescale that takes a package lock to read a consistent view.

**Fix.**
- Document the order at `RESCALE`'s declaration and at `check`.
- Record the change to invariant 8, and the reason no Loom model is still needed, in the hand-over.

### R106-10 (Low): `send_device_vector` and `take_thermal` are public and safe, and the round sends 0x44 even when the handler is not registered

**Where.** `timer.rs:207` and `:297`; `hfi.rs:1221-1228`.

**What is wrong.**
- Any code in the kernel crate can now send any device vector, 0x40 to 0x4F, to any processor. That runs another driver's handler (NVMe, virtio-net) with no device event behind it.
- If `irq::register` refused 0x44 (`REGISTERED == 2`), the round still sends 0x44 to every processor, and runs whichever handler owns it.

**Failure scenario.** A later proof calls `send_device_vector(…, NET_VECTOR)`. virtio-net's handler runs with nothing completed. Its safety does not depend on that, but its counters and wake-ups do.

**Fix.**
- Make both functions `pub(crate)`.
- Restrict the send to `THERMAL_VECTOR`, or fold it into `round`.
- Skip the round's sends, and say why on the line, unless `REGISTERED == 1`.

### R106-11 (Low): "force idle" is taken from *either* capability's flag; Intel's rule needs bit 1 set across all of them

**Where.** `hfi.rs:1038`.

**What is wrong.** §17.6.7 (p. 560) gives force idle as two things together:
- a processor's cells zeroed across all classes;
- Capability Flag bit 1 set "across all capabilities and classes".

The code sets `P_FORCE_IDLE` on `performance_force_idle || efficiency_force_idle`.

**Fix.** Require bit 1 in every enumerated capability's flag of class 0: performance, and efficiency where EDX\[1\] enumerates it. Add a host case where only one flag has bit 1.

### R106-12 (Low): the TCG expected lines and the ADR note rest on M1 and M2, which are not measured; several records are not in the tree

**Where.**
- The ledger's §6 ("to be filled").
- xtask `capacity_markers`: "CPUID.01H:EDX\[22\] on 0", "HWP on 0", "AMD CPPC on 0".
- The ADR-0020 note: "What QEMU shows is the absence of every source".

**What is wrong.**
- **Measurements first.** The contract's §7 puts M1 and M2 *before any code that depends on the answers*.

### R106-13 (Low): control C1, as planned, cannot fire under QEMU

**Where.** The contract's §7, C1: "`hfi.rs` ignores CPUID.06H:EAX\[19\] → the probe catches 17D0H's #GP".

**What is wrong.**

**Fix.** Plant C1 on a path QEMU runs: for example, `Words::hwp()` returning true makes the kernel read IA32_PM_ENABLE (770H), which TCG faults on. State the expected first register on the line (`first 0x770`).

### R106-14 (Info): `Package`'s derived `Debug` prints the HFI table's physical address

**Where.** `hfi.rs:556` (`#[derive(Debug)] struct Package { table: AtomicU64, … }`), reached through `Slot`'s `Debug`.

**What is wrong.**

- TASKS 76 and 80's lesson is that a derived `Debug` holding an address is one `{:?}` away from a boot line.

### R106-15 (Info): "no row read before bit 26 is seen" holds only through `run_probe`'s SeqCst disarm

**Where.** `hfi.rs:965-990` (`Table::status`, then `copy`).

**What is wrong.**
- RDMSR is not a serializing instruction. Vol. 3 §10.3 (p. 333) lists WRMSR, not RDMSR. So nothing in the instruction itself keeps the table's loads after the status read.
- What does keep them after is `run_probe`'s `probe_rip.store(0, SeqCst)`, a locked XCHG on x86-64, after `read_msr`'s store of EAX. That store depends on RDMSR's result, so RDMSR has executed before the fence completes, and no later load passes the fence.

**Fix.** Say so in `Table::copy`'s SAFETY. Or add an explicit `lfence` after the status read, so that the protocol does not rest on how the probe disarms.

### R106-16 (Info): two notions of "avoid" now reach placement

**Where.** `capacity.rs`: `current()` and `avoid()`.

**What is wrong.**
- A row with performance 0 and efficiency above 0 scales to capacity 0. That is S17's "Avoid: a processor with capacity 0 takes no movable thread".
- Yet `flags::AVOID`, Intel's "avoid altogether" (§17.6.7), needs *every* cell to be 0.
- Items 98 and 99 will read both, so they need one rule.

**Fix.** Say in `current()`'s documentation which one placement must use, and tell items 98's and 99's sessions.

### R106-17 (Info): small accuracy points

- **`read` (`hfi.rs:669`) is safe over any MSR**, and `Table::write_status` (`hfi.rs:969`) over any value. Their SAFETY arguments hold only for their callers in the module. Narrow them: make `read` take the module's MSR constants, and let `write_status` take the status read and compute the acknowledgement itself.
- **Two `_CPC` failures are filed as "malformed".** `cpc::outcome` (`cpc.rs:62`) files an evaluation error that is not a refusal as `Malformed(NumEntries)`. A `_CPC` method that reaches a region outside spaces 0 to 2, such as PCC, counts as "not read otherwise" rather than refused.
- **"Reading a row" can count processors that read none.** The first capacity line's "{hfi_members} reading a row" includes processors whose package is not used (`P_NO_LVT`, `P_FIRMWARE_HFI`): `HFI_MEMBER` is set whatever the package's state.
- **The round checks "at least once".** It counts a processor as handled if its count rose. The contract's §6 says "handled exactly once".
- **The ledger's §7 notes that Volume 4 gives bit 1 of the thermal status registers as R/W.** Under that reading, writing the logs as 1 would *set* a clear bit 1. Following Volume 3, as the ledger does, is right. A one-line note in `acknowledgement` would say why.
