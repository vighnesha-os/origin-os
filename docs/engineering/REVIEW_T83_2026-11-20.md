## Findings

### T83-1 (High): CI's 8 GiB `boot-rented` will fail `check_memory` on a correct kernel

- **Where:** `developer-tools/xtask/src/main.rs:2607-2625` (`check_memory`, the rule `free * 100 < ram * 99`), with `settings.rs:308` (`large_memory`: 8 GiB when `GITHUB_ACTIONS=true`) and `main.rs:504` (`RENTED_SHAPE.top_reserved_pages = 8192`, 32 MiB).
- **What is wrong:** the 1% allowance is relative, but what the firmware keeps is roughly fixed, and the rented machine adds its own fixed 32 MiB. The records give the figures:
  - 64 GiB, `boot-large`: 65475 MiB free (STATUS), so about 61 MiB is not free.
  - 64 GiB, `boot-rented`: 65443 MiB free (`com1.log` line 42), so 93 MiB is not free, 32 MiB more.
  - 8 GiB, the findings' trial (`cargo xtask run`): 8133 MiB free (`docs/research/2026-11-20-rental-b-findings.md`), so 59 MiB is not free.
  - At 8 GiB the rule needs at least 8110.08 MiB free (8192 × 0.99). `boot-large` passes with about 23 MiB to spare. `boot-rented` should show about 8133 − 32 = 8101 MiB, and 8101 × 100 = 810100 < 811008, so it fails: "the frame allocator has 8101 MiB free of the machine's 8192 MiB: not within 1% of it".
- **Failure scenario:** the first pull request carrying this branch runs `boot-matrix` in three CI jobs (`ci.yml` `boot-software-cpu` and both `boot-real-cpu` runners, plus `processor-sweep.yml`). Each reaches `boot-rented` (Intel first) and stops there, although the kernel is correct. This configuration, the one ruling Q1 relies on ("so the shapes and the move are covered on every pull request"), was never booted: every recorded run is at 64 GiB. `boot-matrix` and `boot-rented` refuse `ORIGIN_QEMU_MEMORY`, so on the Mac only `GITHUB_ACTIONS=true` selects 8 GiB.
- **Status of this finding:** predicted from the recorded figures, not booted by this review. Under KVM, OVMF's share may differ by a few MiB in either direction, but the shortfall is about 9 MiB and the margin it would need is 10.
- **Fix:** hold the free figure against what the machine can give, not against `-m`. Two ways: subtract the application's reservation (`RENTED_SHAPE.top_reserved_pages × 4 KiB`) from the RAM before applying the rule, or replace the 1% rule with a fixed firmware allowance (say 128 MiB) plus the reservation. Better still, also compare the kernel's own `boot info 0.7, N memory regions, M MiB usable` line with the frame allocator's figure, which should agree to within a few MiB. Then run `GITHUB_ACTIONS=true cargo xtask boot-large` and `boot-rented` once under the turn and record the figures. Add a host test of `check_memory` at 8 GiB and 64 GiB, with and without the shape.

### T83-2 (Medium): `ORIGIN_QEMU_MEMORY` from 513 MiB to about 6 GiB fails every correct kernel boot

- **Where:** `settings.rs:469-478` (the parser takes 512M to 64G), `main.rs:2607-2625` (`check_memory` applies to every non-default size), and the usage text at `main.rs:245-246`.
- **What is wrong:** OVMF keeps about 59 MiB whatever the RAM, so the rule "at least 99% of `-m`" only holds above about 6 GiB. The doc comment exempts only 512 MiB ("OVMF keeps more than 1% of so little"), but the parser and the usage text offer 1G, 2G, 4G and so on, with no warning.
- **Failure scenario:** a person runs `ORIGIN_QEMU_MEMORY=4G cargo xtask boot-test` to look at a memory problem. The kernel boots correctly with about 4038 MiB free, the rule needs 4055, and the boot fails with "not within 1% of it". That points the person at a kernel memory fault that does not exist.
- **Fix:** the same fix as T83-1 (a fixed allowance, or a comparison with the boot info's usable figure). Otherwise, accept only sizes at which the rule holds, or skip the check below a stated size and say so in the usage text.

### T83-3 (Medium): two of `large`'s contracted checks are not built, and a requirements row cites `boot-large` for one of them

- **Where:** the contract's table (TASKS §83, the `large` row: "`page tables loaded: … direct map` covering it; the NUMA proofs on 32 GiB nodes"); `main.rs:2607-2625` checks only the frame allocator; `docs/requirements/adr-0004.md:8` (A04-H2: "Since TASKS item 83, `boot-large` builds the direct map over 64 GiB", with evidence `xtask:boot-large`); `docs/STATUS.md:23`.
- **What is wrong:**
  - **The direct map.** Nothing holds the `page tables loaded: … N MiB direct map` figure. The markers are prefix-only (`"origin-kernel: page tables loaded: "`).
  - **NUMA.** Nothing holds the `numa: 2 nodes, …, 65535 MiB` total or the per-node sizes. The markers are `"origin-kernel: numa: "` and `"; consistent true"`.
  - **No proof reaches memory above 4 GiB through the direct map.** The frame allocator hands out low frames first (`allocated, wrote and freed 3 frames at 0x1000, 0x2000, 0x3000`, com1.log line 52).
  - **The top reservation.** On `boot-rented`, nothing holds the kernel's report against the 32 MiB the application reserves at the top, although the module's own documentation says the application prints each change "so the checker can hold the kernel's report against it". At 64 GiB that range sits inside the 1% allowance.
  - **The records.** TASKS "As built" does not say that these checks were left out. STATUS quotes the direct-map line directly after "The frame allocator must hold at least 99% of the RAM", which reads as though it were checked.
- **Failure scenario:** a regression in `build_kernel_tables` makes the direct map stop at 4 GiB. If nothing that boot runs touches a frame above 4 GiB, `boot-large` still passes, because the frame count is taken from the bitmap and is still right, while A04-H2 cites it as evidence. In the same way, a kernel that took EfiReservedMemoryType at the top of RAM as free RAM would pass `boot-rented`.
- **Fix:**
  - Parse the direct-map figure and the NUMA total, and hold each against the RAM. (The logs show 65527 MiB for `boot-large`, and 65495 MiB for `boot-rented`, exactly 32 MiB less.)
  - On `boot-rented`, require the direct map and the free figure to end at least 32 MiB short of `boot-large`'s, or to exclude the range the application printed.
  - Record the gap in "As built" and narrow A04-H2's wording until a check exists.
  - Propose a kernel proof that writes and reads back a frame at the top of RAM, as a task of its own (kernel code is outside this task's ownership).

### T83-4 (Medium): RB-1's and RB-2's records do not show their stated reason, and RB-2 departs from the contract without saying so

- **Where:** `docs/adr/ADR-0013-boot-proof-policy.md:803-812`; the contract's controls (TASKS §83).
- **What is wrong:**
  - **RB-1 and RB-2.** Each is recorded as caught with the same evidence: nothing on COM2, and COM1's last kernel line `M1 entry complete; halting`. That shows only that the console did not move. It does not show why: for RB-1 the contract says the kernel refuses to read the RSDP copy, and for RB-2 that the SPCR's lend is refused. Any failure of the move gives the same evidence. The ADR says the reason lines will be recorded at a later run, so the table claims more than its runs show today.
  - **RB-2's design changed.** The contract's RB-2 was "an FBPT whose declared length covers the SPCR". By the locator's documented rule (`framekernel/frame/src/acpi.rs`, the doc of `changing_ranges`, and `Overlaps` at :281), a table beyond a structure's minimum but inside its declared extent stays lendable and is reported to the census. So the contract's RB-2 would not have stopped the move; it would have failed the census instead. As built, RB-2 puts the SPCR inside the FBPT's 56-byte minimum (`Changing::minimum`, `acpi.rs:271`). That is the right control, but neither TASKS "As built" nor the ADR records it as a departure.
  - **RB-2's edit is ambiguous.** "The FBPT's header put 16 bytes before a copy of the SPCR" can be read two ways. If the edit wrote only the 8-byte FBPT header at A−16, the SPCR copy at A is intact and the lend is refused by the overlap rule. If it wrote the whole 56-byte `fbpt()` at A−16, it overwrote the first 40 bytes of the SPCR copy, header included. The SPCR would then be refused for its signature or checksum, not for the never-lent rule, and the record would look the same.
  - **Missing detail.** The controls' IOMMU is not recorded (a person's `boot-test` defaults to Intel; the contract names AMD as the board's), and the temporary edits were not kept.
- **Failure scenario:** a later change breaks the never-lent check, for example by dropping the minimum guard. Re-running RB-2 as described could still "fail as recorded", because of a clobbered SPCR, and nobody would notice that the property it was meant to show is gone.
- **Fix:**
  - Re-run RB-1 and RB-2 on the final tip, with `5a184a3c`'s report, and record the console's line about the firmware's UART for each. The expected reasons are a refused read of the RSDP's memory and a refused lend of the SPCR.
  - State RB-2's edit byte by byte (which bytes were written, and where), and keep each control's edit as a patch in the record.
  - Name the IOMMU of each control run.
  - Add RB-2's change of design to TASKS "As built" as a departure.

### T83-5 (Low): the shaped tables leave the RSDT naming the firmware's FADT and no FPDT, and do not say whether the FADT change changed anything

- **Where:** `tests/emulator/reserved-memory/src/main.rs:355-369` (the FADT copy is put only in the XSDT); `lib.rs:382-395` (`rsdp_naming` keeps `RsdtAddress`); `lib.rs:402-420` (`facs_by_32_bit_field`).
- **What is wrong:**
  - The RSDP copy still names the firmware's RSDT. That RSDT lists the original FADT and no FPDT, so the census sees an RSDT of 10 entries and an XSDT of 11 (com1.log lines 102-103), and the two name different FADTs. No firmware publishes such a pair. The kernel's locator reads only the XSDT (`acpi.rs` `changing_ranges`), so this does not weaken today's test, but a future census rule comparing the RSDT with the XSDT would fail this machine because of the fixture, not the kernel.
  - The application prints "the FACS at … by FIRMWARE_CTRL alone" whether or not QEMU's FADT already had `X_FIRMWARE_CTRL` at zero. No record says which it was, so whether this shape differs from every other machine's is not shown.
- **Fix:** print the FADT's two FACS fields before the edit. Either point the RSDT's FACP entry at the copy as well (and append the FPDT's 32-bit address, if it lies below 4 GiB), or record why the RSDT is left as it is.

### T83-6 (Low): the application departs from UEFI 2.11 §7.2's note on runtime memory types, although the contract says it keeps to the specification

- **Where:** `main.rs:540-554` (`allocate`, `AllocateMaxAddress` below 4 GiB), used for `EfiACPIReclaimMemory`, `EfiACPIMemoryNVS` and `EfiReservedMemoryType`; `main.rs:462-512` (`allocate_at_top`, `AllocateAddress` for `EfiReservedMemoryType`).
- **What is wrong:** §7.2 says that drivers and applications not targeted at a specific implementation must allocate those runtime types (ACPI reclaim, ACPI NVS, runtime code and data, reserved) with `AllocateAnyPages`. The application uses `AllocateMaxAddress` and `AllocateAddress` for them. It works on OVMF, which is the implementation it is aimed at, but the contract's line "The application keeps to the UEFI specification" and the crate's documentation do not record the exception. The reserved type with `AllocateMaxAddress` dates from TASKS item 40; NVS, reclaim and `AllocateAddress` are new here.
- **Failure scenario:** another firmware build (a later OVMF, or one with memory-type bins for S4) refuses `AllocateAddress` of a reserved type at the top of RAM. The application then fails, the loader never starts, and the boot times out (see T83-7 for how that failure is reported).
- **Fix:** record the application as targeted at OVMF, naming the departure. Where the address does not matter (the RSDP and XSDT copies, the FADT copy, the FPDT), use `AllocateAnyPages`. Keep `AllocateAddress` only for the top reservation, which is the shape itself.

### T83-7 (Low): when the application fails, the failure report hides its message

- **Where:** `main.rs:6724-6748` (`com1_last_kernel_line`); `main.rs:7020-7028` (the failure message); `main.rs:6828-6868` (failures judged on the captured UART only).
- **What is wrong:**
  - The application's own failure, for example `origin-test-reserved: AllocatePages at the top of the RAM failed: …`, goes to COM1. After it, OVMF moves on to its next boot option (the NIC, then the shell), so COM1's last non-empty line is the firmware's text, not the application's. The report says "COM1 has no kernel line; its last line: <firmware text>", and stdout (COM2) holds nothing useful.
  - The COM1 log's path (`target/xtask/com1.log`) is not named in the error. Only COM2's scenario log is.
  - Failure strings are judged on COM2 only, so a loader refusal printed on COM1 (`origin-boot: kernel rejected`) ends the boot only at its timeout.
- **Fix:** in the report, name the last `origin-test-reserved:` and `origin-boot:` lines on COM1 as well as the last kernel line, and print the COM1 log's path. Optionally, judge the failure list on COM1 too once the scenario ends.

### T83-8 (Low): `rented_scenario` skips its edits silently when an anchor is missing, and no host test covers its markers

- **Where:** `main.rs:2671-2719`.
- **What is wrong:** each edit is wrapped in `if let Some(at) = … position(…)`: the drain up to `HANDOVER_LINE`, `MOVED_LINE` before "allocated, wrote and freed 3 frames", the FPDT line before "acpi: FADT: ", and the FBPT, S3PT and never-lent lines before " tables: ". If an anchor's text changes, the edit is dropped and the scenario quietly checks less. `rented_firmware_markers` does the same at `main.rs:2655` (`map_or(0, …)`: no loader markers at all). The established pattern in `reserved_markers` (`main.rs:1575-1588`) pushes an impossible marker ("xtask: the marker … is missing") so that the boot fails instead. No host test asserts that the rented scenario contains `MOVED_LINE`, the FBPT, S3PT and never-lent markers, or the loader markers on COM1.
- **Failure scenario:** someone renames the census's summary line. `" tables: "` is no longer found, the FBPT, S3PT and never-lent markers vanish from `boot-rented`, and the FPDT and FACS shapes are no longer held on COM2, while the machine still passes.
- **Fix:** use the `swap_marker` and `reserved_markers` pattern for each anchor, and add a host test listing the rented scenario's required markers.

### T83-9 (Low): settings a person combines with `ORIGIN_QEMU_SHAPE` drop checks silently

- **Where:** `main.rs:1028-1044` (`boot_scenario`'s order), `main.rs:1588` (`reserved_markers` sets `check_reserved_boot`), `main.rs:2674` (`rented_scenario` sets `check_rented_boot`), `main.rs:1125` (`no_generator_markers` sets `check = None`).
- **What is wrong:**
  - With `ORIGIN_QEMU_RESERVED=on ORIGIN_QEMU_SHAPE=on cargo xtask boot-test`, `check_rented_boot` replaces `check_reserved_boot`, so the planted-range checks are gone.
  - With `ORIGIN_QEMU_SHAPE=on` and a CPU lacking both RDSEED and RDRAND, `no_generator_markers` runs after `rented_scenario` and sets the check to `None`. That drops `check_com1_stopped_at_the_move`, the COM1 markers and `check_memory`.
  - `boot-matrix` never makes these combinations, but `boot-test` accepts them without a word.
- **Fix:** compose the checks (run each one the scenario collected) or refuse these combinations in `Settings`.

### T83-10 (Low): the `ORIGIN_QEMU_MEMORY` parser panics on some values and accepts a sign

- **Where:** `settings.rs:472`: `value.split_at(value.len().saturating_sub(1))`.
- **What is wrong:** `str::split_at` panics when its index is not on a character boundary, so a value ending in a multi-byte character (`8É`, `8Ｇ`) panics instead of being refused. `u32::from_str` accepts a leading `+`, so `+8G` is taken as 8 GiB, although the test refuses `-8G`. This breaks the module's rule that each value is checked and refused, naming the variable.
- **Fix:** use `strip_suffix('G')` and `strip_suffix('M')`, refuse anything that is not ASCII digits before the unit, and add `8É` and `+8G` to the refused list.

### T83-11 (Low): two `unsafe` paths rely on firmware data they do not check first (existing pattern, extended here)

- **Where:** `tests/emulator/reserved-memory/src/main.rs:176-197` (`xsdt_at`, moved from `xsdt`) and `main.rs:515-537` (`install_configuration_table`).
- **What is wrong:**
  - `xsdt_at` reads `XsdtAddress` at offset 24 and dereferences it before checking that the RSDP's revision is at least 2 (offset 15) and that the address is not 0. An ACPI 1.0 RSDP under the 2.0 GUID makes it read beyond the 20-byte structure and then dereference whatever lies there. `rsdp_naming` checks the revision, but only later.
  - The new slot `device_paths[1]` (offset 192, `InstallConfigurationTable`) is called on the strength of §4.4's layout, which this review confirmed. But the application never checks the boot-services header's signature or `HeaderSize`, as the loader does, so the SAFETY note's premise is assumed, not verified.
  - The application takes the last ACPI 2.0 entry in the configuration table, and the loader takes the first. They agree on any conformant firmware.
- **Fix:** check `Revision >= 2` and a non-zero `XsdtAddress` before the read. Check `hdr.signature == BOOT_SERVICES_SIGNATURE` and that `HeaderSize` covers offset 216 before using `device_paths` and `images`. Take the first ACPI 2.0 entry, as the loader does.

## Checked and found sound

- **Table layouts against ACPI 6.6:**
  - The RSDP (Table 5.3): signature, the checksum over bytes 0–19 at offset 8, Revision at 15, `RsdtAddress` at 16, Length at 20 (36), `XsdtAddress` at 24, and the extended checksum over all 36 bytes at 32. `rsdp_naming` computes the 20-byte checksum first, then the extended one, which covers it. That order is correct.
  - The FADT: `FIRMWARE_CTRL` (4 bytes at 36) and `X_FIRMWARE_CTRL` (8 bytes at 132). The precedence §5.2.9 gives (`X_` when non-zero) is what `facs_by_32_bit_field` applies, and the length guard (`len >= 140`) covers the field. QEMU's FADT is revision 3, 244 bytes.
  - The FPDT (Table 5.121, revision 1, 36-byte header) with its pointer records (Tables 5.125 and 5.126: type 0 and 1, length 16, revision 1, 4 reserved bytes, an 8-byte pointer at +8).
  - The FBPT: an 8-byte header (Table 5.129), then the type-2 record of length 48 and revision 2 (Table 5.130), 56 bytes in all.
  - The S3PT: an 8-byte header (Table 5.131), then the type-0 record of length 24 and revision 1 (Table 5.132), 32 bytes in all, with a resume count of 0.
  - The FBPT and S3PT are put in `EfiReservedMemoryType` pages, which matches "AddressRangeReserved" in §5.2.24.4 and §5.2.24.5.
- **UEFI 2.11:**
  - The `EFI_BOOT_SERVICES` member order (§4.4.1): `LocateDevicePath` at 184, `InstallConfigurationTable` at 192, `LoadImage` at 200. `BootServices` in `boot/uefi/src/protocols.rs:201-238` matches it.
  - The values of `EFI_ALLOCATE_TYPE` (1 and 2) and `EFI_MEMORY_TYPE` (0, 2, 7, 9, 10).
  - The offsets of `EFI_MEMORY_DESCRIPTOR` (Type 0, PhysicalStart 8, NumberOfPages 24), with the stride taken from `DescriptorSize`.
  - `InstallConfigurationTable` updates an existing GUID's entry in place.
- **Failure paths in the application:** every step returns `Err`, and `run` returns before `start_loader`, so tables that are half edited never reach Origin's loader. Whatever OVMF boots next (the NIC or the shell) cannot start `\EFI\ORIGIN\LOADER.EFI`, and the boot fails at its timeout. Buffers are large enough: the configuration file of 16 + 16 × 24 bytes fits in 1024; the memory map is checked against its buffer; file names are below 64 UTF-16 units.
- **The SAFETY notes on the new `unsafe` blocks** (the FADT, FPDT, XSDT and RSDP copies, `GetMemoryMap`, `AllocatePages` at an address, the transmute of `InstallConfigurationTable`) are accurate apart from the premises named in T83-11. No `&mut` is created over memory a live `&` still reads. `lib.rs` forbids `unsafe`.
- **The application at run time** (com1.log of the RB-4 run, 64 GiB): it reserved `0x107e000000-0x107fffffff`, exactly the top of q35's RAM above 4 GiB. The XSDT copy is 124 bytes (11 entries) in NVS. The census found the FPDT (OEM "ORIGIN"), the FBPT and the S3PT, and recorded the FACS, FBPT and S3PT as never lent. The kernel's direct map and free figure are each exactly 32 MiB short of `boot-large`'s.
- **The checker cannot pass a boot that never moved its console.** COM2 carries the kernel's text only after the move (the replay), `rented_scenario` drains every marker up to the loader's hand-over, and `check_com1_stopped_at_the_move` requires COM1's last kernel line to be the move, with at least 10 kernel lines. RB-4's run shows it: the reason line `the ACPI SPCR names a UART at I/O port 0x2f8 that cannot be used (nothing answers at that address)` is on COM1 and nothing is on COM2. RB-3 fails `check_memory` for its stated reason (1989 MiB of 65536).
- **The FPDT census markers indirectly prove the RSDP copy was used.** The FPDT is listed only in the XSDT copy, which only the RSDP copy names. The located FACS can only come from the one FADT the XSDT lists, the copy whose `X_FIRMWARE_CTRL` is 0.
- **Settings:**
  - The parsing of `ORIGIN_QEMU_SHAPE` (`on`/`off`, case-sensitive) and `ORIGIN_QEMU_MEMORY` (except T83-10).
  - `boot-matrix` and its scenario commands refuse a non-default size and `SHAPE=on`, and `512M` passes as the default.
  - `boot-large` and `boot-rented` are in `SETS_ITS_MACHINES`, and the entry test iterates that list.
  - `GITHUB_ACTIONS` is compared with `"true"` exactly. `FULL_MEMORY_GIB` is private and no `ORIGIN_QEMU_` literal appears outside `settings.rs`, so `only_this_module_names_the_variables` holds (`USAGE` begins with "usage:", which its rule does not catch, as intended).
  - `-m` and the two node backends sum correctly (`Memory::node` halves the size, and MiB values must be even), and the ACPI machine's `maxmem` is RAM + 512 MiB.
- **An 8 GiB guest on a GitHub-hosted runner:** standard Linux runners for public repositories have 16 GB (to this reviewer's knowledge; not checked today). The memory backends are allocated lazily, and the 64 GiB trial peaked at 0.23 GB resident, so 8 GiB fits under TCG and under KVM. The obstacle in CI is T83-1, not memory.
- **Security invariant 1 (TEST ONLY):** the application is built only by `build_reserved_fixture`, called only from `stage` when `reserved || shape`. `cargo xtask build` does not stage it.
