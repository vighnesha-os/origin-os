## Checked and found sound

By reading, unless marked:

- **W^X is structural.** The access type has no writable-and-executable variant, and its readable and writable forms set NX.
- **Each page is mapped once, with its final permissions,** written through the direct map before any thread exists. Code is never writable, and RELRO is read-only from the start.
- **No mapping over a mapping, and none outside the user half.** Frames are zeroed.
- **`check` runs before anything is mapped** and holds what the launch relies on: slots strictly ascending, 8-byte aligned and inside the bytes of a writable or RELRO segment; segments aligned, apart and within the span; one read-execute segment that holds the entry. `fill_page` relies only on those rules; every access is bounds-checked and the base addition is checked.
- **Randomness.** Every draw goes through `origin_frame::random::next_u64`. With no generator the launch is refused before a child exists, and the proof is counted as not run.
- **Ranges.** Bases and stacks are page-aligned in `[0x1000_0000, 0x1000_0000_0000)`, apart from the start records' and `memory_map`'s range.
- **Nothing prints an address:** not the proof, the fault report or the debug calls.
- **Entry state.** RIP is the base plus the entry, RSP the page-aligned top of the stack, RDI the start record, every other general register zero, RFLAGS `0x202`.
- **The direction flag and the kernel.** The interrupt entry clears it and SYSCALL masks it, so a backward copy interrupted in the middle cannot run kernel code with it set.
- **CLAUDE.md §10.** No `bool` crosses an `extern "C"` or system-call boundary in the new code.
- **The host tool.** Every offset and size is range-checked, loops are bounded by the file, and the output depends on the input bytes alone.
- **In the built bytes:** `_start` clears RBP, aligns RSP to 16 and calls; `memmove` restores the direction flag on the one path that sets it; `thread_exit` is `syscall` then `ud2`; the five `mem*` functions are reached through RELRO slots.

Inferred and not verified: that a description the build writes always passes `check`. Nothing checks it at build time, only at each launch.

## Records that say more than the code shows

- **Threat row R1, "Proven (control R3-1)".** The control exercised the converter at build time, not the launch path. The clauses for the write to code, the jump into data and the write to RELRO have never been seen to fail.
- **R3.** The read-back uses the same slot list and addends as the writer, so it cannot see a slot the description lacks or a wrong addend.
- **R4, "Proven".** The control fixed the base only. The stack's half of the clause, and the refusal with no generator, have never been run.
- **R8, "Boot".** Only a good record is ever read; no refusal of a bad one is exercised.
- **STATUS and R6:** "between unmapped pages" and "stack never executable" hold by design only (F1).
- **`carried.rs`'s header:** "nothing in them comes from … a path" is true of the conversion, and the bytes carry a path from the compiler (F5).
- **The provenance entry** says the final gate results are in the hand-over report, which is not in the repository. The acceptance condition has no durable evidence there.
- **Row E11** (no CET shadow stack, though P6 asks for one) is recorded as an open deviation, and the kernel has none.

## Resolution

Written by the author, the S4-1 session, on `claude/s4-1-rust-ring3-fde097`, after fast-forwarding it to the third batch at `e51e098`, which had merged `ef1db6a`. Nothing above this section is changed but the "Status" column. The gates on the answers' last commit of code, and the controls, are in `SOURCE_PROVENANCE.md`, "Task S4-1: the answers to its review", and ADR-0013.

- **F1, `b3230f3`.** Before each of the six launches' threads starts, the proof walks the child's tables: every page of the span against the description (`program::page_access`, host-tested), present to ring 3, writable for the writable segment alone, executable for the code alone, unmapped where no segment is; every page of the stack writable and not executable; the page below the stack and the page above it unmapped. A clause of its own on the proof's first line. The three controls asked for each fail the boot by that clause: R3-4, the stack mapped executable; R3-5, the page above the stack mapped; R3-6, a read-only segment mapped writable (ADR-0013).
- **F2, `b3230f3`, on `539f813`.** The clause that rested on a status is replaced by two, each counting the heap and the free frames, page tables among them, before and after: a launch refused before anything is made (a stack of no pages, `invalid_args`), and one refused part-way through mapping (a stack of 32 × 512 pages, which needs at least 32 tables of its own, as many as a space may have in all; `limit`), after the image and part of the stack are mapped, with no new kernel code. Control R3-7, a child kept on that refusal, fails it. That the refusal comes part-way rests on the code's order, and is recorded so. The refused record placement and thread start are still by reading.
- **F3, `539f813`.** A stack of no pages or of more than `program::MAX_STACK_PAGES` (2 GiB, as much as a span) is refused with `invalid_args` before the child exists; `place_stack` adds its neighbours with `checked_add` and its size with `checked_mul`.
- **F4, `539f813`: kept as a limit.** The reason: an estimate in the launch path would be a second copy of the framework's private bound (32 tables a space) and of the paging layout, which could drift from them; a carried program is first-party and fixed at build time, and the one carried is 7 pages; and F2's control shows a part-way refusal gives everything back. What the finding found wrong is fixed: `UserSpace::map_page` now tells the bound (`ChangeError::Limit`) from a want of memory, as `map_shared_run` has since S3-5b's review, and the launch path reports `limit`, `no_memory` or `invalid_args` where it reported `no_memory` for all. `load_program`'s documentation states the limit.
- **F5: fixed by TASKS item 32, `119d78d`.** Confirmed in this build before the fix: the program's first segment held the toolchain's `core` source path under the account's home directory. Item 32 passes its remap to the ring-3 build too, and its reproducible-build gate searches the kernel image, the program's bytes included; its control, the remap taken out of the ring-3 build alone, fails that gate at `…/core/src/slice/index.rs` (item 32's record). Merged here at `366f53c`, keeping item 32's text for the six matrix rows on reproducible images; `carried.rs`'s header, STATUS and row A11-L1 say so.
- **F6, `b411bd6`.** The bodies are in `runtime/rt-mem` (`origin-rt-mem`), a default member, and `runtime/rt/src/mem.rs` keeps the five C names around them. Host tests against `core::ptr::copy`, slice fill and slice comparison: zero length, length 1 and every length to 40, and nine longer; every overlap distance from one past the length below to one past it above; the source at 8 offsets. On an x86-64 host (CI) they run the instructions and read RFLAGS.DF after a copy down; on the development Mac a byte-by-byte stand-in of each instruction runs, so there they check the direction and the end pointers. Three planted mistakes fail them. The comment now says ERMS and FSRM are not part of `x86-64-v3`, nothing is measured, and a copy down gets no fast-string handling.
- **F7, `39e40d1`.** `_start` begins with `cld`. Whether ADR-0005 P6 states RFLAGS at entry went to the coordinating session as a proposal for task S4-2's ABI items; P6 is unchanged.
- **F8, `b3230f3`.** The expected word takes its oldest minor from `start::ABI_MIN_MINOR`.
- **F9, `81d748b`.** `carried::stale` decides before anything is written: a directory holding any file of a description's names for the program must hold a `<name>.rs` that begins with the line this tool writes for that name, or nothing is written or removed; in its own directory only the `<name>.<k>.bin` files the new description lacks are removed. Host tests, and the command checked on a hand-written `first_program.rs`. The `DT_HASH` length is recorded in `check_symbols`' documentation as a limit, with why it is harmless.
- **F10: fixed by TASKS item 32,** whose `xtask` refuses `RUSTFLAGS` and `CARGO_ENCODED_RUSTFLAGS` at start for every command but `exclusive` (`dfa8281`, merged here at `366f53c`). A residual, sent to the coordinating session: the per-target variable for the userspace triple, `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS`, is not refused, as the kernel's and the loader's are. Seen with Cargo 1.99.1 (`cargo build -v`), it reaches a ring-3 build, ahead of `.cargo/userspace.toml`'s flags, so the file's wins where both set a flag (frame pointers stayed on with `-C force-frame-pointers=no` in it) and a flag the file does not set gets through.
- **F11, `00ad331`.** The gate's reason for `faults.rs` names its three faults. `origin-rt`'s documentation records that its three exit codes share a program's code space; whether `origin.core` reserves them is held for S4-2.
