## Checked and found sound

- **Each stub's form [code; the six forms in use and every number load, `syscall`, `ret` and `ud2`: bytes].** Zero for `u8`, `u16`, `u32`, `bool` and bits (`movzx r32, r8`; `movzx r32, r16`; `mov r32, r32`); the sign for `i8`, `i16`, `i32` (`movsx r64, r8`; `movsx r64, r16`; `movsxd r64, r32`). The fourth goes from RCX to R10 in one instruction, extended on the way (`mov r10, rcx`; `mov r10d, ecx`; `movzx r10d, cx` or `cl`; `movsxd r10, ecx`; `movsx r10, cx` or `cl`). The number is loaded last, by `mov eax, imm32`, which clears the upper half of RAX. A method that never returns ends in `ud2`. No stub touches the stack, memory, or a register the C convention preserves. The forms the definition does not use today are right by reading **[inferred: the assembler's reading of them is the author's host test, not run here]**.
- **The stub, the C signature and the kernel's decoder agree [code].** `stub_registers`, `abi_params` and `gen_sys_decode` walk parameters then results in the same order and take two registers for a vector or a string. Each extension is the one the decoder's check needs. A `bool` is `u8` at the boundary (CLAUDE.md §10). The generator refuses a method with more than six registers.
- **The built image [bytes].** 20 functions, exactly `origin_kernel_<method>` for the 20 methods. 197 bytes. Entry 0, `DT_SONAME` `origin.core`, no relocation, no `DT_NEEDED`. Three `PT_LOAD`s: headers and symbol tables (read-only), `.text` (0xC5 bytes, read-execute), and the dynamic table (0xA0 bytes) with zero-filled padding. Every export is a global function of default visibility whose size is exactly its instructions.
- **The description is that image's [bytes].** `origin_core.0.bin` is the read-execute segment's 197 bytes. It holds `0F 05` 20 times, at the 20 pins. Every pin is five bytes after `B8` and its own call's number. Every export's offset is its stub's first byte. The release fingerprint in the description, in the generator's list and in the committed `framekernel/syscalls` are the same 32 bytes. Every byte outside a stub is `CC`.
- **`describe` [code].** Every byte of the code segment is inside exactly one listed, exported stub or is `CC`. Each stub holds the pair once; a pair anywhere else, across a boundary included, is refused. Any relocation or import is refused. An alias or an overlap of two exports is refused. What is written into the kernel's source is plain identifiers and numbers. A wrong symbol size fails closed: zero is refused, too small leaves a byte outside every stub or a stub with no pair, too large overlaps.
- **What ties the pieces [code].** The offset for a number goes: the kernel's `Pins` field of that method's name, the description's line of that name, the list's entry, the export of that symbol, the one pair in its bytes. The gate checks the same chain from the other end: the definition's method, the function of its name in the disassembly, the address of its `syscall`, the description. A stub that loaded another call's number would be refused by the gate, and at run time by the pin itself. The fingerprint covers the definition with its numbers. It does not cover the generator's version, the image's bytes or the offsets; those rest on the description and the code being written by one run, on `check`, and on the gate.
- **`core_image::check` [code].** A `const fn`, run on the included description by a `const` assertion. No arithmetic can wrap: `at + 1` is taken only when `at` is below the code's length, which is at most 1 MiB. Every index is bounded first. Pins are distinct and each is at `0F 05`. It does not look for other pairs, which the pin does not need: a pair that is no pin is accepted for no number.
- **`pinned` [code].** A `match` on the whole 64-bit number whose arms compare the offset with a field, and `_ => false`. No table is indexed by anything from ring 3. Nothing calls it yet.
- **`install` [code].** It runs once, on the boot processor, after the heap is up and before `sched::prove`, where every proof that makes a process runs. The other processors are already online; it is the `SetOnce`, not the order, that makes a second writer lose. Frames come zeroed. On any failure the frames taken so far are dropped, and a dropped frame is freed. A boot with no memory for it prints the failure and goes on (F1, F17 d).
- **`unsafe` [code, and the generated file as built].** No committed kernel or ring-3 file gained `unsafe` in this range. `core_image.rs` forbids it. Each generated stub has three `unsafe` tokens (`naked`, `no_mangle`, the `unsafe extern "C" fn`) and a SAFETY comment (F12). `naked_asm!` takes no flags option, so CLAUDE.md §13's rule on `preserves_flags` has nothing to judge. The `unsafe` gate does not read the generated stubs, since they are not committed; the generator's own test holds them to the two named shims. The gate's list and its reasons are unchanged and still accurate.
- **The ELF reader [code].** `parse` (the KRN image and a static program) refuses `DT_NEEDED`, `DT_SONAME`, an undefined symbol and `R_X86_64_GLOB_DAT` as before, with tests. The importing reading accepts one `DT_NEEDED` that names the library, undefined symbols only among its exports, and `GLOB_DAT` only against an undefined symbol of the table, with no addend, at a slot that keeps the relocation-slot rules and is no relocation slot. `JUMP_SLOT` and `DT_JMPREL` are refused. No build step uses this reading yet.
- **The gate's independence [code].** `expected_stub` calls nothing of `codegen`. It shares the `oidl` front end and model with the generator: `Int::size`, `Int::signed`, a method's number, `never` and types. A fault there would be in both, and also in the kernel's decoder.
- **Reproducibility of the new steps [code, bytes].** The description is a function of the two input files: exports sorted by name, pins in number order, no path, time, environment value or map order. The generated `modules.rs` and `runtime/core`'s `include!` name absolute paths under the target directory; none reaches the built `.so`, the first program or any described file. `.comment` holds the fixed linker line.
- **The entry [bytes].** With `--entry=_start` gone from the shared flags, the first program's entry is still `_start`, and `origin.core`'s is 0.
- **`remove_linked` and the `cdylib`'s second file [code].** As the author says: a stale `deps/liborigin_core.so` can only fail a build. `relink_stale` checks the file again after the second link.

Inferred and not verified: that `-C jump-tables=no` gives `pinned` compares only (R2's gate); that `llvm-objdump` prints `(bad)` for bytes it cannot decode; that the reproducible-build gate took `origin.core`'s three files in (the author's run); that the framework refuses a writable mapping of an executable frame (S3's proof, not reread).

## The author's invariants and open points

The ten invariants:

1. **A stub's form.** Held where it says. The hand-written table in `generated.rs` and the gate's rule 2 would each fail on a wrong form. "Shares no code with the generator's writer" is true of the writer; the model is shared.
2. **The stubs and nothing else.** Held for the code segment, for relocations and for imports. "No data" is narrower in the code: read-only data and zero-filled writable memory are not refused (F3). Only the code reaches the kernel.
3. **`0F 05` once a method, nowhere else.** Held by `describe` and by rule 6, with fixtures for a second pair, a pair in an immediate, none, and one after the last stub. The straddling pair has no fixture (F6 a).
4. **The kernel's offset is that call's `syscall`.** Held by all three places named, each with a test that plants the fault.
5. **One definition.** Held by `check`, with a host test. The `const` assertion has never stopped a real build (F6 c). The fingerprint is the definition's, not the generator's or the image's.
6. **`pinned`.** Held, with a test that tries every number at every offset and four unknown numbers. Not called yet.
7. **The client holds no stub.** True of the generator's `rust/` tree, and the test would fail on `asm!` or `naked` there. At `ac22d57` the crate the programs link (`runtime/kernel-stubs`) includes the stubs' file through `modules.rs`, as the hand-over says elsewhere, so the built first program holds three `syscall`s **[bytes]**.
8. **Written once, reached by nothing else.** Held by reading. No test would fail if it broke (F1), and the framework does not enforce it (F7).
9. **A program's import.** Held, with a fixture for each refusal and a really linked program.
10. **Same inputs, same files.** By reading, and no host path in the built files. The gate's run is the author's.

The six "least sure" points:

1. **The writable segment.** A segment that also holds initialised data cannot pass: the dynamic table's offset and size must be the segment's. Zero-filled data can pass, and so can bytes after `DT_NULL` in a file no linker writes (F3).
2. **The disassembly as text.** No two instructions of different effect that print alike were found. A redundant prefix and another encoding of the same instruction do print alike. The `syscall`'s place is checked by bytes (F9). Rule 3 has only been seen on a hand-made `(bad)` (F5).
3. **Sizes of naked functions.** All 20 are exact in the built image **[bytes]**. A missing or wrong size fails closed in `describe`. One sentence of the hand-over is not so: the gate does not compare a stub's end with its last instruction. It never reads a size; it reads label to label.

## Questions for the owner or the coordinator

1. **L13's sentence on enums (ADR-0011 Amendment 3; decision item 273).** The accepted text says zero for an enum. The code extends an enum as its underlying integer, which is the only reading the kernel's decoder accepts for a signed one. Proposed wording: "an enum and a bits type as its underlying integer: zero where that is unsigned, the sign where it is signed". No call of `origin.kernel` is affected today. The author has sent the same proposal.
2. **A trap after a stub's `ret` (ADR-0017 Z10).** Z10's rule is for the code the kernel's build compiles. `origin.core` is first-party code in every process, 12 of its 19 `ret`s run straight into the next stub, and the userspace flags have no such option for any ring-3 code. Does ADR-0017 want an `int3` after each stub's `ret`? It would add one instruction to the form L6 and L13 fix, to the generator and to the gate's table, and about 48 bytes. The same question covers the page's zero tail (F11).
3. **A seal in the framework (F7).** Should `origin_frame` refuse `write_u64` on a frame that is executable in any space, or offer a frame that is sealed after its first fill? The framework is another session's, and the contract forbids this task to edit it.
4. **L2's "no writable data" (F3).** Is "nothing but the code segment reaches the kernel, and no initialised writable byte exists" the rule that was meant? If L2 means the linked file itself, zero-filled segments must be refused too.

## Resolution

Written by the author, the S4-2 session, on `claude/dreamy-bose-c5c3e3`. Nothing above this section is changed but the "Status" column. - **F1, `cca0faa`; control CP-9 in `666c128`.** All four points. (1) `install` reads every word back and compares it with the image before it keeps the frames; a mismatch is `InstallError::ReadBack`, and nothing is kept, so no process can then be launched. What a word must hold is `image_word`, a `const fn` with host tests. (2) The boot test fails on "origin.core could not be written" as well as on ": origin.core failed", and requires the good line. (3) Control CP-9: with each word written eight bytes late, the install fails its read-back and the boot test fails on that line. (4) The last clause of "origin.core and the call pin" reads the frames again after every other clause, the hostile runs among them, and fails the boot unless they hold the image word for word.
