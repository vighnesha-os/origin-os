## Summary

No finding is High. The three claims the fix rests on hold as far as I can trace them, and I found no path by which a stack is given back while a processor may still run on it, nor one by which W1 or W2 can pass with its window open. One finding is Medium: the retirement `stack_in_use` makes with interrupts on can be preempted between its swap and its store, and a reap on the same processor in that gap leaks the ended thread's stack. That gap also breaks the capacity count. Six findings are Low. On the open item: I found no path in the fix that holds four frames in the directory proof. There is a pre-existing race in `settle` that gives exactly the logged symptom, recorded as T70-7.

## Findings

### T70-1 (Medium): a retirement in `stack_in_use` can be preempted between its swap and its store, and a reap in that gap leaks the ended stack

**Where:**
- `framekernel/frame/src/cpu.rs:836-844`: `stack_in_use` calls `retire_ended` with whatever interrupt state its caller has. `GuardedStack::drop` (`stack.rs:424-436`) calls it with interrupts on from thread context, for example from `reap_zombies` (`sched.rs:254`) on an AP's idle loop (`sched.rs:575-580`, "idles with interrupts on").
- `framekernel/frame/sync/src/contexts.rs:260-271`: `retire_ended` takes `ended` by `swap(NONE)` at line 261 and stores `home = 0` at line 269. The `running_on` check runs between them.
- `contexts.rs:47-58` and `TASKS.md:2206`: ruling (c) is answered with "a `switch` that interrupts it ... then takes the other record or none".
- `contexts.rs:71-79` and `cpu.rs:763-770`: the capacity count, "at most one that has ended and is not yet retired".

**The failing scenario.** On processor P, thread E ends: its exit's `switch` sets `ended = E`. Context X on P then drops some other stack with interrupts on, for example while reaping an older zombie.
1. X's `stack_in_use` swaps `ended` to `NONE` and gets E.
2. A timer tick or a reschedule IPI preempts X before line 269, and P switches to context Y. That `switch`'s own `retire_ended` finds `NONE`.
3. Y reaps on P: `reap_zombies` takes E's zombie and drops E's stack. `stack_in_use` finds `ended == NONE`, and `covers` still finds E's home, which only X will clear.
4. The drop decides "in use" and calls `REGION.leak`. E's stack, 4 frames and its slot, is lost for the rest of the boot.
5. X resumes later and clears E's home. The slot comes back but the stack does not.

This is safe, since the stack is leaked, not freed. But it is the leak the retirement in `stack_in_use` exists to prevent (W-2 shows how often a reap comes before the next switch), and ruling (c) asked that this retirement "must not race this processor's own `resume`".
- **The capacity count is also wrong.** While X holds E, E is neither in `ended` nor retired, so "at most one ended and not yet retired" does not hold. Each context suspended inside that gap holds one more slot. That is at most 16 + 16 + 1 = 33 of 32 in a pathological interleaving, and in practice one or two. A publication refused when the table is full then reaches `spawn_with`'s queued-but-unpublished slot (the hand-over's follow-up 1), which is a panic.

**Reach today, as far as I traced it: limited.**
- The boot flow on the boot processor reaps with interrupts off (`yield_until_away` calls `reap` after `interrupt_window`'s `cli`).
- If X is an AP's idle loop, Y is a thread. If X is a thread, the idle context cannot run while X is ready, so Y is again a thread. Either way the second reaper has to be a thread on the same processor that calls `reap` or drops a stack.
- I found no such pair in today's proofs. In particular, this does not explain the directory proof's four frames: its reapers are the APs' idle loops and the boot flow.

**How sure:** sure of the interleaving. Experiment (a) shows on the real `Contexts` code that a reaper deciding in that gap finds the ended stack in use. I did not boot it, and I did not find a pair of contexts in today's proofs that hits it.

**Suggested fix.** In `stack_in_use`, make the retirement `without_interrupts(|| table.retire_ended(running_on))`. Only NMI, #MC and #DB can then interleave, and none of them touches the table. Answer ruling (c) as "interrupts off" in `contexts.rs` and `TASKS.md`, and state the capacity count with that condition. If the swap is kept as well, add a Loom model in which a third thread asks `covers` between the dropper's swap and its store, to pin the property.

### T70-2 (Low): every `resume` now executes a locked `xchg`, including a tick that switches nothing

**Where:** `contexts.rs:217-220` (`switch` calls `retire_ended` before `if next == here`) and `contexts.rs:261` (an unconditional `swap`). The records: `TASKS.md:2232`, "A switch adds no locked instruction ... An exit adds one `xchg`", and the contract's constraint, "The switch path adds no locked instruction".

**What happens:**
- The base returned at once when `next == here` (`git show 0ed7bfb9:framekernel/frame/src/cpu.rs`, `resume`'s first line), with no locked instruction.
- Now every tick on every processor executes an `xchg` with memory, which is implicitly locked, even when nothing switches. So does every reschedule IPI and every stack drop.
- For a real switch the fix does better than the base. The base's take and record were `compare_exchange` scans, each failed `lock cmpxchg` included. Now there is one plain-load-guarded `lock cmpxchg` and one `xchg`.
- So the claim is wrong only for the path that does not switch.

**Suggested fix:** in `retire_ended`, return early on `self.ended.load(Relaxed) == NONE`, then swap. Only this processor writes `ended`, so a stale `NONE` only defers a retirement. Then correct the records' sentence.

### T70-3 (Low): the Loom execution of L5 with a plain store is one C++20 forbids, so the question the records leave open can be settled

**Where:** `contexts.rs:52-58`, `SOURCE_PROVENANCE.md:5200`, `TASKS.md:2211`, and the author's `loom-L5-trace-plain-store.log`.

**The reasoning.** In the trace, the main thread's exit store `ended = 1` is sequenced before its final `swap` (the one after `dropper.join()`), yet that swap read `NONE`. The dropper's swap also read `NONE`. Two C++20 rules, which Rust's atomics follow, forbid this:
- **Write-read coherence ([intro.races]):** a value computation that a side effect X happens before must take X's value or that of a side effect after X in the modification order.
- **Read-modify-write atomicity ([atomics.order]):** an RMW reads the last value before its own write in the modification order.

Here is why the final swap cannot read `NONE`:
- The final swap must read `1` or a later write.
- The only later candidate is the dropper's swap. If that swap followed the store in modification order, it would have read `1`, not `NONE`.

So no C++20 execution matches the trace. The author's reading is right. The trace is Loom 0.7.2 exploring an execution outside C11: a false alarm, not a missed bug. The swap is therefore not needed by the memory model the module cites. It is needed to keep L5 passing under this Loom. Its cost is small (and see T70-2).

**Suggested fix:**
- Replace "whether Loom's search is wider than C11 there was not settled" with this argument, and say that the exit's swap accommodates the checker.
- Add a rule for future work: a Loom failure on a location written by both plain stores and RMWs gets a C11 check before the code is changed for it.

**Reproduced.** Experiment (b) reproduces the failure: with a plain store, L5 fails on context 2's home, so the report is not an artefact of the author's tracing. I enumerated every modification order that C++20's constraints allow for L5's writes of `ended` after the setup's exit store: the third switch's swap, its exit store, the dropper's swap and the final swap. Three orders are possible, and in each both homes are retired.

### T70-4 (Low): W3 has never been shown to fail, and its no-room branch passes without judging

**Where:**
- `framekernel/src/stacks.rs:600-611`: `Some(State::Lost) => (true, "lost with no room kept, so not judged")`.
- `developer-tools/xtask/src/main.rs:3338`: the W3 marker accepts any `true (`.
- `framekernel/frame/src/stack.rs:426-429`: "the kernel stacks proof's W3 shows that this drop gives back a stack the records no longer hold".
- `ADR-0013-boot-proof-policy.md:589`: MS-7, "the kernel stacks proof's W3 judges the drop's own decision".

**What is wrong:**
- W-2 was caught by the IPC proof's frame count before the boot reached W3, and W-2b by a panic. No control in ADR-0013 shows W3 printing `false`.
- If the cache of kept stacks is full when W3 samples `room` (line 600), a drop that leaked is reported as given back. W3 then passes without judging the drop.
- The evidence shows `kept for reuse` in all 37 window lines, so the branch was not taken in these runs. The proof's own final comparison, `after == before` at `stacks.rs:266`, with `lost` in `Counts`, would still catch such a leak. So this is not a proof that passes while wrong, but W3 itself is unshown.
- The records' sentence "A `Lost` state is then the drop's own leak" (`TASKS.md:2216`) omits the branch.
- MS-7's role, showing that the drop reads the records, is now carried by W-2's IPC count, not by W3.

**Suggested fix:**
- Call `stack::trim()` on the boot flow before the thread ends, so that room is certain, and make "no room" a failure of the clause's set-up rather than a pass.
- Add a control that reaches W3. One option: skip `stack_in_use`'s retirement only when the ended home lies in `WINDOW_SLOT`, so that the IPC proof is unaffected.
- Reword MS-7's note to cite W-2.

### T70-5 (Low): the windows' 5-second waits are longer than the 1-second shootdown budget, and ruling (e) was confirmed only for the boot flow's own path

**Where:** `stacks.rs:431` (`WINDOW_SECONDS = 5`), `stacks.rs:559-563` (the boot flow spins for `HELD` with interrupts off, the boot flow's normal state), `stacks.rs:511-514` (the AP spins for `ANSWERED` with interrupts off), `framekernel/frame/src/tlb.rs:33` (`WAIT_SECONDS = 1`) and `tlb.rs:240` (`shootdown`/`shootdown_all` panic on a stall).

**The scenario:**
- A third processor makes a kernel mapping change while the AP is held, or while the boot flow is spinning for `HELD` because the AP has not yet reached it.
- That processor's shootdown waits on both. Past 1 s, `tlb::shootdown` panics, and a stack reclaim marks its stack `Lost`, which fails the proof's final comparison.
- Nothing in the clause does this today, and every hold measured was at most 112 µs. Neither held side waits on anything the third processor holds, so nothing deadlocks.
- But the budget the ruling asked to be "generous" is generous only for the clause. Past 1 s it turns into a panic elsewhere.

**Also on the records:**
- Ruling (e) asked for "the longest wait on each machine". The records give the AP's hold, not the boot flow's waits for `READY` and `HELD`.
- The figures in `TASKS.md:2217` come from the second `boot-matrix` run only. The first run on `12e48e93` held the exit window for 106 µs on the 65-processor Intel machine (`gate-boot-matrix-1-12e48e93.log:4210`). ADR-0013's "longest hold seen was 112 µs" is still true.

**Suggested fix:**
- State in ADR-0013's row that the clause relies on no concurrent kernel mapping change and that a hold over 1 s would stall one.
- Report the boot flow's two waits as well.
- Optionally, cap the hold below 1 s.

### T70-6 (Low): the refused retirement's put-back can overwrite a newer exit's record

**Where:** `contexts.rs:265-268` (`let _ = self.ended.swap(ended, AcqRel)`) and `contexts.rs:52` ("cannot ... lose a later exit's record").

**The scenario:** while a retirement runs with interrupts on (T70-1), an interrupting exit sets `ended = E2`. If the retirement is then refused (`StillOnIt`), the put-back writes the old slot over E2 and discards E2. Both callers panic on `StillOnIt`, so nothing goes on to run with the lost record.

**Suggested fix:** remove the put-back, since the caller halts, or make it `compare_exchange(NONE, ended)`. Correct the sentence. T70-1's fix also closes it.

### T70-7 (Low, pre-existing, not in this diff): `settle` can trim before an AP's reap has given its stack back, which gives the directory proof's four frames

**Where:**
- `framekernel/src/sched.rs:251-254`: `reap_zombies` decrements `ZOMBIES` before `drop(fpu)` and `drop(stack)`.
- `sched.rs:224-226`: `settle` waits for `zombies() == 0`, then calls `stack::trim()` once.
- `framekernel/src/ipc_proof/directory.rs` (`prove_directory`): it polls `same` for 2 s after `settle`, and nothing trims again.

**The scenario:**
1. An AP's idle loop decrements the count (line 251), then is descheduled by the host or delayed.
2. The boot flow sees `zombies() == 0` and trims.
3. The AP's drop then calls `give_back(slot, true)`, and the stack goes into the now-empty cache as `Idle`: 4 frames, still mapped.

`settle` passes (no zombie, nothing retired, nothing lost). The heap is exact, because the FPU area was freed first. The free frames stay 4 short through the 2-second poll.

That is exactly `126933 free frames (was 126937)` with the heap equal and both settles passing, on a TCG machine where vCPU threads are descheduled. The code is the same at `0ed7bfb9`.

**How sure:** I have shown the path, not reproduced it. It fits every logged detail. I found no path specific to the fix that holds four frames in that proof: T70-1 needs a second reaper on one processor, and the directory proof has none.

**Suggested fix (a follow-up for the coordinator):** decrement `ZOMBIES` after the zombie's stack has been given back, or have `settle` trim again after a second `zombies() == 0`.

## Checked and found sound

**The argument (focus 1):**
- **Claimed before any resume.** `spawn_with_fpu` publishes under the target queue's lock, after `push_weighted` and before the slot can be picked (`sched.rs:528-545`). `publish_first_frame` takes `&mut GuardedStack` and `first_frame.take()`, so a stack is published once, by its holder.
- **Retired only on its own processor, after leaving.**
  - `retire_ended` is reached only through `CONTEXTS.get(this_cpu())`, from `resume` and from `stack_in_use`.
  - After the exit's `switch`, `resume` returns at once, `dispatch` returns, and `exception_saved` runs `mov rsp, rax`. Nothing on that path drops a stack.
  - NMI and #MC are taken on IST stacks. NMI returns `here` without touching the table, and a recovered #MC does the same. #DB has its own stack, and its only switch is an exit.
  - An exit taken from the #DB stack leaves a `here` that is never recorded. The thread's home still covers its own stack.
- **No switch writes a home.** `switch` writes a home only to claim a free slot (`0 → BOOT_FLOW`), and retires only the previous `ended`.
- **Any interleaving of a reader.** A live context's home is constant from claim to retirement.
  - Slot reuse is ordered by the release sequence: the retirement's Release store of 0 is followed by claims that are RMWs.
  - A reader whose Acquire load reads a later claim therefore synchronises with the retirement. A later retirement is on the same processor and sequenced after the earlier one.
- **Two exits before a retirement.** The second exit's `switch` retires the first before it records itself.
- **The boot or idle flow (home 1).** It never ends. Its first switch-out claims a slot or halts on `Full`. Its stack is the loader's, or an AP stack that `smp.rs` forgets before the AP starts (`smp.rs:815`).
- **Publication from another processor.** Covered by the queue lock and by L4. Free slots hold frame 0, so `switch`'s plain-load-then-CAS search cannot take a frame a publisher is still writing.
- **A thread that never runs.** Its home and frame stay. Nothing removes a thread from a run queue except its exit, so its stack is never dropped while published.
- **An exit inside a measured closure.** The measured stack is never dropped: its `GuardedStack` lives in a dead frame. The thread's home is retired and its own stack given back. No one can drop the measured stack while the processor is still on it.
- **`current`.** It stays consistent through every `resume` path: `next == here`, refusals that halt, the first switch-out, exits.

**Orderings (focus 2):**
- Claim (AcqRel CAS), then the frame store (Release); the take (AcqRel CAS); retirement (Release store); the readers' Acquire loads. These suffice for the stated claims.
- `kernel_stack`'s Release/Acquire is harmless and nothing load-bearing rests on it.
- `ended` needs atomicity only on its own processor. On hardware a `switch` cannot interleave inside another `switch`.
- The C11 analysis in T70-3.

**The Loom models and controls:**
- L1 and L2 put a reader beside one switch-out and one switch-in. L3 covers the last use before retirement, L4 concurrent claims, L5 two retirers.
- Each of C1 to C6 breaks the property its model checks, for the stated reason:
  - C1 removes the only record of a running context;
  - C2 and C4 remove the release, or the ordering after the last use;
  - C3 moves the record, which L2 catches (L1 cannot, and none is claimed for it);
  - C5 makes a double claim;
  - C6 fails on a sequentially consistent interleaving that an interrupt between the load and the swap realises on hardware, so it does not rest on the artefact in T70-3.

**`unsafe` and soundness (focus 3):**
- No new `unsafe` site. `cpu::stack_pointer` (`cpu.rs:787-792`) is the old read moved. A `mov` from RSP leaves flags alone, and `nomem` and `nostack` are right. `stack.rs`'s copy went with `LEFT`.
- `with_measured_stack`'s SAFETY comment holds. The stack a call leaves is a thread's home, covered from publication to retirement, or an outer measured stack held by its call, or a stack nothing gives back (the loader's, an AP's).
- Removing `LEFT` therefore loses nothing for a measured call's caller. It also ends T68-9's cap.
- `running_on` and `slot_holding` take no lock, so `switch` stays legal under any lock the interrupted code holds.

**The boot clauses (focus 4):**
- W1 and W2 ask strictly inside the window. The AP's CAS `GO → HELD` (AcqRel) publishes `follow_thread`'s `kernel_stack` store to the boot flow's Acquire. The boot flow's `ANSWERED` store (Release), which the AP must read before it goes on, orders its ask before the AP's later frame store and `ended` swap. A "held 0 us" line is therefore still an ask inside the window.
- In the window only the home can answer `true`: the AP's `kernel_stack` was cleared or moved, and the frame is not yet saved. W-0 and W-1 show the answer is `false` without it, and W-4 shows the clause cannot pass unheld.
- The held AP holds no lock: `with_queue` has returned.
- From `GO` to `ANSWERED` the boot flow takes no lock, sends no IPI and does not yield. `slot_in_use` reads atomics and retires only the boot processor's own record.
- The hold costs one relaxed load on every sleep and exit outside the proof.

**Records (focus 6):**
- No address is printed by the new code. P-1's log shows `stack region +0x11ff00`. `Probe`, `GuardedStack` and `Contexts` format no region address. `stacks.rs`'s lines print processor names and microseconds.
- No KVM, CI or hardware claim: the control header names QEMU 11.1.3 TCG.
- ADR-0013's row, its control table and MS-6's note match the logs.
- The provenance entry lists no source outside the repository.
- My tabulation of the 37 window lines matches the stated 112 µs maximum.
