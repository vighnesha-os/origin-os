## Verdict

**No High finding.** For each of the 13 required properties I traced every place that writes or reads a record. I found no reachable path where the tip behaves differently from the base. The details:

- **Where the location is written.** It is set in one place only, `sched.rs:952`, after the push and under the queue lock. It is cleared in one place only, `sched.rs:740`, in the same critical section as `RunQueue::exit`, which is the only path that frees a slot.
- **Where the generation is written.** Only in `Block::take`.
- **Waking.** `KernelQueues::wake_slot` reaches exactly the slot whose location was read again and whose record generation was compared under that queue's lock.
- **Lock order.** No lock is ever taken against the stated order:
  - spawn: queue, then allocator, then record;
  - `on_exit`: queue, then table, then record, then allocator;
  - reap: table, then record, then allocator;
  - a switch takes the old and the new record one after the other, never together.

  Every one of these locks is taken with interrupts off.
- **Same as before.** The spawn-refusal and slot-reuse proofs get the same results (`Full`, `Ok(1)`). The IPI decision is the same. No `unsafe` is added: both new files have `#![forbid(unsafe_code)]`.
- **Block size.** A full queue (15 threads) plus a full zombie list (16) plus one spawn in progress holds 32 records, which is exactly `PER_CPU`.
- **Loom control anchors.** Every anchor text in `loom.rs` that points into `models.rs`, `threads.rs`, `wait.rs`, `lib.rs`, `exits.rs` or the kernel's `runqueue.rs` occurs exactly once. I checked this with a script.

## Findings

**R92-1. Medium. The move models cannot tell a wake-up that changes processor but keeps the old slot from a correct one.**
- Where: `framekernel/frame/sync/src/models.rs:1526` and `:643`/`:863`.
- `Cpu::new` queues the waiter in slot 1 of processor 0. `move_if_asked` moves it to `Cpu::idle(…)`, so it arrives in slot 1 there too. The location goes from (0,1) to (1,1).
- So a bug in `threads::wake` that follows the new processor but wakes the slot it read first (`at₀.slot()`) passes both `threads_a_wake_follows_a_move` models.
- This is the bug most likely to appear once S6's real move exists.
- Fix: put a ready thread or a dummy frame in processor 1's slot 1 before the move, so the thread arrives in slot 2. Then add a control that wakes the first-read slot on the new processor.

**R92-2. Medium. Nothing checks at run time that every record is given back. All three give-backs drop the result.**
- Where: `framekernel/src/sched.rs:529` (reap), `:766` (the leak branch of `on_exit`), `:937` (a refused push).
- Each one is `let _ = threads::give_back(number)`. A refused give-back (record not held, or location still set) silently loses a record for good.
- Nothing notices until spawns on that processor start returning `Full`: no settle, no proof line, no counter. Properties 1 and 13 rest only on reading the code.
- Fix: count refused give-backs and name them in `settled::judge`. Better, have every settle also check, per processor, that records held = queued threads (`live() − 1`) + zombies.

**R92-3. Medium (coverage gap). The kernel's half of the protocol is checked by no model and no host test.**
- What is unchecked:
  - spawn's order: take, push, fill the state, set the location, all under the queue lock;
  - `on_exit`'s clear in the same critical section as the exit;
  - reap emptying the record before the give-back;
  - `KernelQueues::wake_slot`.
- The Loom models run hand-written copies of these (`move_if_asked`, the "`sched::on_exit`" blocks in the models at :1584 and :1650, `World::wake_slot`).
- `framekernel/src/threads.rs` is built only for the kernel target (`lib.rs:224`), so `take` (including its overflow path), `give_back` and `split` have no host tests either.
- Example of a bug that passes everything except possibly a boot proof: moving `record.clear_location()` after `with_queue` returns, outside the lock.
- Fix: host tests for numbering and overflow. Longer term, put the spawn and exit steps in `origin_sync::threads` so that the models run the real code.

**R92-4. Low. The kernel's wake-up no longer has the slot generation as a second check.**
- Where: `sched.rs:673-677`, and `World::wake_slot` in the models.
- `wake_slot` passes `queue.generation(slot)`, the slot's own current value, so `RunQueue::wake`'s stale-name check can never fail. Correctness now rests on property 2 alone.
- Today that holds. But a future path that frees or reuses a slot without clearing the location (for example S6's `depart`) would let a record name wake the slot's next thread, and nothing else would stop it.
- Fix: keep the slot generation in the record next to the location (or in the packed location) and pass it to `RunQueue::wake`.
- The module comment at `runqueue.rs:30` ("names its thread by slot and the slot's generation") is now misleading for the kernel.

**R92-5. Low. The spawn path drops some impossible failures silently.**
- Where: `sched.rs:951-953`. If `u16::try_from(slot)` fails, the thread is queued with no location. Every wake-up then returns `Gone`: a silent lost wake-up. It cannot happen while `CAPACITY` is 16.
- Where: `sched.rs:941-942`. The tuple evaluates `parts.take()` even when `threads::record` returns `None`, so the parts would be dropped under the queue lock. Also unreachable.
- Fix: a compile-time assertion that `CAPACITY` fits in a `u16`, or refuse the spawn rather than skip the step.

**R92-6. Low. A Relaxed location load would break the follow count, and no control would notice.**
- Where: `threads.rs:151` and `:362-368`.
- `changed()` reads the generation under the *old* queue's lock. It is correct only because the location load is Acquire.
- With a Relaxed load, a waker that locks the old queue after the exit's critical section could see a new thread's location with the old generation and answer `Moved`. It would then follow to the new queue and get `Stale` with `retries = 1`, so the kernel would count a followed move where none happened and the boot proof would fail.
- `threads_a_wake_racing_an_exit_follows_nothing` could catch this, but no control plants it. Add a `location_load_relaxed` control against that model.

**R92-7. Low. Misleading comments.**
- `threads.rs:249-250`: "no holder of a queue lock can be comparing this generation" is not true. `changed()` reads it under the old queue's lock while a `take` can be writing it. This is harmless, because both values differ from the name's generation, but the comment should say so.
- `framekernel/src/threads.rs:11-17` and the assertion at `:40-43` (`>= 2*CAPACITY-1`, which is 31): spawn takes its record *before* the push, so a full queue plus full zombies uses 32 for a moment. With 31 the outcome would still be `Full`, but "never runs out before its queue does" needs 32 = 2 × `CAPACITY`.
- `spawn_with_parts`' doc ("leaves … the thread table as they were"): a refused push still moves the record's generation on.

**R92-8. Low. The fourth model claims more than it shows.** (`threads_a_switch_takes_each_record_in_turn`, `models.rs:1705`)
- The `unlock_release_relaxed` control (loom.rs:258) makes the model fail through the run queue's own cell: the reader locks processor 0's queue after the timer. So the control does not show that the *record's* lock is what orders record state.
- `NOT_RESTORED` has no control.
- The "no lock waiting in a circle" claim cannot fail: no thread in the model takes two record locks, so no inversion can be written.
- The timer is a hand copy, not `switch_fpu`/`follow_thread`.

**R92-9. Info. Small cost and memory changes.**
- A switch now takes the incoming record's lock twice: in `switch_fpu`'s restore and again in `follow_thread`. Merging the two would save one lock per switch.
- The bytes per processor printed in D3's line rise by roughly 1 KB per processor (my estimate: about 4.0 KB against 2.95 KB). The boot line already prints this figure.
- `percpu.rs` now sizes `THREADS` later in the list. Under heap pressure that order decides which table comes up short.
- I did not check the cost gate or the boot-matrix low-memory scenarios against these numbers.

**R92-10. Info. ADR wording.** S1's "Ownership" bullet still says every field except the location is under the owning queue's lock. The Q3 note moves the state to the record's own lock and is labelled "no decisions change". The bullet should say it was amended by ruling Q3.

## The Loom models and their controls

- **`threads_a_wake_follows_a_move` and its timed version.**
  - `wake_to_the_stale_slot`: the model can fail. The wake-up reaches processor 0's freed slot, `RunQueue::wake` on a free slot returns false, and the waiter blocks with nothing pending, so Loom reports a deadlock.

  - A real bug that passes: the stale-slot variant in R92-1.
- **`threads_a_stale_name_wakes_nobody`.**
  - `generation_not_compared`: the model fails in every interleaving, because the outcome is `Reached`. The model is effectively a sequential test; the race adds nothing.
  - It never tries to give back a record whose location is set; only the host tests do.
- **`threads_a_wake_racing_an_exit_follows_nothing`.**
  - `an_exit_followed_as_a_move` and `a_new_thread_followed_as_a_move`: the model can fail for both. The waker must read the location before the exit and lock processor 0 after it, which one or two preemptions reach. The run uses `preempted(3)` and an exhaustive deep run.

- **`threads_a_switch_takes_each_record_in_turn`.**
  - `unlock_release_relaxed`: the model can fail, but not specifically because of the record lock (R92-8).

**Could a bug in the real code pass every model?**

- In `sched.rs`: any bug at all, since the models never run it (R92-3).
