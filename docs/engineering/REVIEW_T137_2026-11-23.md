**The rounding as a largest-remainder rule (question 2).** `Tally::shares`, `progress.rs:131-146`.

- It always sums to 1,000. The four remainders sum to a whole multiple of the total, so 0 to 3 tenths are owed, and `take(owed)` gives exactly that many.
- Each share is less than a tenth from its exact value. A state is raised only if its remainder is not zero: when `k` tenths are owed, at least `k + 1` remainders are above zero, so the `k` largest are.
- A state with no requirement never has a share (its remainder is zero), on any total.
- Two states are never shown against their counts. A smaller count has a smaller floor, or the same floor and a smaller remainder, so it is raised only if the larger one is. 400,000 random tallies: no inversion.
- The tie-break is what the doc says and is deterministic. `sort_by_key` is a stable sort, and the order starts as `[3, 2, 1, 0]`, so among equal remainders the less complete state comes first.
- Equal counts can differ by a tenth (ADR-0018: 4 done 44.4%, 4 not started 44.5%). That follows from summing to 100.0.

## Findings

### R137-1 (Medium). The share shown for done depends on the other three states, so it can rise when nothing more is done

`progress.rs:131-146`; the page's line 3 and every "Done" cell.

Largest remainder gives the owed tenths to whichever states have the largest remainders. So done's share is not a function of done and the total alone. The generator does what the contract says; the finding is against the rule, measured against decision items 193 and 221.

- **Today's page, against the old page, with no count changed:** "Testing, hardware qualification and release" shows done 1.5% (1 of 69 is 1.449%; the old page said 1.4%). "All fourteen areas" shows done 2.1% (17 of 834 is 2.038%; the old page said 2.0%). Two lines went the other way: "Toolchain, build and CI" 20.7% (20.755%; was 20.8%) and §72 6.2% (6.25%; was 6.3%).
- **One row from now, on the page's first line:** move one requirement from not started to built: 58, 373, 248, 1,007. The page then opens "**3.5% of 1,686 requirements are done.**" Done is still 58, which is 3.4401%. A requirement becoming *built* raised the completion figure. Item 221 says built does not count as coverage.
- **Two figures from one tool:** on that tree `cargo xtask check` prints "58 of 1686 counted rows are done (3.4%)" (`requirements.rs:2051-2057`, `:2069-2072`, rounding to nearest), and the page it has just accepted says 3.5%. `the_page_agrees_with_the_requirements_gate` compares counts, not this percentage.
- Over random tallies, done's share differs from rounding to nearest in about 8% of lines and is above it in about 4%.

The doc comment and the commit message say "done is never rounded up on a tie". That is true and is not this: here done is rounded up from a remainder below a half with no tie.

**Suggested fix, for the coordinating session to rule on, since the contract names the rule.** Round done to the nearest tenth (a half down), which depends on done and the total only, and give the rest of the owed tenths to the other three by largest remainder:

```rust
let rem = parts.map(|part| part * 1000 % whole);
let mut owed = 1000 - shares.iter().sum::<usize>();
if 2 * rem[0] > whole {
    shares[0] += 1;
    owed -= 1;
}
let mut order = [3, 2, 1];
order.sort_by_key(|&state| std::cmp::Reverse(rem[state]));
```

I checked this rule over every tally of up to 40 requirements and 400,000 random ones: it always sums to 1,000, every share stays within a tenth, a state with no requirement has no share, and done is always the nearest tenth, so the page and the gate agree. Its cost: done and a state one requirement away from it can be shown a tenth out of order (3 of 400,000 random tallies; for example 551 done 16.1% beside 550 not started 16.2%), so the test's ordering assertion would exempt done. If the rule stays as it is, say so on the record (the TASKS entry and `shares`' doc): a share, done's included, can be up to a tenth above its exact value and can move when another state changes.

### R137-2 (Medium). The page's sentence for Built is not true of 88 of the 372 built requirements, and "usually an emulator" is against the page's own evidence table

`progress.rs:74-77`; page line 20. The wording is the contract's, so the contract needs the change too.

The page says: "It is written and tested, but in a weaker environment than it asks for, usually an emulator where it asks for a real machine." The matrix's rule (`docs/requirements/README.md:65`) is: "Implemented, with evidence, but short of the row's scope **or of its acceptance criteria**."

- 88 built requirements have evidence from an environment at least as strong as their scope asks for (83 of them ask for the host and ran on the host). They are built because their acceptance criteria do not pass yet. Example: S8-03 (and H-06), scope `eng/host`, evidence on the host, built because "no gate refuses a crate that sets its own" edition. The page's sentence tells a reader these are complete but for the machine they ran on.
- Of the other 284, 173 ran in "a virtual machine on a real processor" and 105 in "an emulator (QEMU)", in the words of the table two sections below. So "usually an emulator" names the less common case in the page's own terms.

**Suggested fix:** one sentence that covers both, for example: "It is written and tested, but not all of its acceptance tests pass yet, or they pass only in a weaker environment than it asks for, such as a virtual machine where it asks for a real one." (About 170 characters; one sentence.)

### R137-4 (Low). Nothing refuses a second page left at `docs/PROGRESS.md`
