## 1. MV4's control, asked on its own (the coordinating session's ruling on Q6)

A fresh reviewer was given the protocol's code with every comment stripped (the scratch file `protocol.rs`, cut from `contexts.rs` at `ed73b872`), MV4's property and ADR-0020 S4's control for it ("the second raise made before forget"), and asked whether a correct model of MV4 should catch that control. Its answer, as received:

> **Answer: No.** With the control applied, no execution permitted by C++20 gives `covered: false`. A correct model of MV4 should pass it, so it does not work as a negative control for MV4.
>
> **Why the control is harmless.** For a fast pass to return `covered: false`, the scanner needs `pass()` to be false and the readings to agree: `f == b`, then `b2 == b`, where `b2` is the reload of `begun` in `settled`. There is one move, so there are two cases.
>
> 1. **f = 1.** The scanner's Acquire load of `finished` reads the only raise, which is a Release fetch_add. Under the control, that raise comes after `adopt` in the mover's program order. So adopt's CAS on `T0[k].home` (0→H) happens-before every load in `pass()`. Write-read coherence then forces the load of `T0[k].home` to read H: no later write exists, because nothing withdraws X from T0. `T0.covers` is true. Scan order does not matter here.
> 2. **f = 0.** Then b = 0 and b2 = 0. For `T1.covers` to be false, the load of `T1[s].home` must read something other than H. That means it read `forget`'s Release store of 0, or the claimer's CAS to Y, which reads from `forget`. Either way the load synchronizes with `forget`. The mover's `begun.fetch_add` comes before `forget` in its program order, so it happens-before the scanner's `b2` load, and coherence gives `b2 ≥ 1`. The check is not settled, so the scanner retries.
>
> The gated path is also unchanged. The gate's lock word is in a single modification order. If the scanner locks first, its pass happens-before `lend` and `forget`, so `T1[s].home` reads H. If it locks second, it synchronizes with the release that follows `forget`, so `T0[k].home` reads H.
>
> What the protocol needs is that `finished` means "the destination holds the context", so the raise must come after `adopt`. Where it falls relative to `forget` does not matter for MV4. A scanner that has seen the raise already sees X in T0, and no step of the move removes X from T0.
>
> **A control MV4 would catch:** raise `finished` after `lend` and **before `adopt`**, still with Release. Everything else stays the same.
>
> Execution:
> - **Mover:** m1 locks the gate. m2 does `begun` += 1. m3 runs `lend`, a CAS on `T1[s].frame` from H to 0. m4 raises `finished` to 1 (moved here). m5 runs `adopt`: a CAS on `T0[k].home` from 0 to H, then a store of H to `T0[k].frame`. m6 runs `forget`, storing 0 to `T1[s].home` with Release. m7 releases the gate.
> - **Claimer (optional):** its CAS on `T1[s].home` reads m6's 0 and writes Y, then it stores Y to `T1[s].frame`.
> - **Scanner:**
>   - s1 loads `finished` and reads 1, from m4.
>   - s2 loads `begun` and reads 1, from m2.
>   - s3 runs `T0.covers`. `leaving` reads 0, and `T0[k].home` and `T0[k].frame` both read their initial 0. That is allowed: s3 synchronizes only with m4, and m5 comes after m4 in the mover's program order, so m5 does not happen-before s3.
>   - s4 runs `T1.covers`. `T1[s].home` reads 0 (from m6) or Y, and `T1[s].frame` reads 0 (from m3) or Y. The other slots hold other homes.
>   - s5 reloads `begun` and reads 1.
>   - `settled` sees `(1, 1)` and `b2 = 1`, so the scan returns `covered: false` on the first pass.
>
> This is even a sequentially consistent interleaving: m1–m4, then s1–s3, then m5–m7, then the claimer, then s4–s5. So a model that explores only SC interleavings will also catch it. It also shows why the scan reads T0 first. The stale read has to land on the destination before the scanner sees the source already emptied. If the pass read T1 before T0, seeing `forget` would make `adopt` happen-before the T0 loads, and this mutant would go uncaught.
>
> Dropping the `begun` reload in `settled` would also be caught. Take f = b = 0: the scanner reads T0 stale, the whole move runs, and the scanner then reads T1 after `forget`. That is SC-visible too. The raise-before-adopt control is closer to what the proposed control was aiming at.

**The author's answer, given to the coordinating session before this one came back:** the same, no. The two agree, so no ruling is needed. What Loom found is under "Resolution".

## 2. The change, `a25228c9..ed73b872`

An AI reviewer given the diff, ADR-0020 S2, S4 and S5, and the contract's ten invariants, and asked to check the module documentation's outline rather than trust it. The report as received:

Review of a25228c9..ed73b872 (TASKS 95, ADR-0020 S4/S5). I did this read-only: nothing was built or run, and nothing was edited or committed.

**No blockers.** The lend/adopt/forget order and the begun/finished acceptance test are sound in C++20 when they are used through `relocate`. So is S5's publish-then-clear with `covers` reading the leaving record first. The problems are in the API's guarantees, the termination claim, one integration site, the docs, and the controls.

**R95-1 — should fix.** contexts.rs:846-895 (`Lent`, `restore`, `forget`) and 948-961 (`adopt`).
- `adopt` only borrows `&Lent`. Safe code can therefore adopt twice, into two tables, or adopt and then `restore`. Either way frame F is resumable in two tables, which breaks invariant 1.
- `forget` without `adopt` clears the home while the frame is in no table.
- A `Lent` that is bound and then dropped loses its context. There is no `Drop`, and `#[must_use]` does not fire on `let lent = …;`.
- The doc at 846-848 says "the move cannot end before it is settled". The types only make the `Moving` outlive the `Lent`; they do not force a settle.
- Fix: `adopt(self) -> Result<Adopted, (AdoptRefused, Lent)>`, with `forget` only on `Adopted`, and a `Drop` on `Lent` that restores or panics. Add compile_fail doctests.

**R95-2 — should fix.** lib.rs:167-181; contexts.rs:198-203 and 755-757; ADR S4/B20.
- The gate is a test-and-test-and-set `SpinLock`, which is not FIFO. A scanner in its gated pass, with interrupts off, can lose the gate to every mover in turn.
- So "one wait for the gate, one move's critical section, whatever the rate of moves" is false. The wait is bounded only by the total rate of moves across up to 288 processors.
- Loom cannot show this. `prim::spin_loop` prunes any execution that spins past SPINS, so MV7 shows only "if the gate is won within the bound".
- Fix: use a ticket lock for the gate, or restate the bound.

**R95-3 — should fix.** cpu.rs:958-963.
- `this_cpu()` and `CONTEXTS.get` are evaluated before `without_interrupts`. Once threads can move (TASKS 96+), a caller preempted there and resumed on processor 1 would run `publish_leaving` and `retire_ended` on processor 0's table.
- That can clear a leaving record processor 0 is writing, which loses a frame. It can also publish a frame while processor 0 is still between `switch` and `mov rsp, rax`, which breaks invariant 2.
- This is latent today, since S2 pins every thread. Fix: move the index read inside the closure.

**R95-4 — should fix (docs and a hazard).**
- cpu.rs:943-946 still says `stack_in_use` "never waits and takes no lock". It now may spin on the gate. It also omits the leaving record from what it checks. cpu.rs:826 still says a stack is "always in this table".
- contexts.rs:109-110 says "a stack may still be dropped under any lock". That is false under the gate itself.
- The hazard: a gate holder that drops a stack, or calls `slot_in_use`/`slot_in_contexts`, deadlocks on its own lock. Its own move keeps begun ≠ finished, so every fast pass is unsettled and the gated pass calls `gate.lock()`.
- `relocate`'s `between` doc says only "takes no lock". Name stack drops there explicitly, or add a debug owner check.

**R95-5 — should fix (doc and model; precondition for TASKS 96).** contexts.rs:157-159 and 898-901; moves_models.rs:136-138.
- "At most one takes it" is true. But when the loser is the source's `switch`, the result is `Refused::NeverSaved`, and the kernel panics (cpu.rs:931).
- Windows where this happens:
  - the hook has named F and released its queue lock before `switch`'s compare-and-swap;
  - `switch`'s own publication of the leaving frame (452) is followed by the take (477), and a lend can land in between when switching straight back;
  - relocate's lend → adopt Full → restore window.
- MV2 asserts this halting outcome as acceptable. The docs should state that a mover must never lend a frame the source scheduler may already have named.
- No model combines S5 publication, a source switch back to the leaving context, and a lend.

**R95-6 — minor (outline is wrong in places).** contexts.rs:172-183.
- Later writes to the source home word include plain Release stores: a withdrawal's or retirement's 0, or a later forget. These are not in the forget's release sequence.
- The conclusion still holds, for a different reason. Every writer of a home word is ordered after the previous write:
  - a claim's compare-and-swap reads it;
  - a withdrawal follows its own claim;
  - a retirement follows the switch's take of the frame stored after the claim;
  - a forget follows lend's Acquire read of the home.
  So each home word's modification order lies inside happens-before.
- "Finished after forget" is stronger than needed. Only "after adopt", or "after restore", is load-bearing.
- That is why the ADR's MV4 control (finished raised before forget) was not caught: it is not a bug. Correct S4's control column. ADR line 163 still reads OUTCOME_PENDING in the uncommitted working tree.

**R95-7 — should fix (missing controls).** loom.rs:1914-2131. There is no control for:
- (a) `publish_leaving` clearing the record before storing the slot. This is the writer side of LV2; LX2b covers only the reader. LV2 should catch it.
- (b) `publish_leaving`'s slot store made Relaxed. LV1 should catch it.
- (c) finished raised, or read, Relaxed. MV1 should catch it.
- (d) `settled` without `finished == begun`, checking only that begun is unchanged. MV1 should catch it: a move whose begun raise is visible but whose claim is not. Nothing currently shows finished is needed.
- (e) begun raised after lend. No model moves a frame that is off its home stack, so 189-193's "the sequence covers them anyway" is unverified.

**R95-8 — minor (vacuous checks).**
- moves_models.rs:315-318: `passes <= FAST_TRIES + 1` cannot fail by construction, and MV7 does not show the scan ends (see R95-2).
- :245: MV5's scan cannot fail for any mutation, because the home never leaves the source on the refusal path.

**R95-9 — minor.** contexts.rs:1163.
- `covers(0, 2)` is true from any free slot's zero words, and now also from `leaving == 0`. That test proves nothing about BOOT_FLOW.
- `covers` treats 0 as an address. Harmless in the kernel, whose ranges are in the stack region, but the test should use a range that excludes 0.

**R95-10 — note (performance).** The gated pass holds the gate with interrupts off for a full pass over every processor's table: on 288 processors, about 288 × 65 Acquire loads of lines other processors write. Movers wait behind it, and B20 (2 µs) budgets only a move. CL48 should measure it on the 65- and 67-processor machines.

**R95-11 — minor (formatting).**
- loom.rs:1914 has `},    Control {`, and 18 new lines exceed 100 columns (1925, 1948, 2098, …).
- rustfmt probably gives up on the whole `CONTROLS` initializer because of the over-width comments, so `fmt --check` will not flag it. Reformat by hand.
- stack.rs:669 has a doc line of about 150 columns.

**R95-12 — note.** `Moves::begin` enforces neither interrupts-off nor the queue locks; the second half of invariant 5 is doc-only. `Moves::new` is public, so a `Moving` from another instance satisfies lend/adopt's witness. One static exists today; consider requiring S3's interrupts-off witness in `begin`.

**Host-test gaps:**
- No counting `Quiet` that asserts `quietly` runs exactly once on the gated path and never on the fast path.
- No test of relocate's `NotRestored` mapping.
- No compile_fail tests for misuse (see R95-1).
- No test of a lend that finds the same frame address republished in a later round (ABA). The compare-and-swap makes this benign, but it is unshown.

**Invariants checked and found to hold**
1. Inside relocate, switch, withdraw and lend each take a frame by compare-and-swap of the same word, so at most one succeeds. The API exception is R95-1.
2. Publication happens only at the top of `switch` or in `stack_in_use` (interrupts off, through interrupt gates). After `resume`, `dispatch` returns straight to `mov rsp, rax`. NMI, #MC and kernel-mode #DB/#DF never reach `resume`. The future-migration exception is R95-3.
3. relocate claims in the destination before forgetting in the source, and `restore` touches only the frame word.
4. The pass count is at most FAST_TRIES + 1. "Not covered" is accepted only when finished == begun before the pass and begun is unchanged after it, which I proved sufficient via the forget's synchronisation, or under the gate. The wait claim fails (R95-2).
5. lend and adopt require a `&Moving`. `Lent`'s lifetime keeps the `Moving` alive for restore and forget. The gated pass runs inside `Quiet`. Lock order is queue locks, then the gate, with no cycle.
6. lend refuses: `<= BOOT_FLOW`, the leaving frame, the BOOT_FLOW home, and running or ended slots (their frame word is 0).
7. adopt iterates a fixed `[Context; SLOTS]`.
8. Moves, Moving and Lent have hand-written name-only `Debug`. The derived `Debug`s hold only enums, bool and u32.
9. contexts.rs keeps `forbid(unsafe_code)`. cpu.rs adds no `unsafe` and no assembly.
10. With no mover, begun and finished stay 0, so every scan settles on its first pass with no gate. `switch` publishes before taking `next`, and `covers` reads the leaving record, so same-processor switching and every coverage answer are unchanged. I established this by reading, not by running the boot proofs.

The Loom controls MX1–MX7, LX1, LX2a and LX2b each mutate what their model checks, and I believe each is caught for the reason its comment states. C3 still plants the T68-2 bug that L2 catches.

## 4. The switch path inlined, `a66985f8` (the coordinating session's ruling on Q9, option 1)

A fresh AI reviewer, given the commit, CL49's budget and four questions: whether `#[inline]` can change behaviour, whether it affects the crate's lints and the no-panic check, whether the Loom controls still apply, and whether any other `origin_sync` function is called out of line on the switch path. The report as received:

**Review of a66985f8 (`#[inline]` on `Contexts::publish_leaving` and `Contexts::record_leaving`)**

I found no behaviour change and nothing above Low. Details:

**DI-1 (Info): orderings and interrupts are unchanged.**
- Inlining does not change what the program means. That is set by the source-level memory model, which Loom checks.
- `publish_leaving`'s two stores keep their order: a Release store lets no earlier write move below it. In `record_leaving`, the Release store of `leaving` likewise keeps the Relaxed store of `leaving_slot` before it.
- What inlining does newly allow is later operations in `switch` moving above those stores: the Relaxed frame loads and `current.store`. The model allows that, and x86's own store-to-load reordering already does it.
- The only Relaxed locations involved are `leaving`, `leaving_slot` and `current`, and only this processor writes them. So no processor sees a new load-buffering pattern outside what Loom explores.
- A switch straight back reads the frame it just stored in the same slot. Same-location coherence guarantees it sees that store.
- Interrupts stay off where they must:
  - Every IDT gate is an interrupt gate (0x8E/0xEE, `descriptors.rs:85`), and SFMASK `0x4_4700` clears IF on a system call.
  - `without_interrupts`' `cli` and `sti` blocks (`cpu.rs:1766`, `cpu.rs:1770`) have no `nomem`, so they still stop the compiler moving memory accesses across them. The inlined stores in `stack_in_use` cannot sink past the `sti`.
- `mov rsp, rax` sits in the naked function `exception_saved`, a separate function, so publication still happens only at the next call into the table (ADR-0020 S5).

**DI-2 (Low): the no-panic check no longer sees these two bodies.**
- No lint fires on `#[inline]`: neither `inline_always` nor `missing_inline_in_public_items` is configured. The crate's Clippy denies still apply to the source.
- In the object: the only non-test caller in `origin-sync` is the generic `switch`. So both functions drop out of `origin-sync`'s release object, and `no_panic_check` stops inspecting them.
- Their code now lands in the kernel library `origin-frame`, which is not in `FREESTANDING_LIBS`.
- No panic path exists today: `slots.get` returns `Option`, and the orderings are literals, so `core`'s panic branches for invalid orderings fold away.
- Scenario: a later edit adds indexing under an `#[allow]`, or an overflow-checked addition. Only the source lints would catch it, not the object check.
- `switch` and `retire_ended`, which are generic, were already in this position.

**DI-3 (Info): the Loom controls still apply.**
- All 32 controls whose `file` is `CONTEXTS` find their `from` text exactly once, in both the base and the tip.
- C3, LX1, LX3 and LX4 (the ones on `record_leaving`, `publish_leaving` or `leaving_slot`) anchor inside function bodies. None spans the signature lines next to the new attribute.
- After C3 or LX1, `record_leaving` is still used by the boot or idle flow's branch (line 514), so no new `dead_code` warning appears.

**DI-4 (Info): other out-of-line calls on the switch path.**
- Generic, so compiled into the caller:
  - `switch` and `retire_ended` (both take `impl Fn`) and the closures inside them;
  - the `core` pieces `switch` and `retire_ended` use: the atomics, `slice::get`, `iter::position`, `Option::map` and `ok_or`.
- `PerCpu`, `this_cpu`, `name_kernel_stack` and `Switch` belong to `origin-frame`.
- So the only non-generic, non-inline `origin_sync` call from `resume` is `Context::claim` (`contexts.rs:511`), made only when `current` is `NONE`.
- Next to that: `Contexts::running_home` is non-generic and not `#[inline]`. `check_landing` calls it at the head of `dispatch` (`cpu.rs:828`, `cpu.rs:1226`) on every entry from ring 3 through a gate with no IST stack.
- So a switch that starts in ring 3 (a timer preempting a program, or a yield, sleep, block or exit call) still makes one out-of-line call into `origin_sync` before `resume`. It is TASKS item 77's cost, not CL49's.
- `covers` and the gate's `lock` are on the stack-reclaim path, not the switch.
- I judged all of this from the source, not the binary.

**DI-5 (Info): `#[inline]` is only a hint.** Whether the two GOT calls are really gone is a property of the built kernel. The Q9 re-comparison should confirm it in the disassembly of `resume`. If they were still there, `#[inline(always)]` would be the stronger form.

I built nothing and ran no cargo command, test or boot. I used only `git show`, `grep` and `sed`, plus one Python script that counts text in `loom.rs` and in the base and tip copies of `contexts.rs`.
