## What holds

- **The harnesses cover the bounds they state.** Each one takes every byte value of a buffer of the stated size, at every length up to it, and every `u64` where it says so. No `assume` or `any_where` cuts out states that the property covers. `any_where` limits only the lengths (≤ N), the shift (< 64) and the profile ID (1–8). That is proofs.rs:106–108, 144–147, 189–191, 213–216, 325–327, 360–362, 378–380 and 406–408, and image/proofs.rs:37–43.
- **The P2 checks follow the specification.** They read the specification's offsets through the proof's own `le` and `zero` helpers (proofs.rs:66–86), not through the parser's `Reader`. I checked every offset against ONBF.md §4.2 and §4.3: the magic at 0, `format_major` at 8, `header_size` at 14, `header_flags` at 16, `section_count` at 20, the table at 24, the signature offset and size at 32 and 40, `arch` at 112, reserved at 114+14, the flags at 4, `stored_size` and `content_size` at 16 and 24, and reserved at 50+2, 56+8 and 96+32. The masks are right too: WRITE|EXECUTE = 0x18 and the defined bits = 0x3F. The limits are right: 1–256, 1 MiB and 1 TiB (proofs.rs:113–130 and 150–166).
- **`align_up_any_value` proves the whole property** (proofs.rs:192–204). Take `y ≥ x`, `y % align == 0` and `y − x < align` together: `y` is the smallest multiple at or above `x`. The `None` branch's bound, `x > ⌊MAX/align⌋·align`, is the exact condition for no such multiple existing. The `Some` branch also rules out a `Some` whenever no multiple exists. Both directions hold.
- **`check_padding_is_exact` proves "exactly" both ways, and "first"** (image/proofs.rs:44–68). Each result implies its condition: `Ok` implies the range is inside the input and every byte of it is zero, because `i` is arbitrary. `Truncated` implies the range is outside. `PaddingNotZero(n)` implies the range is inside, `n` is in it, `bytes[n] ≠ 0`, and every byte before `n` is zero. "Any other error" is refused, and P1 makes the function return. So each converse follows by exhaustion: a range inside and all zero can only be `Ok`, and a range outside can only be `Truncated`. A range inside with a nonzero byte can only be `PaddingNotZero` of the first such byte.
- **`utf8_walk` matches RFC 3629 §4's grammar** (proofs.rs:237–246). The leads are C2–DF, E0/A0–BF, E1–EC and EE–EF/80–BF, ED/80–9F (no surrogates), F0/90–BF (no overlongs), F1–F3/80–BF, and F4/80–8F (nothing past U+10FFFF). C0, C1 and F5–FF are refused, and the tails are 80–BF. A truncated character is refused at its first byte, which is `valid_up_to`'s meaning. My differential run found no mismatch.
- **The stand-ins are sound for their uses.**
  - `any_utf8_result` (proofs.rs:295–301) allows both results for every text. The crate's only UTF-8 call, ocbor.rs:164, discards the error (`map_err(|_| …)`), and `grep` finds no other `from_utf8` or `str::` call outside tests. So, for this crate, the stub's behaviours include core's.
  - `validation_by_walk` (proofs.rs:309–317) is deterministic. That is what P3 needs, because `validate` and `Cursor` validate the same body twice. It equals core on every text it can return for: the equality covers texts of ≤ 8 bytes, and the stand-in asserts that bound (proofs.rs:310–313). In P3, bodies are at most 3 bytes.
  - The `Utf8Error` values are made by const evaluation of the real `from_utf8` (proofs.rs:271–289). That needs no `unsafe` and no layout guess, and a stub cannot affect it: the stubs are not `const` and act on codegen, not CTFE.
  - If the stub path failed to resolve, the harness would not build, and the runner then fails it ("Kani did not report it", kani.rs:889). If the stub silently did not apply, real core would run, which is slower but still sound.
- **Each of the ten controls plants a real bug and names a check that bug must break.**
  - `section-count-zero` accepts a count of 0, which breaks "1 to 256" (proofs.rs:120).
  - `stored-size-unlimited` lets a zstd entry carry a `stored_size` over 1 TiB.
  - `merkle-loop-runs-on` never leaves `hashes == 1`: an unwinding failure in the function's only loop.
  - `align-up-wraps` turns `u64::MAX` into `Some(0)`.
  - `slice-end-clamped` returns a short slice.
  - `ocbor-argument-indexed` and `le32-indexed` panic on a short input.
  - `ocbor-trailing-data-accepted` accepts `00 00`, and the cursor then stops at 1.
  - `padding-first-byte-unchecked` both accepts `[1]` and names the wrong byte.
  - `utf8-walk-past-u10ffff` makes the walk accept `F4 90 80 80`, which core refuses.

  Every `from` text occurs once in its file. Every one of the ten new harnesses is named by a control (kani.rs:384–467). The `utf8-walk-past-u10ffff` control, planted in the proof's own specification, is a reasonable one: it shows that the equality proof can see a divergence in its deepest branch.
- **The runner change fails closed for the proofs.** Each harness runs alone with `--exact`, a missing report is a problem, and a second harness reported in the same run is a problem (kani.rs:873–898). Both `time` formats parse as their test shows (kani.rs:729–742, 1173–1182). A missing or broken `time` changes only the memory line, never a verdict.
- **The module docs list the exclusions the coordinating session ruled, and state them accurately:** `Image::parse` and its accessors, `check_against`, the signature block past its header, `KrnManifest::decode`, OCBOR-1 past 6 and 4 bytes, and the shipped machine code (proofs.rs:40–51; image/proofs.rs:13–23). The exceptions are R143-S3-1 and R143-S3-2.

## Findings

### R143-S3-1 (Medium): a declaration's doc comment says Kani proves `Image::parse` and its accessors

- **Where:** `runtime/onbf/format/src/image.rs:317–318`: "Kani's proofs of `Image::parse`, its padding check and its accessors (TASKS item 143)". Also `runtime/onbf/format/src/lib.rs:69`: "Kani's proofs of the parsers".
- **Defect:** the module that line declares proves only `check_padding`. Its own documentation says "`Image::parse` itself is not proved by Kani, nor are its accessors" (image/proofs.rs:19–23), and proofs.rs:42–44 says the same. lib.rs's "the parsers" also takes in `Image::parse`, `SignatureBlock::parse` past its header, and `KrnManifest::decode`, none of which is proved. CLAUDE.md §73 and final rule 29 require the properties actually proved to be stated precisely.
- **Failure scenario:** a reader of `image.rs`, the file that holds `Image::parse`, sees the declaration and takes the image parser as verified to a bound. A later requirements-matrix or provenance entry could then be written from that line, recording §13 item 5 as covered for the image when it is not.
- **Fix:** say what the module proves: "Kani's proof of `check_padding` (TASKS item 143); `Image::parse` and its accessors are not proved (TASKS item 159)". In lib.rs, say "Kani's proofs of some of the parsers' parts; see the module for what is and is not proved".

### R143-S3-2 (Medium): the documentation states as fact that the loader checks overflow in release builds, and it does not

- **Where:** `runtime/onbf/format/src/proofs.rs:11–13`: "The loader builds this crate with overflow checks on in release (CLAUDE.md §14), so an overflow P1 rules out would be a loader panic."
- **Defect:**
  - `[profile.release]` sets only `codegen-units` (`Cargo.toml:148–151`), and `.cargo/config.toml`'s UEFI flags hold no `-C overflow-checks`. `overflow-checks` appears nowhere outside `docs/`.
  - TASKS.md:233 and :1021 record that the overflow-checks half of item 22 is "not started".
  - SOURCE_PROVENANCE.md:4123 says outright that "the workspace sets no `overflow-checks`".

  CLAUDE.md §14 is a directive, not yet a fact of the build. As shipped, an overflow in this crate would wrap silently, not panic.
- **Failure scenario:** a reader, or the security review behind §13, reasons from this line that any arithmetic slip in `onbf-format` stops the loader. Overflow is then treated as fail-stop in code Kani does not cover (`Image::parse`, `KrnManifest::decode`), when it would really wrap into a wrong offset or length.
- **Fix:** state the build as it is: "Release builds wrap on overflow today (TASKS item 22's second half is not started). P1 shows that no arithmetic in these functions overflows within the bounds, so none would wrap either." P1's result is unaffected.

### R143-S3-3 (Medium): per-harness log names contain `::`, which CI's artifact upload most likely refuses, and `continue-on-error` hides it

- **Where:** `developer-tools/xtask/src/kani.rs:879`, `logs.join(format!("{name}.log"))`. The names are `proofs::header_parse_any_bytes`, `image::proofs::check_padding_is_exact`, `frames::proofs::…` and so on. `.github/workflows/ci.yml:176–187` uploads `target/xtask/kani` with `actions/upload-artifact` (v7.0.2) and `continue-on-error: true`.
- **Defect:** before this change the logs were per package (`origin-frame.log`). Now every proof log's name holds colons. As far as I know, `@actions/artifact`'s upload refuses any file path that contains `"`, `:`, `<`, `>`, `|`, `*`, `?`, CR or LF, for NTFS compatibility ("Contains the following character: Colon :"). It refuses the whole upload, not only that file. I am confident in this but did not check it here: no fetch, and the CI log was not available to me.
- **Failure scenario:** on every CI run, "Keep Kani's reports" errors and is marked as passed by `continue-on-error`, and no `kani-reports` artifact exists. The step comment promises each run's full output, "kept when the job fails too". When a proof or a control fails in CI, its full report (the checks' locations and traces, beyond the lines the runner echoes) is gone. The new peak-memory figures survive only in the console log.
- **Fix:** name the logs without colons. For example, `name.replace("::", "/")` gives `proofs/header_parse_any_bytes.log` and `image/proofs/check_padding_is_exact.log`, which can clash neither with each other nor with `controls/`. Alternatively, use `name.replace("::", "__")`. Add a host test that no log name holds any of the nine refused characters. Then confirm in the next run's upload step that the artifact appears.

### R143-S3-4 (Low): `slice_any_range` checks the returned slice's length, not where it starts

- **Where:** `runtime/onbf/format/src/proofs.rs:221`, `kani::assert(s.len() as u64 == end - start, "the range asked for")`. Also the claim at proofs.rs:21 and 208–209.
- **Defect:** "with the range asked for" needs the slice to start at `start`. The assertion is satisfied by any slice of the right length.
- **Failure scenario:** suppose `slice` regressed to `bytes.get(0..end - start)` after a range check, or took `start` from the wrong argument. Every call site would read the wrong bytes (the padding checks, the section and signature-block accessors), and this harness and its control would still pass.
- **Fix:** add `kani::assert(core::ptr::eq(s.as_ptr(), bytes.as_ptr().wrapping_add(start as usize)), "the range starts at start")`. That is safe Rust, because `wrapping_add` on a raw pointer is safe. Alternatively, compare `s` element by element with `buf[start..end]`.

### R143-S3-5 (Low): the header's P2 is claimed as "§4.2's rules" but leaves out the profile rule, and the documentation does not say which §4.3 rules the entry proof leaves unproved

- **Where:** `runtime/onbf/format/src/proofs.rs:17` ("P2: §4.2's rules, read from the raw bytes") and proofs.rs:109–135. Also the not-proved list at proofs.rs:40–51.
- **Defect:**
  - ONBF.md:98 requires `profile` to be one of §1's IDs, and nothing asserts it: there is no `le(bytes, 12, 2)` check and no tie between `h.profile` and the field.
  - Of `Header`'s fields, only `section_count` is tied to its raw bytes (proofs.rs:121–124). `signature_block_offset`, `signature_block_size` and `profile` are not.
  - For the entry, the table rightly says "§4.3's flags and reserved fields". But the entry-local rules that `SectionEntry::parse` enforces and nothing proves go unmentioned among the things not proved:
    - `content_size == stored_size` when the entry is uncompressed (ONBF.md:117);
    - no compression on a MAPPABLE entry (ONBF.md:120);
    - `merkle_index` (ONBF.md:123);
    - the memory rules (ONBF.md:118–119);
    - §4.4's kind-by-profile table.
- **Failure scenario:** a regression that accepts profile 0 or 9, or that decodes `signature_block_offset` from the wrong bytes, passes the header proof. A reader of the table believes §4.2 is fully proved.
- **Fix:** add `kani::assert((1..=8).contains(&le(bytes, 12, 2)) && h.profile as u64 == le(bytes, 12, 2), "§4.2: a profile of §1")`, and tie the signature fields to their bytes. Add one line to "Not proved": "`SectionEntry::parse`'s other §4.3 and §4.4 rules (sizes, compression, integrity, `merkle_index`, memory layout, kind against profile): P1 only."

### R143-S3-6 (Low): the equality proof fixes the text's position, although the documentation says core's check depends on the text's address

- **Where:** `runtime/onbf/format/src/proofs.rs:325–327`: the text is always `&buf[..len]` of a `[u8; 8]`. Against it, proofs.rs:26–27 says core's check has a shape that "depends on the text's address", and proofs.rs:36–37 claims equality "on every text of up to 8 bytes". In P3 the stand-in replaces core for bodies at offsets 1 to 3 of `[u8; 4]` (proofs.rs:378–380; ocbor.rs:159).
- **Defect:** the proof covers each text at one position only: the start of a stack array, whose alignment CBMC's object model most likely fixes. Nothing proved shows that core gives the same answer at the other alignments where P3 relies on the stand-in. That core's address-dependent fast path only matters for texts of two words or more is an argument from core's source. It is very likely true, but the harness does not prove it.
- **Failure scenario:** suppose a core in which a short text at an odd address took a different path and refused what the walk accepts, or the other way round. P3 under `validation_by_walk` would then prove a property that real core does not have at those addresses, and no harness would notice.
- **Fix:** take `buf: [u8; 16]` and `off = kani::any_where(|&o| o <= 8)`, and check `text = &buf[off..off + len]`. Or state the assumption in the documentation.

### R143-S3-7 (Low): nothing stops a stand-in from becoming an under-approximation, and no cover shows that the UTF-8 paths are reached

- **Where:** `runtime/onbf/format/src/proofs.rs:295–301` and 309–317 have no `kani::cover`. The covers of `ocbor_any_document` and `ocbor_validate_then_cursor_read` (proofs.rs:368 and 393) can be met by documents with no text. The only UTF-8 control (kani.rs:442–448) breaks the Err branch of `utf8_walk_equals_core`. Nothing breaks its Ok branch (proofs.rs:330–333) or the 8-byte assertion of `validation_by_walk`.
- **Defect:** the soundness of P1 rests on `any_utf8_result` allowing both results. If an edit made it always `Ok`, or always `Err`, the InvalidUtf8 refusal path, or the accepted-text path, would go unexplored. Every harness, cover and control would still pass.
- **Failure scenario:** someone "simplifies" the stub to `Ok(())` to speed up the run. P1 for `read_item`'s refusal of invalid text is then silently no longer proved.
- **Fix:** add harness-level covers in `ocbor_any_document`: "a text item is read" (`matches!(item, Item::Text(t) if !t.is_empty())`) and "a text is refused" (`validate` returns `OcborErrorKind::InvalidUtf8`). Add the same covers in P3. Do not put covers inside the stubs: `signature_block_any_input` never reaches UTF-8, so a cover there would be unsatisfiable. Add a control that makes the walk refuse something core accepts, such as `0xF1..=0xF3 => (4, 0x80, 0xBE)`.

### R143-S3-8 (Low): the run-count check cannot fail

- **Where:** `developer-tools/xtask/src/kani.rs:866–905`.
- **Defect:**
  - `runs` counts one run per element of `names`, summed over `packages`.
  - `packages` is the set of `chosen`'s packages, and each `names` is `chosen` filtered by its package.
  - So the sum is always `chosen.len()`, even with duplicates.
  - A failed `cargo_kani` returns early through `?`, before the check.

  The check "`{runs} runs for {} harnesses`" is therefore a tautology that reads like a guard.
- **Failure scenario:** a future edit that skips a harness, for example by filtering `names` differently, still passes. Anyone trusting the check believes it would catch that.
- **Fix:** compare against something the loop does not derive from, such as the names the reports matched: collect the matched names and require them to equal `chosen`. Otherwise, remove the check.

- **Defect:**

### R143-S3-10 (Info): the negative controls check one assertion per harness

The controls show that each harness can fail, but they test only one of its assertions. Most P2 assertions have no control of their own: the magic, `format_major`, `header_size`, the flags, the table offset, the signature size and the unsigned case, and the arch and reserved fields of the header (proofs.rs:113–130); and the unknown flags, W+X and the reserved fields of an entry (proofs.rs:151–163). A typo that weakened one of them would go unnoticed. A few cheap controls would close that, for example dropping `flags.has(Flags::WRITE | Flags::EXECUTE)` in section.rs:239, or the arch check in header.rs:126.

### R143-S3-11 (Info): `SLICE_PANIC` matches any panic with a formatted message

kani.rs:470–473 matches the placeholder Kani prints for every panic whose message is formatted at run time. It is acceptable, because the unplanted harness passes, so any new failure comes from the plant. But it does not show that the planted line is the one that failed. If Kani's report gives the failing check's line, matching it as well would make the control specific.

### R143-S3-12 (Info): what the memory figure measures, and that nothing enforces it

`time -v` and `time -l` report the largest single process's peak resident set in the tree (rusage of waited children), not the tree's total (kani.rs:731–742). That is right for one CBMC per run. Nothing compares the figure with the 8 GB ruling (kani.rs:864–865): it is printed only. A missing `time`, or one with an unexpected format, gives "not measured" and passes. Ubuntu 24.04's GNU time 1.9 does not have the 4× RSS error of 1.7.

### R143-S3-13 (Info): `package_of` and `apply` accept any path a control names

`apply` runs before `package_of` (kani.rs:936–937). `starts_with` (kani.rs:978–980) is lexical, so a path such as `runtime/onbf/format/src/../../../../../../../X` would pass it, and `scratch.join` would then write outside the scratch tree, into the working tree. With today's constants no control can touch the working tree, and the widened rule picks the right package for all 37 controls. Because the gate does not refuse a control path that is absolute or contains `..`, that protection depends on nobody adding such a path. Add a check to `control_list_problems` and call `package_of` before `apply`.

### R143-S3-14 (Info): the CI step for `time`

`test -x /usr/bin/time || { sudo apt-get update && sudo apt-get install -y time; }` (ci.yml:172–173) installs an unpinned package from Ubuntu's signed archive. The runner image normally ships it already. If apt fails, the job fails before any proof runs, so the step fails closed and no proof result is falsely reported. xtask itself carries on without `time` (kani.rs:641–648). That split is consistent, but `time` belongs in the CI dependency record next to Kani's pinned bundle (CLAUDE.md §60).

### R143-S3-15 (Info): wording in the module documentation

- proofs.rs:26–28 says "every harness that reached [core's check] ran past 300 s". But `utf8_walk_equals_core` reaches it on purpose, presumably within that time.
- `signature_block_any_input` never reaches UTF-8, because every input of 19 bytes or fewer is refused before any OCBOR (signature.rs:249), so its stub (proofs.rs:404) is dead.
- proofs.rs:24 says "its 16-byte header and the first entry's size". The size is never read in full.
- The P1 argument (proofs.rs:30–31) could add that core's own validator is itself checked by `utf8_walk_equals_core` on every text of up to 8 bytes. That covers all the texts the P1 harnesses can form, which are at most 5 bytes.
- `ocbor_any_document` covers a single call sequence: `next_item`, then `skip_contents` of that item. "Every input of up to 6 bytes" for `Cursor::next_item` and `skip_contents` means that sequence only.
