## Verdict

From the code at `f3f485df`, I1 to I5 hold. Reclaims run one at a time behind the role, so a slot is unmapped only when nothing is waiting. What `unmap` returned goes into `Table.waiting` on a stall and is released only after a `shoot` that returned `Ok`. A re-ask always sends a new request for the same `(slot, pages)`. Two things put that request after the unmap: the table lock and the role. In the protocol, a `shoot` can complete only if every target stored `served = g` while the initiator still held the turn. During that time `generation == g`, so each target read g's own request. `answered` gates only whether to ask again, never a release.

I found no High defect. There is one Medium, and it matters only if `f3f485df` lands without `c548658d`. The rest are Low: comments that claim more than the code does, gaps in the models, and a liveness and contention cost while a stack waits.

`c548658d` removes the whole Amendment 3 allowance. Apart from that removal, `run_scenario` is byte-for-byte the old one-boot function, and the new test is not vacuous.

I built, tested and booted nothing. Everything below comes from reading the code.

## I1. No early reuse: holds

**First job** (`slots.rs:534–568`):
- `job()` marks the slot `Reclaiming` under the lock (`:341`). Then `unmap`, then `shoot`, in program order.
- On `Ok`, `release(unmapped)` runs (`:539`), and only then does `free(slot)` run under the lock (`:543`).
- On `Err`, the K moves into `table.waiting` (`:554`) and nothing is released.

**Re-ask** (`:569–601`):
- If `answered` is false, it returns at once (`:570–572`) with no release and no shoot.
- If true, it sets `Reclaiming`, then `shoot(slot, pages)` with the same slot and pages, taken from `Waiting`.
- `release(waiting.kept)` runs only in the `Ok` arm (`:577–581`), and before `free(slot)` (`:584`).
- In the `Err` arm, the slot goes back to `Waiting` and stays in the table.

**The fresh request comes after the unmap, including across processors.**
- R1 unmaps (`vm.rs:366`, under `KERNEL_SPACE`'s lock), stalls, then writes `waiting` under the table lock and releases the lock and the role.
- R2 takes the role (`Acquire` CAS) and the table lock, and `job()` reads `waiting`.
- R2's `shoot` then publishes with `generation.fetch_add(Release)` and a `SeqCst` fence (`shootdown.rs:732–737`).
- So the clearing of the page-table entries happens before the new generation. A target that `Acquire`-loads that generation (`:692`) invalidates after it.

**Completion means these pages were dropped** (`shootdown.rs:687–702`, `:762–797`):
- Only the turn holder increments `generation`.
- While g's initiator spins, `generation == g`. A target's `served` can reach g only if it loaded g and then read `request`. The `Acquire` load means it reads g's request or a later one, and no later one can exist while the turn is held.
- A late answer after a stall can record `served = g1` after invalidating some later request. This is why `answered` is not proof. Nothing treats it as proof: the only release paths are the two `Ok` arms.
- A processor that comes online later flushes everything (`mark_online`).

**Paths I checked:**
- `answered` true or false: covered above.
- Two reclaimers: the second gets `Busy` (`:524`), or `None` once the work is done.
- `take`, `give_back`, `abandon` and `leak` need a slot that is Free, Idle or Live, so they refuse `Reclaiming` and `Waiting`.
- `trim` touches only idle-list entries.
- `grow` only adds Free slots behind the lock.

**Panics:** `x86_64-unknown-none` aborts on panic by default, and I found no override in `Cargo.toml` or `.cargo/config.toml`. On the host, where panics unwind:
- A panic in First `shoot` drops `unmapped`. In the kernel that would be a leak, not a free, since `OwnedFrame` has no `Drop`.
- A panic in Again `shoot` leaves the K in `waiting`, and the next reclaim recovers.
- In every case `Role`'s `Drop` gives the role back.

## I2. Nothing counted or freed twice: holds

- **`retired`:** goes up in `retire` (`:321`) and down once, in First `Ok` (`:541`) or Again `Ok` (`:583`). A stall leaves it alone, so it counts Retired, Reclaiming and Waiting slots.
- **`pages`:** goes down once, on First `Ok` or First `Err` (`:542`, `:552`), never on Again.
- **`lost`:** only `leak` raises it (`:473`).
- **`findable` and `pending`:**
  - `findable` changes only in `retire` and `job`, and `publish` runs after each.
  - `waiting` changes only in First `Err` and Again `Ok`, and both call `publish`.
  - Again `Err` does not change `pending`.
- **No overwrite:** `table.waiting = Some(..)` (`:554`) cannot replace an existing entry. While the role is held, `job()` returns First only if `waiting` is None, and only the role holder writes `waiting`.
- **The K:** it is released exactly once, by the reclaim whose `shoot` completed (`Option::take`, `:578`), and never dropped on a stall.
- **The `?` returns** (`:578`, `:592`) cannot be reached while the role is held. If one were reached, it would leave the slot `Reclaiming` with no trace (see T73-6).

## I3. The bound: holds

- While `waiting` is `Some`, `job()` returns only Again, so no new unmap.
- With the role, at most one slot is out of the tables and not yet free: the Reclaiming one or the Waiting one, never both.
- Retired slots behind it stay mapped and keep their frames.
- `Unanswered` costs nothing, and every idle loop reaps each tick (`sched.rs:806`, `yield_until`'s `reap()`).
- A stall names only the first processor that did not answer. A re-ask can then stall on a later one, so the bound applies per stall, as the contract says.
- A processor that never answers keeps the slot `Waiting` for good. `take` then returns `None`.

## I4. Nothing waits under a lock: holds

- The table lock is held only in `job`, the state changes and the count updates.
- `unmap` takes only `KERNEL_SPACE`'s lock. `shoot`, `answered` and `release` run with no table lock held.
- The role uses a load, then a CAS, with no spin.
- When `pending == 0` (`:521`), nothing is retired and nothing waits, and `reclaim` takes no lock.
- Locals drop in reverse order, so the role is released after the last table guard.
- While a stack waits, every reap takes the role and the lock (see T73-4).

## I5. `settle`: holds

The `settle` diff changes only doc comments and adds `stack::waiting().map(|s| s.cpu)` after `counts.retired` (`sched.rs:427`). `judge` filters `waiting_for` when `retired == 0` (`settled.rs:85`), and the host test `judge(0,0,0,Some(7),0,0) == Ok` pins that.

## Memory orderings

- **`pending`:** stored `Relaxed` under the lock, loaded `Relaxed`. It is only a gate:
  - A stale non-zero value leads to the role, the lock, then `job` returns None.
  - A stale zero only means a reclaim is missed this time, which costs liveness, not safety.
- **Role:** the `Relaxed` pre-check and `Acquire`/`Release` add nothing for data, because every table field is read under the lock. They do no harm. There is one store-buffer race, covered in T73-3.
- **`answered`'s `Acquire`:** no safety depends on it; `Relaxed` would be safe too.
- **Stale table state:** no reclaim can see it.
- **Re-ask ordering:** no ordering lets a re-ask publish before the unmap; the chain is under I1.

## Loom models and controls

- **L1** (`slots_stalled_reclaim_is_given_back_only_after_a_fresh_shootdown`):
  - It does exercise the case where a late answer serves NEXT_PAGE's request, so the processor has answered but still holds THE_PAGE.
  - It checks `reuse` against the holder's `touch` with Loom's cell, plus `!holds()`.
  - `slot_released_on_a_stall` (First path, `match outcome.or(Ok(..))`) and `slot_freed_on_an_answer_without_a_fresh_shootdown` both break what they target.
- **L2** (two reclaimers): `the_reclaim_role_never_refused` lets both get Again. The second can then set `Reclaiming` after the first has freed the slot, and the `state == Free` check (`NEVER_GIVEN_BACK`) catches it.
- **L3** (at most one out): the role control and `a_slot_unmapped_while_one_waits` both fail at `OutOfTables::unmapped` (`TWO_OUT`). The `Drop` assertion also catches a K dropped by an overwrite.
- **L4** (`answered` after service):
  - It proves only the single-request case, and its doc says so.
  - Its control is an off-by-one (`served + 1`); "always true" or a `Relaxed` load would be stronger controls.
- **Not in any model:** see T73-5.

## Kernel side

- **`stacks.rs` `cost`:** the `else { reclaimed(tsc_hz) }` branch only waits after a round that was not counted. The verdict is still `alone > 0`. Its comment claims more than that (T73-3).
- **`sched.rs`:**
  - `report_withheld` and `report_given_back` print processor numbers, counts and milliseconds, and no address.
  - `Stalled.generation` is never printed.
  - `Slots`' `Debug` leaves the table out.
- **`settled.rs`:** the `Display` and filtering are correct.
- **`measured_stack.rs` and `switch_windows`:** both count `Waiting` as given back, not leaked. That is correct.

## Findings

**T73-1 (Medium; fixed by `c548658d`, so the two must land together).**
- Where: `developer-tools/xtask/src/main.rs` at `f3f485df` (`allow_lost_stacks`, `stacks_lost`, `forgave_lost_stacks`).
- Problem: after TASKS 73, `lost` counts only `Slots::leak`, a stack dropped while some processor's record still held it, which is a kernel defect. On the 65-, 67- and 288-processor software-processor machines, Amendment 3 (a) still let `lost: N > 0` through. It printed "forgave N kernel stacks lost to a stalled shootdown … each withholds its slot and its 4 frames for good".
- Scenario: on `f3f485df` alone, a leak before the stacks proof on a named machine is reported as a forgiven stall and passes.
- Fix: land `c548658d` with, or before, the kernel change. Part (b) was already inert, because the kernel no longer prints "kernel stacks lost to a stalled shootdown".

**T73-2 (Low).**
- Where: `shootdown.rs:553–556` (`answered` doc).
- Problem: the doc says `answered` is "True also for a processor with no record … left to a fresh request, which then stalls at once". That is wrong.
  - `must_answer` needs a record (`:707–713`), so a fresh request never asks such a processor. It would complete without it, not stall.
  - No stall can name a processor without a record: a mark is set only where `must_answer` holds.
- The case that really "stalls at once" is different: a processor with a record but no `Asked` mark. It is never sent an IPI, so `answered` stays false for good.
- Fix: correct the doc.

**T73-3 (Low).**
- Where: `stacks.rs:395–401` (comment) and `stack.rs:529` (`stack::reclaim`'s doc).
- Problem 1: "takes each stack retired meanwhile, so a stack is still given back, by the role's holder" is not guaranteed.
  - H drops the role (`Release` store) and then loads `pending` (`Relaxed`).
  - B publishes `pending` under the lock, then reads the role (`Relaxed`, with no CAS since `f3f485df`) and sees it held.
  - This is a store-buffer pattern: both can read old values, on x86-TSO and in the Rust model alike. B returns `Busy` and H returns `None`.
  - The stack is then given back by the next reap anywhere. I3 still holds, but this comment overstates.
- Problem 2: "the next round starts with none under way" is not guaranteed either.
  - `reclaimed` waits for `retired == 0`, which H makes true at `free(slot)`, before H drops the role and before its next `pending` load.
  - Nothing stops another idle processor taking the next round's stack.
- Problem 3: a round is counted when `done.stacks == 1`. That one stack can be another processor's or the waiting one, and `took` can include a 1 s stall that came after the `Freed`.
- Fix: reword both comments. If the clause should measure only its own reclaim, exclude rounds where `done.stalled` or `done.given_back` is `Some`.

**T73-4 (Low, performance).**
- Where: `slots.rs:521–531`, `:570`.
- Problem: while a stack waits on a processor that never answers, every idle processor's reap, every tick, takes the role and the table lock and runs `job` and `answered`. The table lock is the same one stack `take` and `give_back` use.
- This is within I4's letter, which promises a lock-free fast path only when nothing is waiting, but the cost has no time limit.
- Fix: keep the waiting stall's `(cpu, generation)` in atomics, so a reaper can check `answered` before taking the role or the lock.

**T73-5 (Low, gaps in the models).**
- No model runs the unmap and the re-ask on different threads against the TLB world. L1 re-asks on the same thread, and L2 and L3 use made-up `shoot` closures.
- In L1, and in the earlier `slots_reclaimed_slot_is_taken_only_after_its_shootdown`, no processor walks the page tables, so nothing ever reads `world.pte.store(0)`. Moving `unmap` after `shoot`, or publishing a re-ask before the unmap is visible, would pass every slots model.
- No Loom model covers a re-ask that stalls (Again `Err`), and no control changes that arm. Only the host test `a_stalled_shootdown_keeps_the_slot_retired_until_a_fresh_one_completes` covers it.
- Fix: in L1, have the holder `walk()` after each `service` before it touches the frame, and do L1's re-ask on a separate thread. Add a control that releases in the Again `Err` arm.

**T73-6 (Low).**
- Where: `slots.rs:578`, `:592`.
- Problem: `table.waiting.take()?` and `as_mut()?` turn an internal inconsistency into a silent `None` that leaves the slot `Reclaiming`, counted as retired, for good.
- Fix: since the role makes these unreachable, make the inconsistency visible, for example with a `debug_assert` or a distinct outcome.

**T73-7 (Low, docs).**
- `State::Reclaiming` (`slots.rs:67`) says "unmapped". On the First path it is set in `job()` before `unmap` runs.
- `Counts.pages` (`:134–138`) counts first-time Reclaiming slots as "mapped" after their unmap has returned.
- `settled.rs` prints "one waiting for CPU X to answer" even after X has answered, when only the re-ask is still due.
