## Parser hardening (CLAUDE.md §13, §72)

Every parser in the host-tested library that reads firmware or device data has a deterministic, seeded mutation soak on `crate::testing`: the ACPI tables (RSDP, XSDT, FADT, MADT, SRAT, SLIT, MCFG, HPET), PCI configuration space and capabilities, NVMe registers and Identify, GPT, the CMOS RTC, virtio capabilities and rings, CPUID decoders, the boot info, the archive and filesystem formats and the network parsers. Each soak checks that nothing panics (overflow checks on), nothing reads out of bounds, and anything accepted keeps its documented invariants, round-tripping where an encoder exists. Checksummed structures are re-sealed so the checks behind them are reached. A default run is about 1.3 million mutated inputs and takes 1 s. The soaks found 13 bugs in the library (a CPUID overflow, an on-disk arithmetic overflow, device-reported virtqueue ids that panicked, virtio capabilities read past the capability area and taken in the wrong order, and others) and kernel paths that trusted what the parsers returned (structures and MSI-X tables outside their memory BARs, a queue size that was not a power of two, doorbells past BAR 0). Each is fixed with a regression test, and each test is shown to fail with its fix reverted. The malformed-device paths in the kernel binary can only be shown on a fault-injecting device model or hardware (§74). The full inventory and per-parser results are in `docs/engineering/SOURCE_PROVENANCE.md`.

The ONBF parsers, which run in the boot loader on data read before any signature is checked, have their own seeded multi-fault soaks: one to four faults per case over the container, OCBOR-1, the KRN manifest and the signature block, plus Merkle and signature verification, each judged by a model written from the specification (re-encoding byte for byte where an encoder exists, and compared in both directions). A default run is about 98,000 cases and adds about 1 s to `cargo xtask check`. They found five conformance bugs, none a panic or an out-of-bounds read, since all of these crates are panic-free by lint and by the object check: a mapped MERKLE or DWARF section was accepted, a certificate chain longer than four, a statement version that is not SemVer, and a block larger than 1 MiB passed straight to `SignatureBlock::parse`. Each is fixed with a regression test and shown to fail with its fix reverted.

## Boot proofs under host load (CLAUDE.md §68, §72)

Every boot proof that times one clock against another now tolerates a loaded host. Under a loaded host a virtual CPU is descheduled for milliseconds, and each such proof read that as the clock being wrong:

- the RTC second: updates are seen through the seconds register, which cannot be missed, instead of the 244 µs update-in-progress pulse QEMU shows (a pulse was missed at 29 % of updates under load), and each is located between the polls around it (`rtc::UpdateWatcher`). A measurement decides only if its whole interval of uncertainty is inside or outside 1 % (`rtc::SecondMeter`), so a stall costs a measurement, never a wrong verdict; a vague pair gives way to the next edge, at most 3.2 s in all.
- the PIT calibration of the TSC: a 10 ms window with a stall at either end (or between programming the count and raising the gate) is recognised and measured again (`apic::CalibrationWindow`); before, such stalls corrupted the TSC rate by up to 39 %, which was behind all but one of the `one RTC second lasted … clock failed` boots.
- the cross-CPU TSC check keeps going, to 500 ms at most, until the processors have really interleaved; the HPET and PM-timer reads are paired tightly with the TSC (`clock::closest_read`); and `prove_timers` repeats a run in which the polling loop itself stalled.

With every host core loaded (10 busy-loop processes, 30 boots each, alternating boot by boot), `cargo xtask boot-test`'s failure rate went from 83 % (the original kernel) to 3 % (this one: 1 boot in 30, the scheduler's weighted-share bound, untouched here). RTC-wait timeouts went from 11 of 30 boots to 0. Twelve negative controls fail the boot: frozen and stuck RTCs, an RTC 3 % slow, an RTC at 2× and at ½ speed, a PIT rate 3 % high, a corrupted PIT window accepted, an AP's TSC skewed by 5000 ticks, handoffs unreachable, the HPET and PM timer 3 % fast, and a timer genuinely late while the poller runs. Three positive controls show a stall is forgiven, not hidden: an injected stall in a PIT window, in an HPET read and in a timer run is each detected and retried, and the boot passes. Evidence: `docs/engineering/SOURCE_PROVENANCE.md`, "The clock proofs under host load".

The scheduler's weighted-share proof (weights 1, 4 and 16 on one processor for 2 s), the last boot proof that still failed on a loaded host, has the same treatment. It counted loop iterations, and on a loaded host the iterations in a 10 ms slice vary by more than tenfold whatever the scheduler did, while the lightest thread's share is the sum of about ten slices; so each worker now reports the time it saw itself running (steps under 3 ms), with the bound unchanged and pinned by a host test. A run whose shares are wrong although its processor visibly lost timer ticks or was away for over a tenth of the window is measured again, at most three runs in all; a wrong result from an undisturbed run fails at once. Over 150 runs of the proof per measure with every host core loaded, the old iteration count broke the bound once and the new measure never; at double load (two `yes` per core) 9 times (6 %) and twice (1.3 %, both visibly disturbed, so repeated). In `cargo xtask boot-test`, alternating the two kernels boot by boot, neither failed in 30 boots at one `yes` per core; at two per core the old kernel failed this proof in 2 boots of 15 and this change in none (`timers`, a different proof, failed one boot of each). Negative controls fail the boot (a wrong weight, weights ignored, a worker never picked, a wrong pick, no preemption, and a step limit so large that preemptions count), and a 70 ms stall injected into a run is repeated and passes, and fails if the repeat is disabled. Evidence: `docs/engineering/SOURCE_PROVENANCE.md`, "The weighted-share proof under host load".

On the merged IOMMU branch (`31b4347`), `cargo xtask boot-matrix` passed in full on its first attempt with the host at load 50–260 (mean 168) and another session's QEMU running for most of it: 8 kernel boots, one `timers` run repeated after a stall, and 41 calibration windows discarded over 6 of those boots. Five attempts on the tree before this merge failed at load 57–170 or with another session's boots running. That is one run, not a failure rate. At two busy-loop processes per core the `timers` and ping-pong proofs are reported to still fail; that work continues on `claude/priceless-einstein-d6f3b9`.
